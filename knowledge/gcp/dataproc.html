Dataproc Architecture

Dataproc is Google Cloud's managed Hadoop and Spark service — it provisions clusters of GCE instances pre-configured with the Hadoop ecosystem. Key architectural features:

Core Components

  • Master node(s): Runs YARN ResourceManager, HDFS NameNode, Spark History Server, Hive Metastore. 1 master (standard) or 3 masters (HA with ZooKeeper).
  • Worker nodes: Run YARN NodeManager and HDFS DataNode. Execute Spark executors and MapReduce tasks.
  • Secondary workers (preemptible): Optional worker nodes using Spot/preemptible VMs. Run YARN NodeManager only (no HDFS) — pure compute.
  • GCS Connector: Native connector for reading/writing Google Cloud Storage. Replaces HDFS for most workloads (decoupled storage).
  • Component Gateway: Provides authenticated access to Hadoop web UIs (Spark UI, YARN RM, Jupyter) via IAP without SSH tunneling.

Key Differentiators from Self-Managed Hadoop

  • 90-second cluster startup: Dataproc provisions a full Hadoop cluster in ~90 seconds (vs 10–15 minutes for EMR). Pre-built images with all components.
  • Per-second billing: Charged per second of cluster uptime (minimum 1 minute). Enables transient cluster patterns.
  • Integrated with GCP IAM: Service accounts, Workload Identity, VPC Service Controls — no Kerberos needed for basic access control.
  • Connector ecosystem: Native BigQuery connector (read BQ tables as Spark DataFrames), Pub/Sub connector, Bigtable connector.
Key insight: Dataproc's 90-second startup time fundamentally enables the "ephemeral cluster" pattern that's impractical on EMR (5–8 min startup). A Spark job can create its own cluster, run, and terminate — with total overhead of ~3 minutes. This makes per-job clusters viable even for 15-minute ETL jobs, eliminating idle cluster costs entirely.

Cluster Types

Standard Cluster

  • 1 master + N workers. Default configuration for most workloads.
  • Master failure = cluster failure (no automatic recovery).
  • Workers: 2 minimum for HDFS replication (or 0 if using GCS only).
  • When to use: Development, testing, non-critical batch jobs where HA isn't required.

High-Availability (HA) Cluster

  • 3 master nodes with ZooKeeper-based failover (YARN RM HA, HDFS NN HA).
  • Survives single master failure without job interruption.
  • HDFS uses quorum-based journaling for NameNode metadata.
  • When to use: Long-running clusters shared by multiple users, streaming jobs that can't tolerate restart, production persistent clusters.
  • Cost: 3x master cost. Only justified for clusters running >8 hours or serving critical real-time workloads.

Single-Node Cluster

  • 1 node acting as both master and worker. No HDFS replication.
  • Lowest cost option for development and small-scale testing.
  • When to use: Local development, unit testing Spark jobs, prototyping with small datasets (<10GB).
  • Limitations: No parallelism benefit, no fault tolerance, max memory limited to single machine.
Create Dataproc Cluster (gcloud CLI)
# Standard cluster with preemptible workers and GCS connector
gcloud dataproc clusters create prod-spark-cluster \
  --region=us-central1 \
  --zone=us-central1-a \
  --master-machine-type=n2-highmem-8 \
  --master-boot-disk-size=500GB \
  --num-workers=4 \
  --worker-machine-type=n2-standard-8 \
  --worker-boot-disk-size=200GB \
  --num-secondary-workers=8 \
  --secondary-worker-type=preemptible \
  --image-version=2.1-debian11 \
  --optional-components=JUPYTER,HIVE_WEBHCAT \
  --enable-component-gateway \
  --properties="\
spark:spark.sql.adaptive.enabled=true,\
spark:spark.sql.adaptive.coalescePartitions.enabled=true,\
spark:spark.dynamicAllocation.enabled=true,\
spark:spark.dynamicAllocation.minExecutors=2,\
spark:spark.dynamicAllocation.maxExecutors=50,\
spark:spark.sql.sources.partitionOverwriteMode=dynamic,\
mapred:yarn.app.mapreduce.am.resource.mb=4096" \
  --initialization-actions=gs://my-project-init/install-deps.sh \
  --metadata=PIP_PACKAGES="pandas==2.1.4 pyarrow==14.0.2 great-expectations==0.18.8" \
  --service-account=dataproc-sa@my-project.iam.gserviceaccount.com \
  --scopes=cloud-platform \
  --max-idle=30m \
  --labels=team=data-engineering,env=production

Dataproc Serverless

Dataproc Serverless runs Spark workloads without cluster management — submit a job and Google handles all infrastructure:

How It Works

  • No cluster to manage: Submit Spark batch jobs directly. Google provisions compute, runs the job, and releases resources automatically.
  • Per-job billing: Charged for Data Compute Units (DCUs) consumed during job execution. No idle cost — you pay only while the job is actively processing.
  • Auto-sizing: Google determines the number of executors based on input data size and query complexity. Scales mid-job if needed.
  • Startup time: ~60 seconds cold start (pre-warmed sessions reduce to ~15s for interactive/notebook use).

Supported Workloads

  • Spark batch: PySpark scripts, Spark SQL, JAR submissions.
  • Spark Interactive (Sessions): Jupyter notebooks backed by serverless Spark — similar to Databricks serverless notebooks.
  • Spark Streaming: Structured Streaming with micro-batch (NOT continuous processing — limited to structured streaming triggers).

Limitations

  • No HDFS — all data must be in GCS or BigQuery.
  • No SSH access or custom system packages (limited to Python packages via --properties spark.dataproc.conda.packages).
  • Max 2000 DCUs per job (soft limit, can be increased).
  • No persistent Spark state between jobs (no shared RDD cache).
  • Limited Spark config overrides — some JVM tuning options are locked.
Dataproc Serverless — Submit Spark Batch Job
# Submit a PySpark job to Dataproc Serverless
gcloud dataproc batches submit pyspark \
  gs://my-project-code/etl/daily_transform.py \
  --region=us-central1 \
  --project=my-project \
  --batch=daily-etl-20240615 \
  --service-account=dataproc-sa@my-project.iam.gserviceaccount.com \
  --subnet=projects/my-project/regions/us-central1/subnetworks/dataproc-subnet \
  --properties="\
spark.sql.adaptive.enabled=true,\
spark.sql.shuffle.partitions=auto,\
spark.dynamicAllocation.executorAllocationRatio=0.5" \
  --deps-bucket=gs://my-project-staging/dataproc-deps \
  --py-files=gs://my-project-code/libs/common_utils.zip \
  --jars=gs://spark-lib/bigquery/spark-bigquery-with-dependencies_2.12-0.36.1.jar \
  --version=2.1 \
  --labels=pipeline=daily-etl,team=data-engineering \
  -- --input-date=2024-06-15 --output-path=gs://data-lake/silver/

# Submit Spark SQL job
gcloud dataproc batches submit spark-sql \
  --region=us-central1 \
  --project=my-project \
  --batch=sql-aggregate-20240615 \
  "gs://my-project-code/sql/build_aggregates.sql" \
  --vars="input_date=2024-06-15,output_table=gold.daily_metrics"
Key insight: Dataproc Serverless is the GCP equivalent of EMR Serverless — ideal for teams that want Spark without infrastructure management. The per-DCU pricing means you pay proportionally to workload size. For a job processing 100GB, you might use 50 DCUs for 10 minutes (~$2.50). The same job on a provisioned 10-node cluster costs more if the cluster sits idle before/after the job.

Autoscaling Policies

YARN-Based Autoscaling

  • Scale-up trigger: Pending YARN containers (tasks waiting for resources) exceed threshold. Dataproc adds worker nodes.
  • Scale-down trigger: YARN memory utilization drops below threshold for sustained period. Dataproc removes idle workers.
  • Graceful decommission: Workers are YARN-decommissioned before removal — running containers are allowed to finish (configurable timeout).
  • Cooldown period: Minimum time between scaling events to avoid thrashing (default 2 minutes).

Autoscaling Policy Configuration

Dataproc Autoscaling Policy (YAML)
# autoscaling-policy.yaml
workerConfig:
  minInstances: 2
  maxInstances: 10
  weight: 1

secondaryWorkerConfig:
  minInstances: 0
  maxInstances: 20
  weight: 1

basicAlgorithm:
  yarnConfig:
    scaleUpFactor: 1.0          # Add 100% of needed capacity per scale event
    scaleDownFactor: 1.0        # Remove 100% of excess capacity per scale event
    scaleUpMinWorkerFraction: 0.0  # Scale up even for a single pending container
    scaleDownMinWorkerFraction: 0.0
    gracefulDecommissionTimeout: 3600s  # 1 hour to finish running tasks

  cooldownPeriod: 120s  # Wait 2 min between scaling events

# Create the policy
# gcloud dataproc autoscaling-policies import my-policy \
#   --source=autoscaling-policy.yaml \
#   --region=us-central1

# Attach to cluster
# gcloud dataproc clusters create my-cluster \
#   --autoscaling-policy=my-policy \
#   --region=us-central1

Autoscaling Best Practices

  • Primary workers (standard): Set min/max with small range (2–10). These have HDFS — scaling down risks data loss without decommission.
  • Secondary workers (preemptible): Set min=0, max=large (0–50). These are pure compute — scale aggressively.
  • Graceful decommission timeout: Set to your longest task duration. Too short = killed tasks and retries. Too long = paying for idle workers waiting to drain.
  • Streaming workloads: Disable autoscaling or set conservative thresholds — streaming jobs have constant resource requirements.
Pitfall: Autoscaling with HDFS-backed clusters is dangerous. If primary workers scale down, HDFS blocks on those nodes must be replicated first (decommission). For large datasets, decommission can take 30+ minutes — during which the cluster appears "stuck." Best practice: use GCS for storage and keep primary workers at a fixed count. Only autoscale secondary (preemptible) workers.

Initialization Actions

Initialization actions are shell scripts that run on all cluster nodes during creation — equivalent to EMR Bootstrap Actions:

Use Cases

  • Install additional Python packages (pip install)
  • Install system dependencies (apt-get install)
  • Configure custom logging/monitoring agents
  • Set up database drivers (JDBC connectors)
  • Mount additional storage or configure network
Initialization Action Script
#!/bin/bash
# install-deps.sh — Stored in GCS: gs://my-project-init/install-deps.sh

set -euxo pipefail

# Determine node role
ROLE=$(/usr/share/google/get_metadata_value attributes/dataproc-role)
echo "Node role: $ROLE"

# Install Python packages (on all nodes)
PACKAGES=$(usr/share/google/get_metadata_value attributes/PIP_PACKAGES || echo "")
if [[ -n "$PACKAGES" ]]; then
    pip install $PACKAGES
fi

# Install system packages
apt-get update -y
apt-get install -y libpq-dev jq

# Master-only: install additional tools
if [[ "$ROLE" == "Master" ]]; then
    # Install dbt
    pip install dbt-bigquery==1.7.4
    
    # Configure Spark defaults for all jobs on this cluster
    cat >> /etc/spark/conf/spark-defaults.conf << 'EOF'
spark.sql.catalog.spark_catalog=org.apache.spark.sql.delta.catalog.DeltaCatalog
spark.sql.extensions=io.delta.sql.DeltaSparkSessionExtension
spark.jars.packages=io.delta:delta-core_2.12:2.4.0
EOF
fi

# Worker-only: configure local SSDs for shuffle
if [[ "$ROLE" == "Worker" ]]; then
    # Symlink Spark local dirs to fast local SSDs if available
    if [[ -d /mnt/0 ]]; then
        mkdir -p /mnt/0/spark-local
        ln -sf /mnt/0/spark-local /tmp/spark-local
    fi
fi

echo "Initialization complete for $ROLE node"

Best Practices

  • Idempotent scripts: Init actions may run multiple times on retry. Use set -e and conditional checks.
  • Fast execution: Keep init actions under 5 minutes. Long init actions delay cluster readiness and increase failure risk.
  • Version pinning: Pin all package versions to avoid non-deterministic cluster builds.
  • Custom images alternative: For complex/slow init actions, build a custom Dataproc image (pre-baked with all dependencies). Cluster startup uses the image directly — no init action delay.

Dataproc on GKE

Kubernetes-Native Spark

  • Architecture: Spark jobs run as pods on an existing GKE cluster — similar to EMR on EKS.
  • Virtual cluster: Create a Dataproc virtual cluster on GKE — submit Spark jobs to it without managing dedicated Dataproc instances.
  • Benefits: Share GKE infrastructure across Spark and non-Spark workloads. Use Kubernetes features (pod priority, resource quotas, node affinity). Custom container images for complete dependency control.
  • Autoscaling: Leverages GKE node auto-provisioning or Cluster Autoscaler — pods trigger node scale-up when pending.

When to Choose Dataproc on GKE

  • Organization already standardized on GKE — want to consolidate workloads on one platform.
  • Need fine-grained resource isolation (namespaces, resource quotas per team).
  • Custom Spark images with non-standard dependencies (ML libraries, custom JARs).
  • Multi-tenant Spark serving different teams with isolated namespaces.
Dataproc on GKE — Virtual Cluster & Job Submission
# Create Dataproc virtual cluster on existing GKE
gcloud dataproc clusters gke create spark-on-gke \
  --region=us-central1 \
  --gke-cluster=projects/my-project/locations/us-central1/clusters/shared-gke \
  --spark-engine-version=latest \
  --namespace=spark-workloads \
  --pools='name=driver-pool,min=1,max=5,machineType=n2-standard-4' \
  --pools='name=executor-pool,min=0,max=50,machineType=n2-highmem-8,preemptible=true'

# Submit Spark job to GKE-backed virtual cluster
gcloud dataproc jobs submit pyspark \
  gs://my-project-code/jobs/transform.py \
  --cluster=spark-on-gke \
  --region=us-central1 \
  --properties="\
spark.kubernetes.executor.request.cores=2,\
spark.kubernetes.executor.limit.cores=4,\
spark.executor.memory=8g,\
spark.executor.instances=10,\
spark.kubernetes.container.image=gcr.io/my-project/spark-custom:v2.1"

Dataproc Metastore

Managed Hive Metastore

  • What it is: Fully managed, serverless Hive Metastore service — stores table schemas, partition metadata, and storage locations.
  • Decoupled from compute: A single Dataproc Metastore instance can be shared across multiple Dataproc clusters, Dataproc Serverless jobs, and even other services (Spark on GKE, BigQuery via federated queries).
  • Persistence: Metadata persists independently of cluster lifecycle — create/destroy ephemeral clusters without losing table definitions.
  • Versions: Supports Hive Metastore 3.x protocol. Compatible with Spark, Hive, Presto/Trino.

Configuration

Dataproc Metastore Setup
# Create a Dataproc Metastore service
gcloud metastore services create prod-metastore \
  --location=us-central1 \
  --tier=ENTERPRISE \
  --hive-metastore-version=3.1.2 \
  --network=projects/my-project/global/networks/prod-vpc \
  --port=9083

# Attach metastore to a Dataproc cluster at creation time
gcloud dataproc clusters create my-cluster \
  --region=us-central1 \
  --dataproc-metastore=projects/my-project/locations/us-central1/services/prod-metastore \
  --properties="hive:hive.metastore.warehouse.dir=gs://data-lake/warehouse/"

# Use in Spark SQL — tables persist across cluster restarts
# spark.sql("CREATE TABLE IF NOT EXISTS db.events (id STRING, ts TIMESTAMP) USING DELTA LOCATION 'gs://data-lake/events/'")
# spark.sql("SELECT * FROM db.events WHERE ts > '2024-01-01'")
Key insight: Dataproc Metastore + GCS + ephemeral clusters = the GCP equivalent of the Glue Data Catalog + S3 + transient EMR pattern. Metadata (table definitions) lives in the managed metastore, data lives in GCS, and compute clusters are created per-job and destroyed after completion. Total cost of idle infrastructure approaches zero.

Cost Optimization

Preemptible (Spot) Workers

  • 60–80% cheaper than on-demand instances.
  • Can be reclaimed by Google with 30-second notice.
  • Configuration: Add as "secondary workers" — they run YARN NodeManager only (no HDFS). Safe to lose without data loss.
  • Best practice: Use 70–80% preemptible workers for batch jobs. Keep 2–4 standard workers as baseline capacity.

Scheduled Deletion (Ephemeral Clusters)

  • --max-idle=30m: Automatically delete cluster after 30 minutes of no job activity. Prevents forgotten clusters running indefinitely.
  • --max-age=8h: Hard limit — cluster automatically deleted after 8 hours regardless of activity. Safety net for long-running jobs that get stuck.
  • --expiration-time: Delete at a specific timestamp.

Other Cost Strategies

  • Right-size instances: Use n2-standard-4 instead of n2-standard-8 if executor memory fits. Monitor YARN container utilization.
  • Local SSDs for shuffle: Add local SSDs to worker nodes for Spark shuffle. Reduces shuffle spill-to-network and improves job speed (faster completion = less cost).
  • GCS instead of HDFS: Eliminate HDFS overhead. Primary workers can be smaller (no DataNode). All data on GCS enables ephemeral clusters.
  • Committed Use Discounts (CUDs): For persistent clusters running 24/7, commit to 1-year or 3-year GCE usage for 20–57% discount on compute.

Interview Questions

Compare Dataproc Serverless with provisioned Dataproc clusters. When would you choose each for a production data platform?

Choose Dataproc Serverless when:

(1) Jobs are sporadic/bursty — a daily ETL job that runs for 20 minutes doesn't justify a 24/7 cluster. (2) Team lacks Spark ops expertise — no cluster sizing, scaling policy tuning, or init action debugging needed. (3) Jobs are independent (no shared state between runs) — each job gets a fresh environment. (4) Quick iteration in development — submit a job in 60s without waiting for cluster provisioning. (5) Per-job cost isolation — each job's DCU cost is attributable to that specific pipeline.

Choose provisioned clusters when:

(1) Streaming workloads (Spark Structured Streaming) that need persistent clusters with checkpoints. (2) Complex dependencies requiring custom system packages, init actions, or custom Dataproc images. (3) Workloads needing HDFS (data locality for iterative algorithms like ML training). (4) Steady-state batch workloads running hours/day — provisioned with preemptible workers is cheaper than Serverless at high utilization. (5) Shared interactive clusters for multiple data engineers (Jupyter notebooks with shared SparkContext).

Hybrid approach: Use Serverless for most batch ETL (80% of jobs) and maintain one persistent cluster for streaming jobs and interactive development. This minimizes management overhead while supporting all workload types.

Your Dataproc cluster autoscaling isn't working effectively — jobs are slow despite having autoscaling enabled. How do you diagnose and fix?

Common autoscaling failures and fixes:

(1) Scale-up too slow: Default cooldown (2 min) + node provisioning (~90s) = 3.5 min before new capacity is available. For short-lived tasks, the job finishes before new nodes are ready. Fix: Increase scaleUpFactor to 1.5–2.0 (provision more than needed, faster). Reduce cooldown period to 60s.

(2) HDFS blocking scale-down: Primary workers can't be removed if HDFS blocks haven't been replicated off them. Graceful decommission timeout is too short. Fix: Move to GCS-based storage. Set primary worker min = max (fixed). Only autoscale secondary workers (no HDFS).

(3) YARN metrics lag: Autoscaling uses YARN metrics which update every ~3s. Sudden spikes in task parallelism may not register immediately. Fix: Set scaleUpMinWorkerFraction=0 so even 1 pending container triggers scale-up.

(4) Preemptible worker reclamation: Google reclaims spot instances during high-demand periods. Autoscaling replaces them, but there's a gap. Fix: Diversify zones (--zone spread). Increase min secondary workers so a buffer exists. Consider using a mix of spot + on-demand secondary workers.

(5) Spark dynamic allocation conflict: Spark's own dynamic allocation can fight with Dataproc autoscaling. Spark releases executors (YARN shows low utilization → scale down) then requests them again (scale up). Oscillation. Fix: Set spark.dynamicAllocation.cachedExecutorIdleTimeout=60s to keep executors longer. Alternatively, disable Spark dynamic allocation and rely solely on Dataproc autoscaling for worker count.

Design an architecture for a data platform processing 500 daily batch jobs of varying sizes using Dataproc on GCP.

Architecture: Hybrid Serverless + Ephemeral Clusters

Job classification:

- Small jobs (input <50GB, ~350 jobs): Route to Dataproc Serverless. Zero management, pay-per-DCU, 60s startup. Cost-effective for jobs completing in <30 minutes.

- Large jobs (input 50GB–1TB, ~120 jobs): Group into 4–5 ephemeral clusters (by schedule window). 2 standard workers + 10–20 preemptible secondary workers. Auto-delete on 10-min idle.

- Very large jobs (input >1TB, ~30 jobs): Dedicated ephemeral clusters per job. Custom sizing based on input (auto-calculated from GCS file listing). 4 standard + 30–50 preemptible workers.

Shared infrastructure:

- Dataproc Metastore (1 instance): Shared across all clusters and Serverless jobs. Persists table metadata independently.

- GCS: All data in GCS (no HDFS). Enables fully ephemeral clusters.

- Cloud Composer: Orchestrates all 500 jobs. Uses DataprocCreateClusterOperator for large jobs, DataprocSubmitBatchOperator for Serverless.

Cost optimization:

- Preemptible for all secondary workers (60–80% savings on compute).

- Max-idle + max-age on all clusters (safety net against forgotten resources).

- CUDs for the baseline GCE usage (Composer nodes, persistent Metastore).

Expected vs naive approach: A single persistent cluster sized for peak (50 workers) costs ~$12K/month. This hybrid approach: ~$4K/month (Serverless for small jobs + ephemeral preemptible for large) — 65% savings.

How does Dataproc on GKE differ from standard Dataproc? When is the Kubernetes deployment model preferable?

Architectural differences:

Standard Dataproc: Dedicated GCE instances per cluster. Each cluster is isolated (own VMs, own YARN, own HDFS). Cluster = fixed pool of resources.

Dataproc on GKE: Spark driver and executors run as Kubernetes pods on a shared GKE cluster. Multiple Spark jobs share the same node pool. Kubernetes handles scheduling, resource allocation, and node provisioning.

Choose Dataproc on GKE when:

(1) Multi-workload GKE cluster: Organization runs microservices, ML inference, AND Spark on the same GKE infrastructure. Consolidating reduces operational overhead and improves node utilization.

(2) Fine-grained resource isolation: Kubernetes namespaces + resource quotas give per-team isolation. Standard Dataproc isolation is per-cluster (more expensive).

(3) Custom container images: Need specific OS libraries, ML frameworks, or custom Spark builds. GKE uses Docker images — full control over the execution environment.

(4) Advanced scheduling: Pod priority, preemption rules, node affinity (pin Spark to specific node pools), and gang scheduling for all-or-nothing executor allocation.

Avoid Dataproc on GKE when: Simple batch ETL (standard Dataproc or Serverless is simpler), need HDFS (not available on GKE mode), team lacks Kubernetes expertise, or jobs need full Hadoop ecosystem (HBase, Hive Server2).
