What Unity Catalog Solves

Before Unity Catalog, Databricks governance was fragmented across multiple layers:

Pre-Unity Catalog Pain Points

  • Workspace-level metastores: Each workspace had its own Hive Metastore. Tables in workspace A were invisible to workspace B — no cross-workspace data discovery or sharing.
  • No unified access control: Permissions set in one workspace didn't propagate. A user granted access in dev could bypass controls in prod by accessing the same GCS path directly.
  • No lineage: No automatic tracking of which tables derived from which sources. Manual documentation was always stale.
  • Cloud-credential sprawl: Each cluster had its own service account or mount point. Revoking access meant finding and updating dozens of configurations.
  • No data sharing standard: Sharing data outside the organization required copying data to shared storage — no governed, audited sharing protocol.

What Unity Catalog Provides

  • Single metastore across all workspaces in a region — unified data discovery.
  • Centralized GRANT/REVOKE permissions with inheritance.
  • Automatic column-level lineage tracking.
  • Credential abstraction — storage credentials managed centrally, not per-cluster.
  • Delta Sharing for cross-organization data sharing.
  • Row/column security (filters and masks).
  • Complete audit trail via system tables.
Key insight: Unity Catalog is not just a metastore upgrade — it's a fundamental governance re-architecture. It moves access control from the infrastructure layer (IAM policies on GCS buckets, cluster-level credentials) to the data layer (table/column-level grants). This enables fine-grained governance without requiring users to understand cloud IAM.

Three-Level Namespace

Unity Catalog organizes all data assets in a three-level hierarchy: catalog.schema.table

Hierarchy

  • Catalog: Top-level container — typically maps to an environment (prod, staging, dev) or a business domain (marketing, finance).
  • Schema (Database): Groups related tables/views/functions — equivalent to a Hive database. Maps to a logical data product or team.
  • Object: Tables, views, volumes, functions, models — the actual data assets.
Three-Level Namespace Examples
-- Full qualified names
SELECT * FROM prod_catalog.customer_schema.customers;
SELECT * FROM dev_catalog.customer_schema.customers;  -- Same table, different environment

-- Set default catalog and schema to avoid repetition
USE CATALOG prod_catalog;
USE SCHEMA customer_schema;
SELECT * FROM customers;  -- Resolves to prod_catalog.customer_schema.customers

-- List all catalogs, schemas, tables
SHOW CATALOGS;
SHOW SCHEMAS IN prod_catalog;
SHOW TABLES IN prod_catalog.customer_schema;

-- Common organizational patterns:
-- Pattern 1: Catalog per environment
--   prod.sales.orders  |  dev.sales.orders  |  staging.sales.orders

-- Pattern 2: Catalog per domain
--   marketing.campaigns.events  |  finance.accounting.transactions

-- Pattern 3: Catalog per team (with shared catalog for cross-team data)
--   shared.core.customers  |  analytics.models.churn_predictions

Metastore Architecture

Account-Level Metastore

  • One metastore per region: A Unity Catalog metastore is created at the Databricks account level, scoped to a cloud region (e.g., us-central1).
  • Workspace binding: Multiple workspaces in the same region can be attached to the same metastore — enabling cross-workspace data access.
  • Metadata stored by Databricks: Table schemas, permissions, lineage, and audit logs are stored in Databricks-managed infrastructure. Actual data stays in customer storage.
  • Managed storage: Each metastore has a root storage location (GCS bucket) where managed tables are stored by default.

Workspace Binding

  • A workspace can be bound to exactly ONE metastore (in the same region).
  • Once bound, all users in that workspace see the same catalogs (subject to permissions).
  • Unbinding removes access but doesn't delete data — rebinding restores visibility.
  • Isolation: Use catalog-level permissions to restrict which workspaces/users see which data. Dev workspace users only see dev_catalog; prod workspace users see prod_catalog.
Metastore Setup (Account Admin API)
# Create a metastore for us-central1 region
curl -X POST "https://accounts.cloud.databricks.com/api/2.0/unity-catalog/metastores" \
  -H "Authorization: Bearer $ACCOUNT_TOKEN" \
  -d '{
    "name": "us-central1-metastore",
    "storage_root": "gs://my-company-unity-catalog/metastore/",
    "region": "us-central1"
  }'

# Assign workspace to metastore
curl -X PUT "https://accounts.cloud.databricks.com/api/2.0/unity-catalog/workspaces/12345/metastore" \
  -H "Authorization: Bearer $ACCOUNT_TOKEN" \
  -d '{
    "metastore_id": "abc-123-metastore-id",
    "default_catalog_name": "main"
  }'

Permissions Model

GRANT/REVOKE Syntax

  • SQL-standard GRANT/REVOKE on all securables (metastore, catalog, schema, table, view, function, volume, external location, storage credential).
  • Privileges: SELECT, MODIFY (INSERT/UPDATE/DELETE), CREATE TABLE, CREATE SCHEMA, CREATE CATALOG, USAGE, ALL PRIVILEGES.
  • USAGE: Required to traverse the namespace. GRANT SELECT on a table does nothing if the user doesn't also have USAGE on the parent schema and catalog.

Inheritance

  • Privileges granted on a catalog apply to ALL schemas and tables within it.
  • Privileges granted on a schema apply to ALL tables within that schema.
  • Explicit DENY at a lower level overrides inherited GRANT.

Ownership

  • Every securable has an owner — the creator by default.
  • Owners have ALL PRIVILEGES on the object (including GRANT to others).
  • Ownership can be transferred: ALTER TABLE ... SET OWNER TO group_name.
  • Best practice: Set ownership to a group (e.g., "data-engineering-team") not an individual — survives personnel changes.
Permission Setup — Production Pattern
-- Create groups
CREATE GROUP data_engineers;
CREATE GROUP data_analysts;
CREATE GROUP data_scientists;

-- Grant catalog-level access
GRANT USAGE ON CATALOG prod_catalog TO data_engineers;
GRANT USAGE ON CATALOG prod_catalog TO data_analysts;
GRANT USAGE ON CATALOG prod_catalog TO data_scientists;

-- Data engineers: full access to all schemas
GRANT CREATE SCHEMA ON CATALOG prod_catalog TO data_engineers;
GRANT ALL PRIVILEGES ON SCHEMA prod_catalog.bronze TO data_engineers;
GRANT ALL PRIVILEGES ON SCHEMA prod_catalog.silver TO data_engineers;
GRANT ALL PRIVILEGES ON SCHEMA prod_catalog.gold TO data_engineers;

-- Analysts: read-only on silver and gold, no access to bronze
GRANT USAGE ON SCHEMA prod_catalog.silver TO data_analysts;
GRANT USAGE ON SCHEMA prod_catalog.gold TO data_analysts;
GRANT SELECT ON SCHEMA prod_catalog.silver TO data_analysts;
GRANT SELECT ON SCHEMA prod_catalog.gold TO data_analysts;

-- Data scientists: read silver/gold, write to their own schema
GRANT USAGE ON SCHEMA prod_catalog.silver TO data_scientists;
GRANT USAGE ON SCHEMA prod_catalog.gold TO data_scientists;
GRANT SELECT ON SCHEMA prod_catalog.silver TO data_scientists;
GRANT SELECT ON SCHEMA prod_catalog.gold TO data_scientists;
GRANT ALL PRIVILEGES ON SCHEMA prod_catalog.ml_features TO data_scientists;

-- Transfer table ownership to team group
ALTER TABLE prod_catalog.gold.customer_360 SET OWNER TO data_engineers;
Pitfall: Forgetting to grant USAGE at every level is the #1 Unity Catalog permission error. A user with SELECT on a table but no USAGE on the parent schema gets "permission denied." The fix: always grant USAGE on both the catalog AND schema in addition to the table-level privilege.

Managed vs External Storage

Managed Tables

  • Data stored in the metastore's managed storage location (GCS bucket configured during metastore creation).
  • Databricks manages the data lifecycle — DROP TABLE deletes both metadata AND data files.
  • Path: gs://metastore-bucket/<metastore-id>/tables/<table-uuid>/
  • Best for: Tables fully managed by Databricks pipelines where you don't need external access to the underlying files.

External Tables

  • Data stored at a customer-specified GCS location (via external location).
  • DROP TABLE removes only metadata — data files remain untouched.
  • Multiple tools can read the same data (Databricks, BigQuery, Dataproc).
  • Best for: Data shared across multiple compute engines, data produced by non-Databricks systems, data with separate lifecycle management.

External Locations & Storage Credentials

  • Storage credential: Wraps a GCP service account — provides authenticated access to GCS.
  • External location: Maps a storage credential to a specific GCS path prefix. Grants can be applied to control who creates tables at that location.
  • Hierarchy: Storage credential → External location → Table. Users need CREATE EXTERNAL TABLE on the location to write there.

Data Lineage

Automatic Column-Level Lineage

  • Unity Catalog automatically tracks lineage for all operations executed through Databricks — no manual annotation required.
  • Table-level: Knows that gold.customer_360 reads from silver.orders and silver.customers.
  • Column-level: Tracks that gold.customer_360.total_revenue derives from silver.orders.amount (sum aggregation).
  • Captured from: Spark jobs, SQL queries, DLT pipelines, notebook executions — anything running on Databricks compute.
  • Visualization: Available in the Catalog Explorer UI — interactive DAG showing upstream/downstream dependencies per table or column.

Lineage Limitations

  • Only captures lineage from Databricks compute — external tools (Dataproc, BigQuery) writing to the same tables won't appear.
  • Dynamic SQL (string-built queries) may not be fully traced if column references are constructed at runtime.
  • Python UDFs are opaque — lineage shows the UDF as a dependency but not the internal column transformations.

Delta Sharing

Delta Sharing is an open protocol for secure data sharing across organizations — without data copying:

How It Works

  • Provider: Shares specific tables/schemas by creating a "share" and adding recipients.
  • Recipient: Receives a credential file (activation link) and can read shared data using any compatible client (Databricks, Apache Spark, pandas, Power BI).
  • Protocol: REST-based, open-source protocol. Recipients read Parquet/Delta files directly from the provider's cloud storage using short-lived, pre-signed URLs.
  • No data copying: Data stays in the provider's storage — recipients read it in place. Provider controls access and can revoke at any time.
Delta Sharing — Provider Setup
-- Create a share (logical container for shared data)
CREATE SHARE customer_data_share
COMMENT 'Shared customer data for partner analytics';

-- Add tables to the share
ALTER SHARE customer_data_share
ADD TABLE prod_catalog.gold.customer_demographics;

ALTER SHARE customer_data_share
ADD TABLE prod_catalog.gold.purchase_history
  PARTITION (region = 'US');  -- Share only US partition

-- Add schema (shares all current and future tables in schema)
ALTER SHARE customer_data_share
ADD SCHEMA prod_catalog.gold;

-- Create a recipient (external organization)
CREATE RECIPIENT partner_analytics
COMMENT 'Analytics partner - Acme Corp'
USING ID 'acme-corp-databricks-account-id';  -- For Databricks-to-Databricks sharing

-- Grant the share to the recipient
GRANT SELECT ON SHARE customer_data_share TO RECIPIENT partner_analytics;

-- Recipient side: create a catalog from the share
CREATE CATALOG partner_data
USING SHARE provider_workspace.customer_data_share;

-- Recipient can now query shared data
SELECT * FROM partner_data.gold.customer_demographics WHERE region = 'US';
Key insight: Delta Sharing eliminates the "data copy" anti-pattern. Traditional B2B data sharing involves: export → encrypt → transfer → decrypt → load — creating stale copies, security risks, and operational overhead. Delta Sharing provides live access to the source data with full governance (audit logging, revocable access, partition-level granularity).

Credential Management

Storage Credentials

  • Centrally managed credentials that provide access to cloud storage (GCS service accounts on GCP).
  • Created once, referenced by multiple external locations — single point of credential rotation.
  • Only metastore admins can create storage credentials — prevents credential sprawl.

External Locations

  • Bind a storage credential to a GCS path prefix.
  • Granular grants control who can create tables at each location.
  • Overlapping paths are resolved by longest-prefix match.
Credential & Location Setup for GCP
-- Step 1: Create storage credential (wraps GCP service account)
CREATE STORAGE CREDENTIAL data_lake_cred
COMMENT 'Service account for prod data lake access'
WITH (GCP_SERVICE_ACCOUNT_EMAIL = 'unity-catalog-sa@my-project.iam.gserviceaccount.com');

-- Step 2: Create external locations for different data zones
CREATE EXTERNAL LOCATION bronze_zone
URL 'gs://data-lake-prod/bronze/'
WITH (STORAGE CREDENTIAL data_lake_cred)
COMMENT 'Bronze zone - raw ingested data';

CREATE EXTERNAL LOCATION silver_zone
URL 'gs://data-lake-prod/silver/'
WITH (STORAGE CREDENTIAL data_lake_cred)
COMMENT 'Silver zone - cleansed data';

CREATE EXTERNAL LOCATION gold_zone
URL 'gs://data-lake-prod/gold/'
WITH (STORAGE CREDENTIAL data_lake_cred)
COMMENT 'Gold zone - business aggregates';

-- Step 3: Grant access to teams
GRANT CREATE EXTERNAL TABLE ON EXTERNAL LOCATION bronze_zone TO data_engineers;
GRANT CREATE EXTERNAL TABLE ON EXTERNAL LOCATION silver_zone TO data_engineers;
GRANT CREATE EXTERNAL TABLE ON EXTERNAL LOCATION gold_zone TO data_engineers;

-- Analysts can browse locations but not create tables
GRANT READ FILES ON EXTERNAL LOCATION gold_zone TO data_analysts;

Row & Column-Level Security

Row Filters

  • Define a SQL function that filters rows based on the querying user's identity or group membership.
  • Applied transparently — users see a filtered view of the table without knowing rows are hidden.
  • Useful for: multi-tenant tables, regional data access, PII isolation.

Column Masks

  • Define a SQL function that transforms column values based on the querying user.
  • Common patterns: hash email for non-privileged users, show only last 4 digits of SSN, return NULL for restricted columns.
  • Applied at read time — underlying data is unchanged.
Row Filters & Column Masks
-- Create a row filter function: users see only their region's data
CREATE FUNCTION prod_catalog.security.region_filter(region_col STRING)
RETURNS BOOLEAN
RETURN (
  -- Admins see all rows; others see only their region
  IS_MEMBER('admin_group')
  OR region_col = CASE
    WHEN IS_MEMBER('us_team') THEN 'US'
    WHEN IS_MEMBER('eu_team') THEN 'EU'
    WHEN IS_MEMBER('apac_team') THEN 'APAC'
    ELSE NULL  -- No access if not in any regional group
  END
);

-- Apply row filter to table
ALTER TABLE prod_catalog.gold.sales
SET ROW FILTER prod_catalog.security.region_filter ON (region);

-- Create a column mask function: mask email for non-privileged users
CREATE FUNCTION prod_catalog.security.mask_email(email_col STRING)
RETURNS STRING
RETURN (
  CASE
    WHEN IS_MEMBER('pii_access_group') THEN email_col
    ELSE CONCAT(LEFT(email_col, 2), '***@', SPLIT_PART(email_col, '@', 2))
  END
);

-- Apply column mask
ALTER TABLE prod_catalog.gold.customers
ALTER COLUMN email SET MASK prod_catalog.security.mask_email;

-- Result for non-privileged user:
-- ad***@company.com (instead of aditya@company.com)

Audit Logging & System Tables

System Tables

  • system.access.audit: Every action performed in the workspace — who queried what table, when, from which cluster. Retained for 365 days.
  • system.billing.usage: DBU consumption by cluster, job, user — for cost attribution and chargeback.
  • system.compute.clusters: Cluster lifecycle events (created, started, terminated, resized).
  • system.lineage.table_lineage: Programmatic access to lineage data (upstream/downstream tables).
  • system.lineage.column_lineage: Column-level lineage relationships.
Audit & Compliance Queries
-- Who accessed sensitive tables in the last 7 days?
SELECT
  event_time,
  user_identity.email AS user_email,
  request_params.full_name_arg AS table_name,
  action_name,
  source_ip_address
FROM system.access.audit
WHERE action_name IN ('getTable', 'commandSubmit')
  AND request_params.full_name_arg LIKE '%pii%'
  AND event_date >= CURRENT_DATE() - INTERVAL 7 DAYS
ORDER BY event_time DESC;

-- Cost attribution by team (using cluster tags)
SELECT
  usage_metadata.cluster_id,
  custom_tags['team'] AS team,
  SUM(usage_quantity) AS total_dbus,
  SUM(usage_quantity * list_price) AS estimated_cost
FROM system.billing.usage
WHERE usage_date >= CURRENT_DATE() - INTERVAL 30 DAYS
GROUP BY 1, 2
ORDER BY estimated_cost DESC;

Interview Questions

You're migrating from workspace-level Hive Metastore to Unity Catalog. Describe the migration strategy and key challenges.

Migration strategy (phased approach):

Phase 1 — Assessment: Inventory all tables in existing Hive Metastore (hive_metastore.<database>.<table>). Classify into managed vs external. Identify ownership and access patterns using workspace ACLs.

Phase 2 — Infrastructure: Create Unity Catalog metastore, storage credentials, and external locations. Design the catalog/schema namespace (map existing databases to the 3-level model). Create groups that mirror existing workspace groups.

Phase 3 — Upgrade tables: For external tables — use CREATE TABLE ... USING DELTA LOCATION '...' in Unity Catalog pointing to existing data (metadata-only, no data movement). For managed tables — use CREATE TABLE ... AS SELECT * FROM hive_metastore.db.table or the SYNC command for zero-copy upgrade.

Phase 4 — Permission mapping: Translate workspace ACLs to Unity Catalog GRANT statements. This is the hardest part — workspace ACLs are implicit (cluster access = data access) while UC is explicit (GRANT required at every level).

Phase 5 — Cutover: Update all job references from hive_metastore.db.table to catalog.schema.table. Run both in parallel during transition period. Disable old Hive Metastore access once validated.

Key challenges: (1) USAGE grants at every level (users accustomed to implicit access hit permission errors). (2) External tables that were accessed via mounts — mounts bypass UC. (3) Legacy notebooks using spark.sql("USE database") without catalog prefix. (4) Service principals and automation need updated credentials/tokens.

How does Unity Catalog handle data lineage? What are its limitations and how would you address gaps?

How it works: Unity Catalog instruments the Spark query planner. When a job reads from table A and writes to table B, UC automatically records: (1) table-level dependency (A → B), (2) column-level mapping (A.col1 → B.col2 via transformation X). Lineage is stored in system tables and visualized in Catalog Explorer.

Captured scenarios: All Spark/SQL operations via Databricks compute — INSERT, MERGE, CREATE TABLE AS SELECT, DataFrame writes, DLT pipelines. Column-level lineage traces through SELECT projections, aggregations, JOINs, and CASE statements.

Limitations: (1) External writes — data written by non-Databricks tools (Dataproc, BigQuery, Airflow operators running Spark elsewhere) doesn't appear in lineage. (2) Python UDFs are opaque — UC records "this UDF was called" but not the internal column transformations. (3) Dynamic SQL (building queries as strings) may not be traced. (4) Cross-platform lineage (BQ → Databricks → another system) requires an external tool.

Addressing gaps: (1) For cross-platform lineage, integrate with OpenLineage standard — emit lineage events from non-Databricks systems to a shared lineage store (Marquez, DataHub). (2) For UDF opacity, annotate UDFs with manual lineage metadata or refactor to SQL expressions where possible. (3) For external writes, use trigger-based detection — monitor GCS bucket changes and correlate with known pipeline schedules.

Compare Unity Catalog with AWS Lake Formation. When would you choose each?

Choose Unity Catalog when: (1) You're already using Databricks as primary compute — it's deeply integrated and automatic. (2) You need cross-cloud governance (AWS + GCP + Azure workspaces under one metastore). (3) Column-level lineage is a requirement. (4) You need to share data externally via Delta Sharing (open protocol, not cloud-locked). (5) Row/column security using SQL-native patterns (row filters, column masks).

Choose Lake Formation when: (1) Multi-engine governance on AWS — need to govern access for EMR, Athena, Redshift, Glue all under one permission model. (2) Already using AWS Glue Data Catalog extensively. (3) Tag-based access control (LF-Tags) suits your organization better than explicit grants. (4) Need to integrate with AWS IAM Identity Center (SSO) and existing AWS permission boundaries.

Key difference in philosophy: Unity Catalog is Databricks-centric governance — it governs all data accessed through Databricks (regardless of storage location). Lake Formation is AWS-centric governance — it governs all data in AWS (regardless of compute engine). If Databricks is your primary platform, UC is the natural choice. If you have heterogeneous AWS compute (EMR + Athena + Redshift), Lake Formation provides broader coverage.

Design a Unity Catalog governance model for a 200-person data organization with multiple teams, environments, and external data consumers.

Namespace design: Catalogs per environment + shared: dev, staging, prod, shared (cross-team reference data). Within each: schemas per domain (sales, marketing, finance, ml_features).

Workspace topology: 3 workspaces (dev, staging, prod) all bound to the same regional metastore. Catalog-level USAGE grants control which workspace users see which catalogs (dev users: only dev catalog; prod users: prod + shared).

Groups & inheritance: Account-level groups: data_engineers, data_analysts, data_scientists, platform_admins. Sub-groups per team: de_sales, de_marketing, etc. Inheritance: de_sales inherits from data_engineers, gets additional MODIFY on prod.sales.* schemas.

Row/column security: PII columns (email, phone, address) masked for all non-PII-approved groups. Regional row filters on customer tables — EU team sees only EU data (GDPR compliance). Audit table for PII access: query system.access.audit weekly, flag unexpected access.

External sharing: Delta Shares for partner organizations — separate share per partner, scoped to specific gold tables. Automated share monitoring via system tables to detect unused shares (revoke after 90 days inactive).

Operational governance: Cluster policies enforce tags (team, cost_center) — enables chargeback via system.billing.usage. Quarterly access reviews: compare GRANT statements against actual usage from audit logs, revoke stale permissions.
