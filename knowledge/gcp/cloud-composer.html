Cloud Composer Architecture

Cloud Composer is a fully managed Apache Airflow service running on Google Kubernetes Engine (GKE). Understanding the architecture helps with sizing, debugging, and cost optimization:

Core Components

  • Airflow Scheduler: Runs as a GKE pod. Parses DAG files, schedules task instances, triggers task execution. Heart of the system — if the scheduler is unhealthy, nothing runs.
  • Airflow Workers: GKE pods that execute tasks. Use CeleryExecutor (Composer 1) or KubernetesExecutor (Composer 2) to run task instances.
  • Airflow Webserver: GKE pod serving the Airflow UI. Accessed via Identity-Aware Proxy (IAP) for authentication.
  • Triggerer: (Composer 2 / Airflow 2.2+) Lightweight process for deferred operators — holds thousands of waiting tasks without consuming worker resources.
  • Cloud SQL (PostgreSQL): Managed metadata database storing DAG state, task instances, XCom values, connections, variables.
  • GCS DAG Bucket: DAG files synced from a GCS bucket to the scheduler/workers. Upload DAGs to GCS, and Composer picks them up automatically.
  • Redis: (Composer 1 only) Message broker for Celery task queue between scheduler and workers.
Key insight: Cloud Composer 2's biggest architectural improvement is autoscaling workers via KubernetesExecutor. Each task runs in its own pod — pods spin up on demand and terminate after task completion. No idle workers consuming resources between task executions. This fundamentally changes the cost model from "always-on infrastructure" to "pay-per-task-execution."

Pitfall: Composer 1 to Composer 2 migration is NOT in-place. You must create a new Composer 2 environment, migrate DAGs, connections, variables, and pools, then cut over. There's no "upgrade" button. Plan for: (1) Export connections/variables via CLI, (2) Test all DAGs in new env, (3) Parallel run period, (4) DNS/trigger cutover.

Environment Sizing

Scheduler Sizing

  • Small (0.5 vCPU, 2GB): Up to ~100 DAGs, ~200 task instances/hour. Dev/test environments.
  • Medium (2 vCPU, 4GB): 100–500 DAGs, ~1000 task instances/hour. Production with moderate complexity.
  • Large (4 vCPU, 8GB): 500+ DAGs, thousands of task instances/hour. Large-scale production.
  • Key metric: Scheduler heartbeat rate and parsing time. If DAG parsing takes >30s for a file, the scheduler is undersized or DAGs need optimization.

Worker Configuration (Composer 2)

  • Min workers: Set to 1–2 for always-warm capacity (avoids cold-start on first task). Set to 0 for maximum cost savings (but 30–60s startup delay).
  • Max workers: Based on peak concurrent tasks. Each worker handles 1 task by default (configurable with worker_concurrency).
  • CPU/Memory per worker: Default 0.5 vCPU, 2GB. Increase for memory-intensive tasks (large pandas operations, local Spark). Keep small if tasks are just API calls or operator invocations.

Triggerer Sizing

  • Handles deferrable operators (tasks waiting on external events). Very lightweight — one triggerer handles thousands of deferred tasks.
  • Default: 1 triggerer pod (0.5 vCPU, 0.5GB). Only scale if you have >1000 concurrent deferred tasks.

DAG Design Patterns

Idempotent Tasks

  • Rule: Every task must produce the same result whether run once or N times. This enables safe retries and backfills.
  • Pattern: Overwrite target partition (not append). Use MERGE/upsert instead of INSERT. Delete-then-write for non-Delta targets.
  • Anti-pattern: INSERT INTO without deduplication — retried tasks create duplicate rows.

XComs (Cross-Communication)

  • Pass small data between tasks via the metadata database (stored in PostgreSQL).
  • Limit: Keep XCom values small (<48KB). Large XComs slow down the metadata DB and can cause serialization issues.
  • Pattern for large data: Write to GCS, pass the GCS path as XCom value. Downstream task reads from GCS.

Dynamic DAGs

  • Generate DAGs programmatically from configuration (YAML/JSON files or database queries).
  • Best practice: Generate at parse time (not execution time). Keep the config in GCS alongside DAGs — scheduler reads config during parsing.
  • Gotcha: Don't query external databases during DAG parsing — this runs on every scheduler heartbeat (every 30s) and can overwhelm the DB.

Task Groups

  • Visual grouping of related tasks in the Airflow UI — replaces the deprecated SubDagOperator.
  • Lightweight — no separate DAG run, no scheduler overhead.
  • Use for: grouping transform tasks by domain, grouping quality checks, or creating reusable task patterns.
Production DAG with TaskFlow API & Task Groups
from airflow.decorators import dag, task, task_group
from airflow.providers.google.cloud.operators.bigquery import (
    BigQueryInsertJobOperator,
    BigQueryCheckOperator
)
from airflow.providers.google.cloud.transfers.gcs_to_bigquery import GCSToBigQueryOperator
from datetime import datetime, timedelta

default_args = {
    "owner": "data-engineering",
    "depends_on_past": False,
    "retries": 2,
    "retry_delay": timedelta(minutes=5),
    "retry_exponential_backoff": True,
    "execution_timeout": timedelta(hours=2),
    "sla": timedelta(hours=3),
}

@dag(
    dag_id="daily_sales_pipeline",
    schedule="0 6 * * *",  # 6 AM daily
    start_date=datetime(2024, 1, 1),
    catchup=False,
    default_args=default_args,
    tags=["production", "sales", "daily"],
    doc_md="""## Daily Sales Pipeline
    Ingests raw sales data from GCS, transforms in BigQuery,
    builds gold aggregates, and runs quality checks.
    """,
    max_active_runs=1,
)
def daily_sales_pipeline():

    @task_group(group_id="ingest")
    def ingest_raw():
        """Ingest raw files from GCS to BigQuery staging."""
        
        load_orders = GCSToBigQueryOperator(
            task_id="load_orders",
            bucket="raw-data-landing",
            source_objects=["sales/orders/dt={{ ds }}/*.parquet"],
            destination_project_dataset_table="staging.raw_orders${{ ds_nodash }}",
            source_format="PARQUET",
            write_disposition="WRITE_TRUNCATE",  # Idempotent: overwrite partition
            autodetect=True,
        )

        load_returns = GCSToBigQueryOperator(
            task_id="load_returns",
            bucket="raw-data-landing",
            source_objects=["sales/returns/dt={{ ds }}/*.parquet"],
            destination_project_dataset_table="staging.raw_returns${{ ds_nodash }}",
            source_format="PARQUET",
            write_disposition="WRITE_TRUNCATE",
            autodetect=True,
        )
        
        return [load_orders, load_returns]

    @task_group(group_id="transform")
    def transform_silver():
        """Clean and conform raw data into silver tables."""
        
        transform_sql = BigQueryInsertJobOperator(
            task_id="transform_orders",
            configuration={
                "query": {
                    "query": """
                        MERGE silver.orders AS target
                        USING staging.raw_orders AS source
                        ON target.order_id = source.order_id
                        WHEN MATCHED AND source.updated_at > target.updated_at THEN
                          UPDATE SET
                            target.status = source.status,
                            target.amount = source.amount,
                            target.updated_at = source.updated_at
                        WHEN NOT MATCHED THEN
                          INSERT (order_id, customer_id, amount, status, created_at, updated_at)
                          VALUES (source.order_id, source.customer_id, source.amount,
                                  source.status, source.created_at, source.updated_at)
                    """,
                    "useLegacySql": False,
                }
            },
        )
        return transform_sql

    @task_group(group_id="quality_checks")
    def run_quality_checks():
        """Data quality validation on silver tables."""
        
        check_row_count = BigQueryCheckOperator(
            task_id="check_order_count",
            sql="""
                SELECT COUNT(*) > 0
                FROM silver.orders
                WHERE DATE(created_at) = '{{ ds }}'
            """,
            use_legacy_sql=False,
        )

        check_nulls = BigQueryCheckOperator(
            task_id="check_no_null_amounts",
            sql="""
                SELECT COUNT(*) = 0
                FROM silver.orders
                WHERE amount IS NULL AND DATE(created_at) = '{{ ds }}'
            """,
            use_legacy_sql=False,
        )
        
        return [check_row_count, check_nulls]

    @task
    def build_gold_aggregates():
        """Build daily revenue aggregates."""
        from google.cloud import bigquery
        client = bigquery.Client()
        query = """
            CREATE OR REPLACE TABLE gold.daily_revenue
            PARTITION BY order_date
            CLUSTER BY region
            AS
            SELECT
                DATE(created_at) AS order_date,
                region,
                COUNT(*) AS order_count,
                SUM(amount) AS total_revenue,
                AVG(amount) AS avg_order_value
            FROM silver.orders
            GROUP BY 1, 2
        """
        client.query(query).result()
        return "Gold aggregates built successfully"

    # DAG dependency chain
    ingest_raw() >> transform_silver() >> run_quality_checks() >> build_gold_aggregates()

daily_sales_pipeline()

Deferrable Operators (Async)

  • Traditional sensors block a worker slot while waiting (polling every N seconds). Expensive at scale.
  • Deferrable operators free the worker and register with the Triggerer — zero worker resources consumed while waiting.
  • Example: BigQueryInsertJobOperator(deferrable=True) — submits the BQ job and immediately frees the worker. Triggerer polls for completion.

Dependency Management

PyPI Packages

  • Install via environment config: gcloud composer environments update ... --update-pypi-packages-from-file=requirements.txt
  • Limitation: Package installs trigger environment update (5–15 min downtime). Plan installs during maintenance windows.
  • Conflicts: Composer pins many packages (airflow, google-cloud-*). Adding packages with conflicting version requirements fails silently or causes import errors.

Custom Images (Composer 2)

  • Build custom Docker images extending the Composer base image — install OS-level dependencies, custom binaries, or pre-compiled wheels.
  • Best practice: Use for heavy dependencies (pandas, numpy, dbt) that are slow to install via PyPI at pod startup.
Custom Composer Image (Dockerfile)
# Extend the official Composer image
FROM us-docker.pkg.dev/cloud-airflow-releaser/airflow-worker-scheduler-2/airflow-worker-scheduler-2:composer-2.7.1-airflow-2.7.3

# Install system dependencies
USER root
RUN apt-get update && apt-get install -y \
    libpq-dev \
    build-essential \
    && rm -rf /var/lib/apt/lists/*

# Install Python packages (pinned versions)
USER airflow
COPY requirements.txt /opt/requirements.txt
RUN pip install --no-cache-dir -r /opt/requirements.txt

# requirements.txt:
# dbt-bigquery==1.7.4
# great-expectations==0.18.8
# pandas==2.1.4
# pyarrow==14.0.2

Monitoring & Alerting

Airflow-Level Monitoring

  • Airflow UI Grid View: Visual timeline of DAG runs and task states (success/failed/running/queued).
  • Task duration trends: Detect performance degradation — tasks taking 2x longer than historical average.
  • SLAs: Define expected completion time per task. SLA misses trigger email notifications and appear in the SLA Misses view.

Cloud Monitoring Metrics

  • composer.googleapis.com/environment/scheduler_heartbeat — scheduler health (should be ~5s interval).
  • composer.googleapis.com/environment/worker/pod_eviction_count — indicates memory pressure.
  • composer.googleapis.com/environment/dag_processing/total_parse_time — DAG parsing performance.
  • composer.googleapis.com/environment/database/health — metadata DB health.
  • Alert policy: Alert if scheduler heartbeat >30s, worker evictions >0, or parse time >60s.

CI/CD for DAGs

DAG Deployment Pipeline

  • Source: DAGs stored in git repo (not edited directly in GCS).
  • Validation: Pre-commit hooks run python -c "import dag_file" to catch syntax errors. Airflow CLI dags test for logical validation.
  • Deploy: CI/CD pipeline (Cloud Build, GitHub Actions) syncs DAG files to the Composer GCS bucket on merge to main.
  • Promotion: dev → staging → prod environments. Same DAGs, different connections/variables per environment.
Cloud Build CI/CD for Composer DAGs

Cost Optimization

Composer 2 Cost Levers

  • Right-size scheduler: Monitor CPU/memory utilization. Most teams over-provision schedulers — "medium" handles 500+ DAGs.
  • Min workers = 0 or 1: For non-time-critical environments, set min_workers=0 to avoid idle worker costs. Accept 30–60s cold start.
  • Deferrable operators: Use deferrable=True for sensors and long-running operators — frees worker pods (cost) while the triggerer (cheap) monitors completion.
  • Task consolidation: Combine many tiny tasks into fewer batch tasks — reduces pod spin-up overhead and scheduler load.
  • Environment sharing: One Composer environment for multiple teams (separate DAGs via folder conventions) rather than one environment per team.

Cost Breakdown

  • Compute (GKE nodes): ~60% of cost. Scheduler, workers, triggerer, webserver all run on GKE.
  • Cloud SQL: ~20% of cost. Metadata database (fixed cost regardless of usage).
  • GCS: ~5%. DAG storage, logs.
  • Networking: ~15%. VPC, Private Google Access, IAP for webserver.
Key insight: The biggest cost optimization in Composer 2 vs Composer 1 is autoscaling workers. A typical data team has 50 DAGs running 6 AM–9 AM and mostly idle the rest of the day. Composer 1 pays for workers 24/7. Composer 2 with min_workers=1 scales to 10 workers during peak and back to 1 during off-hours — ~70% compute savings.

Airflow 2.x Features

TaskFlow API

  • Pythonic syntax for defining tasks using @task decorator — XCom passing is implicit via return values.
  • Replaces verbose PythonOperator boilerplate. Type annotations enable auto-serialization.
  • Supports task dependencies via function call chaining — more readable than >> operator for complex flows.

Data-Aware Scheduling (Datasets)

  • Datasets: Logical identifiers representing data produced by a task (e.g., a BigQuery table, a GCS path).
  • Producer DAG: Declares that a task produces a dataset via outlets=[Dataset("bq://project.dataset.table")].
  • Consumer DAG: Scheduled on dataset updates instead of cron. schedule=[Dataset("bq://project.dataset.table")] triggers the DAG when the producer completes.
  • Benefit: Event-driven orchestration without sensors or polling. Eliminates arbitrary cron offsets ("run 30min after the upstream DAG probably finishes").
Data-Aware Scheduling with Datasets
from airflow.decorators import dag, task
from airflow.datasets import Dataset
from datetime import datetime

# Define datasets (logical identifiers)
orders_dataset = Dataset("bq://my-project.silver.orders")
revenue_dataset = Dataset("bq://my-project.gold.daily_revenue")

# Producer DAG — runs on cron, produces a dataset
@dag(
    dag_id="ingest_orders",
    schedule="0 6 * * *",
    start_date=datetime(2024, 1, 1),
    catchup=False,
)
def ingest_orders():
    @task(outlets=[orders_dataset])  # Declares this task produces the orders dataset
    def load_and_transform():
        """Load raw orders and write to silver.orders."""
        from google.cloud import bigquery
        client = bigquery.Client()
        client.query("INSERT INTO silver.orders SELECT * FROM staging.raw_orders").result()
        return "Orders loaded"

    load_and_transform()

# Consumer DAG — triggers when orders_dataset is updated (no cron!)
@dag(
    dag_id="build_revenue_aggregates",
    schedule=[orders_dataset],  # Event-driven: runs when orders_dataset updates
    start_date=datetime(2024, 1, 1),
    catchup=False,
)
def build_revenue():
    @task(outlets=[revenue_dataset])
    def aggregate_revenue():
        """Build daily revenue from silver.orders."""
        from google.cloud import bigquery
        client = bigquery.Client()
        client.query("""
            CREATE OR REPLACE TABLE gold.daily_revenue AS
            SELECT DATE(created_at) AS dt, SUM(amount) AS revenue
            FROM silver.orders GROUP BY 1
        """).result()
        return "Revenue aggregated"

    aggregate_revenue()

ingest_orders()
build_revenue()

Interview Questions

Your Cloud Composer environment is experiencing scheduler lag — DAGs are not being picked up on time. How do you diagnose and fix this?

Diagnosis steps:

(1) Check scheduler heartbeat: Cloud Monitoring metric scheduler_heartbeat. If interval >10s (normal is ~5s), the scheduler is overloaded.

(2) Check DAG parsing time: dag_processing/total_parse_time metric. If parsing takes >30s, complex/numerous DAG files are bottlenecking the scheduler. Airflow re-parses ALL DAG files every dag_dir_list_interval (default 300s in Composer).

(3) Check metadata DB: If Cloud SQL CPU >80%, the scheduler's metadata queries are slow. Common with large XCom tables or many task instances.

(4) Check worker queue depth: If tasks are queued but not starting, workers are saturated or pods can't schedule (GKE node pool exhausted).

Fixes:

(1) Reduce DAG complexity: Move top-level code out of DAG files (imports, configs). Use .airflowignore to exclude non-DAG files. Reduce DAG count by combining related DAGs.

(2) Scale scheduler: Increase scheduler CPU/memory. In Composer 2, add a second scheduler pod (HA mode) for parallelized parsing.

(3) Tune config: Increase dag_dir_list_interval (less frequent re-parsing). Increase min_file_process_interval. Reduce max_active_runs_per_dag.

(4) Database cleanup: Purge old task instances: airflow db clean --clean-before-timestamp 2024-01-01. Clear old XCom entries. Reduce log retention.

Design a CI/CD pipeline for deploying Airflow DAGs to Cloud Composer with proper validation and rollback capability.

Pipeline stages:

(1) Static validation (PR check): Import each DAG file in a clean Python environment — catches syntax/import errors. Run airflow dags test dag_id execution_date for logical validation. Lint with ruff/pylint. Check for banned patterns (no top-level DB queries, no hardcoded credentials).

(2) Unit tests (PR check): Test custom operators, sensor logic, and transform functions in isolation (mock external services). Test DAG structure (correct dependencies, no cycles, expected task count).

(3) Deploy to staging (on merge to main): gsync DAG files to staging Composer GCS bucket. Wait for scheduler to parse (check dag_processing/last_duration). Run integration tests — trigger DAG runs with test data, verify output.

(4) Deploy to production (manual approval or automated after staging success): Sync to prod GCS bucket. Monitor for 1 hour — check for import errors, task failures, SLA misses.

Rollback: GCS versioning enabled on DAG bucket. Rollback = copy previous version from GCS version history. Alternative: keep last-known-good commit SHA, gsync from that commit on failure. Automation: if >3 task failures in 30 min post-deploy, auto-rollback to previous version.

Explain Airflow Datasets (data-aware scheduling). How does this compare to sensor-based triggering? What are the limitations?

How Datasets work: Producer tasks declare outlets=[Dataset("uri")]. When the task succeeds, Airflow records that the dataset was updated. Consumer DAGs with schedule=[Dataset("uri")] are triggered by dataset update events — no polling, no sensors.

Advantages over sensors: (1) Zero resource consumption while waiting — no worker slots blocked. (2) Guaranteed triggering — the scheduler handles event propagation (no missed polling intervals). (3) Multi-dataset triggers: schedule=[dataset_a, dataset_b] waits for ALL datasets before triggering (implicit AND). (4) Clear dependency visualization in the Airflow UI (Dataset tab).

Limitations: (1) Only works within the same Airflow instance — cross-environment triggers still need sensors or external events. (2) URI is a logical identifier only — Airflow doesn't verify the dataset actually changed (the producer task completing is the signal). (3) No conditional triggering (e.g., "trigger only if dataset has >1000 rows"). (4) OR logic not natively supported (workaround: intermediate DAG). (5) Limited to DAG scheduling — can't use datasets to trigger individual tasks within a DAG.

Best practice: Use Datasets for all intra-Airflow dependencies (replaces ExternalTaskSensor). Keep sensors for external system dependencies (waiting for a file in GCS, an API to return success, or a partition to appear in BigQuery).

Compare Cloud Composer with self-managed Airflow on GKE. When would you choose each?

Choose Cloud Composer when: (1) Team size <5 data engineers — don't want to dedicate 0.5–1 FTE to Airflow ops. (2) Standard Airflow usage (DAGs, operators, sensors) without exotic customization. (3) Need managed upgrades — Composer handles Airflow version upgrades, security patches, GKE node pool management. (4) Compliance requirements — Composer provides SLA guarantees and integrates with GCP audit logging. (5) Fast time-to-value — environment ready in 30 min vs days for self-managed.

Choose self-managed Airflow on GKE when: (1) Need custom Airflow components (custom executors, non-standard auth backends, heavily modified webserver). (2) Very large scale (1000+ DAGs, 50K+ task instances/day) where Composer's fixed architecture limits performance. (3) Cost sensitivity at scale — Composer adds ~40% premium over raw GKE costs. At high scale, self-managing saves significant money. (4) Need latest Airflow version immediately (Composer lags by 1–3 months). (5) Multi-cluster Airflow (separate schedulers for different teams with shared metadata).

Hybrid approach: Start with Composer for fast iteration. If you hit limitations (cost, customization, scale), migrate to self-managed — DAGs are portable, only infrastructure changes.
