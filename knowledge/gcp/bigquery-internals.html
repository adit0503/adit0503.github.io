Architecture Overview

BigQuery is a serverless, multi-tenant analytics data warehouse that separates compute from storage at the infrastructure level. Understanding the four pillars of its architecture is critical for optimization:

Dremel — Execution Engine

  • Origin: Google's internal query engine (2006 paper) — predecessor to BigQuery's compute layer.
  • Role: Parses SQL, creates execution plans, orchestrates distributed query execution across thousands of workers.
  • Multi-level serving tree: Root server → intermediate mixers → leaf nodes (workers). The root coordinates, mixers aggregate partial results, leaves scan data.
  • Scheduling: Dynamically assigns slots to queries at runtime — no fixed cluster allocation per user.

Colossus — Distributed Storage

  • What it is: Google's next-generation distributed file system (successor to GFS). Stores all BigQuery table data.
  • Properties: Erasure-coded (not replicated like HDFS — more storage efficient), globally distributed, supports petabytes per table.
  • Data format: Capacitor columnar format — designed specifically for Dremel's tree execution model.
  • Decoupling: Storage is independent of compute — adding more slots doesn't require more storage nodes and vice versa.

Jupiter — Network Fabric

  • Bandwidth: Google's petabit-scale network connecting compute and storage — 1 Pb/s bisection bandwidth.
  • Why it matters: Enables the separation of compute and storage without I/O bottlenecks. Each slot can read from any Colossus storage node at high throughput.
  • Shuffle: Intermediate shuffle data flows through Jupiter rather than spilling to disk (unlike traditional MapReduce).

Borg — Cluster Management

  • Role: Google's cluster scheduler (predecessor to Kubernetes) — allocates compute resources for Dremel workers.
  • Multi-tenancy: Thousands of BigQuery users share the same Borg-managed infrastructure. Isolation is at the slot/query level, not machine level.
  • Elasticity: Borg can spin up thousands of Dremel workers in seconds for a large query, then release them immediately after completion.
Key insight: BigQuery's true innovation is not any single component — it's the tight integration of Dremel + Colossus + Jupiter + Borg that enables serverless, multi-tenant analytics at petabyte scale. No other cloud warehouse achieves this level of infrastructure abstraction.

Dremel Query Execution

Understanding how Dremel executes queries helps explain why certain query patterns are fast and others are expensive:

Multi-Level Serving Tree

  • Root server: Receives the SQL query, parses it, generates the execution plan, and dispatches work to mixers.
  • Intermediate mixers (Level 1–N): Perform partial aggregation. For a COUNT(*), each mixer sums the counts received from nodes below it. Multiple mixer levels exist for very large queries.
  • Leaf nodes (workers/slots): Read data from Colossus in Capacitor format, apply filters (WHERE clauses), project columns (SELECT), and compute local aggregations. Each leaf processes one or more storage units.

Columnar Execution at Leaf Nodes

  • Leaves read only the columns referenced in the query — never full rows. A query touching 3 columns out of 200 reads ~1.5% of the raw data.
  • Predicate pushdown: Filters are applied during column scan using Capacitor metadata (min/max values per column chunk) to skip entire blocks.
  • Vectorized processing: Operates on batches of column values rather than row-by-row — enabling SIMD and CPU cache optimization.

Shuffle Architecture

  • BigQuery uses a distributed in-memory shuffle layer (not disk-based like MapReduce).
  • Shuffle is needed for: JOINs, GROUP BY, ORDER BY, WINDOW functions, and DISTINCT operations.
  • The shuffle layer streams data between stages via Jupiter network — allows pipelining (downstream stages start before upstream completes).
  • Slots writing shuffle output ≠ slots reading shuffle input — BigQuery dynamically assigns different slot counts per stage.
Pitfall: Queries with large JOINs producing massive intermediate shuffle data can exhaust slot memory, causing "Resources exceeded" errors. This happens when join keys are highly skewed — one key produces millions of matching rows. Use APPROX_TOP_COUNT to identify skewed keys before joining.

Slot-Based Compute Model

A slot is BigQuery's unit of computational capacity — a virtual CPU with a portion of RAM. Understanding slot behavior is essential for capacity planning:

On-Demand Pricing

  • Pay per byte scanned ($6.25/TB in US multi-region, as of 2024).
  • Up to 2,000 concurrent slots per project (default quota — can be increased).
  • No guaranteed capacity — during peak load, queries may queue waiting for slots.
  • Best for: sporadic/exploratory queries, dev environments, cost-sensitive workloads that can tolerate variable latency.

Flat-Rate / Editions (Capacity Pricing)

  • Editions model (current): Standard, Enterprise, Enterprise Plus — each with increasing features and slot commitment options.
  • Commitments: Annual or 3-year for lowest per-slot cost. Autoscaling adds pay-as-you-go slots above the baseline.
  • Slot commitments: Purchase in 100-slot increments. E.g., 500-slot baseline + autoscale up to 2000 slots during peaks.
  • Reservations: Assign slot pools to specific projects/folders. A "prod" reservation of 400 slots guarantees capacity for production queries even when ad-hoc queries spike.
Create BigQuery Reservation & Assignment
-- Create a reservation with 500 baseline slots (Enterprise edition)
CREATE RESERVATION `project.region-us.prod_reservation`
OPTIONS (
  slot_capacity = 500,
  edition = 'ENTERPRISE'
);

-- Create an assignment binding the reservation to a project
CREATE ASSIGNMENT `project.region-us.prod_reservation.prod_assignment`
OPTIONS (
  assignee = 'projects/my-prod-project',
  job_type = 'QUERY'
);

-- Enable autoscaling: burst up to 1500 additional slots
ALTER RESERVATION `project.region-us.prod_reservation`
SET OPTIONS (
  autoscale_max_slots = 1500
);

Storage Internals

Capacitor Columnar Format

  • Google's proprietary columnar format (not Parquet/ORC) — optimized specifically for Dremel's execution model.
  • Encoding: Hybrid encoding per column — dictionary, run-length, delta, and bit-packing. Automatically selected based on data distribution.
  • Nested data: Supports complex types (STRUCT, ARRAY) natively using repetition and definition levels (same concept as Parquet, which was inspired by Dremel paper).
  • Metadata: Per-block min/max, null counts, distinct counts — used for partition/cluster pruning without scanning data.

Partitioning

  • Types: Time-unit (HOUR, DAY, MONTH, YEAR), integer-range, ingestion-time (_PARTITIONTIME).
  • Limit: Max 4,000 partitions per table.
  • Partition pruning: Queries with filters on the partition column skip scanning irrelevant partitions entirely — direct cost savings in on-demand mode.
  • Best practice: Partition by the primary filter column (usually a date/timestamp). Choose granularity to keep partition size between 1GB–10GB.

Clustering

  • Co-locates rows with similar values in the clustering columns within each partition.
  • Up to 4 clustering columns — order matters (first column is primary sort key).
  • Automatic re-clustering: BigQuery periodically re-clusters data in the background — no OPTIMIZE command needed.
  • Block pruning: During scan, BigQuery uses clustering metadata to skip blocks where the clustering column values don't match the filter.
Partitioned + Clustered Table Creation
CREATE TABLE `project.dataset.events`
(
  event_id STRING,
  user_id STRING,
  event_type STRING,
  event_timestamp TIMESTAMP,
  properties JSON,
  country STRING
)
PARTITION BY DATE(event_timestamp)
CLUSTER BY user_id, event_type
OPTIONS (
  partition_expiration_days = 365,
  description = 'Partitioned by date, clustered by user+event for efficient lookups'
);

Query Optimization Techniques

Partition Pruning

  • Always filter on the partition column in WHERE clauses. Without it, BigQuery scans ALL partitions.
  • Gotcha: Wrapping the partition column in a function disables pruning. WHERE DATE(timestamp_col) = '2024-01-01' prunes, but WHERE EXTRACT(YEAR FROM timestamp_col) = 2024 does NOT.
  • Use _PARTITIONTIME or _PARTITIONDATE pseudo-columns for ingestion-time partitioned tables.

Cluster Pruning

  • Filter on clustering columns (in order) to benefit from block-level skipping.
  • Effectiveness depends on how well-sorted the data is — freshly loaded/re-clustered tables have better pruning.
  • Check INFORMATION_SCHEMA.TABLE_STORAGE for last_clustering_time to monitor clustering freshness.

Materialized Views

  • Precomputed aggregations that BigQuery automatically maintains when base tables change.
  • Auto-rewriting: BigQuery can automatically rewrite incoming queries to use a materialized view — even if the query doesn't reference the view directly.
  • Freshness: Views are updated within minutes of base table changes (not real-time).
  • Cost: You pay for storage of the materialized view, but queries using it scan less data.
Materialized View with Auto-Refresh
CREATE MATERIALIZED VIEW `project.dataset.daily_revenue_mv`
OPTIONS (
  enable_refresh = true,
  refresh_interval_minutes = 30
)
AS
SELECT
  DATE(order_timestamp) AS order_date,
  region,
  SUM(revenue) AS total_revenue,
  COUNT(*) AS order_count
FROM `project.dataset.orders`
GROUP BY 1, 2;

-- Any query filtering on order_date + region with SUM(revenue)
-- will automatically be rewritten to use this view

BI Engine

  • In-memory analysis service that accelerates BigQuery queries by caching data in RAM.
  • Provides sub-second query response for BI dashboards (Looker, Data Studio, Tableau).
  • Reservation-based: allocate GB of memory per project (e.g., 10GB BI Engine reservation).
  • Automatically decides which table data to cache based on query patterns.

Query Caching

  • BigQuery caches query results for ~24 hours. Identical queries (same SQL text, same user) return cached results at zero cost.
  • Cache invalidation: Any DML on the base tables, table expiration, or non-deterministic functions (CURRENT_TIMESTAMP, RAND) bypass cache.
  • Scripting limitation: Queries inside scripts or procedures don't benefit from result caching.

Slot Reservations for Priority

  • Create separate reservations for critical vs. ad-hoc queries.
  • Use IDLE_SLOTS sharing so reserved but unused slots can be borrowed by other workloads.
  • Set concurrency targets per reservation to limit queuing.
Pitfall: SELECT * in BigQuery is incredibly expensive on wide tables. Unlike row-oriented databases, each additional column is a separate Colossus read. A SELECT * on a 500-column table with 10TB scans all 10TB. SELECT just the 5 columns you need scans only ~100GB — a 100x cost reduction.

DML & Streaming Ingestion

Streaming Buffer (Legacy insertAll API)

  • Rows inserted via the legacy streaming API land in a temporary streaming buffer before being moved to managed Colossus storage.
  • Buffer behavior: Data is queryable immediately but not yet in Capacitor format — queries on buffer are slightly slower.
  • Deduplication: Provide an insertId for best-effort deduplication within a short window (~minutes). Not guaranteed — design for at-least-once semantics.
  • Cost: $0.05/GB ingested (separate from storage/query costs). No charge for batch loads.

Storage Write API (Recommended)

  • Committed mode: Exactly-once semantics with stream-level transactions. Data visible only after explicit commit.
  • Default mode: At-least-once, data visible immediately (best effort dedup). Higher throughput, ~2x cheaper than legacy streaming.
  • Buffered mode: Data buffered and committed on flush — useful for micro-batch patterns.
  • Protocol Buffers: Uses protobuf wire format — more efficient than JSON (legacy API). ~50% bandwidth reduction.
  • Throughput: 3GB/s per project (default). Multiplexing allows many tables to share a single connection.
Storage Write API — Python (Committed Mode)
from google.cloud.bigquery_storage_v1 import BigQueryWriteClient
from google.cloud.bigquery_storage_v1 import types
from google.protobuf import descriptor_pb2
import event_pb2  # Your protobuf definition

client = BigQueryWriteClient()
parent = f"projects/{project}/datasets/{dataset}/tables/{table}"

# Create a write stream in COMMITTED mode (exactly-once)
stream = client.create_write_stream(
    parent=parent,
    write_stream=types.WriteStream(type_=types.WriteStream.Type.COMMITTED)
)

# Serialize rows using protobuf
request = types.AppendRowsRequest()
request.write_stream = stream.name
proto_rows = types.ProtoRows()
for event in batch:
    row = event_pb2.Event()
    row.event_id = event["id"]
    row.timestamp = event["ts"]
    proto_rows.serialized_rows.append(row.SerializeToString())

request.proto_rows = types.AppendRowsRequest.ProtoData(
    rows=proto_rows,
    writer_schema=types.ProtoSchema(
        proto_descriptor=descriptor_pb2.DescriptorProto()
    )
)

# Append and get offset confirmation
response = client.append_rows(iter([request]))
print(f"Committed at offset: {response.append_result.offset}")

MERGE (Upsert) Behavior

  • BigQuery MERGE rewrites entire partitions affected by the merge — not in-place row updates.
  • DML quotas: Max 1,500 DML statements per table per day (standard). Partitioned tables: 1,500 per partition.
  • Best practice: Batch DML operations — instead of 1000 individual UPDATEs, do a single MERGE from a staging table.
  • Cost: DML statements are billed for bytes scanned in affected partitions (not just changed rows).
Efficient MERGE Pattern for CDC
MERGE `project.dataset.customers` AS target
USING `project.dataset.customers_staging` AS source
ON target.customer_id = source.customer_id
   AND target.updated_at < source.updated_at  -- Only update if newer
WHEN MATCHED THEN
  UPDATE SET
    target.name = source.name,
    target.email = source.email,
    target.updated_at = source.updated_at
WHEN NOT MATCHED THEN
  INSERT (customer_id, name, email, created_at, updated_at)
  VALUES (source.customer_id, source.name, source.email,
          source.created_at, source.updated_at);

-- Truncate staging after successful merge
TRUNCATE TABLE `project.dataset.customers_staging`;

BigQuery ML

  • What it is: Train and serve ML models directly in BigQuery using SQL — no data export needed.
  • Supported models: Linear/logistic regression, K-means, matrix factorization, time-series (ARIMA+), boosted trees (XGBoost), DNN (TensorFlow), imported TensorFlow/ONNX models.
  • Key advantage: Data stays in BigQuery — eliminates the ETL pipeline to a separate ML platform for training.
  • Limitations: Less control over hyperparameters than dedicated ML frameworks. Not suitable for custom architectures or very large deep learning models.
BigQuery ML — Training & Prediction
-- Train a churn prediction model
CREATE OR REPLACE MODEL `project.dataset.churn_model`
OPTIONS (
  model_type = 'BOOSTED_TREE_CLASSIFIER',
  input_label_cols = ['churned'],
  max_iterations = 50,
  learn_rate = 0.1,
  data_split_method = 'AUTO_SPLIT'
) AS
SELECT
  days_since_last_order,
  total_orders,
  avg_order_value,
  support_tickets_30d,
  churned
FROM `project.dataset.customer_features`
WHERE signup_date < '2024-01-01';

-- Predict on new data
SELECT
  customer_id,
  predicted_churned,
  predicted_churned_probs[OFFSET(1)].prob AS churn_probability
FROM ML.PREDICT(
  MODEL `project.dataset.churn_model`,
  (SELECT * FROM `project.dataset.customer_features`
   WHERE signup_date >= '2024-01-01')
)
WHERE predicted_churned_probs[OFFSET(1)].prob > 0.7;

BigQuery Omni (Multi-Cloud)

  • What it is: Run BigQuery queries on data stored in AWS S3 or Azure Blob Storage — without moving data to GCP.
  • Architecture: BigQuery compute runs on Google-managed infrastructure in AWS/Azure regions (using Anthos). Data stays in the external cloud.
  • Use cases: Multi-cloud analytics, data sovereignty requirements, joining cross-cloud datasets.
  • Limitations: Cannot join Omni tables with native BigQuery tables directly. Must use CREATE TABLE AS SELECT to materialize results first. Higher latency than native BQ.
  • External connections: Create a connection to AWS/Azure, then create external tables referencing S3/Blob paths.

Cost Optimization

Storage Billing Model

  • Active storage: $0.02/GB/month — data modified in the last 90 days.
  • Long-term storage: $0.01/GB/month — data NOT modified for 90+ days. Automatic transition, no performance difference.
  • Partition expiration: Automatically delete old partitions to avoid storing stale data indefinitely.
  • Time travel storage: 7 days of change history stored by default (configurable 2–7 days). Adds ~20% storage overhead.

Slot Monitoring with INFORMATION_SCHEMA

Identify Top Slot-Consuming Queries
-- Top 20 most expensive queries by slot-hours consumed (last 7 days)
SELECT
  job_id,
  user_email,
  query,
  total_slot_ms / (1000 * 60 * 60) AS slot_hours,
  total_bytes_processed / POW(1024, 4) AS tb_scanned,
  TIMESTAMP_DIFF(end_time, start_time, SECOND) AS duration_sec,
  total_slot_ms / GREATEST(TIMESTAMP_DIFF(end_time, start_time, MILLISECOND), 1) AS avg_slots_used
FROM `region-us`.INFORMATION_SCHEMA.JOBS
WHERE creation_time > TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 7 DAY)
  AND job_type = 'QUERY'
  AND state = 'DONE'
ORDER BY total_slot_ms DESC
LIMIT 20;

-- Hourly slot utilization pattern (capacity planning)
SELECT
  TIMESTAMP_TRUNC(period_start, HOUR) AS hour,
  SUM(period_slot_ms) / (1000 * 60 * 60) AS slot_hours_consumed,
  MAX(period_slot_ms / TIMESTAMP_DIFF(period_end, period_start, MILLISECOND)) AS peak_slots
FROM `region-us`.INFORMATION_SCHEMA.JOBS_TIMELINE
WHERE period_start > TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 7 DAY)
GROUP BY 1
ORDER BY 1;

Cost Reduction Strategies

  • Avoid SELECT *: Only select columns you need — directly reduces bytes scanned.
  • Use partitioned tables: Always filter on the partition column.
  • Require partition filters: Set require_partition_filter = true on tables to prevent accidental full scans.
  • Materialized views: Precompute expensive aggregations — queries scan the smaller MV instead of base table.
  • BI Engine cache: For dashboards hitting the same tables repeatedly.
  • Dry run: Use --dry_run flag to estimate bytes scanned before running expensive queries.
  • Editions autoscaling caps: Set autoscale_max_slots to prevent cost spikes during unexpected load.
Enforce Partition Filters & Set Expiration

Interview Questions

Explain how BigQuery achieves sub-second query performance on petabyte-scale datasets. What are the key architectural components?

Four pillars work together:

(1) Dremel execution engine uses a multi-level serving tree — a single query is distributed across thousands of leaf workers that read in parallel. With 3000 leaf nodes, scanning 1PB of columnar data takes seconds because each node handles only ~300GB.

(2) Colossus storage with Capacitor columnar format means queries only read referenced columns. A query touching 5 of 200 columns reads 2.5% of the data. Encoding/compression further reduces I/O by 5–10x.

(3) Jupiter network at 1Pb/s bisection bandwidth eliminates the traditional bottleneck of separated compute/storage. Each leaf node reads from Colossus at multi-GB/s without network contention.

(4) Borg scheduling provides instant elasticity — thousands of slots allocated in seconds, released immediately. No cluster startup time.

Additionally: in-memory shuffle (no disk spill for intermediate data), predicate pushdown to storage layer (skip blocks via metadata), and automatic query optimization (join reordering, filter pushdown, materialized view rewriting) all contribute.

You have a 50TB table with 200 columns. Queries are slow and expensive. Design an optimization strategy.

Step 1 — Partition: Identify the primary time-based filter (e.g., event_date). Partition by DAY if daily granularity makes sense. This alone can reduce scans from 50TB to ~140GB for single-day queries.

Step 2 — Cluster: Identify the top 3–4 filter columns from query patterns (use INFORMATION_SCHEMA.JOBS to find most common WHERE clauses). Cluster by those columns within each partition.

Step 3 — Column discipline: Enforce that no dashboards use SELECT *. Create views with only the columns needed for each use case. Use authorized views to abstract the wide base table.

Step 4 — Materialized views: For repeated aggregation queries (daily revenue, hourly counts), create materialized views. BQ auto-rewrites queries to use them.

Step 5 — Partition expiration: If data older than N days is rarely queried, set expiration to auto-drop old partitions. Archive to cheaper GCS if needed for compliance.

Step 6 — BI Engine: For dashboard queries hitting the same data repeatedly, allocate BI Engine cache (10–50GB typically covers hot data for common dashboards).

Expected impact: Partitioning + clustering + column pruning typically reduces effective scan by 95%+ on well-optimized tables. For a 50TB table with daily partition and common filters, a typical analytical query scans 5–50GB instead of 50TB.

Compare the BigQuery Storage Write API vs the legacy streaming insertAll API. When would you choose each?

Storage Write API (recommended for new projects):

- Exactly-once semantics in COMMITTED mode (stream-level transactions with offset tracking). Legacy streaming is at-least-once only.

- ~50% lower cost than legacy streaming (uses protobuf — more efficient wire format than JSON).

- Higher throughput: 3GB/s default vs ~1GB/s for legacy. Connection multiplexing allows many tables per stream.

- Schema evolution: can update schema mid-stream. Legacy API rejects rows that don't match current schema.

Legacy insertAll API:

- Simpler integration — just POST JSON. No protobuf compilation step.

- Best-effort dedup via insertId. Suitable when at-least-once is acceptable and you want minimal client complexity.

- Still works fine for low-throughput use cases (<10MB/s) where client simplicity matters more than cost/guarantees.

Decision: Use Storage Write API for any production streaming pipeline. Use legacy API only for quick prototypes or systems where adding protobuf compilation is prohibitively complex (e.g., legacy applications with frozen build systems).

How does BigQuery handle data skew in JOIN operations? What tools do you use to diagnose and fix it?

Diagnosis:

(1) Check the query execution plan in the BigQuery console — look for stages where one worker processes significantly more rows than others (max vs avg row count per worker).

(2) Use APPROX_TOP_COUNT(join_key, 100) to identify the most frequent key values. If a single key has millions of rows (e.g., NULL, "unknown", or a popular entity), that key causes skew.

(3) Check INFORMATION_SCHEMA.JOBS for queries with high slot_ms but low bytes_scanned — often indicates shuffle skew (one slot is overloaded).

Fixes:

(1) Filter skewed keys: Handle the hot key separately. JOIN the non-skewed portion normally, handle the hot key with a broadcast or pre-aggregation.

(2) Salting technique: Add a random suffix (0–N) to the skewed key in the large table. Replicate the small table N times with each suffix. Distributes the hot key across N slots.

(3) Pre-aggregate: If you're joining and then aggregating, aggregate first to reduce the large side before the join.

(4) BROADCAST join hint: If one side is small (<10GB), force a broadcast join: SELECT /*+ BROADCAST(small_table) */ .... Eliminates shuffle entirely.

(5) Approximate functions: For analytics, APPROX_COUNT_DISTINCT, APPROX_QUANTILES avoid skew-sensitive exact computations.

Design a real-time analytics pipeline feeding BigQuery. Requirements: <30s end-to-end latency, exactly-once semantics, 100K events/sec.

Architecture:

(1) Ingestion: Pub/Sub as the message bus — handles 100K events/sec easily with auto-scaling. Provides at-least-once delivery with message ordering per key.

(2) Stream processing: Dataflow (Apache Beam) streaming job — reads from Pub/Sub, applies deduplication (using event_id in a state store with 10-min window), transforms/enriches events, writes to BigQuery.

(3) BigQuery write: Use Storage Write API in COMMITTED mode for exactly-once. Dataflow's BigQuery connector handles this natively with Method.STORAGE_WRITE_API and useExactlyOnceSemantics().

(4) Table design: Partition by ingestion time (HOUR granularity for real-time queries). Cluster by the most common filter columns.

(5) Query layer: Materialized views on the real-time table for dashboard aggregations. BI Engine cache for sub-second dashboard response.

Latency budget: Pub/Sub delivery ~100ms + Dataflow processing ~5–15s (windowed micro-batch or per-element) + Storage Write API commit ~2–5s = ~20s total. Within 30s SLA.

Exactly-once guarantee: Achieved through Dataflow's checkpointing + Storage Write API committed streams with offset tracking. If Dataflow retries, it resumes from the last committed offset — no duplicates in BigQuery.
