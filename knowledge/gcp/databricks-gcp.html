Databricks Architecture on GCP

Databricks on GCP uses a split-plane architecture that separates management from execution:

Control Plane (Databricks-Managed)

  • Hosted by Databricks in a Databricks-owned GCP project.
  • Contains: Workspace UI, REST API endpoints, job scheduler, notebook state, cluster manager, Unity Catalog metadata, secrets manager.
  • Communication: Secure relay channel from control plane to data plane (no inbound connections required from customer VPC).
  • Region-locked: Control plane runs in the same GCP region as the workspace for data residency.

Data Plane (Customer-Managed)

  • Runs in customer's GCP project — all compute (GCE instances) and data stays within customer's environment.
  • Network: Clusters launch in customer-managed VPCs (or Databricks-managed VPCs for simpler setup). Supports Private Google Access, VPC Service Controls.
  • Storage: All data (Delta tables, checkpoints, logs) stored in customer's GCS buckets. Databricks never stores customer data.
  • Secrets: Cluster credentials, service account keys never leave the data plane.
Key insight: The control/data plane separation is critical for security and compliance. Customer data never leaves the customer's GCP project. The control plane only sees metadata (table schemas, job status, notebook code) — never the actual data being processed. This enables SOC2/HIPAA compliance without data egress concerns.

Workspace Deployment

  • One workspace maps to one GCP project + region combination.
  • Workspace creation provisions: a managed GKE cluster (for workspace services), GCS bucket (DBFS root), service accounts, and network infrastructure.
  • Multi-workspace patterns: separate workspaces per environment (dev/staging/prod) or per team for isolation.

Cluster Types

All-Purpose Clusters (Interactive)

  • Long-running, shared clusters for interactive development, ad-hoc analysis, and notebook exploration.
  • Auto-terminate after configurable idle timeout (default 120 min).
  • Support multiple users concurrently — each gets isolated SparkSession but shares cluster resources.
  • When to use: Development, exploration, collaborative analysis.
  • DBU rate: Higher per-DBU cost than job clusters (~2x premium).

Job Clusters (Automated)

  • Created for a specific job run and terminated immediately after completion.
  • Cannot be shared — one job per cluster instance.
  • When to use: Production ETL/ELT pipelines, scheduled workloads, CI/CD test runs.
  • DBU rate: Lower cost per DBU. Combined with auto-termination, most cost-effective for batch work.
  • Cold start: 3–5 min cluster startup time. Mitigated with instance pools.

SQL Warehouses

  • Dedicated compute for SQL workloads — BI tools, dashboards, SQL-based analytics.
  • Sizes: 2X-Small through 4X-Large (each size doubles slots: 2X-Small = 1 cluster, Large = 16 clusters).
  • Auto-scaling: Horizontally scales by adding clusters within the warehouse (each cluster handles concurrent queries).
  • Serverless SQL Warehouses: Databricks-managed compute — instant startup, no cluster management, usage-based pricing.
  • When to use: BI dashboards (Tableau, Looker), SQL analytics, data exploration with SQL.

Autoscaling & Cluster Configuration

Autoscaling Behavior

  • Min/Max workers: Define the scaling range. Min workers are always running (baseline cost). Max workers is the upper limit during load spikes.
  • Scale-up: Triggered when pending tasks exceed available slots. Databricks adds workers exponentially (1→2→4→8 until max).
  • Scale-down: Triggered after idle timeout (configurable). Removes workers one at a time with graceful decommission (waits for running tasks to finish).
  • Optimized autoscaling: Databricks-enhanced algorithm that scales more aggressively on GCP — uses predictive signals from task queue depth and shuffle data volume.

Spot (Preemptible) VMs Strategy

  • Driver node: NEVER use Spot — driver failure kills the entire job.
  • Workers: Use Spot for workers with fallback to on-demand. Databricks handles automatic Spot eviction gracefully — redistributes partitions to remaining workers.
  • Configuration: Set first_on_demand = 1 (driver) and spot_bid_max_price = -1 (use current Spot price). Set availability = SPOT_WITH_FALLBACK_GCP.

Instance Pools

  • Pre-provisioned pool of idle instances that clusters can draw from — eliminates cold-start time (startup in ~30s vs 3–5min).
  • Configured with min/max idle instances and instance types.
  • Shared across multiple clusters — great for dev environments where multiple engineers start/stop clusters frequently.

Photon Engine

Photon is Databricks' next-generation query engine — a C++ vectorized execution engine that replaces the JVM-based Spark SQL engine for supported operations:

How Photon Works

  • Vectorized execution: Processes data in columnar batches (vectors) rather than row-by-row. Enables SIMD CPU instructions and better cache utilization.
  • Native C++: No JVM overhead (no GC pauses, no object headers, no boxing/unboxing). Direct memory management with memory-mapped I/O.
  • Columnar memory format: Data stays in columnar layout throughout execution — no row-to-columnar conversion overhead.
  • Adaptive execution: Falls back to Spark JVM engine for unsupported operations (UDFs, complex types) — seamless, no job failure.

When Photon Helps (Significant Speedup)

  • Aggregations and GROUP BY operations — 3–8x faster
  • JOIN operations (hash joins, sort-merge joins) — 2–5x faster
  • Scan + filter patterns (WHERE clauses on large tables) — 2–4x faster
  • String operations (LIKE, CONCAT, SUBSTRING) — 5–10x faster (C++ string handling vs JVM)
  • Window functions — 2–4x faster
  • Delta Lake writes (MERGE, UPDATE, INSERT) — 2–3x faster

When Photon Does NOT Help

  • Python UDFs (pyspark UDFs, pandas_udfs) — still execute in Python worker processes
  • RDD-based operations — Photon only accelerates DataFrame/SQL operations
  • Complex nested types (deeply nested structs/arrays) — partial support only
  • Non-SQL ML workloads (MLlib) — uses Spark's existing engine
  • Small data volumes (<1GB) — startup overhead negates the speedup
Key insight: Photon's cost-effectiveness depends on the workload profile. It costs ~2x the DBU rate, so it needs to provide >2x speedup to break even. For aggregation-heavy SQL workloads and Delta MERGE operations, it consistently delivers 3–8x speedup — clear ROI. For UDF-heavy Python workloads, Photon provides zero benefit at double the cost.

Workspace Organization

Repos (Git Integration)

  • Native git integration — clone repos from GitHub, GitLab, Bitbucket directly into the workspace.
  • Supports branching, commits, PRs without leaving Databricks.
  • Best practice: Use Repos for production code. Avoid one-off notebooks in personal folders for anything beyond quick exploration.
  • Folder structure: /Repos/<username>/<repo-name>/

Notebooks

  • Interactive coding environments (Python, SQL, Scala, R) — similar to Jupyter but with collaborative features.
  • %run magic: Import other notebooks as modules. Used for shared utilities.
  • Widgets: Parameterize notebooks — pass arguments from jobs/workflows.
  • Best practice: Keep notebooks thin — orchestration logic only. Business logic in Python modules imported from the repo.

DBFS & External Storage (GCS)

DBFS (Databricks File System)

  • Root storage: Every workspace gets a DBFS root backed by a GCS bucket (auto-created during workspace provisioning).
  • Abstraction: Provides a unified file system interface over GCS — accessible as dbfs:/ or /dbfs/ from notebooks.
  • Limitation: DBFS root is workspace-scoped — not shared across workspaces. Not recommended for production data.
  • Best practice: Use DBFS root only for temp files, libraries, and init scripts. Store production data in external GCS locations managed by Unity Catalog.

External Locations (Unity Catalog)

  • Register GCS paths as external locations in Unity Catalog — provides governed access to cloud storage.
  • Requires a storage credential (GCP service account) and an external location mapping the credential to a GCS path.
  • Tables created at external locations are "external tables" — data lifecycle managed outside of Databricks.
Configure External Storage with Unity Catalog
-- Create storage credential (maps to GCP service account)
CREATE STORAGE CREDENTIAL gcs_data_lake_cred
WITH (
  GCP_SERVICE_ACCOUNT_KEY = '{"type":"service_account","project_id":"my-project",...}'
);

-- Create external location pointing to GCS bucket
CREATE EXTERNAL LOCATION prod_data_lake
URL 'gs://my-company-data-lake/prod/'
WITH (STORAGE CREDENTIAL gcs_data_lake_cred)
COMMENT 'Production data lake on GCS';

-- Create managed table (data stored in Unity Catalog managed location)
CREATE TABLE catalog.schema.customers (
  customer_id STRING,
  name STRING,
  email STRING
) USING DELTA;

-- Create external table (data at specific GCS path)
CREATE TABLE catalog.schema.raw_events (
  event_id STRING,
  payload STRING,
  received_at TIMESTAMP
) USING DELTA
LOCATION 'gs://my-company-data-lake/prod/raw/events/';
Pitfall: Avoid mounting GCS buckets with dbutils.fs.mount() in new projects. Mounts bypass Unity Catalog governance (no fine-grained access control, no lineage tracking, no audit logging). Legacy mounts should be migrated to external locations. Unity Catalog's external locations provide the same access patterns with full governance.

Job Orchestration

Multi-Task Workflows

  • Task types: Notebook, Python script, JAR, SQL, Delta Live Tables pipeline, dbt task, or another workflow (nested).
  • Dependencies: DAG-style task dependencies — define upstream/downstream relationships. Tasks run in parallel where dependencies allow.
  • Cluster allocation: Each task can use a shared job cluster or its own dedicated cluster. Shared clusters reduce startup overhead for dependent tasks.
  • Parameters: Pass parameters between tasks using task values (dbutils.jobs.taskValues.set/get).
Multi-Task Job Definition (Databricks Asset Bundle YAML)
# databricks.yml — Asset Bundle workflow definition
resources:
  jobs:
    daily_etl_pipeline:
      name: "Daily ETL Pipeline"
      schedule:
        quartz_cron_expression: "0 0 6 * * ?"
        timezone_id: "America/New_York"
      
      job_clusters:
        - job_cluster_key: "shared_etl_cluster"
          new_cluster:
            spark_version: "14.3.x-scala2.12"
            node_type_id: "n2-highmem-8"
            autoscale:
              min_workers: 2
              max_workers: 10
            gcp_attributes:
              availability: "PREEMPTIBLE_WITH_FALLBACK_GCP"

      tasks:
        - task_key: "ingest_raw"
          job_cluster_key: "shared_etl_cluster"
          notebook_task:
            notebook_path: "/Repos/prod/my-platform/notebooks/orchestration/ingest"
            base_parameters:
              env: "prod"
              date: "{{start_date}}"
          
        - task_key: "transform_silver"
          depends_on:
            - task_key: "ingest_raw"
          job_cluster_key: "shared_etl_cluster"
          python_wheel_task:
            package_name: "my_transforms"
            entry_point: "run_silver"
            parameters: ["--date", "{{start_date}}"]

        - task_key: "build_gold"
          depends_on:
            - task_key: "transform_silver"
          job_cluster_key: "shared_etl_cluster"
          notebook_task:
            notebook_path: "/Repos/prod/my-platform/notebooks/orchestration/gold"

        - task_key: "data_quality_check"
          depends_on:
            - task_key: "build_gold"
          job_cluster_key: "shared_etl_cluster"
          notebook_task:
            notebook_path: "/Repos/prod/my-platform/notebooks/orchestration/quality"

      email_notifications:
        on_failure:
          - "data-team@company.com"

Cost Management

DBU Pricing Model

  • DBU (Databricks Unit): Normalized unit of compute — 1 DBU ≈ 1 vCPU-hour of processing capacity.
  • Tiers: Standard, Premium, Enterprise — each with increasing features and per-DBU cost.
  • Total cost = DBU consumption × DBU rate + GCP infrastructure cost (GCE VMs, GCS storage, networking).
  • Key insight: ~40% of total Databricks cost is the DBU license; ~60% is underlying GCP infrastructure. Optimize both.

Delta Live Tables (DLT)

Delta Live Tables is a declarative ETL framework — you define WHAT data transformations should produce, and DLT handles the HOW (orchestration, error handling, monitoring, data quality):

Core Concepts

  • Pipeline: Collection of datasets (tables/views) and their transformations. Represents an end-to-end data flow.
  • Streaming tables: Incrementally process append-only data (new rows only). Uses Spark Structured Streaming under the hood.
  • Materialized views: Fully recomputed on each refresh. Used for aggregations or transformations that need the complete dataset.
  • Expectations: Declarative data quality constraints — drop, fail, or quarantine rows that violate quality rules.
  • Automatic dependency resolution: DLT figures out the execution order from dataset references. No explicit DAG definition needed.
DLT Pipeline — Medallion Architecture
import dlt
from pyspark.sql.functions import col, current_timestamp, expr

# --- Bronze: Raw ingestion (streaming) ---
@dlt.table(
    name="raw_events",
    comment="Raw event stream from Pub/Sub via GCS",
    table_properties={"quality": "bronze"}
)
@dlt.expect_or_drop("valid_event_id", "event_id IS NOT NULL")
def raw_events():
    return (
        spark.readStream
        .format("cloudFiles")  # Auto Loader
        .option("cloudFiles.format", "json")
        .option("cloudFiles.schemaLocation", "/mnt/checkpoints/raw_events_schema")
        .option("cloudFiles.inferColumnTypes", "true")
        .load("gs://raw-data-bucket/events/")
    )

# --- Silver: Cleansed & enriched (streaming) ---
@dlt.table(
    name="cleaned_events",
    comment="Validated and enriched events",
    table_properties={"quality": "silver"}
)
@dlt.expect_or_fail("valid_timestamp", "event_timestamp > '2020-01-01'")
@dlt.expect_or_drop("valid_user", "user_id IS NOT NULL AND user_id != ''")
@dlt.expect("has_event_type", "event_type IS NOT NULL")  # Warn only, don't drop
def cleaned_events():
    return (
        dlt.readStream("raw_events")
        .select(
            col("event_id"),
            col("user_id"),
            col("event_type"),
            col("event_timestamp").cast("timestamp"),
            col("properties"),
            expr("CASE WHEN country IS NULL THEN 'unknown' ELSE country END").alias("country"),
            current_timestamp().alias("processed_at")
        )
    )

# --- Gold: Business aggregates (materialized view) ---
@dlt.table(
    name="daily_active_users",
    comment="DAU metrics by country",
    table_properties={"quality": "gold"}
)
def daily_active_users():
    return (
        dlt.read("cleaned_events")
        .groupBy(
            col("event_timestamp").cast("date").alias("event_date"),
            "country"
        )
        .agg(
            expr("COUNT(DISTINCT user_id) AS dau"),
            expr("COUNT(*) AS total_events"),
            expr("COUNT(DISTINCT event_type) AS unique_event_types")
        )
    )
Key insight: DLT pipelines are idempotent by design — re-running a pipeline produces the same result regardless of partial failures. This is achieved through Delta's transactional guarantees and DLT's automatic checkpointing. For streaming tables, DLT maintains exactly-once processing across restarts using Spark checkpoints stored in the pipeline's storage location.

Interview Questions

Explain the difference between Databricks control plane and data plane. Why does this architecture matter for security?

Control plane (Databricks-managed): Hosts workspace UI, job scheduler, notebook state, API endpoints, Unity Catalog metadata. Runs in Databricks' own GCP project.

Data plane (customer-managed): All compute (GCE VMs), all data (GCS buckets), all network traffic. Runs entirely in the customer's GCP project and VPC.

Security implications: (1) Customer data NEVER leaves the customer's GCP project — even Databricks cannot access it. This satisfies data residency, HIPAA, and SOC2 requirements. (2) Network isolation: clusters in the data plane communicate with the control plane via a secure relay (Databricks SCC) — no inbound ports opened in customer VPC. (3) Credential isolation: service account keys and secrets exist only in the data plane — the control plane never sees them. (4) Compromise containment: if the control plane is breached, attackers get metadata (table names, job configs) but NOT actual data.

Practical impact: Security teams approve Databricks deployments faster because the risk model is clear — Databricks is a "management SaaS" that orchestrates but never touches data. Compare with fully-managed services where the vendor has direct data access.

When would you enable Photon, and when would you avoid it? How do you measure ROI?

Enable Photon when: (1) Workloads are dominated by SQL operations — aggregations, joins, filters, window functions. (2) Delta Lake MERGE/UPDATE operations on large tables. (3) String-heavy transformations (parsing, regex, concat). (4) SQL warehouses for BI workloads — Photon is default and consistently delivers 3–5x speedup.

Avoid Photon when: (1) Workloads heavily use Python UDFs or pandas_udfs — Photon cannot accelerate these. (2) ML training with MLlib or custom Python code — no benefit. (3) Small datasets (<1GB) — overhead outweighs gains. (4) Budget-constrained dev/test environments where absolute cost matters more than speed.

Measuring ROI: Run the same job with and without Photon. Calculate: (Photon time × Photon DBU rate) vs (Standard time × Standard DBU rate). If Photon costs less total despite higher per-minute rate, it's a win. Example: A job takes 60 min standard (60 DBUs) vs 20 min with Photon (40 DBUs at 2x rate). Standard: 60 × $0.40 = $24. Photon: 40 × $0.80 = $32. In this case, Photon is faster but more expensive. But if Photon reduces it to 15 min (30 DBUs × $0.80 = $24), it breaks even on cost while being 4x faster.

Design a cost-optimized Databricks deployment for a team of 15 data engineers running daily batch pipelines and ad-hoc analysis.

Production pipelines (70% of spend):

- Job clusters with Spot VMs (70% Spot, 30% on-demand fallback). Auto-scaling 2–20 workers based on data volume.

- Delta Live Tables for streaming ingestion — managed scaling, no cluster management overhead.

- Shared job cluster for tightly-coupled tasks within a workflow — avoids multiple cold starts.

Interactive development (20% of spend):

- Instance pool with 4 pre-warmed n2-standard-8 instances — instant cluster startup for developers.

- Cluster policy: max 8 workers, auto-terminate 45 min, mandatory Spot workers, enforced tags for cost attribution.

- Single-user clusters (not shared) — simpler permission model, better isolation.

SQL analytics (10% of spend):

- One serverless SQL warehouse for BI tools — auto-scales, no management, pay-per-query.

Governance: Tag all clusters with team/project. Use Databricks account-level cost dashboards. Set budget alerts at project level. Review over-provisioned clusters monthly (Ganglia metrics showing <40% CPU = right-size down).

Expected total savings vs naive deployment: 45–55% through Spot VMs + right-sizing + auto-termination + job clusters.

Explain Delta Live Tables vs traditional Spark Structured Streaming. When would you choose each?

Delta Live Tables (DLT) advantages: (1) Declarative — define datasets, not execution logic. DLT handles scheduling, retries, and dependency ordering. (2) Built-in data quality — expectations with drop/fail/warn semantics. No custom validation code. (3) Automatic lineage — tracks data flow across all tables in the pipeline. (4) Managed infrastructure — DLT sizes and manages its own clusters. (5) Operational monitoring — built-in event log, data quality metrics, pipeline health dashboard.

Traditional Structured Streaming advantages: (1) Full control over checkpoint management, trigger intervals, and output modes. (2) Supports complex stateful operations (flatMapGroupsWithState, arbitrary state) that DLT doesn't expose. (3) Can write to multiple sinks (Kafka, custom HTTP endpoints) — DLT only writes to Delta. (4) Easier unit testing — standard Spark code, no DLT framework dependency. (5) No DLT-specific cost premium (DLT has higher DBU pricing).

Choose DLT when: Building medallion-architecture pipelines with multiple tables and quality gates. Team prefers declarative over imperative. Operational simplicity is prioritized over flexibility.

Choose Structured Streaming when: Writing to non-Delta sinks, complex stateful processing, need fine-grained checkpoint control, or integrating into an existing Spark streaming codebase.
