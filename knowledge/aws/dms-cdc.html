DMS Architecture

AWS DMS consists of three components that work together for data migration and ongoing replication:

Replication Instance

  • EC2 instance running the DMS replication engine. Performs the actual data transfer.
  • Sizing: dms.r5.large (2 vCPU, 16GB) for small loads. dms.r5.4xlarge (16 vCPU, 128GB) for large-scale CDC with many tables.
  • Multi-AZ: Enable for production CDC — standby instance in another AZ for automatic failover. Adds ~50% cost but ensures replication continuity.
  • Storage: Local storage buffers CDC events during spikes. Size = max_spike_duration × change_rate. Default 50GB, increase for high-volume sources.

Source Endpoint

  • Connection configuration to the source database (hostname, port, credentials, SSL, extra connection attributes).
  • Supported sources: Oracle, SQL Server, MySQL, PostgreSQL, MongoDB, S3, SAP ASE, IBM Db2.
  • CDC-specific requirements per source (detailed in CDC Internals section).

Target Endpoint

  • Connection to the destination: RDS, Redshift, S3 (Parquet/CSV), Kafka, Kinesis, DynamoDB, Elasticsearch, Neptune.
  • Target-specific settings control output format, batching, and apply mode.

Replication Task

  • Defines WHAT to replicate: source endpoint → target endpoint, table mappings, transformation rules.
  • Task types: Full Load, CDC only, Full Load + CDC (recommended for initial migration).
Key insight: The replication instance is the bottleneck. All data flows through it — source → instance buffer → target. Under-sizing causes CDC lag. Over-sizing wastes money. Monitor CDCLatencySource and CDCLatencyTarget metrics to right-size.

Full Load vs CDC

Full Load

  • Reads entire table contents via SELECT statements. One-time bulk copy.
  • Parallel threads per table (configurable: MaxFullLoadSubTasks). Large tables split by segment (range-based).
  • Target table options: DROP and CREATE, TRUNCATE, DO_NOTHING (append).
  • Performance: 50-200 GB/hour depending on source/target throughput and instance size.

CDC (Change Data Capture)

  • Captures ongoing changes (INSERT, UPDATE, DELETE) from source transaction logs in near real-time.
  • Continuous process — runs indefinitely after full load completes.
  • Typical latency: 1-10 seconds (source commit → target apply), depending on change rate and network.
  • Changes are applied in transaction order to maintain referential integrity.

Full Load + CDC (Recommended Pattern)

  1. DMS starts CDC capture (begins reading transaction log from current position).
  2. Full load executes — copies existing data to target.
  3. After full load completes, CDC applies all changes that accumulated during the full load.
  4. Target reaches consistency — full historical data + all changes since task start.
  5. CDC continues running — ongoing replication.

CDC Internals — Log-Based Capture

MySQL — Binary Log (Binlog)

  • Required settings: binlog_format = ROW (not STATEMENT or MIXED), binlog_row_image = FULL, log_bin = ON.
  • How DMS reads: Connects as a MySQL replication slave. Reads binlog events via the replication protocol. Each event contains before/after row images.
  • Retention: Binlogs must be retained long enough for DMS to read. Set expire_logs_days = 3 minimum (RDS: binlog retention hours parameter).
  • Performance impact on source: Minimal — DMS reads binlog files from disk/archive, doesn't add query load to the active database.

PostgreSQL — Write-Ahead Log (WAL)

  • Required settings: wal_level = logical, max_replication_slots ≥ 1 (per DMS task), max_wal_senders ≥ 1.
  • Logical decoding: DMS uses a replication slot with the test_decoding or pgoutput plugin to receive decoded WAL changes.
  • Critical issue — WAL retention: A replication slot HOLDS WAL segments until consumed. If DMS stops/pauses, WAL accumulates on the source → disk fills → source database crashes. Always monitor pg_replication_slots and set max_slot_wal_keep_size as a safety limit (PostgreSQL 13+).
  • RDS-specific: Use rds.logical_replication = 1 parameter. Requires reboot to activate.

Oracle — LogMiner / Binary Reader

  • LogMiner mode (default): DMS uses Oracle's LogMiner API to parse redo/archive logs. Runs SQL against the source (some CPU overhead). Easier setup.
  • Binary Reader mode (recommended for production): DMS reads redo logs directly at the binary level. Lower source impact, higher throughput. Requires: SUPPLEMENTAL LOGGING at table/database level.
  • Required: ALTER DATABASE ADD SUPPLEMENTAL LOG DATA, archive log mode enabled, redo log retention sufficient for DMS to keep up.
PostgreSQL CDC Setup for DMS
-- On source PostgreSQL (RDS parameter group or postgresql.conf)
-- rds.logical_replication = 1 (requires reboot)

-- Verify settings
SHOW wal_level;           -- Must be 'logical'
SHOW max_replication_slots; -- Must be >= number of DMS tasks

-- DMS automatically creates a replication slot named: 
-- dms_replication_slot_{task_id}

-- Monitor slot lag (CRITICAL — prevents WAL bloat)
SELECT slot_name, 
       pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn) AS lag_bytes,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS lag_readable,
       active
FROM pg_replication_slots;

-- If lag_bytes grows continuously and active=false → DMS is stuck
-- DROP the slot manually to release WAL:
-- SELECT pg_drop_replication_slot('dms_replication_slot_xyz');
Critical production risk: A stalled DMS task on PostgreSQL will hold WAL indefinitely. A 500GB/day change rate with a 2-day outage = 1TB of unreclaimed WAL disk space. Set CloudWatch alarms on OldestReplicationSlotLag (RDS metric) and CDCLatencySource (DMS metric). Automate slot cleanup if lag exceeds threshold.

Key Settings Explained

  • BatchApplyEnabled: Groups multiple changes into batch SQL statements (INSERT INTO ... VALUES (...), (...), ...). 5-10x throughput improvement for high-volume CDC.
  • ParallelLoadThreads: Number of threads per table during full load. Increase for large tables (8-16).
  • LOB handling: Full LOB mode reads LOBs inline (slow for large BLOBs). Limited LOB mode truncates at size limit (fast but may lose data). Set LobMaxSize based on your actual LOB sizes.

S3 as Target

DMS can write directly to S3 in Parquet or CSV format — building a data lake from database CDC:

S3 Target Endpoint Configuration
{
  "S3Settings": {
    "BucketName": "datalake-raw",
    "BucketFolder": "cdc/production",
    "CompressionType": "gzip",
    "DataFormat": "parquet",
    "ParquetVersion": "parquet-2-0",
    "EnableStatistics": true,
    "ParquetTimestampInMillisecond": true,
    "TimestampColumnName": "_dms_ingestion_timestamp",
    "IncludeOpForFullLoad": true,
    "CdcInsertsAndUpdates": true,
    "CdcPath": "cdc_changes",
    "DatePartitionEnabled": true,
    "DatePartitionSequence": "YYYYMMDD",
    "DatePartitionDelimiter": "SLASH",
    "AddColumnName": true,
    "CannedAclForObjects": "bucket-owner-full-control",
    "MaxFileSize": 131072
  }
}

S3 Output Structure

  • Full load files: s3://bucket/folder/schema/table/LOAD00001.parquet
  • CDC files: s3://bucket/folder/schema/table/cdc_changes/20240115/20240115-143052-changes.parquet
  • CDC records include: Op column (I=insert, U=update, D=delete), all column values (before/after for updates depending on config).
  • File size: Controlled by MaxFileSize (KB). Smaller = more files but lower latency to S3. Larger = fewer files but higher latency.
Production pattern: DMS CDC → S3 Parquet (raw) → Spark/Glue job applies CDC operations (MERGE) into an Iceberg/Delta table (curated). This two-stage approach decouples ingestion from transformation, making it easier to reprocess and debug.

DMS + MSK — Streaming CDC to Kafka

  • DMS can publish CDC events directly to Kafka (MSK) topics — each table maps to a topic.
  • Message format: JSON with before/after images + metadata (operation type, timestamp, transaction ID).
  • Partitioning: Messages keyed by primary key — ensures ordering per entity across partitions.
  • Topic mapping: Default = one topic per table. Custom topic naming via transformation rules.
  • Use case: Real-time event streaming from OLTP databases to consumers (dashboards, materialized views, event-driven microservices).

DMS vs Debezium critical difference: DMS is a managed black box — limited configurability, occasional bugs with specific source/target combinations, AWS-only targets. Debezium gives full control (custom serialization, transforms, dead letter queues) but requires managing Kafka Connect infrastructure. For Kafka-first architectures, Debezium is almost always the better choice. For simple "database → S3 lake" pipelines, DMS wins on operational simplicity.

Error Handling & Monitoring

Error Handling Modes

  • Suspend table: On error, suspend replication for the affected table. Other tables continue. Check and resume manually.
  • Stop task: Any error stops the entire task. Conservative but safe — no silent data loss.
  • Log and continue: Log the error to a control table, skip the record, continue. Risk: data gaps. Use for non-critical data only.

Key Monitoring Metrics

  • CDCLatencySource: Seconds between source commit and DMS reading the change. High = DMS can't keep up with source log production.
  • CDCLatencyTarget: Seconds between DMS reading change and applying to target. High = target is slow (capacity, locks, network).
  • CDCIncomingChanges: Number of changes pending in DMS buffer. Growing = falling behind. Should stay near zero for healthy replication.
  • FreeStorageSpace: Replication instance storage. If CDC buffer fills up, task fails. Alarm at <20%.

Data Validation

  • DMS built-in validation compares source and target row counts and row-level checksums.
  • Enable: Set "EnableValidation": true in task settings.
  • How it works: Periodically queries both source and target, compares hash of primary key + data columns.
  • Reporting: Validation state per table in awsdms_validation_failures_v1 control table. States: Validated, Mismatched, Error, Pending.
  • Limitation: Validation adds read load to both source and target. Schedule during low-traffic periods for large tables.

Limitations & Workarounds

  • DDL changes: DMS handles basic DDL (ADD COLUMN) but may fail on complex DDL (ALTER TYPE, RENAME COLUMN, DROP TABLE). Workaround: stop task, apply DDL to target manually, restart task.
  • Large transactions: Transactions with millions of rows can overflow DMS buffer memory. Workaround: increase instance size or set MemoryLimitTotal higher.
  • LOB columns: Full LOB mode is extremely slow (one-row-at-a-time for LOB fetch). Workaround: use Limited LOB mode with generous LobMaxSize, or replicate LOB columns separately.
  • Partitioned tables (Oracle): Partition DDL operations (SPLIT, MERGE, EXCHANGE) may not replicate correctly. Workaround: replicate at the partition level or handle post-migration.
  • No multi-master: DMS is one-directional. No bidirectional/active-active replication. For that, use Oracle GoldenGate or custom conflict resolution.
  • Schema drift: If source schema changes during CDC, DMS may stop or produce corrupted records. Workaround: use schema change notifications + automated task restart/configuration update.

Interview Questions

Design a CDC pipeline from a production PostgreSQL database to a data lake with near-real-time freshness.

Architecture: PostgreSQL → DMS CDC → S3 (raw Parquet) → Spark/Glue MERGE → Iceberg table (curated).

Step 1 — Source preparation: Set wal_level=logical, configure replication slot limits, ensure sufficient WAL retention. Set up monitoring on pg_replication_slots lag.

Step 2 — DMS configuration: Full Load + CDC task with Parquet output to S3. Date-partitioned paths for CDC files. MaxFileSize=128MB for optimal downstream processing. Enable IncludeOpForFullLoad and TimestampColumnName for lineage.

Step 3 — Apply layer: Scheduled Spark/Glue job (every 5-15 minutes) reads new CDC files from S3, applies operations (I/U/D) as MERGE INTO the Iceberg target table. Use Iceberg's MERGE for efficient upserts. Handle deletes via soft-delete column or physical delete.

Step 4 — Freshness SLA: DMS latency ~5s + S3 file flush interval (configurable) + apply job frequency. Achievable: 5-20 minute end-to-end latency. For sub-minute: replace S3 with Kafka target + Spark Structured Streaming consumer.

Step 5 — Monitoring: CDCLatencySource alarm >30s, CDCIncomingChanges alarm >10000, WAL slot lag alarm >1GB. Data quality checks on apply: validate row counts, detect schema drift via column count comparison.

Your DMS CDC task is falling behind — CDCLatencySource is growing at 100ms/sec. Diagnose and fix.

Growing latency means: DMS is reading changes slower than the source produces them. It will eventually exhaust replication instance storage and fail.

Diagnosis 1 — Source log throughput: Check source change rate (binlog bytes/sec for MySQL, WAL bytes/sec for PG). If change rate spiked (batch job, migration), wait for spike to end.

Diagnosis 2 — Instance under-sized: Check DMS instance CPU and memory. If CPU >80% → upgrade instance type. If memory pressure (swap usage) → upgrade or reduce parallel load threads.

Diagnosis 3 — Target bottleneck: Check CDCLatencyTarget. If target apply is slow (target DB locks, S3 throttling), changes back up in DMS buffer, slowing source reads. Fix target performance (add indexes on target, increase S3 max connections, use batch apply mode).

Diagnosis 4 — LOB mode: Full LOB mode processes one row at a time (sequential). If tables have LOB columns, switch to Limited LOB mode with appropriate size limit.

Diagnosis 5 — Table with no PK: Tables without primary keys use full-row comparison for updates — extremely slow. Add a PK or unique index to the source table.

Immediate remediation: (1) Scale up replication instance. (2) Enable BatchApplyEnabled=true if not already. (3) If specific tables are bottlenecks, split into separate tasks for parallel processing.

Compare DMS CDC to Debezium for a Kafka-centric streaming architecture. When would you choose each?

Choose DMS when: (1) Target is S3/Redshift/DynamoDB (native AWS integration). (2) Team doesn't run Kafka or Kafka Connect infrastructure. (3) Simple one-way replication without complex transformation. (4) Migration project with a defined end date (not permanent CDC). (5) Operational simplicity is priority — fully managed, no patching.

Choose Debezium when: (1) Kafka is your event backbone — you want CDC events as first-class Kafka messages with proper keys, schemas, and tombstones. (2) Need DDL change capture (table creates, alters published as events). (3) Need snapshot + streaming with exactly-once semantics (Kafka transactions). (4) Require custom transforms (masking PII, enriching events, routing). (5) Multiple consumers need CDC events (Debezium publishes once, N consumers read). (6) Need outbox pattern integration (poll-based outbox tables). (7) Long-term CDC architecture (not a one-time migration).

Architecture insight: For a permanent streaming data platform, Debezium is superior because CDC events become part of your event-driven architecture. DMS is a "pipe" — it moves data but doesn't make it an event. Debezium makes every database change a proper event with schema, key, and metadata that downstream systems can independently consume.

How do you handle schema evolution in a DMS CDC pipeline without data loss?

Challenge: When source schema changes (ADD COLUMN, ALTER TYPE), DMS may stop, skip records, or produce mismatched data.

Strategy 1 — Additive-only changes: ADD COLUMN is generally safe — DMS detects new columns and adds them to output. Configure "HandleSourceTableDDL": true. New records have the column; old records have NULL.

Strategy 2 — Breaking changes (ALTER TYPE, DROP COLUMN): (a) Stop DMS task at a known checkpoint. (b) Apply DDL to target (match source schema). (c) Restart DMS task — it resumes from checkpoint. (d) For S3 targets: new files will have new schema. Downstream readers must handle schema evolution (Iceberg/Delta handle this natively).

Strategy 3 — Schema-flexible target: Write CDC to S3 as JSON (schema-less). Downstream Spark job handles schema resolution — reads JSON with evolving schemas, applies to a Delta/Iceberg table with schema evolution enabled (mergeSchema=true). DMS never stops regardless of source DDL.

Strategy 4 — Event notification: Monitor DMS task events for TABLE_ERROR or SCHEMA_CHANGE events via EventBridge. Trigger a Lambda that: pauses downstream consumers, evaluates the change, updates target schema, resumes task.
