Glue Architecture — Spark Under the Hood

AWS Glue is a fully managed Apache Spark environment with a proprietary orchestration layer. Understanding the internals is critical for optimization:

DPU (Data Processing Unit)

  • Definition: 1 DPU = 4 vCPUs + 16 GB RAM. This is the billing unit.
  • Standard worker: G.1X = 1 DPU per worker (4 vCPU, 16 GB). G.2X = 2 DPU per worker (8 vCPU, 32 GB). G.4X = 4 DPU per worker (16 vCPU, 64 GB — for memory-heavy transforms). G.8X = 8 DPU per worker (32 vCPU, 128 GB).
  • Cost model: Billed per DPU-hour with 1-minute minimum, rounded to nearest second. Pricing: ~$0.44/DPU-hour.
  • Driver overhead: 1 DPU is always allocated to the Spark driver. A 10-DPU job = 1 driver + 9 executor workers.

Execution Environment

  • Spark runs in isolated Docker containers on AWS-managed infrastructure.
  • Each job gets a fresh Spark cluster — no shared state between job runs.
  • Glue 4.0 runs Spark 3.3.0 with optimized AWS connectors.
  • Supports Python (PySpark) and Scala (Spark Scala). No Java directly — use JARs as dependencies.
  • Warm pools: Glue reuses pre-warmed containers for frequently-run jobs — startup drops from ~45s to ~10s.
Key insight: Glue is literally Spark with managed infrastructure + Glue-specific libraries (DynamicFrame, crawlers, bookmarks). Any Spark optimization technique applies directly to Glue. Think of it as "managed EMR for ETL" with a higher per-DPU cost but zero operational overhead.

Glue ETL vs Glue Studio vs Glue Streaming

Glue ETL (Script-Based)

  • Write PySpark/Scala scripts with Glue libraries.
  • Full Spark API access + Glue DynamicFrame API.
  • Best for: complex transformations, custom logic, experienced Spark developers.

Glue Studio (Visual)

  • Drag-and-drop DAG builder — generates PySpark code behind the scenes.
  • Built-in transforms: ApplyMapping, Filter, Join, SQL, custom code nodes.
  • Best for: simple ETL flows, less experienced teams, rapid prototyping.
  • Limitation: Generated code can be suboptimal — complex logic still needs script mode.

Glue Streaming

  • Micro-batch processing using Spark Structured Streaming.
  • Sources: Kinesis Data Streams, MSK (Kafka).
  • Sinks: S3, JDBC, Kinesis, custom.
  • Window interval: Configurable — 100 seconds default. Minimum effective is ~10s.
  • Uses Glue bookmarks equivalent (checkpointing) for exactly-once semantics.
  • DPUs run continuously — cost = DPUs × hours running (not per-trigger).

DynamicFrame vs DataFrame

DynamicFrame — Glue's Extension

  • Schema flexibility: DynamicFrame handles schema inconsistencies per-record. A column can be int in some rows and string in others — it creates a choice type instead of failing.
  • ResolveChoice: Explicit resolution — cast to target type, make_struct (keep both), or project:type (pick one).
  • Relationalize: Flattens nested JSON/structs into relational tables automatically — critical for loading semi-structured data into Redshift/RDS.
  • Built-in transforms: ApplyMapping (column rename + type cast), Filter, Join, DropNullFields, SelectFields.

When to Use Each

  • DynamicFrame: Reading messy data (inconsistent schemas, nested JSON), simple column-level transforms, loading to JDBC sinks (built-in parallelism and retry).
  • DataFrame: Complex transformations (window functions, UDFs, pivot), aggregations, joins with complex conditions, Spark SQL, performance-critical paths.
  • Conversion: df = dyf.toDF() and dyf = DynamicFrame.fromDF(df, glueContext, "name") — zero-cost conversion, same underlying RDD.
DynamicFrame Pattern — Schema Resolution
from awsglue.context import GlueContext
from awsglue.dynamicframe import DynamicFrame

glueContext = GlueContext(SparkContext.getOrCreate())

# Read from Catalog
dyf = glueContext.create_dynamic_frame.from_catalog(
    database="raw_db",
    table_name="events",
    push_down_predicate="year='2024' and month='01'",
    additional_options={"useS3ListImplementation": True}
)

# Handle schema inconsistencies
# 'user_id' column is sometimes int, sometimes string
dyf_resolved = dyf.resolveChoice(
    specs=[
        ("user_id", "cast:long"),
        ("amount", "cast:double"),
        ("metadata", "make_struct")  # keep nested structure
    ]
)

# Flatten nested JSON
dyf_flat = dyf_resolved.relationalize("events_flat", "s3://temp-bucket/relationalize/")

# Convert to DataFrame for complex logic
df = dyf_flat.toDF()
df_transformed = df.withColumn("event_date", F.to_date("timestamp")) \
                   .filter(F.col("amount") > 0)

# Back to DynamicFrame for Catalog-aware write
dyf_output = DynamicFrame.fromDF(df_transformed, glueContext, "output")
glueContext.write_dynamic_frame.from_catalog(
    frame=dyf_output,
    database="curated_db",
    table_name="events_clean"
)

Glue Crawlers — Schema Detection

How Crawlers Work

  1. List files: Enumerate all files in the target S3 path (or JDBC tables).
  2. Sample: Read a subset of files (not all!) to infer schema. Sampling is based on file size and count.
  3. Classify: Determine format (Parquet, JSON, CSV, etc.) using built-in classifiers or custom classifiers.
  4. Group: Group files into tables based on path structure and schema similarity.
  5. Schema merge: Merge schemas across sampled files — union of all columns found.
  6. Update catalog: Create/update table definitions in Glue Data Catalog.

When to Avoid Crawlers

  • Known schema: If you control the producer, define tables manually via Glue API/Terraform/CloudFormation. Faster, deterministic, no surprises.
  • Partitioned data: Crawlers re-scan ALL partitions to find new ones. For tables with 100K+ partitions, use MSCK REPAIR TABLE or batch_create_partition API instead.
  • Schema evolution: Crawlers may incorrectly merge schemas or change column types. Use explicit schema management with Delta/Iceberg.
  • Cost: Crawlers consume DPU time. A crawler on a million-file S3 prefix costs real money and takes 30+ minutes.
Pitfall: Crawlers can change a column type from bigint to string if they sample a file with a string value in that column. This silently breaks downstream queries. Always set SchemaChangePolicy.UpdateBehavior = LOG in production and review changes before applying.

Glue Data Catalog

The Data Catalog is a Hive Metastore-compatible metadata repository that serves as the single source of truth for schema definitions across AWS analytics services.

Integration Points

  • Athena: Uses Catalog directly — query any Catalog table via SQL.
  • EMR: Set hive.metastore.client.factory.class = com.amazonaws.glue.catalog.metastore.AWSGlueDataCatalogHiveClientFactory.
  • Redshift Spectrum: External schemas point to Catalog databases.
  • Lake Formation: Layered on top of Catalog for fine-grained access control.
  • Glue ETL: Native read/write via create_dynamic_frame.from_catalog().

Catalog Limits and Patterns

  • Partition limit: 10 million partitions per table (hard limit). Design partition schemes accordingly.
  • Batch operations: batch_create_partition adds up to 100 partitions per call — use for ETL jobs that know exactly which partitions they create.
  • Partition indexes: Create indexes on frequently-filtered partition keys for faster pruning in Athena. Up to 3 indexes per table.
Programmatic Partition Registration
import boto3

glue_client = boto3.client('glue')

# Register new partitions after ETL write
partitions_to_add = [
    {
        'Values': ['2024', '01', '15'],
        'StorageDescriptor': {
            'Location': 's3://datalake/events/year=2024/month=01/day=15/',
            'InputFormat': 'org.apache.hadoop.hive.ql.io.parquet.MapredParquetInputFormat',
            'OutputFormat': 'org.apache.hadoop.hive.ql.io.parquet.MapredParquetOutputFormat',
            'SerdeInfo': {
                'SerializationLibrary': 'org.apache.hadoop.hive.ql.io.parquet.serde.ParquetHiveSerDe'
            },
            'Columns': [
                {'Name': 'event_id', 'Type': 'string'},
                {'Name': 'user_id', 'Type': 'bigint'},
                {'Name': 'amount', 'Type': 'double'},
                {'Name': 'timestamp', 'Type': 'timestamp'}
            ]
        }
    }
]

glue_client.batch_create_partition(
    DatabaseName='analytics_db',
    TableName='events',
    PartitionInputList=partitions_to_add
)

Bookmarks — Incremental Processing

Glue bookmarks track which data has been processed in previous job runs, enabling incremental ETL without re-processing the entire dataset.

How Bookmarks Work

  • S3 sources: Tracks processed files by modification timestamp. On next run, only reads files modified after the last bookmark.
  • JDBC sources: Tracks a monotonically increasing column (e.g., id, updated_at). Stores the max value seen and filters on next run.
  • State storage: Bookmark state lives in the Glue service (not S3 or DynamoDB). Accessible via ResetJobBookmark API.

Bookmark Gotchas

  • Late-arriving files: If files are written with old timestamps (e.g., backfill to old partitions), bookmarks may skip them since they appear "already processed" by timestamp.
  • Job failures: Bookmarks only advance on job SUCCESS. Failed runs don't update — ensures retry processes the same data.
  • Pause state: Set job-bookmark-option: job-bookmark-pause for one-time full reprocessing without resetting the bookmark.
Bookmark-Enabled Incremental Read
# Enable bookmarks in job parameters: --job-bookmark-option job-bookmark-enable

dyf = glueContext.create_dynamic_frame.from_catalog(
    database="raw_db",
    table_name="clickstream",
    transformation_ctx="clickstream_source"  # REQUIRED for bookmarks
)

# transformation_ctx is the key — it uniquely identifies this
# read operation for bookmark tracking. Without it, bookmarks
# won't work even if enabled at the job level.

# Process only new data
df = dyf.toDF()
df_transformed = df.filter(F.col("event_type").isNotNull()) \
                   .withColumn("processed_at", F.current_timestamp())

# Write (also needs transformation_ctx for write bookmarks)
glueContext.write_dynamic_frame.from_catalog(
    frame=DynamicFrame.fromDF(df_transformed, glueContext, "output"),
    database="curated_db",
    table_name="clickstream_clean",
    transformation_ctx="clickstream_sink"
)

Pushdown Predicates

Pushdown predicates filter data at the Catalog level BEFORE Spark reads files — reducing I/O dramatically for partitioned tables.

Pushdown Predicate vs push_down_predicate
# PARTITION-LEVEL pushdown (Catalog filter — most impactful)
# Only reads partitions matching the predicate
dyf = glueContext.create_dynamic_frame.from_catalog(
    database="analytics",
    table_name="events",
    push_down_predicate="year='2024' and month='01'"
)

# FILE-LEVEL pushdown (S3 Select / columnar predicate)
# Filters within files (Parquet row-group stats)
dyf = glueContext.create_dynamic_frame.from_catalog(
    database="analytics",
    table_name="events",
    push_down_predicate="year='2024'",
    additional_options={
        "pushDownPredicate": "(amount > 100)"  # file-level filter
    }
)

# Both reduce DPU-hours and cost significantly
# Rule of thumb: partition pushdown = 10-100x reduction
# File-level pushdown = 2-5x reduction on top

Job Metrics & CloudWatch

  • Enable metrics: Set --enable-metrics in job parameters. Adds ~1% overhead but provides critical visibility.
  • Key metrics: glue.driver.aggregate.bytesRead, glue.driver.aggregate.shuffleBytesWritten, glue.ALL.system.cpuSystemLoad, glue.driver.aggregate.elapsedTime.
  • Executor memory: glue.ALL.jvm.heap.used — watch for >80% sustained (risk of OOM).
  • Shuffle detection: High shuffleBytesWritten relative to bytesRead indicates join/aggregation heavy workload — consider broadcast joins or pre-partitioning.

Glue 4.0 Improvements

  • Spark 3.3.0: Adaptive Query Execution (AQE) enabled by default — auto-coalesce, skew handling, join strategy switching at runtime.
  • Faster start: Job startup reduced from ~90s to ~30s with optimized container warm pools.
  • Python 3.10: Latest Python with type hints and performance improvements.
  • Apache Arrow: Optimized PySpark ↔ Pandas conversion via Arrow columnar format.
  • Auto-scaling: Workers can scale down mid-job based on actual workload (not just time-based). Reduces cost for jobs with uneven phases.
  • Iceberg/Hudi/Delta: Native integration with lakehouse table formats — read/write without custom JARs.

Glue Data Quality

Built-in data quality rules engine (based on Deequ) that evaluates data against defined expectations:

Data Quality Ruleset (DQDL Syntax)
Rules = [
    Completeness "email" > 0.95,
    Uniqueness "order_id" = 1.0,
    ColumnValues "amount" between 0 and 1000000,
    ColumnLength "phone" between 10 and 15,
    CustomSql "select count(*) from primary where amount < 0" = 0,
    RowCount > 1000,
    IsComplete "user_id",
    ColumnValues "status" in ["active", "inactive", "pending"],
    ReferentialIntegrity "customer_id" "reference_db.customers.id" > 0.99
]
  • Integration: Runs as a step within Glue ETL jobs or standalone evaluation tasks.
  • Actions on failure: Route failing records to quarantine S3 path, halt the pipeline, or alert via SNS.
  • Recommendations: Auto-generates rules by profiling existing data — baseline from which to set thresholds.

Cost Optimization

Right-Sizing DPUs

  • Start small: Begin with 2 DPU (G.1X) and monitor metrics. Scale up only when CPU utilization is consistently >80% or memory >75%.
  • Auto-scaling: Enable Glue auto-scaling (Glue 3.0+) — let the service manage DPU count. Set max DPU as cost guardrail.
  • Worker type matching: Use G.1X (16GB) for I/O-bound jobs (read/transform/write). Use G.2X (32GB) for memory-intensive (large joins, caching). Use G.4X/G.8X only for truly massive aggregations.

Flex Execution

  • Non-urgent jobs run on spare Glue capacity at reduced cost (compared to standard).
  • No SLA on start time — jobs may queue for minutes during peak hours.
  • Same DPU pricing once running — the discount is in avoiding capacity reservation.
  • Best for: Nightly batch jobs with wide execution windows, backfills, non-time-critical reprocessing.

Other Cost Strategies

  • Partition pushdown: Reduces DPU-hours by scanning less data.
  • Columnar formats: Parquet/ORC → read only needed columns → less I/O → faster job → fewer DPU-hours.
  • Timeout: Set --job-timeout to kill runaway jobs (default: 48 hours — dangerously high).
  • Consolidate small jobs: Each Glue job has 1 DPU minimum + startup overhead. Combine multiple tiny transformations into one job.
Cost formula: Total cost = DPUs × runtime (hours) × $0.44. A 10-DPU job running 30 min = 10 × 0.5 × $0.44 = $2.20. Reducing from 10 to 5 DPUs (by optimizing transforms) saves 50% — often possible by simply adding partition pushdown or fixing broadcast join thresholds.

Interview Questions

Your Glue job processes 500GB daily but takes 3 hours with 20 DPUs. How would you optimize it?

Step 1 — Enable metrics and profile: Check cpuSystemLoad, jvm.heap.used, and shuffleBytesWritten. If CPU is <30% with high shuffle, the job is I/O bound on shuffle — not compute bound.

Step 2 — Reduce input data scanned: Add partition pushdown predicates. If reading full partitions when only recent data changed, enable bookmarks for incremental processing. This alone can reduce runtime from 3h to 30min.

Step 3 — Optimize transforms: (a) Replace wide shuffles with broadcast joins where one side is <200MB. (b) Use columnar format (Parquet) if input is CSV/JSON. (c) Add coalesce before write to avoid thousands of small output files. (d) Cache DataFrames used multiple times.

Step 4 — Right-size workers: If memory is under-utilized on G.2X, switch to G.1X (half the cost). If CPU-bound, try fewer but larger workers to reduce shuffle overhead.

Step 5 — Enable auto-scaling: Let Glue scale down during light phases (e.g., after the heavy join phase, during simple write). This trims 20-30% of DPU-hours for uneven workloads.

When would you choose Glue over EMR, and vice versa?

Choose Glue when: (1) Team doesn't have Hadoop/Spark operational expertise. (2) Jobs are ETL-focused (read → transform → write) without complex iterative algorithms. (3) You want managed schema management (Data Catalog integration). (4) Job count is high but each job is small-medium (avoid managing dozens of EMR clusters). (5) You value development speed over per-job cost efficiency.

Choose EMR when: (1) Workload needs fine-grained Spark tuning (custom JVM flags, off-heap memory, specific Spark versions). (2) Cost sensitivity at scale — EMR is 30-50% cheaper per vCPU-hour than Glue DPUs. (3) Need full Hadoop ecosystem (HBase, Presto, Hive LLAP). (4) Long-running/streaming jobs where Glue's per-DPU-hour pricing becomes expensive. (5) GPU workloads for ML training. (6) Existing Spark code that uses features Glue doesn't support.

Hybrid pattern: Use Glue for orchestration-heavy ETL (dozens of small catalog-aware jobs) and EMR for heavy compute (large aggregations, ML feature engineering). Both can share the Glue Data Catalog as a common metastore.

Explain how Glue bookmarks work and their failure modes.

Mechanism for S3: Bookmarks store the modification timestamp of the last processed file. On the next run, Glue filters the S3 listing to only include files with modification timestamps newer than the bookmark. This is why transformation_ctx is required — it acts as the key for bookmark state storage.

Mechanism for JDBC: Stores the maximum value of a designated bookmark key column (must be sequential — auto-increment ID or timestamp). Generates a WHERE clause: WHERE bookmark_key > last_max_value.

Failure mode 1 — Late-arriving files: If a file is written to an old partition with a past modification timestamp (common in backfills), the bookmark has already advanced past that timestamp. The file is never processed. Fix: use job-bookmark-pause for backfill runs, or design pipelines where new files always have current timestamps.

Failure mode 2 — File overwrites: If a file is overwritten in-place (same path, new content), the bookmark may or may not pick it up depending on whether the modification timestamp changes. This is unpredictable on S3 (eventual metadata propagation). Fix: always write new files, never overwrite.

Failure mode 3 — Multiple sources: Each transformation_ctx tracks independently. If you add a new source mid-pipeline without bookmark state, it processes ALL historical data on first run.

How does Glue Data Quality compare to Great Expectations or custom validation? When would you use each?

Glue Data Quality (GDQ): Native integration with Glue ETL — zero additional infrastructure. DQDL syntax is simpler than GE's JSON expectation suites. Auto-recommendation engine profiles data to suggest rules. Built-in CloudWatch metrics for quality scores. Limitation: tied to Glue ecosystem, less extensible than GE, fewer rule types.

Great Expectations (GE): Framework-agnostic (works with Spark, Pandas, SQLAlchemy). 300+ built-in expectations. Rich documentation and data docs (HTML reports). Custom expectations in Python. Limitation: requires infrastructure management (store backends, docs hosting, CI/CD integration).

Decision: Use GDQ when your pipeline is fully Glue-based and rules are standard (completeness, ranges, referential integrity). Use GE when you need cross-platform validation (same rules across Spark and Pandas), custom business logic expectations, or rich HTML documentation for stakeholders. Use both in combination: GDQ as inline gates within Glue jobs, GE as comprehensive data contracts at domain boundaries.
