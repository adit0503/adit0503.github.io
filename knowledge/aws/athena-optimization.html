Athena Architecture — Serverless Trino

Athena is a serverless, distributed SQL query engine built on Trino (formerly PrestoSQL). Understanding the architecture explains both its strengths and limitations:

Query Execution Flow

  1. Query submission: SQL arrives at Athena's API endpoint.
  2. Catalog lookup: Athena reads table metadata from Glue Data Catalog — schema, partition locations, SerDe, file format.
  3. Query planning: Trino coordinator generates a distributed execution plan — splits based on S3 file locations.
  4. Worker allocation: Serverless workers are assigned from a shared pool (no cold-start for most queries).
  5. S3 scan: Workers read data directly from S3. This is where cost is incurred — bytes scanned.
  6. In-memory processing: All joins, aggregations, filters happen in memory across distributed workers.
  7. Result return: Output written to S3 results location and returned to client.

Athena Engine Versions

  • Athena v2: Based on Presto 0.217. Legacy — limited window functions, no ACID.
  • Athena v3: Based on Trino with continuous updates. Supports Iceberg, ACID, federated queries, EXPLAIN ANALYZE, improved performance (auto-optimization of joins and aggregations).
Key insight: Athena has no persistent storage or compute — it's purely a query engine. Your data lives in S3, metadata in Glue Catalog. Athena's cost and performance are entirely determined by how efficiently it can read from S3. Every optimization technique targets reducing bytes scanned.

Pay-Per-Query Pricing Model

  • Price: $5.00 per TB of data scanned (US regions). Minimum charge: 10 MB per query.
  • What counts as "scanned": Total uncompressed bytes read from S3 data files. Metadata (partition listing, Glue catalog calls) is free.
  • What reduces scan: Partition pruning (skip entire directories), columnar format (read only needed columns), compression (less data on disk = less scanned), file-level stats (skip row groups via min/max).
  • DDL is free: CREATE TABLE, ALTER TABLE, SHOW commands, MSCK REPAIR cost $0.
  • Failed queries: Charged only for data scanned before failure.
  • Cancelled queries: Charged for data scanned up to cancellation point.
Cost Impact Example
-- Table: 10 TB raw data in CSV (unpartitioned, uncompressed)
-- Full scan query:
SELECT * FROM events WHERE event_date = '2024-01-15';
-- Cost: 10 TB × $5/TB = $50 per query!

-- Same table converted to Parquet + partitioned by date:
-- Partition pruning: scans only 1 day = ~33 GB
-- Columnar (select 5 of 100 columns): 33 GB × 5% = 1.65 GB
-- Snappy compression: 1.65 GB × 0.3 = ~500 MB scanned
-- Cost: 0.5 GB × $5/1024 = $0.0024 per query

-- Savings: $50 → $0.002 = 99.99% reduction

Partition Pruning

Partitioning physically separates data into S3 directories. Athena reads partition information from the Glue Catalog and skips entire directories that don't match the WHERE clause.

Effective Partition Design

  • Partition by query pattern: If 90% of queries filter by date, partition by year/month/day.
  • Avoid over-partitioning: Each partition should contain >100MB of data. 1 million partitions with 1MB each = terrible performance (too many S3 LIST operations).
  • Hive-style partitioning: s3://bucket/table/year=2024/month=01/day=15/ — Athena auto-detects key=value format.
  • Partition projection: For predictable partition patterns (contiguous dates), define the pattern in table properties. Athena calculates partition locations mathematically — no catalog lookup needed. Eliminates MSCK REPAIR TABLE entirely.
Partition Projection — Zero-Maintenance Partitioning
CREATE EXTERNAL TABLE events (
    event_id STRING,
    user_id BIGINT,
    event_type STRING,
    payload STRING
)
PARTITIONED BY (event_date STRING)
ROW FORMAT SERDE 'org.apache.hadoop.hive.ql.io.parquet.serde.ParquetHiveSerDe'
STORED AS PARQUET
LOCATION 's3://datalake/events/'
TBLPROPERTIES (
    'projection.enabled' = 'true',
    'projection.event_date.type' = 'date',
    'projection.event_date.range' = '2020-01-01,NOW',
    'projection.event_date.format' = 'yyyy-MM-dd',
    'projection.event_date.interval' = '1',
    'projection.event_date.interval.unit' = 'DAYS',
    'storage.location.template' = 's3://datalake/events/${event_date}/'
);
Partition projection eliminates: (1) Running crawlers or MSCK REPAIR. (2) Glue Catalog partition lookup latency (can be seconds for 100K+ partitions). (3) The 10-million partition limit per table. Athena generates partition paths on-the-fly from the formula.

Columnar Formats & Compression

Format Comparison for Athena

FormatScan EfficiencyBest ForCompression
CSVWorst — reads ALL columns regardless of SELECTNever (for analytics)GZIP possible but still reads all cols
JSONBad — entire row parsed for each columnStaging/raw onlyGZIP
ParquetExcellent — reads only projected columnsDefault choice for analyticsSnappy (default), ZSTD, GZIP
ORCExcellent — similar to ParquetHive ecosystem, Presto-optimized readsZLIB, Snappy, ZSTD

Compression Impact

  • Snappy: Fast decompression, moderate ratio (3-4x). Best for compute-bound queries. Default in Spark/EMR.
  • ZSTD: Higher ratio (5-7x) with still-fast decompression. Best for I/O-bound queries (Athena is almost always I/O-bound). Recommended for Athena.
  • GZIP: Highest ratio (6-8x) but slow decompression. Acceptable for cold/archival data queried rarely.
Converting to Optimized Format with CTAS
-- Convert CSV table to Parquet with ZSTD + partitioning
CREATE TABLE optimized_events
WITH (
    format = 'PARQUET',
    parquet_compression = 'ZSTD',
    partitioned_by = ARRAY['event_date'],
    external_location = 's3://datalake/optimized/events/'
)
AS SELECT
    event_id, user_id, event_type, payload,
    date_format(from_iso8601_timestamp(timestamp), '%Y-%m-%d') as event_date
FROM raw_events
WHERE year = '2024';

Bucketing

Bucketing hashes rows by a column into a fixed number of files per partition. Benefits: predictable file sizes and co-located data for joins.

Bucketed Table Creation
CREATE TABLE bucketed_orders
WITH (
    format = 'PARQUET',
    partitioned_by = ARRAY['order_date'],
    bucketed_by = ARRAY['customer_id'],
    bucket_count = 64,
    external_location = 's3://datalake/bucketed/orders/'
)
AS SELECT * FROM raw_orders;

-- Queries filtering on customer_id read only relevant buckets
-- Joins between two tables bucketed on the same key avoid shuffle
SELECT o.*, c.name
FROM bucketed_orders o
JOIN bucketed_customers c ON o.customer_id = c.customer_id
WHERE o.order_date = '2024-01-15';
  • Bucket count: Choose a power of 2 (32, 64, 128). Should result in files between 128MB–512MB each.
  • Join optimization: Two tables bucketed on the same column with the same bucket count enable bucket-pruned joins — each worker reads matching bucket pairs.
  • Athena v3: Bucket pruning for filters is automatic. Bucket-optimized joins require explicit hints in some cases.

CTAS for Materialization

CREATE TABLE AS SELECT (CTAS) materializes query results as a new table — useful for pre-aggregation, format conversion, and building derived datasets.

CTAS Patterns
-- Pattern 1: Pre-aggregate for dashboards
CREATE TABLE daily_metrics
WITH (format = 'PARQUET', external_location = 's3://analytics/daily_metrics/')
AS SELECT
    event_date,
    count(*) as total_events,
    count(distinct user_id) as unique_users,
    sum(revenue) as total_revenue,
    approx_percentile(latency_ms, 0.99) as p99_latency
FROM events
WHERE event_date >= date_add('day', -30, current_date)
GROUP BY event_date;

-- Pattern 2: Unload query results to S3 (cheaper than repeated scans)
CREATE TABLE report_20240115
WITH (format = 'PARQUET', external_location = 's3://reports/20240115/')
AS SELECT * FROM complex_query_with_multiple_joins;

-- Cost: you pay once for the CTAS scan; subsequent reads of
-- the materialized table scan only the (much smaller) result.
CTAS Limit: Maximum 100 partitions per CTAS query. For large datasets with more partitions, use INSERT INTO with multiple statements, or use Spark/Glue for the initial materialization.

Workgroups for Cost Allocation

  • Purpose: Isolate query costs by team, project, or environment. Each workgroup has its own cost limits, result location, and encryption settings.
  • Per-query limit: Set max data scanned per query (e.g., 1 TB). Queries exceeding this are cancelled before execution — prevents accidental full-table scans.
  • Per-workgroup limit: Monthly/weekly byte-scan budgets. Alerts via CloudWatch when approaching threshold.
  • Result override: Force query results to a specific S3 location per workgroup — control where results land.
Workgroup Configuration (Terraform)
resource "aws_athena_workgroup" "data_team" {
  name = "data-engineering"

  configuration {
    enforce_workgroup_configuration = true
    publish_cloudwatch_metrics_enabled = true
    bytes_scanned_cutoff_per_query = 10737418240  # 10 GB limit

    result_configuration {
      output_location = "s3://athena-results/data-team/"
      encryption_configuration {
        encryption_option = "SSE_KMS"
        kms_key_arn       = aws_kms_key.athena.arn
      }
    }
  }
}

Query Result Reuse

Athena v3 supports query result reuse — if the same query was run recently and underlying data hasn't changed, Athena returns cached results without scanning S3.

  • TTL: Configurable cache duration (up to 60 minutes by default). Results older than TTL trigger a fresh scan.
  • Invalidation: If underlying table data changes (new partitions, file modifications), cache is automatically invalidated.
  • Cost impact: Reused results cost $0 — no data scanned. Huge savings for dashboards with repeated queries.
  • Enable: Set at workgroup level: result_reuse_enabled = true.

Iceberg/Delta Integration

Athena v3 natively reads and writes Apache Iceberg tables, providing ACID transactions, time travel, and schema evolution directly in Athena:

Iceberg Table Operations in Athena
-- Create Iceberg table
CREATE TABLE iceberg_events (
    event_id STRING,
    user_id BIGINT,
    event_type STRING,
    amount DOUBLE,
    event_time TIMESTAMP
)
PARTITIONED BY (day(event_time))
LOCATION 's3://datalake/iceberg/events/'
TBLPROPERTIES ('table_type' = 'ICEBERG');

-- MERGE (upsert) — ACID transaction
MERGE INTO iceberg_events t
USING new_events s ON t.event_id = s.event_id
WHEN MATCHED THEN UPDATE SET amount = s.amount, event_type = s.event_type
WHEN NOT MATCHED THEN INSERT *;

-- Time travel
SELECT * FROM iceberg_events FOR TIMESTAMP AS OF timestamp '2024-01-14 10:00:00';
SELECT * FROM iceberg_events FOR VERSION AS OF 42;

-- Schema evolution
ALTER TABLE iceberg_events ADD COLUMNS (category STRING);

-- Compaction (optimize file sizes)
OPTIMIZE iceberg_events REWRITE DATA USING BIN_PACK;

Athena ACID Transactions

  • Available for Iceberg tables only (not plain Hive/Parquet tables).
  • Supports INSERT, UPDATE, DELETE, MERGE operations.
  • Concurrent writers are serialized via Iceberg's optimistic concurrency (commit retry on conflict).
  • Readers always see consistent snapshots — no dirty reads.
  • Limitation: Write throughput is lower than Spark/EMR — Athena is optimized for queries, not heavy write workloads. Use Spark for bulk ingestion, Athena for ad-hoc mutations.

Federated Query

Athena can query external data sources beyond S3 using Lambda-based connectors:

  • Supported sources: DynamoDB, RDS (MySQL, PostgreSQL), Redshift, CloudWatch Logs, HBase, DocumentDB, Neptune, Elasticsearch, custom (any JDBC via generic connector).
  • Architecture: Lambda functions handle connection, query pushdown, and pagination. Athena invokes Lambda for each split of the query.
  • Pushdown: Connectors push filters and projections to the source when possible — reducing data transferred to Athena.
  • Cost: Standard Athena pricing + Lambda invocation costs + source database charges.
Federated Query Example
-- Register a DynamoDB connector as a catalog
-- (done via Athena console or SAR deployment)

-- Query DynamoDB from Athena
SELECT d.user_id, d.preferences, s.total_orders
FROM dynamodb_catalog.default.user_profiles d
JOIN s3_events.analytics.order_summary s
  ON d.user_id = s.user_id
WHERE d.status = 'active';
Federated query pitfall: Athena pulls data from external sources into its workers for processing. If you join a large S3 table with a large DynamoDB table, ALL matching DynamoDB rows are read via Lambda into Athena memory. Apply filters that push down to the source first. Never do a full cross-catalog JOIN without predicates.

Performance Tuning Tips

Query Writing Best Practices

  • SELECT only needed columns: SELECT * reads all columns from Parquet files. Projecting 5 of 100 columns = 95% scan reduction.
  • Filter on partition columns first: Always include partition keys in WHERE clause.
  • Use approximate functions: approx_distinct() instead of COUNT(DISTINCT) for cardinality — 2-3% error but 10x faster.
  • Avoid LIKE with leading wildcards: WHERE name LIKE '%smith' cannot use file statistics — full scan. Use LIKE 'smith%' or regex.
  • Push ORDER BY + LIMIT together: ORDER BY x LIMIT 100 uses top-N optimization. ORDER BY alone sorts entire result set in memory.

Table Design Best Practices

  • File size: 128 MB–512 MB per file. Smaller files = too many S3 GETs (latency overhead). Larger files = less parallelism.
  • File count per partition: 10–100 files ideal. >10,000 files per partition = slow planning phase.
  • Row group size: For Parquet, 128MB row groups enable effective predicate pushdown via row group statistics.
  • Column ordering: Place frequently-filtered columns first in the schema — some engines benefit from column index locality.

Interview Questions

A data analyst complains their Athena query costs $200 per run. Walk through your optimization approach.

$200 = 40 TB scanned ($5/TB). This is almost certainly a full-table scan on raw/CSV data without partitioning.

Step 1 — Identify the waste: Check the query in Athena History → look at "Data scanned" metric. Run EXPLAIN to see if partition pruning is happening. Common causes: SELECT *, no WHERE on partition columns, CSV format, or querying a non-partitioned table.

Step 2 — Convert to Parquet/ORC: Use CTAS to create a Parquet copy with ZSTD compression. Expected: 10-20x reduction in data size = $200 → $10-20.

Step 3 — Add partitioning: Partition by the most common filter column (usually date). If they typically query one day of a 365-day table: 365x reduction = $20 → $0.05.

Step 4 — Column pruning: Review their SELECT — if they need 5 of 50 columns, that's another 10x reduction on top of Parquet.

Step 5 — Guardrails: Set workgroup byte limit (e.g., 10GB per query) so this can never happen again. Failed queries hit the limit before scanning the full table.

Net result: CSV full-scan $200 → Parquet + partitioned + projected $0.005. This is a real-world 40,000x improvement achievable in 30 minutes of CTAS work.

How does Athena's pricing model influence your data lake design decisions?

Fundamental principle: With Athena, storage format IS your query cost. Every architectural decision should minimize bytes scanned per query.

Format choice: Columnar (Parquet/ORC) is non-negotiable for analytical tables. Store raw ingestion as JSON/CSV only in a bronze/landing zone — never let analysts query it directly.

Partition strategy: Design partitions around ACCESS patterns, not data organization. If analysts filter by date, partition by date — even if the data naturally organizes by region.

Materialization: Pre-aggregate expensive queries into summary tables. A $50 daily aggregation query run once into a summary table → $0.01 for subsequent reads of the summary.

Table tiering: Hot tables (queried 100x/day): heavily optimized Parquet, bucketed, small row groups. Warm tables (queried 5x/day): standard Parquet partitioned. Cold tables: compressed Parquet, larger files, query result reuse enabled.

Column discipline: Wide tables (500+ columns) are expensive even in Parquet. Split into focused tables with only relevant columns per domain — reduces scanned bytes for targeted queries.

Compare Athena vs Redshift Spectrum vs EMR Presto for ad-hoc querying on S3 data.

Athena: Zero infrastructure, pay-per-scan, instant start. Best for: ad-hoc exploration, variable query volume, cost-conscious teams. Limitation: no persistent caching, query concurrency limits (20-30 concurrent), no result materialization between query steps.

Redshift Spectrum: Extension of Redshift — queries S3 data using Redshift's compute layer. Best for: teams already using Redshift who want to extend queries to the data lake without ETL. Benefit: can join S3 data with Redshift local tables. Limitation: requires a running Redshift cluster (fixed cost), billed per TB scanned (same as Athena) PLUS cluster compute time.

EMR Presto/Trino: Self-managed Trino cluster on EMR. Best for: high-concurrency workloads (100s of concurrent queries), sub-second latency requirements (with caching/warm data), complex multi-catalog federation, custom UDFs. Limitation: operational overhead of managing a cluster, pay for cluster uptime regardless of query volume.

Decision matrix: Query volume < 50/day → Athena. Already have Redshift + need lake joins → Spectrum. Need low-latency/high-concurrency BI layer → EMR Presto with Alluxio caching. Cost-sensitive exploration → Athena always.

How would you implement incremental materialized views in Athena (which doesn't have native MV support)?

Pattern: Scheduled CTAS/INSERT INTO with partition replacement

Step 1: Create a target table (Iceberg format for ACID support) representing the "view":

CREATE TABLE materialized_daily_stats (date, total_orders, revenue, ...) USING ICEBERG

Step 2: Schedule a Step Function or EventBridge rule that triggers an Athena query daily:

MERGE INTO materialized_daily_stats t USING (SELECT ... FROM events WHERE event_date = current_date - 1) s ON t.date = s.date WHEN MATCHED THEN UPDATE ... WHEN NOT MATCHED THEN INSERT ...

Step 3: Downstream dashboards query the materialized table (small, fast, cheap) instead of the raw events table (large, slow, expensive).

Alternative (non-Iceberg): Use CTAS to create daily partition, DROP + re-create partition if reprocessing needed. Less elegant but works with standard Hive tables.

Cost model: One expensive materialization scan per day ($X) vs N cheap reads of the materialized result ($0.001 × N). Break-even at ~10 queries/day for most tables.
