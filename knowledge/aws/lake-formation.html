What Lake Formation Adds on Top of IAM

Without Lake Formation, data lake access control relies on S3 IAM policies — which operate at the object/prefix level. This creates fundamental problems for analytics governance:

IAM-Only Problems

  • No column-level control: IAM can't restrict access to specific columns in a Parquet file. If you can read the S3 object, you can read ALL columns.
  • No row-level control: Can't filter rows per-user at the storage level.
  • Policy explosion: A data lake with 500 tables × 10 teams = thousands of IAM policies mapping principals to S3 prefixes. Unmanageable.
  • No table abstraction: IAM knows about S3 paths, not logical tables. Renaming a table's S3 location breaks all policies.
  • Cross-account complexity: Sharing a table across accounts requires bucket policies + IAM roles + resource policies. Each table = complex policy chain.

Lake Formation's Solution

  • Database/Table/Column permissions: Grant access at the logical level — "User X can SELECT columns A, B, C from table Y in database Z."
  • Centralized governance: Single admin console for all permissions. No scattered IAM policies.
  • Tag-based access: Assign tags to tables/columns, grant access to tags. Scale permissions without per-table grants.
  • Transparent enforcement: Athena, EMR, Glue, and Redshift Spectrum all enforce LF permissions automatically.
Key insight: Lake Formation sits BETWEEN the user and the data. When Athena queries a table, it asks Lake Formation "does this principal have SELECT permission on these columns?" Lake Formation returns a filtered view — the user never sees unauthorized columns/rows. The underlying S3 permissions are granted to a Lake Formation service role, not to individual users.

Data Lake Permissions Model vs IAM Policies

How It Works — The "Vending Machine" Model

  1. Register S3 locations: Tell Lake Formation which S3 paths contain data lake tables.
  2. Revoke IAMAllowedPrincipals: By default, Glue Catalog grants "Super" permission to IAMAllowedPrincipals (effectively bypassing LF). You must revoke this to activate LF governance.
  3. Grant LF permissions: Use the Lake Formation API/console to grant specific principals (IAM users, roles, SAML groups) access to specific databases/tables/columns.
  4. Services enforce: When a principal queries via Athena/EMR/Glue, the service checks LF permissions before accessing data.

Lake Formation Permission Grant (AWS CLI)
# Grant SELECT on specific columns to a role
aws lakeformation grant-permissions \
  --principal '{"DataLakePrincipalIdentifier": "arn:aws:iam::123456789:role/analyst-role"}' \
  --resource '{
    "TableWithColumns": {
      "DatabaseName": "analytics",
      "Name": "customer_events",
      "ColumnNames": ["event_id", "event_type", "event_date", "category"]
    }
  }' \
  --permissions '["SELECT"]'

# Grant full table access to a data engineering role
aws lakeformation grant-permissions \
  --principal '{"DataLakePrincipalIdentifier": "arn:aws:iam::123456789:role/data-eng-role"}' \
  --resource '{
    "Table": {
      "DatabaseName": "analytics",
      "Name": "customer_events"
    }
  }' \
  --permissions '["SELECT", "INSERT", "DELETE", "ALTER"]'

LF-Tags — Tag-Based Access Control

LF-Tags enable attribute-based access control (ABAC) — assign tags to resources and principals, then define permissions based on tag matches. This scales to thousands of tables without individual grants.

How LF-Tags Work

  1. Define tags: Create tag keys with allowed values. Example: classification = [public, internal, confidential, restricted]
  2. Assign tags to resources: Tag databases, tables, or columns. customer_events.email → classification:restricted
  3. Create tag-based permissions: "Analysts can SELECT where classification IN [public, internal]"
  4. Auto-inheritance: Tags on databases propagate to tables; tags on tables propagate to columns (unless overridden).
LF-Tag Based Access Control
# Step 1: Create LF-Tags
aws lakeformation create-lf-tag \
  --tag-key "classification" \
  --tag-values '["public", "internal", "confidential", "restricted"]'

aws lakeformation create-lf-tag \
  --tag-key "domain" \
  --tag-values '["marketing", "finance", "engineering", "hr"]'

# Step 2: Assign tags to a table
aws lakeformation add-lf-tags-to-resource \
  --resource '{"Table": {"DatabaseName": "analytics", "Name": "revenue"}}' \
  --lf-tags '[{"TagKey": "classification", "TagValues": ["confidential"]}, {"TagKey": "domain", "TagValues": ["finance"]}]'

# Step 3: Grant access based on tags
# "Finance team can SELECT any table tagged domain=finance AND classification IN [public, internal, confidential]"
aws lakeformation grant-permissions \
  --principal '{"DataLakePrincipalIdentifier": "arn:aws:iam::123456789:role/finance-team"}' \
  --resource '{
    "LFTagPolicy": {
      "ResourceType": "TABLE",
      "Expression": [
        {"TagKey": "domain", "TagValues": ["finance"]},
        {"TagKey": "classification", "TagValues": ["public", "internal", "confidential"]}
      ]
    }
  }' \
  --permissions '["SELECT", "DESCRIBE"]'
Scaling advantage: Without LF-Tags, adding a new table requires explicit grants to every team that should access it. With LF-Tags, you just tag the new table with the appropriate domain/classification — existing tag-based policies automatically apply. This is the recommended approach for organizations with 100+ tables.

Column-Level Security

  • Include mode: Grant SELECT on a whitelist of columns. User sees only those columns.
  • Exclude mode: Grant SELECT on all columns EXCEPT a blacklist. Easier to maintain for tables with many columns where only a few are sensitive.
  • Column-level tags: Tag individual columns (e.g., email → pii:true). Grant based on tags — all PII columns controlled by one policy.
  • Enforcement: Athena's query plan is rewritten to exclude unauthorized columns. Selecting a restricted column returns an access denied error.

Row-Level Filtering

Define filter expressions that restrict which rows a principal can see. Implemented as predicate pushdown at query time.

Row-Level Filter Definition
# Create a row filter — marketing team sees only marketing events
aws lakeformation create-data-cells-filter \
  --table-data '{
    "DatabaseName": "analytics",
    "Name": "events",
    "TableCatalogId": "123456789012"
  }' \
  --data-cells-filter '{
    "Name": "marketing-events-only",
    "DatabaseName": "analytics",
    "TableName": "events",
    "TableCatalogId": "123456789012",
    "RowFilter": {
      "FilterExpression": "department = '\''marketing'\''"
    },
    "ColumnNames": ["event_id", "event_type", "event_date", "channel", "campaign_id"]
  }'

# Grant the filter-based permission
aws lakeformation grant-permissions \
  --principal '{"DataLakePrincipalIdentifier": "arn:aws:iam::123456789:role/marketing-analyst"}' \
  --resource '{
    "DataCellsFilter": {
      "DatabaseName": "analytics",
      "TableName": "events",
      "Name": "marketing-events-only",
      "TableCatalogId": "123456789012"
    }
  }' \
  --permissions '["SELECT"]'
Performance consideration: Row-level filters add a WHERE clause to every query. For heavily filtered tables (filter eliminates 99% of rows), ensure the filter column is a partition key — otherwise every query results in a full-table scan with post-scan filtering.

Cross-Account Data Sharing

Sharing Methods

  • Named Resource Method: Producer account grants specific databases/tables to consumer account ID. Consumer registers shared resources in their own LF console.
  • LF-Tag Method: Share based on tags across accounts. Tag match = access. More scalable for organizations with many accounts.
  • RAM (Resource Access Manager): Under the hood, LF uses AWS RAM to share Glue Catalog resources. The consumer sees shared databases as "resource shares" in their account.

Cross-Account Flow

  1. Producer grants permissions to consumer account (or OU).
  2. Consumer accepts the resource share (auto-accept possible within org).
  3. Consumer creates a resource link (pointer) in their local Glue Catalog.
  4. Consumer queries via Athena/EMR using the resource link — transparent access.
  5. Producer's LF permissions (including column/row filters) are enforced even for cross-account access.

Integration with Glue Catalog

  • Lake Formation permissions layer sits on TOP of the Glue Data Catalog — it doesn't replace it.
  • Tables, databases, and schemas are still defined in Glue Catalog.
  • LF adds a permissions evaluation step: Catalog API calls check LF grants before returning metadata.
  • Hybrid mode: You can have some databases governed by LF and others using legacy IAM-only mode. Controlled by the UseServiceLinkedRole setting per database.
  • Migration path: Enable LF on one database at a time. Revoke IAMAllowedPrincipals, grant explicit LF permissions, validate access, repeat.

Governed Tables

Governed tables provide ACID transactions and automatic compaction managed by Lake Formation (distinct from Iceberg tables managed by Athena/Spark):

  • ACID writes: Multiple writers can safely write to the same table without conflicts.
  • Automatic compaction: LF compacts small files in the background — no manual OPTIMIZE needed.
  • Time travel: Query previous versions of governed tables.
  • Limitation: Governed tables are AWS-proprietary (not Iceberg/Delta format). Vendor lock-in concerns. For most workloads, prefer Iceberg tables with LF permissions — get open format + governance.

Data Location Permissions

Controls which principals can create tables pointing to specific S3 locations. Prevents a rogue IAM role from registering external data as a Catalog table to bypass governance.

  • Register locations: Register S3 paths with Lake Formation. Only principals with DATA_LOCATION_ACCESS permission can create tables at those paths.
  • Service role: LF uses a service-linked role to access S3. Individual users don't need direct S3 access — LF vends temporary credentials.
  • Unregistered paths: Tables at unregistered locations fall back to IAM-based access (bypassing LF governance). Register all data lake paths.

Blueprints for Data Ingestion

  • Pre-built workflows (Glue jobs + crawlers) for common ingestion patterns.
  • Database snapshot: Full JDBC table load into the data lake.
  • Incremental database: CDC-style incremental loads from JDBC sources.
  • Log file: Parse and catalog log files from S3.
  • Limitation: Blueprints are basic templates — production teams usually outgrow them quickly. Better suited for proof-of-concepts than production pipelines.

Key difference: Unity Catalog is a unified governance layer for both data AND compute. Lake Formation governs data access but doesn't control compute resources (EMR clusters, Glue jobs). For full governance parity with Unity Catalog on AWS, you need LF + Service Control Policies + individual service-level controls.

Interview Questions

Your organization has 200 tables and 15 teams. How would you design access control using Lake Formation?

Step 1 — Define tag taxonomy: Create LF-Tags: domain = [marketing, finance, engineering, product, hr, legal], classification = [public, internal, sensitive, restricted], pii = [true, false].

Step 2 — Tag all resources: Assign domain and classification tags to every database and table. Override at column level for PII columns (e.g., email, SSN tagged pii:true, classification:restricted).

Step 3 — Create IAM roles per team: marketing-analyst-role, finance-analyst-role, data-eng-role (superuser). Map SAML groups to roles via Identity Center.

Step 4 — Grant tag-based permissions: "Marketing team → SELECT on domain=marketing, classification IN [public, internal]". "Data engineering → ALL on all domains, all classifications". "Finance → SELECT on domain=finance, all classifications". "All teams → SELECT on classification=public (shared reference tables)".

Step 5 — Add row-level filters where needed: Finance can only see their region's data: region = 'us' filter on revenue tables.

Scaling advantage: When table 201 is created and tagged domain:marketing, classification:internal, the marketing team automatically gets access. Zero manual grants needed.

What are the common pitfalls when migrating from IAM-only to Lake Formation?

Pitfall 1 — IAMAllowedPrincipals: The default "Super" grant to IAMAllowedPrincipals effectively disables LF governance. You MUST revoke this on each database/table you want governed. Forgetting this = false sense of security.

Pitfall 2 — Breaking existing access: When you revoke IAMAllowedPrincipals and enable LF, all existing IAM-based access STOPS immediately. You must pre-create LF grants before revoking. Sequence: grant LF permissions → test → revoke IAM fallback.

Pitfall 3 — S3 direct access bypass: LF only governs access through integrated services (Athena, EMR, Glue). A user with direct S3:GetObject IAM permission can bypass LF entirely by reading Parquet files directly. Mitigation: remove direct S3 data access from user roles; only the LF service role should have S3 access.

Pitfall 4 — EMR integration complexity: EMR requires specific session tags and EMRFS credential provider configuration to enforce LF permissions. Without proper setup, EMR jobs run with full S3 access bypassing LF.

Pitfall 5 — Cross-account resource links: Shared tables appear as resource links in consumer accounts. Some services (older Glue versions) don't follow resource links properly. Test cross-account queries thoroughly.

How do you implement GDPR right-to-deletion in a Lake Formation-governed data lake?

Challenge: GDPR Article 17 requires deleting a user's personal data across all tables when requested. In a data lake with 200+ tables, this is operationally complex.

Architecture:

1. Discovery (LF-Tags): Tag all PII columns with pii:true. Use Glue Catalog search to find every table containing PII. LF-Tags make this discoverable — query all resources where pii=true.

2. Deletion pipeline: Use Iceberg tables (support row-level DELETE). Build a Step Function workflow: receive deletion request → query LF tag API to find all PII tables → submit DELETE WHERE user_id = X to each table → log compliance proof.

3. Verification: After deletion, run a verification query across all PII-tagged tables confirming zero rows for the user. Store audit trail (deletion request timestamp, affected tables, row counts deleted).

4. Access control during processing: The deletion service needs broad SELECT + DELETE permissions. Use a dedicated LF permission grant: deletion-service-role → DELETE on all tables where pii=true.

Non-Iceberg tables: For Hive/Parquet tables that don't support DELETE, the workflow must: (a) identify affected partitions, (b) rewrite partitions excluding the user's rows via Spark/Glue, (c) update Catalog to point to new files. This is why Iceberg is strongly recommended for GDPR-subject tables.

Compare Lake Formation's access model to a row-level security implementation in a data warehouse like Redshift or Snowflake.

Warehouse approach (Redshift/Snowflake): Row-level security (RLS) policies are database objects — SQL functions evaluated at query time by the engine. Policies reference session context (current_user, current_role) to filter rows. Implementation is within the compute engine itself.

Lake Formation approach: Row filters are metadata in the LF governance layer — external to the compute engine. LF injects filter predicates into the query plan before execution. The compute engine (Athena, EMR) receives a pre-filtered plan.

Key differences: (1) Warehouse RLS is engine-specific (Redshift policy won't work in Athena). LF row filters apply across ALL integrated compute engines from one definition. (2) Warehouse RLS can use complex SQL functions (dynamic user context, session variables). LF filters are simpler expressions (column = value, column IN list). (3) Warehouse RLS is invisible to the optimizer until execution. LF filters can be pushed to partition pruning (if filter column is a partition key). (4) Performance: Warehouse RLS adds negligible overhead (optimized by query engine). LF row filters on non-partition columns require full file scan + post-filter — potentially expensive.

Recommendation: Use LF row filters for coarse-grained access (department, region). For complex per-user RLS (multi-tenant isolation, attribute-based policies), consider Redshift with native RLS or dbt-generated secure views as a complementary layer.
