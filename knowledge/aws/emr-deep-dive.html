EMR Architecture — Node Types

An EMR cluster consists of three logical node types, each serving a distinct purpose in the distributed computing model:

Master Node (Primary Node)

  • Role: Runs the cluster's control plane — YARN ResourceManager, HDFS NameNode, Spark Driver (in cluster mode), Hive Metastore, Ganglia, and the EMR agent.
  • Count: Exactly 1 for standard clusters; 3 for high-availability (HA) clusters (multi-master with ZooKeeper-based leader election).
  • Sizing: Memory-intensive (r5/r6g family). The master holds all HDFS metadata in memory — plan ~1GB heap per million HDFS blocks.
  • Failure impact: Single-master cluster terminates on master failure. HA clusters survive one master loss.

Core Nodes

  • Role: Run YARN NodeManager (execute containers/tasks) AND HDFS DataNode (store data blocks).
  • Scaling: Can scale up but never scale down safely without HDFS decommission (risk of data loss). EMR managed scaling handles graceful decommission.
  • Best practice: Use On-Demand or Reserved for core nodes to protect HDFS data. Minimum core nodes = replication factor (default 3 for clusters ≥10 nodes, 2 for 4–9, 1 for ≤3).

Task Nodes

  • Role: Run YARN NodeManager ONLY — pure compute, no HDFS storage.
  • Best for Spot: Can be terminated without data loss. Ideal for burst capacity.
  • Use case: When your bottleneck is compute (CPU/memory for Spark executors) not storage. With EMRFS (S3), most modern workloads have no HDFS dependency — making task nodes the primary scaling mechanism.
Key insight: In S3-backed architectures (EMRFS), core nodes only need enough capacity to run the YARN NodeManager. The real workhorse is task nodes — scale them aggressively with Spot instances since no data lives on local HDFS.

Instance Fleets vs Uniform Instance Groups

Uniform Instance Groups

  • Each group contains a single instance type (e.g., all m5.xlarge).
  • One group per node role (master group, core group, task group).
  • Simpler to reason about — predictable resource allocation per container.
  • Limited flexibility: if your chosen instance type is unavailable in the AZ, the cluster creation fails.

Instance Fleets

  • Specify up to 30 instance types per fleet — EMR picks from available capacity.
  • Define target capacity in units (vCPU or custom weighting) rather than instance count.
  • Allocation strategy: lowest-price (legacy) or capacity-optimized (recommended — minimizes Spot interruptions).
  • Mix On-Demand and Spot within a fleet: set TargetOnDemandCapacity for baseline + TargetSpotCapacity for burst.
Instance Fleet Configuration (AWS CLI)
aws emr create-cluster \
  --instance-fleets '[
    {
      "InstanceFleetType": "MASTER",
      "TargetOnDemandCapacity": 1,
      "InstanceTypeConfigs": [
        {"InstanceType": "r6g.2xlarge", "WeightedCapacity": 1},
        {"InstanceType": "r5.2xlarge", "WeightedCapacity": 1}
      ]
    },
    {
      "InstanceFleetType": "CORE",
      "TargetOnDemandCapacity": 4,
      "InstanceTypeConfigs": [
        {"InstanceType": "r6g.xlarge", "WeightedCapacity": 1},
        {"InstanceType": "r5.xlarge", "WeightedCapacity": 1},
        {"InstanceType": "r5a.xlarge", "WeightedCapacity": 1}
      ]
    },
    {
      "InstanceFleetType": "TASK",
      "TargetOnDemandCapacity": 0,
      "TargetSpotCapacity": 20,
      "LaunchSpecifications": {
        "SpotSpecification": {
          "TimeoutDurationMinutes": 15,
          "TimeoutAction": "SWITCH_TO_ON_DEMAND",
          "AllocationStrategy": "capacity-optimized"
        }
      },
      "InstanceTypeConfigs": [
        {"InstanceType": "m6g.2xlarge", "WeightedCapacity": 4},
        {"InstanceType": "m5.2xlarge", "WeightedCapacity": 4},
        {"InstanceType": "m5a.2xlarge", "WeightedCapacity": 4},
        {"InstanceType": "c5.2xlarge", "WeightedCapacity": 4},
        {"InstanceType": "r5.xlarge", "WeightedCapacity": 2}
      ]
    }
  ]'
Best practice: Always use Instance Fleets for production. Specify at least 5–10 instance types per fleet to maximize Spot availability. Use capacity-optimized allocation — it draws from Spot pools with the most unused capacity, reducing interruption rates by 60–80% vs lowest-price.

Spot vs On-Demand Strategies

ComponentRecommendationReasoning
MasterOn-Demand (always)Master failure = cluster termination
Core (HDFS)On-Demand or ReservedProtects HDFS data blocks from loss
Core (EMRFS only)50-80% Spot acceptableNo local data at risk; YARN can reschedule
Task100% SpotPure compute — interruptions just retry tasks

Spot Interruption Handling

  • YARN decommission timeout: Set yarn.resourcemanager.nodemanager-graceful-decommission-timeout-secs to allow containers to finish before node loss (default 3600s on EMR).
  • Spark speculation: Enable spark.speculation=true — if a task on an interrupted node is slow/missing, a duplicate launches elsewhere.
  • Spot block (deprecated): Use capacity-optimized allocation instead.
  • Diversification: More instance types = lower interruption probability. A fleet with 15 types sees ~3% interruption vs ~15% for single-type.

EMR on EKS vs EMR on EC2

EMR on EC2 (Classic)

  • Dedicated EC2 instances managed by EMR.
  • Full Hadoop ecosystem: HDFS, Hive, Pig, HBase, Presto, etc.
  • Bootstrap actions for custom software installation.
  • Best for: workloads needing HDFS locality, HBase, or legacy Hadoop tools.

EMR on EKS

  • Spark jobs run as pods on an existing EKS cluster — shared Kubernetes infrastructure.
  • No separate EMR cluster to manage — submit jobs via virtual clusters.
  • Share compute across data engineering and microservices workloads.
  • Up to 3x faster start times (no cluster bootstrap — pods spin in seconds).
  • Custom Docker images for dependency management (no bootstrap actions needed).
  • Supports Karpenter/Cluster Autoscaler for node provisioning.
EMR on EKS Job Submission
aws emr-containers start-job-run \
  --virtual-cluster-id vc-abc123 \
  --name "daily-etl-job" \
  --execution-role-arn arn:aws:iam::123456789:role/emr-eks-role \
  --release-label emr-6.15.0-latest \
  --job-driver '{
    "sparkSubmitJobDriver": {
      "entryPoint": "s3://my-bucket/scripts/etl.py",
      "sparkSubmitParameters": "--conf spark.executor.instances=50 --conf spark.executor.memory=8g --conf spark.executor.cores=4 --conf spark.dynamicAllocation.enabled=true"
    }
  }' \
  --configuration-overrides '{
    "applicationConfiguration": [{
      "classification": "spark-defaults",
      "properties": {
        "spark.kubernetes.executor.podTemplateFile": "s3://my-bucket/pod-templates/executor.yaml",
        "spark.hadoop.fs.s3a.aws.credentials.provider": "com.amazonaws.auth.WebIdentityTokenCredentialsProvider"
      }
    }]
  }'
Limitation: EMR on EKS supports only Spark (not Hive, HBase, Presto natively). If you need the full Hadoop ecosystem, stay on EMR on EC2. For pure Spark/PySpark workloads, EKS is operationally superior.

Bootstrap Actions

Shell scripts that run on every node before applications start. Execute order: after EC2 launch → after EMR agent installs software → before YARN/HDFS/Spark start.

Bootstrap Action Example
#!/bin/bash
# install-python-deps.sh — runs on ALL nodes
set -e

# Install system packages
sudo yum install -y gcc python3-devel

# Install Python libraries (only on master + core for driver code)
if grep -q '"isMaster": true' /mnt/var/lib/info/instance.json || \
   grep -q '"isMaster": false' /mnt/var/lib/info/instance.json; then
  sudo pip3 install pandas==2.1.0 pyarrow==13.0.0 boto3==1.28.0
fi

# Increase open file limits for Spark shuffle
echo "* soft nofile 65536" | sudo tee -a /etc/security/limits.conf
echo "* hard nofile 65536" | sudo tee -a /etc/security/limits.conf

# Install custom JARs for all nodes (needed by executors)
aws s3 cp s3://my-bucket/jars/custom-udf.jar /usr/lib/spark/jars/

Step Execution vs Persistent Clusters

Transient (Step) Clusters

  • Cluster launches → runs steps sequentially → auto-terminates on completion.
  • Cost: Pay only for job duration. No idle costs.
  • Overhead: 5–10 min cluster startup time per job run.
  • Best for: Scheduled batch ETL (daily/hourly), infrequent large jobs, cost-sensitive workloads.

Persistent (Long-Running) Clusters

  • Cluster stays up indefinitely; jobs submitted via YARN, Spark submit, Livy, or notebooks.
  • Cost: Continuous charges even when idle (mitigate with managed scaling to minimum).
  • Best for: Interactive analysis (notebooks), streaming jobs, ad-hoc queries, jobs with shared state (HBase, Hive Metastore).
Modern pattern: Use transient clusters orchestrated by Step Functions or Airflow for batch. Use EMR on EKS or EMR Serverless for interactive/ad-hoc — they eliminate the cluster lifecycle entirely.

Spark Configuration on EMR

spark-defaults.conf on EMR

EMR provides maximizeResourceAllocation — a flag that auto-calculates Spark settings based on cluster hardware:

EMR Classification Configuration
[
  {
    "Classification": "spark",
    "Properties": {
      "maximizeResourceAllocation": "true"
    }
  },
  {
    "Classification": "spark-defaults",
    "Properties": {
      "spark.sql.adaptive.enabled": "true",
      "spark.sql.adaptive.coalescePartitions.enabled": "true",
      "spark.sql.adaptive.skewJoin.enabled": "true",
      "spark.dynamicAllocation.enabled": "true",
      "spark.dynamicAllocation.minExecutors": "2",
      "spark.dynamicAllocation.maxExecutors": "100",
      "spark.dynamicAllocation.executorIdleTimeout": "60s",
      "spark.shuffle.service.enabled": "true",
      "spark.serializer": "org.apache.spark.serializer.KryoSerializer",
      "spark.sql.parquet.mergeSchema": "false",
      "spark.hadoop.mapreduce.fileoutputcommitter.algorithm.version": "2",
      "spark.speculation": "true",
      "spark.speculation.multiplier": "1.5"
    }
  },
  {
    "Classification": "spark-hive-site",
    "Properties": {
      "hive.metastore.client.factory.class": "com.amazonaws.glue.catalog.metastore.AWSGlueDataCatalogHiveClientFactory"
    }
  }
]

What maximizeResourceAllocation Does

  • spark.executor.memory = (node RAM - YARN overhead - system reserve) / executors-per-node
  • spark.executor.cores = (node vCPU - 1 for OS) / executors-per-node
  • spark.executor.instances = total-nodes × executors-per-node
  • spark.default.parallelism = executor-instances × executor-cores × 2
  • Sets spark.driver.memory equal to executor memory on the master
Pitfall: maximizeResourceAllocation disables dynamic allocation by default and creates 1 large executor per node. This can lead to GC pressure on big instances. For r5.4xlarge (128GB RAM), consider splitting into 2–3 executors per node with 40GB each + manual overhead calculation: spark.executor.memoryOverhead = max(384MB, 0.10 × executorMemory).

EMRFS vs HDFS

EMRFS (S3-Backed Storage)

  • Architecture: Translates Hadoop FileSystem API calls to S3 API calls. Appears as s3:// paths.
  • Consistency: S3 now provides strong read-after-write consistency (since Dec 2020). EMRFS consistent view (DynamoDB-based) is legacy and no longer needed.
  • Advantages: Decoupled storage from compute (resize/terminate clusters freely), 11 9's durability, pay-per-GB, no replication factor, unlimited capacity.
  • Drawbacks: Higher latency per operation (50-100ms per S3 GET vs 5ms HDFS), no data locality (network bottleneck for shuffle-heavy jobs).

HDFS (Local Cluster Storage)

  • Use cases: Intermediate shuffle data, iterative ML algorithms (repeated reads of same data), HBase storage.
  • Instance storage: Use i3/i3en instances with NVMe SSDs for HDFS — massive IOPS for shuffle-heavy workloads.
  • Configuration: dfs.replication=2 for transient clusters (data reconstructible from S3), 3 for persistent.
EMRFS Optimization Settings
{
  "Classification": "emrfs-site",
  "Properties": {
    "fs.s3.maxConnections": "200",
    "fs.s3.multipart.th.fraction.parts.completed": "0.95",
    "fs.s3.maxRetries": "20",
    "fs.s3.sleepTimeSeconds": "10",
    "fs.s3.enableServerSideEncryption": "true",
    "fs.s3.serverSideEncryption.kms.keyId": "arn:aws:kms:us-east-1:123:key/abc"
  }
}

Managed Scaling

EMR Managed Scaling automatically adds/removes instances based on workload metrics (YARN pending containers, memory utilization). No custom CloudWatch alarms or scaling policies needed.

Managed Scaling Policy
aws emr put-managed-scaling-policy \
  --cluster-id j-ABC123 \
  --managed-scaling-policy '{
    "ComputeLimits": {
      "UnitType": "InstanceFleetUnits",
      "MinimumCapacityUnits": 4,
      "MaximumCapacityUnits": 100,
      "MaximumOnDemandCapacityUnits": 20,
      "MaximumCoreCapacityUnits": 10
    }
  }'
  • Scale-up trigger: YARN pending containers exist for >30 seconds.
  • Scale-down trigger: Idle task nodes with no running containers (after decommission timeout).
  • Limits: MaximumCoreCapacityUnits caps core node growth (protecting HDFS). Excess scaling uses task nodes.
  • Cool-down: Internal cool-down prevents thrashing (typically 2–5 minutes between scaling actions).

Graviton Instances

  • ARM-based processors (r6g, m6g, c6g) offer 20–30% better price-performance vs x86 equivalents (r5, m5, c5).
  • EMR 6.x+ fully supports Graviton — Spark, Hive, Presto all run natively on ARM.
  • Caveat: Custom native libraries (C/C++ JNI, Python extensions compiled for x86) may not work. Test all UDFs and dependencies before migrating.
  • Migration path: Start with task nodes (lowest risk), validate performance, then move core/master.

EMR Serverless

Fully managed Spark/Hive/Presto runtime — no clusters, no instances, no capacity planning. You submit a job with resource requirements and EMR provisions workers automatically.

EMR Serverless Job Submission
aws emr-serverless start-job-run \
  --application-id app-abc123 \
  --execution-role-arn arn:aws:iam::123456789:role/emr-serverless-role \
  --job-driver '{
    "sparkSubmit": {
      "entryPoint": "s3://my-bucket/scripts/etl.py",
      "entryPointArguments": ["--date", "2024-01-15"],
      "sparkSubmitParameters": "--conf spark.executor.cores=4 --conf spark.executor.memory=16g --conf spark.driver.cores=4 --conf spark.driver.memory=16g"
    }
  }' \
  --configuration-overrides '{
    "monitoringConfiguration": {
      "s3MonitoringConfiguration": {
        "logUri": "s3://my-bucket/emr-serverless-logs/"
      }
    }
  }'
  • Pre-initialized capacity: Keep workers warm for sub-second startup (costs money when idle but eliminates cold-start).
  • Cost model: Pay per vCPU-hour and GB-hour of worker runtime. No idle charges without pre-initialized capacity.
  • Limits: Max 4000 vCPUs per application (soft limit, increaseable). Max 15-minute startup without pre-init.
  • Best for: Variable workloads, teams that don't want to manage infrastructure, dev/test environments.
Decision framework: EMR Serverless for simplicity + variable workloads. EMR on EKS for Kubernetes-native teams with existing clusters. EMR on EC2 for full Hadoop ecosystem needs or strict performance/cost control at scale.

Interview Questions

You're seeing 30% Spot interruptions on your EMR cluster, causing job failures. How do you fix this?

Root cause: Likely using too few instance types or the lowest-price allocation strategy (which concentrates in cheapest pools — also the most contested).

Solution: (1) Switch to capacity-optimized allocation strategy — draws from Spot pools with the most spare capacity. (2) Diversify: add 10–15 instance types across multiple families (m5, m5a, m5n, m6g, c5, r5). (3) Move to Instance Fleets if using Instance Groups. (4) Ensure interruptible work is on task nodes only; core nodes should be On-Demand. (5) Enable Spark speculation: spark.speculation=true to re-launch tasks from interrupted nodes. (6) Increase YARN decommission timeout to let in-progress containers complete during the 2-minute Spot warning.

Explain the tradeoffs between maximizeResourceAllocation and manual Spark executor tuning on EMR.

maximizeResourceAllocation creates one large executor per node, using all available memory and cores. This minimizes JVM overhead (fewer processes) and maximizes memory for caching/broadcast.

Drawbacks of single-large-executor: (1) GC pauses — one executor with 100GB heap can have 10+ second full GC. (2) HDFS throughput limited to 5 concurrent threads per executor regardless of cores. (3) One executor failure loses all its cached data. (4) Uneven memory utilization if tasks vary in size.

Manual tuning approach: Split into multiple executors per node. Rule of thumb: 4–8 cores per executor, ~5GB executor memory per core, leave 1 core + 2–4GB for OS/YARN overhead. Example for r5.4xlarge (16 vCPU, 128GB): 3 executors × 5 cores × 38GB memory + 10% overhead = efficient use without GC pain.

When to use each: maximizeResourceAllocation for simple jobs, small clusters, or proof-of-concepts. Manual tuning for production workloads at scale where GC, shuffle, and stability matter.

Your EMR job reads from S3 and is 3x slower than expected. Walk through your debugging process.

Step 1 — Check S3 request patterns: Look at CloudTrail/S3 access logs. If you see millions of LIST calls, your table isn't registered in a catalog (Glue/Hive) and Spark is doing directory listing. Fix: use Glue Catalog or Delta/Iceberg tables.

Step 2 — Check file sizes: Run aws s3 ls --recursive and analyze file size distribution. Thousands of files under 1MB → "small file problem" — each S3 GET has 50-100ms latency overhead. Fix: run compaction (OPTIMIZE) to create 128MB–1GB files.

Step 3 — Check S3 throttling: Look for HTTP 503 SlowDown errors in EMR logs. S3 allows 5,500 GET/s per prefix. If all files share a prefix pattern, you're hitting rate limits. Fix: use hashed prefixes or partition structure that distributes requests.

Step 4 — Check EMRFS config: Ensure fs.s3.maxConnections is high enough (default 50 is too low for large clusters). Set to 200+. Ensure multipart upload thresholds are tuned.

Step 5 — Check Spark parallelism: If spark.sql.files.maxPartitionBytes is too large, few tasks read lots of data each (under-parallelized). If too small, too many tasks with S3 overhead dominate. Default 128MB is usually good.

Step 6 — Check output committer: Ensure you're using EMRFS S3-optimized committer (algorithm v2 or EMR's proprietary committer) rather than v1 which does expensive rename operations on S3.

When would you choose EMR Serverless over EMR on EC2? What are the limitations?

Choose EMR Serverless when: (1) Team lacks Hadoop/EMR operational expertise. (2) Workloads are sporadic — don't want idle cluster costs. (3) Jobs are pure Spark/Hive/Presto with S3 I/O (no HDFS, HBase). (4) You want per-job cost isolation without managing cluster sharing. (5) Dev/test environments where fast iteration matters more than fine-tuned performance.

Limitations: (1) No HDFS — all data must live in S3. (2) No persistent state between jobs (no shared Spark cache, no HBase). (3) Max vCPU caps per application (4000 default). (4) Cold start latency of 30–60s without pre-initialized capacity. (5) Less Spark tuning control — can't set certain JVM flags or use custom YARN configs. (6) No SSH access for debugging — rely entirely on S3 logs. (7) Higher per-vCPU-hour cost vs well-utilized On-Demand EC2 ($0.052/vCPU-hr Serverless vs ~$0.034/vCPU-hr m5.xlarge).

Bottom line: EMR Serverless trades fine-grained control and cost efficiency (at steady-state) for operational simplicity and elasticity. It's not cheaper for 24/7 workloads but wins on total cost for bursty/variable patterns when you factor in idle cluster waste.

Design a cost-optimized EMR architecture for a data platform running 50 daily batch jobs of varying sizes (1GB to 5TB input).

Architecture: Hybrid approach using transient clusters + EMR Serverless based on job size.

Small jobs (input < 50GB, ~35 jobs): Route to EMR Serverless. No cluster overhead, fast start, pay-per-use. These finish in minutes and the Serverless premium is offset by zero idle time.

Large jobs (input > 50GB, ~15 jobs): Group into 3–4 transient EMR clusters by schedule window. Use Instance Fleets with capacity-optimized Spot for task nodes (80% Spot, 20% On-Demand baseline). Graviton instances (m6g, r6g) for 25% savings.

Orchestration: Airflow/Step Functions dispatches jobs to Serverless or creates transient clusters based on estimated input size (from Glue Catalog table stats).

Shared components: Single Glue Data Catalog for metadata. S3 for all storage. CloudWatch dashboards per job for cost attribution.

Expected savings vs persistent cluster: 40–60% — eliminating 8–12 hours of daily idle time on a persistent cluster that's only busy during batch windows.
