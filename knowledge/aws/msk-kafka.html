MSK Architecture

Amazon MSK is a fully managed Apache Kafka service. Understanding what AWS manages vs what you control is essential:

What MSK Manages

  • Broker provisioning: EC2 instances in your VPC, deployed across AZs (2 or 3 AZ deployments).
  • ZooKeeper/KRaft: ZooKeeper ensemble for metadata (legacy clusters). KRaft mode (Kafka 3.7+) eliminates ZooKeeper — metadata managed by brokers themselves.
  • Storage: EBS volumes attached to brokers. Auto-scaling storage supported (grows automatically, never shrinks).
  • Patching: OS and Kafka version upgrades (initiated by you, executed by MSK with rolling restarts).
  • Monitoring: CloudWatch metrics, Prometheus-compatible JMX export, broker logs to CloudWatch/S3/Firehose.

What You Manage

  • Topic creation and configuration: Partition count, replication factor, retention, cleanup policies.
  • Producer/Consumer applications: Your code, deployed on EC2/ECS/EKS/Lambda.
  • Capacity planning: Choosing broker count and instance types. MSK won't auto-scale brokers (only storage).
  • Networking: VPC, subnets, security groups. Clients must be in the same VPC or connected via peering/PrivateLink.

Multi-AZ Deployment

  • 3-AZ (recommended): Brokers distributed across 3 AZs. With replication.factor=3 and min.insync.replicas=2, survives entire AZ failure without data loss.
  • 2-AZ: Lower cost but higher risk. AZ failure takes out ~50% of brokers. Recovery requires replication from surviving brokers.
Key insight: MSK is "managed Kafka" — not "serverless Kafka." You still choose broker count, instance types, and storage. Think of it as EC2 Auto-Scaling for Kafka with AWS handling the undifferentiated ops (patching, monitoring, ZK management). For true serverless, use MSK Serverless.

Broker Configuration

Instance Type Selection

  • kafka.m5.large: 2 vCPU, 8 GB. Entry-level — good for dev/test. ~100 MB/s network.
  • kafka.m5.xlarge: 4 vCPU, 16 GB. Production minimum. ~200 MB/s throughput per broker.
  • kafka.m5.2xlarge: 8 vCPU, 32 GB. High-throughput production. ~400 MB/s per broker.
  • kafka.m7g.xlarge: Graviton3 — 20% better price-performance than m5.

Storage Configuration

  • EBS gp3: Default. 3000 IOPS baseline, burstable. Good for most workloads.
  • EBS provisioned IOPS (io2): For latency-sensitive workloads needing consistent <5ms writes.
  • Auto-scaling: Storage grows automatically when utilization exceeds threshold. Set Maximum Storage as cost guardrail. Storage never shrinks — over-provisioning is wasted.
  • Sizing rule: Storage = (daily_ingest_bytes × retention_days × replication_factor) / broker_count + 20% headroom.

Topic Design

Partition Count

  • Formula: partitions ≥ max(target_throughput / per_partition_throughput, consumer_count).
  • Per-partition throughput: ~10 MB/s write, ~30 MB/s read (empirical on m5.xlarge brokers with gp3).
  • Example: 200 MB/s target write → need at least 20 partitions. 50 concurrent consumers → need at least 50 partitions.
  • Guideline: Start with 12–24 partitions for most topics. High-volume topics: 48–128. Don't go over 200 per topic without good reason (metadata overhead).
  • Can't reduce: Partition count can only increase. Plan for 2–3x growth. Over-partitioning at creation is safer than under-partitioning.

Replication Factor

  • Production: Always 3 (survives 1 broker failure without data loss when min.insync.replicas=2).
  • Dev/Test: 2 acceptable (or even 1 for ephemeral topics).
  • Cost: RF=3 means 3x storage usage. Factor into capacity planning.

Retention

  • Time-based: retention.ms — how long messages are kept. Common: 7 days (168h) for operational topics, 30 days for analytics, infinite for event sourcing.
  • Size-based: retention.bytes — max bytes per partition before oldest segments are deleted. Use as a safety cap.
  • Compacted topics: cleanup.policy=compact — keeps only the latest value per key. Ideal for changelogs, state stores, configuration topics.

Producer Patterns

Acknowledgment Levels

  • acks=0: Fire and forget. Highest throughput, data loss possible. Use for: metrics/logs where occasional loss is acceptable.
  • acks=1: Leader acknowledges. Balanced throughput/durability. Loss possible if leader fails before replication.
  • acks=all (acks=-1): All in-sync replicas acknowledge. Strongest durability guarantee. Required for exactly-once semantics.

Batching and Compression

High-Throughput Producer Configuration
# Producer config for maximum throughput
bootstrap.servers=broker1:9092,broker2:9092,broker3:9092
acks=all
retries=2147483647
max.in.flight.requests.per.connection=5
enable.idempotence=true

# Batching — accumulate messages before sending
batch.size=65536          # 64 KB batch
linger.ms=20              # Wait up to 20ms to fill batch
buffer.memory=67108864    # 64 MB total buffer

# Compression — reduce network/storage
compression.type=lz4      # Best throughput/ratio tradeoff
# Options: none, gzip (best ratio), snappy (fast), lz4 (fastest), zstd (balanced)

# Idempotent producer — prevents duplicates on retry
enable.idempotence=true   # Requires acks=all + retries > 0
max.in.flight.requests.per.connection=5  # Max for idempotent (ordering preserved)

Exactly-Once Semantics (EOS)

  • Idempotent producer: Each message gets a sequence number. Broker deduplicates retries. Prevents duplicates within a single session.
  • Transactional producer: Atomic writes across multiple partitions/topics. Either all messages in a transaction commit, or none do.
  • Requirements: enable.idempotence=true, transactional.id=unique-id, acks=all.
  • Consumer side: isolation.level=read_committed — consumers only see committed transactional messages.

Consumer Patterns

Consumer Groups

  • Each partition is consumed by exactly ONE consumer in a group — guarantees ordering per partition.
  • Parallelism = min(partition_count, consumer_count): Extra consumers beyond partition count sit idle.
  • Multiple consumer groups on the same topic get independent copies of all messages — enables fan-out pattern.

Offset Management

  • Auto-commit (enable.auto.commit=true): Offsets committed every auto.commit.interval.ms. Risk: crash between commit and processing = skipped messages.
  • Manual commit: Call commitSync() or commitAsync() AFTER processing. Guarantees at-least-once delivery.
  • Exactly-once: Use transactional consumer pattern — commit offsets and produce results in the same transaction.

Rebalancing

  • Trigger: Consumer joins/leaves group, heartbeat timeout, or partition count change.
  • Stop-the-world (eager): All consumers stop, all partitions reassigned. Causes latency spike.
  • Cooperative (incremental): Only affected partitions reassigned. Set partition.assignment.strategy=CooperativeStickyAssignor — minimizes disruption.
Robust Consumer Configuration
# Consumer config for reliable processing
bootstrap.servers=broker1:9092,broker2:9092,broker3:9092
group.id=order-processing-group
auto.offset.reset=earliest          # Start from beginning if no committed offset
enable.auto.commit=false            # Manual commit for at-least-once
max.poll.records=500                # Process in manageable batches
max.poll.interval.ms=300000         # 5 min max processing time per poll
session.timeout.ms=45000            # Heartbeat timeout (detect dead consumers)
heartbeat.interval.ms=15000         # 1/3 of session timeout
fetch.min.bytes=1048576             # 1 MB min fetch (reduce round trips)
fetch.max.wait.ms=500               # Wait up to 500ms for min.bytes
partition.assignment.strategy=org.apache.kafka.clients.consumer.CooperativeStickyAssignor
isolation.level=read_committed      # Only read committed transactional messages
max.poll.interval.ms pitfall: If your consumer's processing time exceeds this value (default 5 min), the broker considers it dead and triggers a rebalance. The consumer loses its partitions, processes duplicate messages, and creates a death spiral. Fix: either increase the interval, decrease max.poll.records, or move heavy processing to a thread pool and commit offsets synchronously.

MSK Connect

Managed Kafka Connect — run source/sink connectors without managing Connect clusters:

  • Source connectors: Pull data into Kafka (e.g., Debezium for CDC from databases, S3 source).
  • Sink connectors: Push Kafka data to external systems (S3 sink, Elasticsearch, JDBC, Redshift).
  • Scaling: Auto-scales workers (MCU = MSK Connect Unit) based on throughput. Min 1, max configurable.
  • Plugin management: Upload connector JARs to S3. MSK Connect deploys them to workers.

Glue Schema Registry

  • Purpose: Centralized schema management for Kafka messages. Enforces compatibility on schema evolution.
  • Formats: Avro, JSON Schema, Protobuf.
  • Compatibility modes: BACKWARD (new schema can read old data), FORWARD (old schema can read new data), FULL (both), NONE (no checks).
  • Integration: Producer serializes message with schema ID. Consumer deserializes using schema from registry. Schema stored in Glue — no separate Confluent Schema Registry needed.
  • Cost advantage: Glue Schema Registry is free (no per-API-call charges). Confluent Schema Registry on MSK requires a running Connect cluster or self-managed service.
Producer with Glue Schema Registry (Java)
Properties props = new Properties();
props.put("bootstrap.servers", "broker1:9092,broker2:9092");
props.put("key.serializer", "org.apache.kafka.common.serialization.StringSerializer");

props.put("region", "us-east-1");

props.put("schemaName", "clickstream-event-v1");
props.put("dataFormat", "AVRO");
props.put("compatibility", "BACKWARD");

Security

Authentication Methods

  • IAM Auth (recommended for AWS-native): Clients authenticate using IAM credentials. No separate user management. Integrates with IAM policies for authorization. Set SASL/OAUTHBEARER mechanism with AWS IAM handler.
  • mTLS: Mutual TLS with client certificates. Best for cross-platform/multi-cloud clients. Requires ACM PCA (Private Certificate Authority).
  • SASL/SCRAM: Username/password stored in AWS Secrets Manager. Simple but requires secret rotation management.
  • Unauthenticated: PLAINTEXT — never for production. Only for dev within private VPC.

Authorization

  • IAM policies: When using IAM auth, IAM policies control which topics a principal can produce/consume. Granular: per-topic, per-consumer-group, per-cluster action.
  • Kafka ACLs: For mTLS/SCRAM auth — traditional Kafka ACL model. Manage via kafka-acls.sh.

Partition Rebalancing for Hot Partitions

  • Problem: If message key distribution is skewed, some partitions get 10x more traffic (hot partitions) — overloading their leader broker.
  • Detection: Monitor per-partition byte rate. If one partition has 5x the average, it's hot.
  • Solutions: (1) Use a composite key (add random suffix for high-volume keys). (2) Increase partitions to spread load further. (3) Use custom partitioner that distributes hot keys across multiple partitions.

Interview Questions

Explain exactly-once semantics (EOS) in Kafka end-to-end. What are the requirements and performance trade-offs?

End-to-end EOS requires three components:

1. Idempotent producer: Each producer instance gets a PID (producer ID). Each message gets a monotonically increasing sequence number. If a retry delivers a duplicate (same PID + seq), the broker silently drops it. This prevents producer-side duplicates.

2. Transactional writes: Producer wraps multiple writes in a transaction (beginTransaction(), send() × N, commitTransaction()). All messages atomically appear or none do. Transaction state is stored in __transaction_state internal topic. Requires: transactional.id configured (survives producer restarts), acks=all.

3. Transactional consumer: Set isolation.level=read_committed. Consumer only sees messages from committed transactions. Messages from aborted/in-progress transactions are invisible. Consumer offsets are committed within the same transaction as the output (consume-transform-produce pattern).

Performance trade-offs: (1) ~3-5% throughput reduction from idempotence (extra metadata per batch). (2) ~20-30% latency increase from transactions (2-phase commit overhead). (3) max.in.flight.requests.per.connection limited to 5 (ordering guarantee). (4) Transaction timeout adds end-to-end latency (messages invisible until commit). (5) More work for brokers: maintaining PID/seq mapping, transaction coordinator overhead.

When to use: Financial transactions, order processing, billing events — where duplicates have business impact. When to skip: Metrics, logs, clickstream — where at-least-once + downstream deduplication (idempotent writes to DB) is simpler and faster.

Your Kafka consumers are experiencing increasing lag despite adding more consumer instances. Diagnose and fix.

Diagnosis 1 — Partition count bottleneck: If consumer instances > partition count, extra consumers sit idle. Check: kafka-consumer-groups.sh --describe — if some consumers have 0 assigned partitions, you need more partitions. Fix: increase topic partitions (requires producer restart for new partition distribution).

Diagnosis 2 — Rebalancing storm: Frequent rebalances cause consumers to stop-the-world. Check: consumer logs for "Revoking partitions" messages. Causes: consumers exceeding max.poll.interval.ms, frequent deploys without graceful shutdown. Fix: increase max.poll.interval.ms, reduce max.poll.records, use CooperativeStickyAssignor, implement graceful shutdown (consumer.close()).

Diagnosis 3 — Slow processing: Each poll takes too long (blocking DB calls, slow external APIs). Check: time between polls vs max.poll.interval.ms. Fix: (a) Decouple processing — poll into in-memory buffer, process in thread pool, commit offsets after buffer drains. (b) Reduce max.poll.records for smaller batches. (c) Move heavy processing to async (publish to another topic for a processing tier).

Diagnosis 4 — GC pressure: Large max.poll.records + heavy deserialization causes long GC pauses → heartbeat timeout → rebalance → repeat. Fix: tune JVM heap, reduce poll size, use more consumer instances with less memory each.

Diagnosis 5 — Fetch throughput: Consumer network is saturated. Check: fetch-size-avg metric at max. Fix: increase consumer instance count (parallelize network I/O), or use fetch.max.bytes to cap memory usage per fetch.

Design a Kafka topic strategy for a data platform ingesting events from 50 microservices.

Approach 1 — Topic per service: 50 topics (orders-events, payment-events, user-events, etc.). Pros: independent retention/partition tuning per service, clear ownership, easy to reason about. Cons: consumers reading "all events" must subscribe to 50 topics.

Approach 2 — Topic per domain: 8–10 topics grouped by business domain (commerce-events, user-lifecycle, payments, notifications). Pros: fewer topics to manage, natural consumer grouping. Cons: mixed SLAs within a topic (critical payment events in same topic as low-priority notifications).

Recommended hybrid: Domain topics for consumption + service-level routing via headers/key prefix. Each service publishes to its domain topic with a service header. Consumers filter on headers when they want service-specific data.

Topic naming convention: {domain}.{entity}.{event-type} — e.g., commerce.orders.created, commerce.orders.fulfilled, payments.transactions.completed.

Partition strategy: Key = entity ID (order_id, user_id). Ensures all events for an entity go to the same partition → ordering guaranteed per entity. Partition count: start with 24 per topic, scale based on throughput monitoring.

Schema strategy: Glue Schema Registry with BACKWARD compatibility per topic. Each service registers its schema. Consumers read latest schema — backward compatibility ensures old messages are still readable.

When would you choose MSK over Kinesis Data Streams for real-time data ingestion?

Choose MSK (Kafka) when: (1) Need true event ordering with arbitrary retention (Kinesis max 365 days, Kafka unlimited). (2) Require exactly-once semantics via transactions. (3) Team has Kafka expertise and existing Kafka tooling (Connect ecosystem, ksqlDB, Schema Registry). (4) Need replay from any offset (Kinesis only supports trim horizon or timestamp). (5) High partition count needed (Kinesis shards are more expensive to scale). (6) Complex stream processing with Kafka Streams/Flink requiring Kafka-specific features.

Choose Kinesis when: (1) Simple ingestion pipeline (stream → Lambda → DynamoDB/S3). (2) AWS-native integration priority (direct Firehose → S3/Redshift delivery without code). (3) Operational simplicity — no broker management, fully serverless scaling. (4) Low throughput (<10 MB/s) where MSK's minimum broker cost is overkill. (5) Team lacks Kafka operational expertise.

Cost comparison: Kinesis: ~$0.015/shard-hour + $0.014/million PUT. MSK: ~$0.21/broker-hour (kafka.m5.large) + storage. At high throughput (1 GB/s), MSK is significantly cheaper per-GB. At low throughput (<5 MB/s), Kinesis wins on cost because MSK has a minimum fixed cost of 3 brokers.

How do you handle schema evolution in a Kafka-based data platform without breaking consumers?

Strategy: Schema Registry + Compatibility Rules

1. Use Avro/Protobuf (not JSON): Binary formats with schema metadata. Schema ID embedded in each message header. Consumers deserialize using the exact schema the message was written with, then translate to their reader schema.

2. Set BACKWARD compatibility (default, recommended): New schema can read data written with old schema. This means: adding optional fields (with defaults) is safe, removing fields is safe, changing types is NOT safe. Consumers upgrade at their own pace — old messages always readable.

3. Breaking changes (major version): When backward-incompatible change is needed (rename field, change type): (a) Create a new topic (orders-v2). (b) Dual-write during migration (produce to both v1 and v2). (c) Migrate consumers one by one to v2. (d) Decommission v1 after all consumers migrated.

4. Glue Schema Registry integration: Register schemas per topic. Enable auto-registration on producers (schema discovered from serialized objects). Set compatibility mode at the registry level — rejects incompatible schema registrations at write time, not at runtime.

5. Consumer defensive coding: Always handle unknown fields gracefully (Avro ignores unknown fields by default). Never assume field presence without checking schema version. Use schema-aware deserialization that maps to internal DTOs rather than direct Avro GenericRecords.
