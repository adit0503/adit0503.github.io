S3 Performance Fundamentals

Request Rate Limits

  • Per-prefix limits: 5,500 GET/HEAD requests per second AND 3,500 PUT/COPY/POST/DELETE per second — per prefix.
  • Prefix definition: Everything between bucket name and object name. s3://bucket/year=2024/month=01/data.parquet → prefix is year=2024/month=01/.
  • No bucket-level limit: Total throughput scales with number of distinct prefixes. A bucket with 1000 prefixes can handle 5.5M GET/s total.
  • Throttling symptom: HTTP 503 SlowDown errors. S3 returns this when a prefix exceeds rate limits.

Prefix-Based Partitioning for Throughput

  • Anti-pattern: All files under one prefix (s3://bucket/data/) — bottlenecked at 5,500 GET/s.
  • Best practice: Spread across many prefixes using partition structure: s3://bucket/data/year=2024/month=01/day=15/hour=14/ — each hour is a separate prefix with its own 5,500 limit.
  • Hash prefixing (legacy): Adding random hex prefix (s3://bucket/a7f3/data/...) was needed before 2018. No longer necessary — S3 auto-indexes internally. Use logical partition structure instead.

Throughput Optimization

  • S3 Transfer Acceleration: Routes uploads through CloudFront edge locations for geographically distant clients. 50-500% improvement for cross-region uploads.
  • Byte-range fetches: Read specific byte ranges of a file in parallel. Enables parallel reads of different Parquet row groups from a single file. Critical for Spark/Athena performance.
  • Request parallelism: S3 performance scales linearly with request count (up to prefix limits). More threads = more throughput. Default Spark fs.s3a.threads.max=64 is often too low for large clusters — set to 200+.
Key insight: S3 is not a filesystem — it's an object store with flat namespace. The "/" in paths is purely cosmetic. Performance is determined by how S3 internally hashes and distributes objects across partitions. Each unique key prefix gets assigned to a partition with its own throughput quota.

Optimal File Sizes

The Small File Problem

  • Problem: Each S3 GET request has ~50-100ms latency overhead regardless of file size. Reading 10,000 × 1MB files = 10,000 requests × 100ms = 16+ minutes just in request overhead.
  • Versus: Reading 10 × 1GB files = 10 requests × 100ms = 1 second overhead. Same total data, 1000x less overhead.
  • Causes: Streaming micro-batch writes (Kafka sink every minute), over-partitioned tables, uncompacted insert-heavy tables.

Optimal Size Guidelines

Use CaseOptimal File SizeReasoning
Spark/EMR reads128 MB – 1 GBMaps well to Spark partition size; minimizes S3 overhead
Athena queries128 MB – 512 MBBalances parallelism with scan efficiency
Streaming ingestion target64 MB – 256 MBSlightly smaller for faster availability
Archive/cold storage256 MB – 5 GBLarger files = fewer objects = less lifecycle overhead

Compaction Strategies

Spark Compaction Job
# Compact small files into optimal size (128MB target)
from pyspark.sql import SparkSession

spark = SparkSession.builder \
    .config("spark.sql.files.maxPartitionBytes", "134217728") \
    .getOrCreate()

# Read all small files
df = spark.read.parquet("s3://datalake/events/year=2024/month=01/day=15/")

# Repartition to target file count
# total_size_bytes / target_file_size = target_partition_count
total_bytes = 10 * 1024 * 1024 * 1024  # 10 GB total
target_size = 128 * 1024 * 1024  # 128 MB target
target_partitions = max(1, total_bytes // target_size)  # ~80 partitions

df.repartition(target_partitions) \
  .write \
  .mode("overwrite") \
  .parquet("s3://datalake/events_compacted/year=2024/month=01/day=15/")

# For Delta/Iceberg tables, use built-in compaction:
# Delta: OPTIMIZE table_name WHERE date = '2024-01-15'
# Iceberg: CALL system.rewrite_data_files(table => 'db.events', 
#           strategy => 'binpack', options => map('target-file-size-bytes', '134217728'))

Intelligent-Tiering

  • Automatically moves objects between access tiers based on actual access patterns.
  • Tiers: Frequent Access → Infrequent (30 days no access) → Archive Instant (90 days) → Archive (optional, 90+ days) → Deep Archive (optional, 180+ days).
  • No retrieval fees for frequent and infrequent tiers. Small monitoring fee per object ($0.0025/1000 objects).
  • Best for: Data lakes where access patterns aren't predictable. Let AWS optimize instead of guessing with lifecycle rules.
Data lake pattern: Raw/landing zone → Standard (first 30 days, active processing). Curated/gold zone → Standard (always hot for queries). Historical partitions → Intelligent-Tiering (access patterns vary). Compliance/archive → Glacier Deep Archive (7-year retention, never queried unless audit).

Lifecycle Best Practices

  • Always add multipart abort rule: Incomplete multipart uploads consume storage but aren't visible in normal listings. They accumulate indefinitely without this rule.
  • Min duration charges: Transitioning a Standard-IA object before 30 days = you still pay for 30 days. Don't transition objects that might be deleted within the minimum.
  • Per-object overhead: Each transition/expiration rule is evaluated per-object. With billions of objects, lifecycle processing can take days to complete a full sweep.
  • Prefix filtering: Use specific prefixes to target rules. Avoid bucket-wide rules that affect temp/staging data unintentionally.

S3 Select

Push filtering and projection down to the S3 storage layer — S3 processes the query and returns only matching data, reducing data transfer by 80%+.

S3 Select — Query Pushdown
import boto3

s3 = boto3.client('s3')

# Query a single Parquet file — S3 does the filtering
response = s3.select_object_content(
    Bucket='datalake',
    Key='events/year=2024/month=01/day=15/part-00001.parquet',
    ExpressionType='SQL',
    Expression="SELECT event_id, amount FROM s3object WHERE amount > 1000 AND event_type = 'purchase'",
    InputSerialization={
        'Parquet': {}
    },
    OutputSerialization={
        'JSON': {}
    }
)

# Process streaming results
for event in response['Payload']:
    if 'Records' in event:
        print(event['Records']['Payload'].decode('utf-8'))

# Use cases:
# - Filter large CSV/JSON files before loading into application
# - Extract specific columns from Parquet without downloading entire file
# - Pre-filter data for Lambda processing (avoid 10GB Lambda /tmp limit)
  • Supported formats: CSV, JSON, Parquet.
  • SQL support: SELECT, WHERE (=, >, <, LIKE, BETWEEN, IN), aggregate functions (COUNT, SUM, AVG, MIN, MAX).
  • Cost: $0.002 per GB scanned + $0.0007 per GB returned. Cheaper than downloading full files if you filter out >60% of data.
  • Limitation: Operates on SINGLE files. Cannot query across files (use Athena for multi-file queries). No JOIN support.

S3 Inventory

  • Purpose: Scheduled report of all objects in a bucket — alternative to expensive LIST operations.
  • Output: CSV, ORC, or Parquet file listing all objects with metadata (size, storage class, encryption status, replication status, last modified).
  • Frequency: Daily or weekly delivery to a destination bucket.
  • Use cases: (1) Audit storage class distribution. (2) Find unencrypted objects. (3) Identify old/orphaned files. (4) Calculate per-prefix storage costs. (5) Input for data catalog reconciliation.
Query S3 Inventory with Athena
-- Create table over S3 inventory output
CREATE EXTERNAL TABLE s3_inventory (
    bucket STRING,
    key STRING,
    size BIGINT,
    last_modified_date TIMESTAMP,
    storage_class STRING,
    is_multipart_uploaded BOOLEAN,
    encryption_status STRING
)
STORED AS ORC
LOCATION 's3://inventory-bucket/datalake-inventory/data/';

-- Find small files (compaction candidates)
SELECT 
    regexp_extract(key, '^([^/]+/[^/]+/[^/]+/)', 1) as prefix,
    count(*) as file_count,
    sum(size) as total_bytes,
    avg(size) as avg_file_size
FROM s3_inventory
WHERE size < 1048576  -- Files under 1MB
GROUP BY regexp_extract(key, '^([^/]+/[^/]+/[^/]+/)', 1)
HAVING count(*) > 1000
ORDER BY file_count DESC;

-- Find storage cost distribution
SELECT storage_class, 
       count(*) as object_count,
       sum(size) / 1073741824.0 as total_gb
FROM s3_inventory
GROUP BY storage_class;

Versioning & Object Lock

Versioning

  • Every overwrite/delete creates a new version — previous versions remain accessible.
  • Data lake protection: Accidental overwrites of Parquet files are recoverable. Critical for tables without Delta/Iceberg transaction logs.
  • Cost impact: All versions consume storage. A table rewritten 5 times has 5x storage cost without lifecycle rules on noncurrent versions.
  • Delete markers: DELETE on a versioned object adds a "delete marker" — object appears deleted but all versions remain. Must delete specific version IDs to truly remove data.

Object Lock

  • WORM (Write-Once-Read-Many): Prevents object deletion or overwrite for a retention period.
  • Governance mode: Root user can bypass lock. For internal compliance.
  • Compliance mode: Nobody can delete — not even root. For regulatory requirements (SEC, HIPAA).
  • Legal hold: Indefinite lock until explicitly removed. For litigation preservation.

Multipart Upload

  • Required for: Files > 5 GB. Recommended for files > 100 MB.
  • How it works: Split file into parts (5 MB – 5 GB each), upload parts in parallel, complete multipart to assemble final object.
  • Benefits: Parallel upload (saturate network bandwidth), resume on failure (retry only failed parts), begin upload before total size is known (streaming).
  • Part size selection: Larger parts = fewer S3 API calls but more data to retry on failure. 64-128 MB per part is common for large files.
  • Cleanup: Always configure lifecycle rule to abort incomplete multipart uploads. Orphaned parts are invisible but billable.
Multipart Upload with boto3
import boto3
from boto3.s3.transfer import TransferConfig

s3 = boto3.client('s3')

# Configure multipart thresholds
config = TransferConfig(
    multipart_threshold=100 * 1024 * 1024,  # 100 MB — use multipart above this
    max_concurrency=10,                       # 10 parallel part uploads
    multipart_chunksize=64 * 1024 * 1024,    # 64 MB per part
    use_threads=True
)

# Upload large file with multipart
s3.upload_file(
    Filename='/data/large_export.parquet',
    Bucket='datalake',
    Key='exports/2024/01/15/large_export.parquet',
    Config=config,
    ExtraArgs={
        'ServerSideEncryption': 'aws:kms',
        'StorageClass': 'STANDARD_IA'
    }
)

S3 Event Notifications

Trigger actions when objects are created, deleted, or modified — foundation for event-driven data pipelines:

  • Targets: Lambda, SQS, SNS, EventBridge (recommended for flexibility).
  • Event types: s3:ObjectCreated:*, s3:ObjectRemoved:*, s3:ObjectRestore:*.
  • Prefix/suffix filters: Trigger only for specific paths or file extensions. prefix: raw/events/, suffix: .parquet.
Event-Driven Pipeline (EventBridge + Step Functions)
# EventBridge rule: trigger when Parquet files land in raw zone
{
  "source": ["aws.s3"],
  "detail-type": ["Object Created"],
  "detail": {
    "bucket": {"name": ["datalake-raw"]},
    "object": {"key": [{"prefix": "events/"}]},
    "reason": ["PutObject", "CompleteMultipartUpload"]
  }
}

# Step Function triggered by EventBridge:
# 1. Wait for batch accumulation (5 min timer or file count threshold)
# 2. Start Glue job with paths of new files as input
# 3. On success: register new partitions in Catalog
# 4. On failure: send alert, retry with exponential backoff
Duplicate notifications: S3 event notifications are delivered at-least-once. Your downstream processing must be idempotent — the same notification may arrive twice. Design pipelines to safely re-process the same file without creating duplicates.

S3 Access Points

  • Purpose: Named network endpoints with individual access policies. Simplifies managing access to shared buckets with many teams/applications.
  • Instead of: One monolithic bucket policy with 100+ statements (one per team/prefix combination).
  • Each access point has: Its own DNS name, its own IAM policy (independent of bucket policy), optional VPC restriction (limit to specific VPC).
  • Use case: Data lake with 10 teams — create 10 access points, each restricting to the team's prefix. Teams reference their access point ARN, never the bucket directly.
  • Limit: 10,000 access points per account per region.

Cost Optimization Strategies

Storage Cost Reduction

  • Compression: ZSTD/Snappy compressed Parquet = 3-5x smaller than uncompressed. Direct cost reduction.
  • Lifecycle tiering: Move data to cheaper tiers based on access patterns. 90% of data lake storage should be IA or colder.
  • Delete test/temp data: Set aggressive expiration on temporary paths (tmp/, staging/, _spark_metadata/).
  • Version cleanup: Expire noncurrent versions after 30-90 days unless compliance requires longer.
  • Incomplete multipart cleanup: Can account for 5-15% of storage costs in active buckets.

Request Cost Reduction

  • Consolidate small files: 10,000 GET requests ($0.004/1000 = $0.04) for 10K small files vs 10 GETs ($0.00004) for 10 large files. At scale: millions of requests/day = significant savings.
  • Avoid unnecessary LIST operations: Use Glue Catalog/Delta log instead of S3 LIST for file discovery. LIST is expensive ($0.005/1000 requests) and slow.
  • S3 Select for targeted reads: Transfer cost ($0.09/GB) dwarfs S3 Select cost ($0.002/GB scanned) when filtering 80%+ of data.

Transfer Cost Reduction

  • Same-region access: S3 → EC2/Lambda in the same region = $0 transfer. Cross-region = $0.02/GB. Always co-locate compute with storage.
  • VPC endpoints: Gateway endpoints for S3 = $0 transfer (no NAT gateway charges). Interface endpoints have per-hour + per-GB charge.
  • Compression for transfer: Compress data before storage — reduces both storage cost AND transfer cost for reads.
Quick wins audit: Run S3 Storage Lens (free) to identify: (1) buckets with no lifecycle rules, (2) high incomplete multipart upload counts, (3) objects never accessed for 90+ days in Standard class, (4) buckets with versioning but no noncurrent version expiration. Fixing these typically saves 20-40% on S3 costs.

Interview Questions

Your data lake on S3 has grown to 500 TB and costs $11,500/month in storage alone. How do you reduce costs by 50%?

Step 1 — Audit with S3 Inventory + Storage Lens: Identify storage distribution by prefix, age, and access pattern. Typically: 60-70% of data is >90 days old and rarely accessed.

Step 2 — Lifecycle tiering (biggest impact): Move data older than 30 days to Standard-IA ($0.0125 vs $0.023 = 46% savings). Move data older than 90 days to Glacier Instant Retrieval ($0.004 = 83% savings). Raw/bronze data older than 1 year → Glacier Deep Archive ($0.00099 = 96% savings).

Step 3 — Intelligent-Tiering for curated zone: Instead of guessing access patterns, let S3 auto-tier the curated/gold zone. No retrieval fees for frequent/infrequent access.

Step 4 — Compression audit: Check if all Parquet data uses ZSTD compression (5-7x ratio vs uncompressed). Re-write uncompressed or Snappy-compressed data with ZSTD — could save 30-50% on already-Parquet data.

Step 5 — Delete waste: Orphaned files (not in any table catalog), incomplete multipart uploads, old noncurrent versions, temporary/staging paths. Typically 5-10% of total storage.

Expected result: Lifecycle tiering alone takes 350 TB of old data from $0.023 to ~$0.006 average = saves ~$6,000/month. Combined with compression and cleanup: 50%+ reduction achievable.

Explain the "small file problem" in a data lake and how you would detect and fix it at scale.

The problem: Thousands of files under 1-5 MB per partition. Each file requires a separate S3 GET request (50-100ms latency), Spark task scheduling overhead, and metadata tracking. A partition with 50,000 × 1MB files takes 100x longer to read than 50 × 1GB files — same data, dramatically worse performance.

Common causes: (1) Spark Structured Streaming writing micro-batches every 10s without compaction. (2) Kafka Connect sinks with small flush intervals. (3) DMS CDC writing one file per batch (100 records). (4) Over-partitioned tables (partition per hour × customer = millions of tiny partitions). (5) INSERT INTO appending without repartition.

Detection at scale: (1) S3 Inventory → Athena query to find prefixes with avg_file_size < 10MB AND file_count > 1000. (2) Glue Catalog stats: check averageRecordSize × recordCount / fileCount per partition. (3) Custom monitoring: Lambda triggered daily that scans inventory report and flags problematic tables.

Fix at scale: (1) For Delta/Iceberg tables: scheduled OPTIMIZE/rewrite_data_files targeting partitions with small files. (2) For Hive tables: Spark compaction job (repartition + overwrite). (3) Prevention: set minimum file sizes in streaming sinks (Kafka Connect flush.size=100000), use Spark coalesce() before write, choose appropriate partition granularity. (4) Automated: EventBridge + Lambda that monitors file counts per partition and triggers compaction jobs when thresholds are exceeded.

Design a storage strategy for a multi-tenant data platform on S3 with cost isolation per tenant.

Architecture option 1 — Bucket per tenant: Each tenant gets a dedicated bucket. Pros: natural cost isolation (S3 cost allocation tags per bucket), simple IAM boundaries, independent lifecycle policies. Cons: doesn't scale beyond ~100 tenants (operational overhead), cross-tenant queries require federation.

Architecture option 2 — Shared bucket with prefix isolation (recommended): One bucket with prefix per tenant: s3://platform/tenant={tenant_id}/table/partition/. Use S3 Access Points per tenant for policy isolation. Cost allocation via S3 Storage Lens with prefix-level breakdown.

Cost tracking: (1) S3 Storage Lens: Configure prefix-level metrics aggregated daily. Dashboard shows GB per tenant, request counts per tenant. (2) S3 Inventory + Athena: Monthly job calculates exact storage per tenant-prefix, multiplied by storage class rates. (3) Cost allocation tags: Tag objects with tenant ID at write time (requires producer cooperation). Use Cost Explorer tag-based reports.

Access control: S3 Access Points with policy restricting each tenant's IAM role to their prefix only. Lake Formation on top for table/column-level governance. VPC endpoint policies restrict which access points are reachable from which VPCs.

Performance isolation: Tenant prefixes naturally distribute S3 request limits (each prefix gets 5,500 GET/s). Heavy-usage tenants don't starve others because they hit different S3 internal partitions.

When would you use S3 Intelligent-Tiering vs manual lifecycle rules? What are the cost tradeoffs?

Intelligent-Tiering (IT) advantages: (1) No retrieval fees when objects move back to frequent access (lifecycle transition FROM IA back to Standard would require re-uploading). (2) Automatic — no guesswork about access patterns. (3) Objects that become "hot" again auto-promote. (4) No minimum storage duration charges (unlike Standard-IA's 30-day minimum).

IT cost: $0.0025 per 1,000 objects/month monitoring fee. For objects <128KB, monitoring fee > savings from tiering. So IT has a break-even point around object count and size.

Use IT when: Access patterns are unpredictable (ad-hoc analytics, user-generated data). Objects may be accessed again after periods of inactivity. You have relatively few, large objects (monitoring fee is negligible relative to storage savings).

Use manual lifecycle when: Access patterns are predictable (time-based: "data older than 30 days is never queried directly"). You have millions of small objects (monitoring fee adds up). You want to move to Glacier tiers (IT's Deep Archive access tier requires 180-day inactivity — may be slower than a lifecycle rule).

Hybrid approach: Use IT for curated/gold zone (unpredictable access). Use lifecycle rules for raw/bronze (predictable: always old = cold) and archive/compliance (always move to Deep Archive after X days).
