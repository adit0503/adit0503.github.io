Software-Defined Assets

An asset is a durable object (table, file, ML model) with an AssetKey (namespace + name, e.g. ["silver", "events"]). @asset declares how to compute it and which assets it depends on via function arguments that Dagster matches by name/key.

Dependencies are function args
from dagster import asset, AssetKey, Output, MetadataValue

@asset(key_prefix=["bronze"])
def events_raw(context):
    path = ingest_to_s3(context.partition_key)
    return Output(path, metadata={"rows": MetadataValue.int(10_000)})

@asset(key_prefix=["silver"])
def events_clean(events_raw):
    # events_raw is loaded by the IO manager, not by Airflow XCom
    return transform(events_raw)

The asset graph is extracted at definition load: edges from inferred deps, explicit ins={}, non_argument_deps / deps, or AssetSpec for external assets you observe but do not compute.

IO Managers — The Real Data Plane Hook

When a step succeeds, the IO manager handle_output persists the in-memory object. Downstream load_input hydrates it. This is Dagster's answer to XCom: the pointer and bytes live in your store (Snowflake table, Delta path, S3 pickle — pick deliberately).

  • Filesystem / pickle IO manager — fine locally; on K8s, ephemeral disks mean downstream runs cannot load inputs unless the same volume is shared (it will not be). Use blob storage.
  • Snowflake / BigQuery IO managers — the "object" is often a table name / partition; the manager issues COPY or CREATE TABLE AS. Memory never holds the dataset.
  • UPath / S3 — store parquet at a deterministic path including partition key.

Type-based dispatch: you can register handlers so pd.DataFrame writes parquet and str writes a path. Returning a 20GB DataFrame from @asset still materializes RAM on the run worker — same anti-pattern as fat Airflow tasks. Return handles (paths, table ids) or run Spark outside the worker (Pipes, SparkResource, job submit).

Partitions

  • TimeWindowPartitionsDefinition — hourly/daily; partition key like 2026-08-22
  • StaticPartitionsDefinition — finite set (regions, tenants)
  • MultiPartitionsDefinition — cartesian product (date × org_id)
  • DynamicPartitionsDefinition — keys added at runtime (new customers); daemon/UI must register keys before materializing

A materialization is per (asset_key, partition_key). Downstream assets can have different partitions; you declare partition mapping (identity, time-window, last partition, all-to-one). Wrong mappings are the #1 silent correctness bug: daily downstream reading only one hourly parent partition.

Backfills submit many runs or one run with a partition subset depending on config. The backfill daemon rate-limits. For lakehouse tables, make the asset idempotent (INSERT OVERWRITE partition, Iceberg overwrite partitions) so retries do not duplicate.

Freshness, Automation, Checks

Declarative automation (auto-materialize policies / AutomationCondition in current Dagster) evaluates whether an asset is stale:

  • parent materialization newer than child
  • missing partition
  • freshness policy (e.g. "this table should be < 6 hours old")
  • max materializations per minute (anti-thundering-herd)

This is closer to a build system (make/ninja) than Airflow's timetable. You still need to cap parallelism via run queues and warehouse pools.

Asset checks are first-class: severity, blocking vs non-blocking, executed as steps. Failed checks can prevent downstream automation from considering the asset "good." This is data quality in the orchestrator, not a bolted-on PythonOperator.

External Assets & Observations

Not everything is computed by Dagster. An Fivetran table can be an external asset. A sensor or a warehouse query emits AssetObservation / materialization events so the graph knows "this landed." Downstream native assets then auto-materialize. This is the clean integration with Airflow: Airflow (or a CDC tool) reports an event; Dagster owns the silver/gold graph — or the reverse.

Lineage You Get for Free

Because deps are the asset graph, the UI lineage is the computation graph. It is not Magic column-level lineage from Snowflake's ACCESS_HISTORY — it is what you declared. Keep keys stable; renaming an asset without a migration orphans history.

Interview Questions

How do you model a 40TB lakehouse in Dagster without 40TB in RAM?

Assets return table identifiers or partition paths. IO managers run Spark/SQL. Run workers are small (submit + wait, or Dagster Pipes in the Spark driver). Partition by date/org. Automation conditions enqueue only stale partitions. Never pickle the lake through the IO manager.

Dynamic partitions vs mapping in Airflow?

Airflow mapping creates N TaskInstances in one DagRun from a list. Dagster dynamic partitions add keys to the catalog, then each key can be a separate materialization (often separate runs). Operationally Dagster backfill daemon + queued runs is closer to "many DagRuns" than "one DAG with map_index 0..N". Choose coarser keys; both systems die if you treat millions of files as first-class partition keys.
