Parse Time vs Run Time

DAG files are executed as Python at parse time, not only when a task runs. Anything at module scope runs on every processor heartbeat for that file.

  • Legal at parse time: constructing DAG / @dag objects, declaring tasks, reading cheap local config, using Variable.get with deserialize_json (still hits DB — avoid in a loop).
  • Illegal / expensive at parse time: Spark sessions, boto3 list-buckets, datetime.now() for business logic, querying warehouses, sleeping, downloading files.
Top-level code runs in the DAG processor
# BAD — processor blocks, DAG refresh lags
rows = warehouse.query("select * from huge_table")  # at import

# GOOD — inside the callable
@task
def extract(ds=None):
    rows = warehouse.query(f"select * from huge_table where dt = '{ds}'")
    return rows

DagBag imports the module, collects DAG objects from globals(), and the processor serializes them. A syntax error in one file is isolated to a subprocess; an infinite loop in a file can still starve that processor slot until dag_file_processor_timeout.

The Scheduling Loop

Simplified Airflow 2 scheduler inner loop (conceptual):

  1. Heartbeat the SchedulerJob row.
  2. Adopt orphaned TIs / detect zombies (TIs in running whose worker heartbeat expired).
  3. Create DagRuns whose timetable says the data interval is due (catchup, max_active_runs gated).
  4. For each active run, examine unfinished TIs: if upstreams succeeded (or skip-downstream logic), mark TI scheduled.
  5. Critical section: pick TIs that are scheduled, pool has slots, DAG/task concurrency not exceeded → set queued, send to executor.
  6. Executor reports back → TI moves running → success/failed/up_for_retry.
  7. Dataset/asset events may create additional DagRuns (data-aware scheduling).

parallelism (global queued+running cap), max_active_tasks_per_dag, pool slots, and executor capacity are all checked. Hitting any one of them looks like "Airflow is stuck" when TIs sit in scheduled.

TaskInstance State Machine

  • none — row exists but not yet scheduled this run
  • scheduled — dependencies met, waiting for a slot
  • queued — handed to executor, not yet started
  • running — worker called execute(); heartbeats tick
  • success / failed
  • up_for_retry — failed, retry remaining, wait retry_delay
  • up_for_reschedule — sensor/reschedule mode released the slot
  • deferred — triggerer owns the wait
  • removed — task disappeared from DAG on a mapped expansion change
  • upstream_failed / skipped — trigger rules

Trigger rules (all_success, all_done, one_failed, none_failed_min_one_success, …) are evaluated in the scheduler, not in the worker. That is why changing a trigger rule does not require the task code to change — only the DAG structure.

Data Interval, Logical Date, Catchup

Airflow 2.2+ models a run as a data interval [start, end) plus a logical date (formerly execution date). For a daily DAG at midnight UTC, the run covering 2026-08-22 data typically has logical date 2026-08-22 and interval that day. Templates:

  • {{ ds }} — logical date as YYYY-MM-DD
  • {{ data_interval_start }} / {{ data_interval_end }} — the actual interval (prefer these for partitioning)
  • {{ ts }} — ISO timestamp of logical date

catchup=True (historical default) creates one DagRun per missed interval since start_date. For a DAG added with a 3-year start_date that is a thundering herd. Production default should be catchup=False unless you intend backfill. Backfill is an explicit airflow dags backfill (or UI) with a date range — it still creates DagRuns and still consumes pool slots.

max_active_runs caps concurrent intervals of the same DAG. Without it, catchup + a slow task means hundreds of parallel runs fighting Spark queues.

Dataset / Asset Scheduling

Classic DAGs are time-table driven. Airflow 2.4+ Datasets (Airflow 3 Assets) let a DAG schedule on schedule=[Dataset("s3://bucket/silver/events")]. An upstream task declares outlets=[Dataset(...)]. On success, a dataset event is recorded; the scheduler starts a downstream DagRun when the schedule's dataset condition is satisfied (AND of listed datasets by default).

This is still orchestration-level lineage (task emitted an event), not column-level warehouse lineage. It decouples DAG files: no ExternalTaskSensor poking another DAG's TI state, no cross-DAG ID hardcoding beyond the URI.

Interview Questions

A task is stuck in scheduled. Walk the diagnosis.

Confirm upstreams are success/skipped per trigger rule. Then check pool slots (pool full), DAG max_active_tasks, global parallelism, executor queue depth, and whether the scheduler is alive (heartbeat). For mapped tasks, also check max_map_length and that expansion completed. Look at scheduler logs for "Not executing" / slot messages, not worker logs — the worker never saw the TI.

Why is using datetime.now() in a DAG file a backfill bug?

Parse time and task run time both become "now" instead of the run's data interval. Backfills reprocess historical intervals but the code loads today's partition. Use {{ ds }} / data_interval_start in templates or context["data_interval_start"] in callables. pendulum.now("UTC") at module scope is even worse — it bakes one timestamp into every parse.
