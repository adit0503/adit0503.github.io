Control Plane vs Data Plane

Airflow is an orchestrator, not a compute engine. The control plane (scheduler, webserver, triggerer, metadata DB) decides when tasks run and records state. The data plane (Spark, dbt, warehouses, Kubernetes pods) does the work. Putting GB-scale processing inside a PythonOperator is a category error — workers become your cluster, without Spark's shuffle, memory management, or isolation.

At the process level, a production Airflow 2.x/3.x deployment is several cooperating services that share one metadata database:

  • Scheduler — scheduling loop + (historically) DAG parsing. In 2.3+ parsing can be split to a dedicated DAG processor.
  • Webserver — Flask/FastAPI UI and REST API. Reads serialized DAGs from the DB; it should not import DAG files in production.
  • Triggerer — asyncio event loop that runs deferrable triggers (sensors that don't occupy a worker slot).
  • Workers — executor-specific processes that actually invoke execute() on operators.
  • Metadata DB — PostgreSQL (preferred) or MySQL. Source of truth for DAG runs, task instances, XCom, serialized DAGs, datasets/assets, slots.
🔑 Key insight:

Every scheduling decision is a database transaction. Throughput is bounded by row locks, connection pool size, and how fast the scheduler can SELECT runnable TIs — not by how many cores the worker has.

Component Internals

Scheduler job heartbeat

The scheduler registers a row in job (type SchedulerJob) and updates latest_heartbeat on an interval (scheduler_heartbeat_sec, default 5s). Other schedulers and the UI use this to detect a dead scheduler. If heartbeats stop, HA peers continue; if you run a single scheduler and it dies, nothing new is queued until it restarts.

DAG processor (Airflow 2.3+)

Parsing DAG files in the same process as the scheduling loop couples CPU-heavy Python imports with latency-sensitive SQL. The standalone DAG processor:

  • Walks dags_folder (and git-sync volume on K8s)
  • Spawns subprocesses per file (DagFileProcessorProcess) so a bad import cannot crash the parent
  • Writes SerializedDagModel + DagModel rows
  • Honors min_file_process_interval and dag_file_processor_timeout

Webserver and serialization

The UI never needs your DAG Python if serialization is on (default). It hydrates a lightweight DAG object from JSON stored in serialized_dag. That JSON includes task IDs, dependencies, operator class names, and UI fields — not closures, not open file handles. If a field is not serializable, the scheduler still runs the DAG but the UI may omit it.

Triggerer

Deferrable operators call self.defer(trigger=..., method_name=...). The worker process exits (frees the slot). The triggerer process runs the trigger's run() async generator, watching an external condition (Hive partition, HTTP, time). When the trigger fires, it writes an event; the scheduler creates a new TI in scheduled/queued and the worker resumes method_name (usually execute_complete).

Metadata Database as Source of Truth

Hot tables:

  • dag / dag_run — DAG identity, next run, run state, data interval
  • task_instance — one row per (dag_id, task_id, run_id) [+ map_index for mapped tasks]
  • task_instance_history — retries (Airflow 2.10+/3.x depending on version)
  • xcom — small payloads keyed by dag_id, task_id, run_id, key
  • slot_pool — named concurrency tokens
  • serialized_dag — JSON blob + hash for change detection
  • dataset / dataset_event (2.4+) or assets in 3.x — data-aware scheduling
  • trigger — parked deferrable work

The scheduler's critical section locks candidate TIs with SELECT … FOR UPDATE SKIP LOCKED (PostgreSQL) so two schedulers cannot queue the same TI. MySQL InnoDB works but PostgreSQL + PgBouncer is the production default at scale.

Operational knobs that actually matter
# parsing vs scheduling isolation
AIRFLOW__SCHEDULER__STANDALONE_DAG_PROCESSOR=True
AIRFLOW__SCHEDULER__MIN_FILE_PROCESS_INTERVAL=30
AIRFLOW__CORE__DAGBAG_IMPORT_TIMEOUT=30

# DB
AIRFLOW__DATABASE__SQL_ALCHEMY_POOL_SIZE=10
AIRFLOW__DATABASE__SQL_ALCHEMY_MAX_OVERFLOW=20
# put PgBouncer in transaction pooling in front of Postgres

# cleanup or the TI table becomes the outage
airflow db clean --clean-before-timestamp "$(date -d '90 days ago' -Iseconds)"

High Availability

  • Multiple schedulers — active-active. Coordination is DB locking, not ZooKeeper/etcd. More schedulers increase scheduling throughput and DB QPS. Past 2–3 schedulers you often need DB vertical scale first.
  • Multiple webservers — stateless behind a load balancer if they share the same fernet key, secret backend, and log storage.
  • Multiple triggerers — triggers are claimed via DB; extra triggerers add asyncio capacity.
  • Workers — scale horizontally with Celery or K8s. They are not HA of the control plane; they are capacity.

Fernet key rotation, secret_key for sessions, and identical AIRFLOW_HOME configs across replicas are the usual HA footguns — mismatched keys mean "tasks ran but XCom/variables decrypt as garbage."

Logging Path

Workers write task logs to local disk by default. The webserver then tries to proxy logs from the worker (Celery) or from the pod (K8s). In Kubernetes, pods die; logs must land on remote storage (s3, gcs, wasb log handlers) or you lose forensic data. Log filename includes try number; mapped tasks add map_index.

Configuration Model

airflow.cfg is overridden by environment variables of the form AIRFLOW__SECTION__KEY. Secrets should never live in cfg: use a secrets backend (AWS Secrets Manager, Vault, GCP Secret Manager). Connections are stored encrypted with the Fernet key in connection unless you use a secrets backend lookup (airflow/connections/my_conn).

Interview Questions

Why can the webserver show a DAG that the scheduler refuses to run?

Usually a parse-time vs serialize-time split. The processor wrote a serialized DAG, so the UI renders it, but the DAG is paused, import errors exist on a later parse, is_active is false, or the timetable cannot compute a next run (misconfigured schedule / schedule_interval). Check import_errors table and scheduler logs for the file processor, not the webserver.

What fails first when you have 2,000 DAGs and one Postgres?

Scheduler queries against task_instance (runnable TI selection) and DAG parsing CPU. Symptoms: scheduling lag, webserver timeouts on Browse → Task Instances, lock waits. Fixes: standalone DAG processor, raise min_file_process_interval, PgBouncer, db clean, fewer top-level imports, multiple schedulers only after the DB can take the extra QPS.
