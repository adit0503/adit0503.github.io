Airflow vs Dagster — Internals Comparison

State machines, backpressure, failure domains, testing, when to choose which, and safe interop without dual-writing tables.

Low-Level Implications

Where backpressure lives

Airflow: pools + parallelism + executor queue. You can cap "how many SnowflakeOperators run" without capping DAG count.

Dagster: queued runs + tags + (optionally) step executors. Asset automation can enqueue faster than you dequeue — always set max materializations / queue limits before enabling aggressive automation on a large graph.

Failure domains

Airflow scheduler down → no new TIs queued; running workers may finish. Dagster daemon down → no new ticks/automation; in-flight runs continue. Dagster code location down → that team's sensors/schedules stop; other locations continue. Airflow single DAG file poison → that file's parse fails; others continue.

Testing

Dagster: execute assets in-process with resources mocked; assert materialization events. Airflow: keep callables pure; use DagBag for structure tests; full runs need a test environment. Both fail equally if business logic lives only inside Spark submitted as a string.

When to Choose Which

  • Airflow — existing MWAA/Composer/Astro estate; 100s of vendor operators; ops team already runs Celery/K8s executors; you think in jobs and SLAs; you need deferrable wait-for-Hive-partition patterns that are already written.
  • Dagster — greenfield lakehouse where tables are the product; you want partition-aware freshness and catalog UI; multiple Python environments as code locations; testability is a hiring/quality requirement.
  • Both — Airflow (or vendor ingest) lands bronze and emits a dataset/event; Dagster owns silver/gold asset graph. Or reverse: Dagster materializes, Airflow triggers legacy Java jobs. Keep a single system as the source of truth for each table to avoid dual scheduling.
Do not dual-schedule the same table.

Two orchestrators writing the same Iceberg partition is a heisenbug factory. If you integrate, one side observes, the other writes.

Interop Patterns

  • Airflow DagsterOperator / GraphQL launch a Dagster job; poll run status with a deferrable trigger.
  • Dagster sensor watches Airflow REST API for DAG success, then RunRequest for downstream assets.
  • Shared contract: object store path + partition key + a completion marker (_SUCCESS) — boring and reliable.

Interview Questions

"We want lineage, so we must use Dagster." True?

Dagster gives you computational lineage of declared assets. Column-level and cross-tool lineage still need OpenLineage/Marquez, warehouse access history, or Spark listener integrations. Airflow 2.4+ datasets give coarse producer/consumer links. Pick Dagster for asset-centric DX; pick a lineage platform for organization-wide truth.

Migrate a 400-DAG Airflow deployment to Dagster in one quarter?

Usually no. Strangle: new data products as assets; leave stable Airflow DAGs; wrap the rest as jobs/ops only when you touch them. Rewrite cost is in business logic and backfill semantics (logical date vs partition key), not in YAML conversion. Prove IO managers and queued runs on one domain (e.g. Customer 360 gold) before moving ingestion.
