What an Executor Actually Does

An executor is a scheduler-side plugin implementing roughly: queue_command, heartbeat (adopt finished work), try_adopt_task_instances. It does not run Python operators in the scheduler process (except Sequential/Local debug cases). The scheduler serializes a command like airflow tasks run dag_id task_id run_id and the executor starts that command in some isolation boundary.

LocalExecutor & SequentialExecutor

  • SequentialExecutor — one task at a time in-process. Tests and tiny laptops. No parallelism.
  • LocalExecutor — multiprocessing pool on the scheduler machine. Fine for Composer-sized-small or a single VM. Shares the scheduler host's CPU/RAM; a memory leak in a task hurts scheduling. Not HA for workers (the host is a single point of capacity).

CeleryExecutor Internals

Architecture: scheduler → broker (Redis/RabbitMQ) → Celery workers → optional result backend.

  • Workers are long-lived processes with a preloaded Python environment (providers, custom operators).
  • Queues route tasks: queue="spark" vs queue="short". Workers subscribe with celery -A ... worker -Q spark.
  • Prefetch (worker_prefetch_multiplier) — a worker may reserve N tasks. Prefetch too high and a slow worker hoards work while idle workers starve. For heterogeneous task durations, set prefetch to 1.
  • acks_late — acknowledge after success so a killed worker redelivers. Required for at-least-once; your operators must be idempotent.
  • Broker persistence: Redis AOF/Rabbit durable queues. Losing the broker loses queued (not yet running) work; TIs stay queued until zombie/timeout logic resets them.
Celery vs K8s latency:

Celery task start is milliseconds (process already up). KubernetesExecutor pays pod schedule + image pull (often 15–60s). For 10-minute Spark submits that is noise; for 5-second Python pokes it dominates.

KubernetesExecutor Internals

Each TI becomes a Pod running the Airflow image with args airflow tasks run …. Isolation is the kernel + resource requests/limits. Configuration layers:

  • Base pod template (pod_template_file)
  • Per-task executor_config={"pod_override": …} for memory/CPU/nodeSelector/image
  • KubernetesExecutor watches pod phase and maps it to TI state

Failure modes unique to K8s: ImagePullBackOff, unschedulable pods (resource requests > node), evictions (preemptible nodes), and log loss if remote logging is not configured. Use a cluster autoscaler; set sensible requests so the scheduler does not create 5,000 pending pods after a catchup.

CeleryKubernetesExecutor (and Airflow 2.10+ executor teams): route by queue name — kubernetes queue uses pods, default queue uses Celery. Use this when 90% of tasks are tiny and 10% need 64Gi RAM.

Pools, Queues, Slots — Do Not Confuse Them

  • Executor slots / parallelism — global Airflow cap.
  • Celery queue — routing to a worker fleet (environment + hardware class).
  • Pool — logical token bucket in the metadata DB (e.g. pool=snowflake_load with 8 slots to protect warehouse credits).

A task can wait on a full pool even when Celery workers are idle. That is intended — pools protect external systems, not Airflow workers.

Heartbeats, Zombies, Adopted Tasks

While running, the task process updates task_instance.pid / hostname and a heartbeat timestamp. If the worker dies (OOM, node kill, kill -9), the scheduler notices heartbeat expiry (scheduler_zombie_task_threshold) and marks the TI failed or retries. False zombies happen if:

  • The task is CPU-starved and cannot heartbeat (heavy C-extension, GIL deadlock)
  • Clock skew between worker and DB
  • Threshold too aggressive relative to GC pauses

After scheduler failover, executors adopt TIs that were queued/running so work is not double-started. Adoption bugs historically caused duplicate Spark jobs — operators must still be idempotent.

XCom Transport Limits

XCom is a metadata-DB row (or custom XCom backend). Default pickling/JSON into Postgres is fine for kilobytes (partition lists, run IDs). Megabyte DataFrames will lock the DB and blow up the webserver. Custom backends (S3/GCS) store a pointer in the DB. TaskFlow @task return values are XCom — returning a pandas DataFrame is the same anti-pattern.

Interview Questions

When is KubernetesExecutor the wrong choice?

High-QPS tiny tasks (hundreds of 2-second tasks per minute), environments without a well-run cluster autoscaler, or when image size is 8GB and pull time exceeds task time. Prefer Celery (or Local on a beefy VM) for chatty control-flow; use K8s for bursty, heterogeneous, isolated ETL.

How do you stop 200 DAGs from melting Snowflake?

A dedicated pool with slot count = max concurrent warehouse queries you will allow, every Snowflake operator/task assigned to that pool. Optionally a Celery queue on a small worker set. Pools are the Airflow-native backpressure valve; warehouse auto-suspend is not sufficient if Airflow can still open 200 sessions.
