Jobs, Ops, Graphs — When Assets Are Not Enough

Assets shine for durable data products. Ops are the lower-level unit (like Airflow tasks): they have inputs/outputs, retry policies, tags, and can be wired into a Graph then wrapped as a Job.

  • Use ops for side effects with no durable asset (call a webhook, vacuum a table as a maintenance job, one-off backfill script).
  • A job can materialize a selection of assets (define_asset_job) — this is the usual production entrypoint for "nightly silver."
  • Resources (ConfigurableResource) are injected into ops/assets: warehouse clients, Spark session factories. They are constructed per run and should be connection-pooled carefully (do not open a SparkSession in a resource if 50 steps each create one — share via resource or external cluster).

Run Executors (in-process vs multiprocess vs K8s)

Inside a run, steps may run:

  • in_process_executor — one process, sequential or threaded depending on config. Debuggable. No isolation.
  • multiprocess_executor — step subprocesses on the run worker host. Analogous to LocalExecutor scoped to one run.
  • k8s_job_executor / Celery-K8s — each step (or the whole run) is a Kubernetes Job. Isolation and resource requests per step, startup tax like KubernetesExecutor.
  • docker_executor — step containers on a Docker host.

Decide two layers independently: how a run is launched (K8s Job for the run worker) vs how steps fan out inside the run (multiprocess vs k8s_job_executor). Nested K8s (run is a pod, each step more pods) is powerful and easy to over-create API load on kube-apiserver.

Run Launchers & QueuedRunCoordinator

The run launcher starts the worker (K8s, ECS, local process). Without a coordinator, every scheduled tick launches immediately and you can stampede Spark.

QueuedRunCoordinator keeps runs in QUEUED until dequeue_interval and tag-based concurrency limits allow. Tag runs with {"dagster/priority": ...} or custom tags like snowflake:heavy and set max concurrent runs per tag — Dagster's equivalent of Airflow pools at run granularity. Combine with warehouse-side warehouses/queues.

Schedules vs Sensors vs Asset Sensors

  • Schedule — cron (or custom tick). Deterministic. Use for "every day at 02:00 UTC materialize daily partitions."
  • Sensor — poll external state (S3, Airflow DAG success, Kafka lag, API). Must return SkipReason or RunRequest quickly; store a cursor (last modified key, last offset).
  • Asset sensor — fires when a watched asset materializes (in-process graph event, not S3 list). Prefer this over S3 sensors when the producer is also Dagster.

Sensor evaluation interval too aggressive + slow S3 listing = daemon lag (similar to Airflow poke sensors burning slots, but here you burn daemon/gRPC time). Use event-driven webhooks where possible (S3 → SQS → sensor cursor, or Dagster+ event ingest).

Retries, Hooks, Run vs Step

Ops/assets declare RetryPolicy(max_retries=..., delay=...) for step retries inside the same run. Run-level retries (submit a new run) are a different knob — useful when the worker VM died. Idempotent writes are mandatory in both cases.

Hooks (success_hook, failure_hook) are for notifications, not for compensating transactions. Failure hooks that "delete the partition" can race with a retry already rewriting it.

Run Config & ConfigSchema

Jobs can take structured YAML/JSON run config (op inputs, resource config). This is stronger than Airflow params: it is typed, nested, and validated before execute. For partition jobs, partition key is injected into context; do not also pass the date as untyped config unless you like mismatches.

Spark submit from an asset (pattern)
@asset(partitions_def=daily, required_resource_keys={"emr"})
def gold_customers(context):
    dt = context.partition_key
    context.resources.emr.submit_and_wait(
        job="gold_customers",
        args=["--dt", dt],
    )
    # IO manager records table partition metadata only
    return f"glue.gold.customers/dt={dt}"

Interview Questions

Sensor vs automation condition for downstream tables?

If upstream is a Dagster asset, use automation conditions / asset jobs on the graph — no polling. If upstream is a black-box (SaaS dump to S3), use a sensor (or asset observation) to emit a materialization, then let automation take over. Polling the warehouse information_schema every 30s from a sensor is how you DDoS your catalog.

How do you mimic Airflow pools in Dagster?

QueuedRunCoordinator with tag concurrency limits for run-level caps. For intra-run step caps, use executor configuration / K8s resource quotas. For the warehouse, still use Snowflake warehouses, BigQuery reservations, or a dedicated resource that internally rate-limits. Dagster does not have Airflow's per-task DB pool tokens unless you build a resource that acquires a lease.
