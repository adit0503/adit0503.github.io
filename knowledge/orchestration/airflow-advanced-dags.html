TaskFlow API — What It Compiles To

@task is syntactic sugar over PythonOperator + XComArg. x = extract(); transform(x) creates a dependency edge and an XCom pull of the return value. It does not magically pass objects in memory across Celery workers — it serializes through XCom. Multiple outputs use @task(multiple_outputs=True) returning a dict; each key becomes an XCom key.

TaskFlow still hits XCom
@dag(schedule="@daily", start_date=datetime(2024, 1, 1), catchup=False)
def media_daily():
    @task
    def list_partitions(ds=None) -> list[str]:
        return [f"dt={ds}"]

    @task
    def submit_spark(parts: list[str]):
        # parts came from XCom JSON, not shared RAM
        spark_submit(parts)

    submit_spark(list_partitions())

media_daily()

Dynamic Task Mapping

Airflow 2.3+ expands one task definition into N TaskInstances at runtime:

  • op.expand(file=files) — one TI per list element
  • expand_kwargs([...]) — per-TI keyword dicts
  • zip / cross-product expansions for multiple mapped args

Low-level details:

  • Each mapped TI has map_index ≥ 0. Unmapped tasks use map_index = -1.
  • Expansion happens after the upstream that returns the list succeeds. The scheduler then inserts N rows. If the list is empty, you get zero TIs (configure skip vs fail via operator flags depending on version).
  • max_map_length (default 1024) is a safety cap. Expanding 100k files will not "just work" — chunk in the callable or use a compute engine.
  • Mapped tasks still share one task_id in the DAG graph; concurrency uses max_active_tis_per_dag.

Do not map 10,000 Spark submits. Map a reasonable fan-out (dozens to hundreds), or have one task submit a parameterized Spark job that internally foreach-partitions.

Deferrable Operators & the Triggerer

Classic sensors in mode="poke" occupy a worker slot every poke interval. mode="reschedule" frees the slot between pokes but still creates many short TIs and scheduler churn.

Deferrable operators:

  1. execute() starts work or immediately defers.
  2. Worker process exits; TI state deferred; row in trigger.
  3. Triggerer runs lightweight asyncio (e.g. DateTimeTrigger, S3KeyTrigger).
  4. Event → scheduler re-queues TI → execute_complete(event).

Write custom triggers as BaseTrigger with a serializable payload (JSON). Triggers must be idempotent and must not do heavy CPU — they share one event loop per triggerer process.

Sensor Patterns That Survive Production

  • Prefer datasets/assets or object-storage events over minute-level pokes.
  • If you must sensor: deferrable first, else reschedule, never long poke on Celery.
  • ExternalTaskSensor couples DAG ids and execution dates — timezone and timetable mismatches cause silent waits. Prefer datasets.
  • Set timeout and execution_timeout; infinite sensors are silent capacity leaks.

Setup / Teardown, Branching, Callbacks

Airflow 2.7+ setup/teardown tasks are work that should run around a group (create/drop temp schema) and have special skip semantics so teardown still runs on failure when marked as teardown.

Branching (BranchPythonOperator / @task.branch) skips non-chosen downstream tasks. Skipped is not failed; trigger_rule=none_failed_min_one_success is the usual join after a branch.

Callbacks (on_failure_callback) run in the worker after the task ends — they can fail independently. Keep them small (Slack/PagerDuty). Do not start Spark from a callback.

Airflow 3 Notes (mental model)

Airflow 3 continues the split of scheduling vs task execution, leans on assets as first-class data objects (evolution of datasets), and tightens the Task SDK / execution API so workers are thinner clients of the API server. When reading docs, map: dataset → asset, execution date → logical date / data interval. Internals you already know (TI states, executors, triggerer) still apply.

Interview Questions

How would you fan out over 50,000 incoming files?

Do not expand() 50k TIs. Batch keys in one task (S3 list → chunks of 500), map over chunks, each chunk a Spark/Glue job. Alternatively a single Spark job with input path glob. Airflow's unit of work should be a job, not a file, at that scale. Guard with max_map_length so a bad list cannot insert tens of thousands of TI rows and stall the scheduler.

Why did switching a sensor to deferrable not reduce DB load?

Deferrable reduces worker slot occupancy. The triggerer still writes events; the scheduler still transitions TIs. If you have thousands of deferred sensors firing every second, you moved load from Celery to triggerer + trigger table. Coalesce waits (one sensor per DAG on a terminal object, or dataset events from the producer) rather than one deferrable per table.
