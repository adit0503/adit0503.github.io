Execution vs Asset Graph

Dagster's core object is not a DAG of tasks. It is a graph of software-defined assets (plus optional ops/jobs). A run is a selection from that graph: "materialize these asset keys (and maybe parents) with this partition." Orchestration state lives in the event log (structured events: STEP_SUCCESS, ASSET_MATERIALIZATION, …), not a single TaskInstance row machine like Airflow.

Code Locations & gRPC Isolation

User code is loaded in a dedicated process (or Kubernetes deployment) called a code location. The webserver and daemon do not import your definitions.py in-process in a proper deployment.

  • The code location process hosts a gRPC server.
  • The webserver asks it for the Definitions snapshot (asset graph, jobs, schedules, sensors) to render the UI.
  • When a run starts, a run worker is launched that again loads that code location (same image) and executes the selected steps.

This is why Dagster reloads are cheap to the control plane: you roll the user-code deployment; daemons keep running. It is also why a parse explosion in user code takes down that location's gRPC server, not the entire dagster-webserver — similar intent to Airflow's DAG processor subprocess, but the unit is a service, not a file.

Definitions is the load unit
from dagster import Definitions, load_assets_from_modules
from . import assets, jobs, schedules

defs = Definitions(
    assets=load_assets_from_modules([assets]),
    jobs=[jobs.nightly_job],
    schedules=[schedules.nightly],
    resources={"io_manager": s3_pickle_io_manager, "snowflake": snowflake_resource},
)

DagsterInstance — Storage Splits

DagsterInstance is the control-plane handle. Typical production split:

  • Run storage — run records, status (Postgres DagsterPostgresRunStorage)
  • Event log storage — append-only events, asset materialization history, used for the asset catalog and partitioning UI. This table grows fast; plan retention.
  • Schedule storage — ticks for schedules/sensors
  • Compute log manager — stdout/stderr of steps to S3/GCS
  • Local artifact storage — intermediates if you use filesystem IO managers (avoid on ephemeral pods)

dagster.yaml on the instance (webserver + daemon + run workers must agree on storage) is analogous to airflow.cfg, but run workers also need network access to the same Postgres and blob store.

The Dagster Daemon

One (HA-capable with appropriate locks) daemon process runs several loops:

  • Scheduler — evaluates ScheduleDefinition cron, submits runs
  • Sensor evaluation — calls sensor functions in the code location via gRPC, may yield RunRequests
  • Queued run coordinator — if enabled, runs sit QUEUED until slots free (global backpressure)
  • Auto-materialize / AutomationCondition (version-dependent naming) — walks the asset graph, decides which assets are stale relative to parents/partitions/freshness, enqueues runs
  • Backfill daemon — chunks large partition backfills into runs so you do not submit 10,000 runs in one API call

Sensors and schedules execute in the code location (or daemon talking to gRPC), not in an Airflow-style worker slot. A slow sensor blocks that location's sensor ticks — keep them I/O bound and fast, persist cursor state via context.update_cursor.

Webserver & GraphQL

The UI is a GraphQL client (dagster-webserver). Launching a run is a GraphQL mutation that creates a run record, then the run launcher (K8s job, ECS task, process) starts a worker with env vars pointing at the instance. There is no "task_instance scheduled vs queued" split identical to Airflow; you have run status + step events inside the run.

Deployment Topologies

  • dagster dev — single process, in-memory or sqlite — local only
  • Docker / docker-compose — webserver + daemon + user-code container + Postgres
  • Helm (dagster-user-deployments) — control plane chart + N user-code Deployments (one per code location / team)
  • Dagster+ — hybrid: control plane hosted, runs in your cloud via an agent

Multi-location is how large orgs isolate Python deps (Spark 3.4 vs 3.5, conflicting protobufs) — something Airflow solves with KubernetesExecutor pod images or separate Airflow deployments.

Interview Questions

Where does a bug in asset code crash — UI, daemon, or run?

Import/definition errors crash or fail health of the code location gRPC (UI shows location error; daemon cannot tick that location's sensors). Runtime exceptions during materialization crash the run worker step (event log STEP_FAILURE). The webserver should stay up. If the UI itself dies, you deployed user code into the webserver image — fix the topology.

Why is the event log a scaling concern?

Every log line and materialization metadata is an event. High-cardinality partitions (per-minute assets) × many assets × retries can dominate Postgres I/O and UI query time. Use compute-log offload, wipe/retention policies, avoid storing payloads in materialization metadata, and prefer coarser partitions (hourly/daily) unless you truly need minute grains.
