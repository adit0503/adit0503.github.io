Micro-Batch vs Continuous Processing

Structured Streaming treats a live data stream as an unbounded table that grows with new records. Queries express the same logic as batch DataFrames — Spark handles the incremental execution.

Micro-Batch (Default)

  • Processes data in small batches at regular intervals (trigger-based)
  • Each micro-batch is a full Spark job — benefits from all Spark optimizations (Catalyst, Tungsten, AQE)
  • Achieves exactly-once semantics via checkpointing + idempotent sinks
  • Latency: 100ms — seconds (depends on trigger interval and batch processing time)
  • Supported for all sources, sinks, and stateful operations

Continuous Processing (Experimental)

  • Long-running tasks that continuously poll for new data (no batch boundaries)
  • Achieves at-least-once semantics (exactly-once requires async checkpointing)
  • Latency: ~1ms end-to-end
  • Very limited operator support — only map-like operations, no aggregations/joins
  • Rarely used in production due to limitations
🔑 Practical guidance:

Use micro-batch for 99% of production streaming workloads. The latency difference (100ms vs 1ms) rarely matters for data engineering pipelines. Micro-batch gives you exactly-once, full SQL support, and all optimizations. Continuous mode is only for ultra-low-latency map-only pipelines.

Trigger Types

Triggers control when a micro-batch is executed:

Trigger types
from pyspark.sql.streaming import Trigger

# 1. ProcessingTime — run batch every N seconds
query = df.writeStream \
    .trigger(processingTime="10 seconds") \
    .start()

# 2. Once — process all available data in ONE batch, then stop
# Great for "streaming-first" batch jobs and testing
query = df.writeStream \
    .trigger(once=True) \
    .start()

# 3. AvailableNow (Spark 3.3+) — process all available data in
# MULTIPLE batches (respects maxFilesPerTrigger), then stop
# Best for scheduled catch-up jobs with rate limiting
query = df.writeStream \
    .trigger(availableNow=True) \
    .start()

# 4. Continuous (experimental) — low-latency continuous processing
query = df.writeStream \
    .trigger(continuous="1 second")  # checkpoint interval
    .start()

# Default: no trigger specified → runs next batch immediately after previous
⚠️ Trigger.Once vs AvailableNow:

once=True processes ALL available data in a single batch — can cause OOM if there's a massive backlog. availableNow=True processes the same data but respects rate limits like maxFilesPerTrigger or maxOffsetsPerTrigger, splitting into multiple manageable batches. Always prefer availableNow for scheduled catch-up jobs.

Watermarks & Late Data

In event-time processing, data can arrive out of order. Watermarks define how long to wait for late data before finalizing results and cleaning up state.

How Watermarks Work

  1. Spark tracks the maximum event time seen across all partitions
  2. Watermark = max_event_time - threshold
  3. Data older than the watermark is considered "too late" and may be dropped
  4. State for windows that are fully below the watermark is cleaned up (prevents unbounded state growth)
Watermark usage
from pyspark.sql.functions import window, col

# Define watermark: tolerate up to 10 minutes of late data
events = spark.readStream.format("kafka")...

windowed_counts = events \
    .withWatermark("event_time", "10 minutes") \
    .groupBy(
        window(col("event_time"), "5 minutes"),  # 5-min tumbling window
        col("device_id")
    ) \
    .count()

# Timeline:
# max event_time seen = 12:30
# watermark = 12:30 - 10min = 12:20
# Window [12:10, 12:15] → finalized, state dropped (end < watermark)
# Window [12:15, 12:20] → still accepting late data
# Window [12:25, 12:30] → active, accepting data
# Event with time 12:15 arriving now → accepted (>= watermark)
# Event with time 12:05 arriving now → DROPPED (< watermark)

Watermark Semantics by Output Mode

  • Append mode: Results emitted only when watermark passes the window end. Guarantees no late updates. State cleaned when watermark crosses window.
  • Update mode: Results emitted every batch (may update). Watermark only used for state cleanup, not output timing.
  • Complete mode: All results emitted every batch. Watermark ignored for output but still used for state cleanup.

Output Modes

Append Mode (Default)

  • Only new rows that will never change are written
  • For aggregations with watermark: rows emitted after window is finalized
  • For map/filter operations: new input rows flow through immediately
  • Use when: Writing to immutable sinks (files, Kafka, append-only tables)

Update Mode

  • Only rows that changed since the last batch are written
  • For aggregations: updated aggregates emitted every batch
  • Use when: Writing to mutable sinks (databases, key-value stores, Delta Lake merge)

Complete Mode

  • The entire result table is written every batch
  • Only supported for aggregation queries (full result required)
  • Use when: Dashboard tables, small aggregation result sets, overwrite-style sinks
Output mode selection
# Append — for file sinks, Kafka sinks
query = aggregated_df.writeStream \
    .outputMode("append") \
    .format("parquet") \
    .option("path", "s3://output/events/") \
    .option("checkpointLocation", "s3://checkpoints/events/") \
    .start()

# Update — for database upserts
query = aggregated_df.writeStream \
    .outputMode("update") \
    .foreachBatch(upsert_to_postgres) \
    .option("checkpointLocation", "s3://checkpoints/agg/") \
    .start()

# Complete — for small result tables
query = aggregated_df.writeStream \
    .outputMode("complete") \
    .format("memory") \
    .queryName("live_dashboard") \
    .start()

Stateful Operations

Built-in Stateful Operations

  • Windowed aggregations: groupBy(window(...)).agg(...) — state tracks partial aggregates per window
  • Stream-stream joins: State buffers both sides within watermark bounds
  • Deduplication: dropDuplicates() — state tracks seen keys within watermark

Custom Stateful Operations

mapGroupsWithState

Arbitrary stateful processing with exactly-once semantics. Maps each group's events + state → output:

mapGroupsWithState example (Scala-style logic)
# Use case: Track user sessions with timeout
# State: last_activity_time, session_data
# Input: user events
# Output: one session summary per update

from pyspark.sql.streaming import GroupState, GroupStateTimeout

def update_session(key, events, state):
    """
    key: user_id
    events: Iterator of events for this user in this batch
    state: GroupState holding session data
    """
    if state.hasTimedOut:
        # Session expired — emit final result, remove state
        session = state.get
        state.remove()
        yield SessionOutput(key, session.start, session.count, "closed")
    else:
        # Update session with new events
        existing = state.getOption or Session(start=None, count=0)
        for event in events:
            existing.count += 1
            existing.start = existing.start or event.timestamp
        state.update(existing)
        state.setTimeoutDuration("30 minutes")
        yield SessionOutput(key, existing.start, existing.count, "active")

# Apply:
sessions = events.groupByKey(lambda r: r.user_id) \
    .mapGroupsWithState(
        update_session,
        outputMode="update",
        timeoutConf=GroupStateTimeout.ProcessingTimeTimeout
    )

flatMapGroupsWithState

Like mapGroupsWithState but can emit zero, one, or many output rows per group per batch. Required when output cardinality doesn't match input groups (e.g., sessionization with multiple sessions per user).

🔑 State management rule:

Always use watermarks with stateful operations to enable state cleanup. Without a watermark, state grows unbounded — eventually causing OOM. For custom state (mapGroupsWithState), set explicit timeouts. Monitor state size via stateOperator metrics in the streaming query progress.

Checkpointing & Recovery

What Checkpoints Store

  • Offsets: Which data has been consumed from sources (Kafka offsets, file list)
  • State: Accumulated state for stateful operations (aggregations, sessions)
  • Commit log: Which batches have been committed to the sink
  • Metadata: Query ID, run ID, schema information

Recovery Semantics

Checkpoint directory structure
s3://checkpoints/my-query/
├── metadata          # Query metadata (id, schema)
├── offsets/          # Offset log per batch
│   ├── 0            # Batch 0 offsets
│   ├── 1            # Batch 1 offsets
│   └── 2            # Batch 2 offsets (latest)
├── commits/          # Commit log (which batches completed)
│   ├── 0
│   └── 1            # Batch 1 committed; batch 2 in progress
├── state/            # State store snapshots
│   └── 0/           # Partition 0
│       ├── 1.delta
│       └── 2.snapshot
└── sources/          # Source-specific metadata

Exactly-Once Guarantees

Achieved through the combination of:

  1. Replayable sources: Can re-read data from a given offset (Kafka, files, Delta)
  2. Idempotent sinks: Writing the same data twice produces the same result (Delta MERGE, Kafka with dedup key)
  3. Checkpoint WAL: Offsets committed atomically — if a batch fails mid-way, it replays from the checkpoint
⚠️ Checkpoint location rules:

1. Never share a checkpoint between different queries. 2. Never delete a checkpoint for a running query (causes data loss or duplication). 3. Changing query logic (new columns, different aggregation) may require a fresh checkpoint — state schema changes are not backward compatible. 4. Use a reliable, durable filesystem (S3, HDFS, ADLS) — never local disk in production.

Sources & Sinks

Sources

  • Kafka: Most common production source. Exactly-once via offset tracking.
  • File source: Monitors a directory for new files. Supports JSON, CSV, Parquet, ORC, Avro.
  • Delta Lake: Read changes from a Delta table (Change Data Feed). Supports rate limiting.
  • Rate source: Generates data at a fixed rate — for testing.
  • Socket source: TCP socket — for development only (no fault tolerance).

Sinks

  • Kafka: Write to Kafka topics. Key/value/topic columns required.
  • File sink: Write Parquet/JSON/CSV files. Append mode only. Exactly-once via file commit protocol.
  • Delta Lake: ACID writes with exactly-once. Supports all output modes with merge.
  • foreach / foreachBatch: Custom sink logic. foreachBatch gives you a static DataFrame per batch — use for JDBC, API calls, complex writes.
  • Console / Memory: For debugging only.
foreachBatch pattern for custom sinks
def write_to_multiple_sinks(batch_df, batch_id):
    """Process each micro-batch as a regular DataFrame."""
    # Persist to avoid recomputation
    batch_df.persist()

    # Write to Delta Lake (primary store)
    batch_df.write.format("delta") \
        .mode("append") \
        .save("s3://lake/events/")

    # Write aggregates to Postgres (analytics)
    agg_df = batch_df.groupBy("event_type").count()
    agg_df.write.format("jdbc") \
        .option("url", jdbc_url) \
        .option("dbtable", "event_counts") \
        .mode("overwrite") \
        .save()

    batch_df.unpersist()

query = events.writeStream \
    .foreachBatch(write_to_multiple_sinks) \
    .option("checkpointLocation", "s3://checkpoints/multi-sink/") \
    .trigger(processingTime="30 seconds") \
    .start()

Kafka Integration Patterns

Reading from Kafka
# Basic Kafka source
df = spark.readStream \
    .format("kafka") \
    .option("kafka.bootstrap.servers", "broker1:9092,broker2:9092") \
    .option("subscribe", "events-topic") \
    .option("startingOffsets", "latest") \  # or "earliest" or JSON offsets
    .option("maxOffsetsPerTrigger", 100000) \  # rate limiting
    .option("kafka.group.id", "spark-consumer-group") \
    .load()

# Kafka DataFrame schema:
# key: binary, value: binary, topic: string,
# partition: int, offset: long, timestamp: timestamp

# Parse JSON value with schema
from pyspark.sql.functions import from_json, col
from pyspark.sql.types import StructType, StringType, TimestampType

schema = StructType() \
    .add("user_id", StringType()) \
    .add("event_type", StringType()) \
    .add("event_time", TimestampType())

parsed = df.select(
    from_json(col("value").cast("string"), schema).alias("data"),
    col("timestamp").alias("kafka_timestamp")
).select("data.*", "kafka_timestamp")
Writing to Kafka
# Write to Kafka — must have 'value' column (key and topic optional)
output = processed_df.select(
    col("user_id").cast("string").alias("key"),
    to_json(struct("*")).alias("value")
)

query = output.writeStream \
    .format("kafka") \
    .option("kafka.bootstrap.servers", "broker1:9092") \
    .option("topic", "processed-events") \
    .option("checkpointLocation", "s3://checkpoints/kafka-out/") \
    .option("kafka.acks", "all") \  # durability
    .option("kafka.retries", "3") \
    .start()

Schema Registry Integration

Avro with Schema Registry (Confluent)
# Using the Confluent Avro deserializer
from confluent_kafka.schema_registry import SchemaRegistryClient
from pyspark.sql.avro.functions import from_avro

schema_registry_conf = {"url": "http://schema-registry:8081"}

# Deserialize Avro (skip first 5 bytes — Confluent wire format)

Monitoring & Production Patterns

StreamingQueryListener

Custom monitoring with StreamingQueryListener
from pyspark.sql.streaming import StreamingQueryListener

class MetricsListener(StreamingQueryListener):
    def onQueryStarted(self, event):
        print(f"Query started: {event.id}")

    def onQueryProgress(self, event):
        progress = event.progress
        print(f"Batch {progress.batchId}:")
        print(f"  Input rows/sec: {progress.inputRowsPerSecond}")
        print(f"  Processed rows/sec: {progress.processedRowsPerSecond}")
        print(f"  Batch duration: {progress.batchDuration}ms")
        # State metrics (for stateful queries)
        for state_op in progress.stateOperators:
            print(f"  State rows: {state_op['numRowsTotal']}")
            print(f"  State memory: {state_op['memoryUsedBytes']}")
        # Publish to CloudWatch/Datadog/Prometheus
        publish_metrics(progress)

    def onQueryTerminated(self, event):
        print(f"Query terminated: {event.id}, error: {event.exception}")

spark.streams.addListener(MetricsListener())

Progress Metrics to Watch

  • inputRowsPerSecond vs processedRowsPerSecond — if input > processed, you're falling behind
  • batchDuration — must be less than trigger interval to avoid backlog
  • stateOperators.numRowsTotal — state size growth indicates missing watermark or leak
  • sources[].endOffset - startOffset — batch size, lag indicator

Graceful Shutdown

Graceful shutdown pattern
import signal
import sys

query = df.writeStream...start()

def graceful_stop(sig, frame):
    """Stop after current batch completes — no data loss."""
    print("Received signal, stopping gracefully...")
    query.stop()  # Waits for current batch to finish
    sys.exit(0)

signal.signal(signal.SIGTERM, graceful_stop)
signal.signal(signal.SIGINT, graceful_stop)

# Block until termination
query.awaitTermination()

Interview Questions

Explain how watermarks work in Structured Streaming and why they're necessary.

Watermarks solve two problems: (1) late data handling — defining how long to wait for out-of-order events, and (2) state cleanup — knowing when to discard state for old windows to prevent unbounded memory growth. The watermark is calculated as max_event_time_seen - threshold. Events with timestamps below the watermark are considered "too late" and dropped (in append mode). State for windows whose end time falls below the watermark is garbage collected. Without watermarks, aggregation state grows indefinitely, eventually causing OOM. The watermark threshold should be set based on your data's maximum expected lateness — too aggressive (small) and you lose data, too conservative (large) and you hold too much state and delay output.

How does Structured Streaming achieve exactly-once semantics?

Exactly-once is achieved through three mechanisms working together: (1) Replayable sources — sources like Kafka and files can re-read data from a specific offset if a batch fails. (2) Checkpointed state — before processing a batch, Spark writes the batch's offset range to the checkpoint WAL. If the driver fails mid-batch, on restart it reads the last committed batch from the checkpoint and replays from there. (3) Idempotent sinks — the sink must produce the same result when the same batch is written twice (e.g., Delta Lake's ACID writes, file sinks with atomic rename, Kafka with exactly-once producers). If any of these three are missing, you get at-least-once. For custom sinks via foreachBatch, you must implement idempotency yourself (e.g., using batch_id as a deduplication key).

When would you use foreachBatch vs foreach as a sink?

foreachBatch: Gives you a complete DataFrame for each micro-batch. Use for: writing to multiple sinks from one stream, performing batch-level operations (MERGE, UPSERT), leveraging existing batch write libraries (JDBC, custom connectors). You get the full DataFrame API. foreach: Processes one row at a time with open/process/close callbacks. Use for: API calls per record, custom per-record logic, very specific output protocols. Almost always prefer foreachBatch — it's more efficient (batch-level writes), gives you DataFrame operations, and is easier to make idempotent. foreach has higher overhead (per-row function calls) and is harder to optimize.

What's the difference between Trigger.Once and Trigger.AvailableNow?

Trigger.Once: Processes ALL available data in a single batch, then terminates. Problem: if there's a large backlog (e.g., missed a day of data), the single batch may be enormous — causing OOM or very long processing times. It also ignores rate-limiting options like maxOffsetsPerTrigger. Trigger.AvailableNow (Spark 3.3+): Processes all available data but splits it into multiple batches, respecting rate limits. Each batch is manageable size. More predictable resource usage and safer for catch-up scenarios. Use AvailableNow for scheduled streaming jobs (e.g., run every hour, process everything since last run) where you want the streaming semantics (checkpointing, exactly-once) but batch-job-like scheduling.

How would you handle schema evolution in a production streaming pipeline?

Schema evolution in streaming is challenging because checkpoint state is schema-bound. Strategies: (1) Forward-compatible schemas: Design sources with schema registry (Avro/Protobuf) using backward/forward compatibility rules. New optional fields don't break consumers. (2) Flexible parsing: Parse JSON with a broad schema and handle missing/new fields with PERMISSIVE mode. (3) Schema hints at source: For Kafka Avro, fetch schema dynamically from registry per message. (4) Stateless queries: If your query is stateless (map/filter only), you can stop, update the schema in code, delete the checkpoint, and restart — no state to migrate. (5) Stateful queries: Breaking changes (remove/rename columns in state) require a new checkpoint and replaying from source. Additive changes (new columns) may be compatible depending on the state format. (6) Delta Lake as a buffer: Write raw data to Delta (schema evolution merge), then run a second stream on the Delta table with the new schema.
