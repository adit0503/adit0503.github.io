Spark Architecture & Internals

Complete breakdown of Spark's distributed execution model — from driver to executors, DAG scheduling, task execution, and the role of each component in the cluster.

Cluster Architecture

A Spark application consists of a Driver process and a set of Executor processes distributed across the cluster.

Driver

  • Runs the main() function of the application
  • Creates the SparkSession / SparkContext
  • Converts user code into a logical plan → physical plan → DAG of stages
  • Negotiates resources with the cluster manager
  • Distributes tasks to executors and monitors their execution
  • Maintains metadata about the application (accumulator values, broadcast variables)

Executors

  • JVM processes that run on worker nodes
  • Execute tasks assigned by the driver
  • Store data in memory/disk for caching (StorageMemory)
  • Report task status and metrics back to the driver
  • Each executor has a fixed number of cores (slots for parallel tasks)

Cluster Manager

Responsible for resource allocation. Spark supports:

  • YARN — most common in Hadoop/Cloudera environments
  • Kubernetes — container-native, good for cloud
  • Standalone — Spark's built-in cluster manager
  • Mesos — legacy, mostly deprecated
spark-submit example
spark-submit \
  --master yarn \
  --deploy-mode cluster \
  --num-executors 10 \
  --executor-memory 8g \
  --executor-cores 4 \
  --driver-memory 4g \
  --conf spark.dynamicAllocation.enabled=true \
  my_app.py

Execution Model — Jobs, Stages & Tasks

Understanding the hierarchy: Application → Job → Stage → Task

Job

A job is triggered by an action (e.g., count(), collect(), write()). Each action triggers one job. Transformations (map, filter, join) are lazy — they only build a lineage graph.

Stage

A job is divided into stages at shuffle boundaries. Within a stage, all operations can be pipelined (narrow dependencies). A shuffle forces a stage boundary (wide dependency).

  • Narrow dependencies: map, filter, union — each input partition maps to at most one output partition
  • Wide dependencies: groupByKey, reduceByKey, join (without broadcast), repartition — data must be shuffled across partitions

Task

A task is the smallest unit of work — one task per partition per stage. If a stage operates on 200 partitions, it generates 200 tasks.

🔑 Key insight for interviews:

The number of tasks = number of partitions in that stage. To control parallelism, you control partitions via spark.sql.shuffle.partitions (default 200) or explicit repartition()/coalesce().

DAG Scheduler & Task Scheduler

DAG Scheduler

  • Receives the logical plan from the driver
  • Builds a DAG of stages based on shuffle boundaries
  • Submits stages in topological order (parent stages first)
  • Handles stage retries on failure
  • Tracks which partitions of which RDDs are cached

Task Scheduler

  • Receives a set of tasks from the DAG scheduler (one TaskSet per stage)
  • Assigns tasks to executors based on data locality:
    • PROCESS_LOCAL — data is in the same executor's cache
    • NODE_LOCAL — data is on the same node (different executor or disk)
    • RACK_LOCAL — data is on a different node in the same rack
    • ANY — data is remote
  • Handles speculative execution (spark.speculation=true)
  • Manages task retries (default: 4 attempts)

RDD Internals & Lineage

Every RDD stores:

  1. Partitions — list of partitions that make up the dataset
  2. Dependencies — list of parent RDDs (narrow or wide)
  3. Compute function — how to compute each partition from parents
  4. Partitioner (optional) — for key-value RDDs (HashPartitioner, RangePartitioner)
  5. Preferred locations (optional) — data locality hints

Lineage & Fault Tolerance

Spark achieves fault tolerance through lineage — if a partition is lost, Spark recomputes it from the parent partitions using the compute function. This avoids expensive replication (unlike Hadoop MapReduce).

⚠️ When lineage gets too long:

Use checkpoint() to truncate the lineage. This writes the RDD to reliable storage (HDFS/S3) and breaks the dependency chain. Useful for iterative algorithms or very long DAGs.

Deploy Modes — Client vs Cluster

Client Mode

  • Driver runs on the machine that submitted the job
  • Good for interactive development (Jupyter, spark-shell)
  • Driver process dies if the submitting machine goes down
  • Network latency between driver and cluster can be an issue

Cluster Mode

  • Driver runs inside the cluster (on a worker node)
  • Standard for production jobs
  • Submitting machine can disconnect after submission
  • Logs are on the cluster (access via YARN UI, Spark History Server)
Key config differences
# Client mode - driver uses local memory
--deploy-mode client
--driver-memory 4g   # on your laptop/edge node

# Cluster mode - driver runs on cluster node
--deploy-mode cluster
--driver-memory 4g   # allocated from cluster resources

Resource Managers — YARN, K8s, Standalone

YARN (Yet Another Resource Negotiator)

  • Most mature for on-prem Hadoop/Cloudera clusters
  • Application Master (AM) acts as the driver in cluster mode
  • Supports dynamic allocation — add/remove executors based on load
  • Queue-based resource management (capacity scheduler, fair scheduler)

Kubernetes

  • Spark 3.1+ has GA support for K8s
  • Driver and executors run as pods
  • Good for cloud-native environments (EKS, GKE)
  • Supports auto-scaling, pod templates, volumes
  • No need for a pre-existing Hadoop cluster

Standalone

  • Spark's built-in cluster manager
  • Simple to set up, good for development
  • Master + Worker architecture
  • Limited resource isolation compared to YARN/K8s

Interview Questions

What happens when you call an action in Spark?

1. The SparkContext creates a job. 2. The DAG Scheduler builds a DAG of stages by analyzing shuffle boundaries. 3. Each stage is submitted as a TaskSet to the Task Scheduler. 4. Tasks are assigned to executor cores based on data locality. 5. Executors run the tasks and return results to the driver. 6. Results are aggregated at the driver (e.g., for collect()) or written to storage (e.g., for write()).

What's the difference between narrow and wide transformations?

Narrow: Each input partition contributes to at most one output partition (map, filter, union). Can be pipelined. Wide: Input partitions contribute to multiple output partitions (groupBy, join, repartition). Requires a shuffle — data must be written to disk and transferred across the network. Wide transformations create stage boundaries.

How does Spark achieve fault tolerance without data replication?

Through lineage. Each RDD records how it was derived from parent RDDs. If a partition is lost (executor crash), Spark recomputes only that partition by replaying the transformations from the last materialized ancestor. For shuffle outputs, Spark stores shuffle files on disk, so completed map-side outputs don't need recomputation.

When would you use client mode vs cluster mode?

Client mode: Interactive development, debugging, Jupyter notebooks — you want to see output locally. Cluster mode: Production jobs, scheduled pipelines — driver runs inside the cluster for reliability, and the submitting machine can disconnect. Always use cluster mode for production Airflow/scheduler-triggered jobs.

What is speculative execution and when would you enable it?

Spark monitors task completion times. If a task is significantly slower than the median (straggler), it launches a duplicate task on another executor. Whichever finishes first wins. Enable via spark.speculation=true. Useful when cluster has heterogeneous hardware. Disable for non-idempotent operations or when writing to external systems.
