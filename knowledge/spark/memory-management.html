Unified Memory Manager

Since Spark 1.6, the Unified Memory Manager (UMM) replaced the older Static Memory Manager. The key difference: storage and execution memory share a unified region and can borrow from each other dynamically.

  • Execution memory — used for shuffles, joins, sorts, aggregations (intermediate computation buffers)
  • Storage memory — used for caching RDDs/DataFrames and broadcast variables
  • Either region can borrow from the other when the other is free
  • Execution memory can evict storage memory (cached blocks) if needed, but storage cannot evict execution
🔑 Key insight:

The Unified Memory Manager gives execution memory priority over storage. If a computation needs more memory than its allocated fraction, it can evict cached data. This prevents OOM errors during heavy shuffles at the cost of cache loss (which triggers recomputation).

Executor Memory Breakdown

When you set --executor-memory 8g, here's how that maps to the actual JVM and OS-level memory:

Total Container Memory

  • spark.executor.memory (8g) — the JVM heap size (-Xmx)
  • spark.executor.memoryOverhead — off-heap memory for JVM internals, native libraries, container overhead. Default: max(384MB, 0.10 × executor.memory) = 800MB for 8g
  • spark.memory.offHeap.size — explicit off-heap for Spark operations (if enabled)
  • spark.executor.pyspark.memory — Python worker memory (PySpark only)

Total container request = executor.memory + memoryOverhead + offHeap.size + pyspark.memory

Memory layout for --executor-memory 8g
Total Container: ~8.8g (YARN/K8s container)
├── JVM Heap (8g) — spark.executor.memory
│   ├── Reserved Memory: 300MB (hardcoded, internal Spark objects)
│   ├── User Memory: (1 - spark.memory.fraction) × (heap - 300MB)
│   │   = 0.40 × 7700MB = 3080MB
│   │   → UDFs, internal metadata, your data structures
│   └── Unified Memory: spark.memory.fraction × (heap - 300MB)
│       = 0.60 × 7700MB = 4620MB
│       ├── Storage Memory: 50% of Unified = 2310MB
│       │   → cached RDDs, broadcast vars
│       └── Execution Memory: 50% of Unified = 2310MB
│           → shuffles, joins, sorts, aggregations
└── Off-Heap (800MB) — memoryOverhead
    → JVM overhead, native libs, direct byte buffers, container padding

Key Configuration Parameters

Memory-related configs
# Core memory settings
spark.executor.memory=8g              # JVM heap
spark.executor.memoryOverhead=2g      # Off-heap overhead (increase for PySpark/heavy native libs)
spark.memory.fraction=0.6             # Fraction of (heap - 300MB) for unified region
spark.memory.storageFraction=0.5      # Initial split within unified (soft boundary)

# Off-heap (explicit)
spark.memory.offHeap.enabled=true
spark.memory.offHeap.size=4g          # Managed off-heap for Spark operations

# Driver memory
spark.driver.memory=4g
spark.driver.memoryOverhead=1g

On-Heap vs Off-Heap Memory

On-Heap (Default)

  • Managed by JVM garbage collector
  • Objects stored as Java objects on the heap
  • Subject to GC pauses — can cause task stalls and executor timeouts
  • Object headers and padding add ~2-5× memory overhead vs raw data
  • Easier to debug (heap dumps, JVM profilers)

Off-Heap

  • Allocated via sun.misc.Unsafe / java.nio.DirectByteBuffer
  • Not subject to GC — eliminates GC pauses for this memory
  • Data stored in compact binary format (Tungsten encoding)
  • Lower memory overhead (no Java object headers)
  • Harder to debug (no heap dump visibility)
  • Must be explicitly managed — risk of memory leaks if Spark has bugs
🔑 When to use off-heap:

Enable off-heap when you see long GC pauses (>5s), when working with very large datasets that cause frequent full GC, or when executors have 32g+ heap (large heaps amplify GC overhead). Off-heap is also beneficial for workloads with large broadcast variables.

Enabling off-heap memory
spark.memory.offHeap.enabled=true
spark.memory.offHeap.size=4g

# The unified memory pool becomes:
# On-heap unified = spark.memory.fraction × (heap - 300MB)
# Off-heap unified = spark.memory.offHeap.size
# Total unified = on-heap + off-heap

Storage vs Execution Memory

Storage Memory

  • Used by cache(), persist(), and broadcast variables
  • Blocks are stored here and evicted using LRU when space is needed
  • Can be spilled to disk (depending on storage level)
  • If execution needs more memory, storage blocks can be evicted

Execution Memory

  • Used for shuffle buffers, join hash tables, sort buffers, aggregation maps
  • Has priority — cannot be evicted by storage
  • If execution memory is insufficient, it spills to disk (external sort/merge)
  • Spilling is expensive — causes disk I/O and recomputation overhead

Borrowing Rules

  1. If execution memory is free, storage can borrow it for caching
  2. If storage memory is free, execution can borrow it for computation
  3. If execution needs memory back and storage borrowed it → storage blocks are evicted
  4. If storage needs memory back and execution borrowed it → storage must wait (execution is never evicted)
⚠️ Common pitfall:

If you cache too aggressively and your workload has heavy shuffles, the cached data will be evicted anyway (wasting the I/O spent caching). Monitor the "Storage" tab in Spark UI — if cached fractions keep dropping, you're over-caching relative to available memory.

GC Tuning — G1GC & CMS

Garbage collection is the #1 cause of executor stalls and task stragglers. The JVM heap has generations: Young Gen (short-lived objects) and Old Gen (long-lived objects).

G1GC (Recommended for Spark 3.x)

  • Default GC for Java 9+ (Spark 3.x typically uses Java 11/17)
  • Region-based — divides heap into equal-sized regions (~2048)
  • Concurrent marking — minimizes stop-the-world pauses
  • Good for heaps > 4GB with target pause times
  • Adapts automatically — less manual tuning needed
G1GC configuration
spark.executor.extraJavaOptions=-XX:+UseG1GC \
  -XX:MaxGCPauseMillis=200 \
  -XX:G1HeapRegionSize=16m \
  -XX:InitiatingHeapOccupancyPercent=35 \
  -XX:ConcGCThreads=4 \
  -XX:+ParallelRefProcEnabled \
  -verbose:gc \
  -XX:+PrintGCDetails \
  -XX:+PrintGCTimeStamps

CMS (Legacy — Java 8)

  • Concurrent Mark-Sweep — reduces pause times for old gen collection
  • Can suffer from fragmentation (no compaction during concurrent phase)
  • Deprecated in Java 9, removed in Java 14
  • Still relevant for Spark 2.x / Java 8 environments
CMS configuration (Java 8)
spark.executor.extraJavaOptions=-XX:+UseConcMarkSweepGC \
  -XX:+UseParNewGC \
  -XX:CMSInitiatingOccupancyFraction=70 \
  -XX:+UseCMSInitiatingOccupancyOnly \
  -XX:NewRatio=2 \
  -XX:SurvivorRatio=8 \
  -verbose:gc \
  -XX:+PrintGCDetails

GC Tuning Best Practices

  1. Increase Young Gen if you see frequent minor GCs with low promotion rates
  2. If full GC is frequent, increase spark.memory.fraction or reduce caching
  3. Use -XX:+PrintGCDetails -XX:+PrintGCTimeStamps to analyze GC logs
  4. Target GC pause time < 200ms for interactive workloads
  5. Consider off-heap memory to reduce GC pressure on large heaps

Serialization — Kryo vs Java

Serialization affects both memory usage (cached data size) and network transfer speed (shuffle).

Java Serialization (Default)

  • Uses java.io.Serializable interface
  • Slow and verbose — stores full class metadata with each object
  • Easy to use — works with any Serializable class
  • Produces large serialized objects (2-5× compared to Kryo)

Kryo Serialization (Recommended)

  • 10× faster than Java serialization
  • Produces compact binary output (often 50-80% smaller)
  • Requires explicit class registration for best performance
  • Not all classes are compatible without registration
Enabling Kryo serialization
# Enable Kryo
spark.serializer=org.apache.spark.serializer.KryoSerializer

# Register classes for optimal performance
spark.kryo.classesToRegister=com.myapp.MyClass,com.myapp.OtherClass

# Require registration (fails fast if unregistered class found)
spark.kryo.registrationRequired=true

# Increase buffer if serialized objects are large
spark.kryoserializer.buffer.max=512m
spark.kryoserializer.buffer=64k
🔑 When Kryo matters most:

Kryo gives the biggest gains for shuffle-heavy workloads (less data over network) and when caching large datasets (more fits in memory). For Spark SQL/DataFrames using Tungsten encoding, the internal serialization already uses compact binary format — Kryo mainly helps RDD operations and UDF object serialization.

Persist, Cache & Storage Levels

cache() vs persist()

  • cache() = shorthand for persist(StorageLevel.MEMORY_ONLY) for RDDs or MEMORY_AND_DISK for DataFrames
  • persist(level) = explicitly choose the storage level
  • Both are lazy — data isn't cached until an action triggers computation
  • Use unpersist() to explicitly free cached data

Storage Levels

Available storage levels
MEMORY_ONLY
  → Store as deserialized Java objects in JVM heap
  → Fastest access, highest memory usage
  → Partitions that don't fit are recomputed on the fly

MEMORY_ONLY_SER
  → Store as serialized byte arrays (use with Kryo)
  → More compact (~2-5× less memory), but CPU cost to deserialize
  → Good when memory is tight but recomputation is expensive

MEMORY_AND_DISK
  → Spill to disk if memory is full (default for DataFrame.cache())
  → Prevents recomputation at the cost of disk I/O
  → Best for expensive computations you can't afford to redo

MEMORY_AND_DISK_SER
  → Serialized in memory, spill to disk
  → Best balance of memory efficiency and fault tolerance

DISK_ONLY
  → Store only on disk — rare, used for very large datasets
  → Useful when you need to persist but have minimal memory

OFF_HEAP
  → Store in off-heap memory (Tachyon/Alluxio or Spark's off-heap)
  → No GC overhead, shared across executors (with external store)
  → Requires spark.memory.offHeap.enabled=true

*_2 variants (e.g., MEMORY_ONLY_2)
  → Replicate each partition on 2 nodes
  → Faster recovery on failure (no recomputation), but 2× memory cost
  → Use for critical datasets in unstable clusters

When to Use persist vs cache

  1. Multiple actions on same DataFrame — cache it to avoid recomputation
  2. Iterative algorithms (ML) — persist training data
  3. Expensive joins/aggregations reused downstream — persist the result
  4. Memory-constrained — use MEMORY_AND_DISK_SER instead of default
  5. Don't cache if data is used only once, or if it's cheap to recompute (reading from local Parquet)

OOM Troubleshooting

Common OOM Scenarios

  • Driver OOM — collect() on large dataset, large broadcast variables, too many small files creating excessive metadata
  • Executor OOM (heap) — data skew causing one partition to be huge, too many cached datasets, complex UDFs holding references
  • Executor OOM (off-heap / container killed) — YARN kills container when total memory exceeds limit. Usually native memory leaks or PySpark memory

Diagnostic Steps

  1. Check Spark UI → Stages → look for skewed tasks (one task processing 10× more data)
  2. Check executor logs for java.lang.OutOfMemoryError: Java heap space vs container killed by YARN
  3. Monitor GC logs — if GC takes >50% of task time, you have memory pressure
  4. Check peak execution memory and peak storage memory in task metrics

Fixes

OOM fixes by scenario
# Driver OOM — never collect large datasets
df.write.parquet("output/")   # instead of df.collect()
spark.driver.memory=8g        # increase if needed

# Executor OOM — data skew
# Increase partitions to reduce per-partition size
spark.sql.shuffle.partitions=400   # default 200

# Repartition skewed data
df.repartition(400, col("skewed_key"))

# Salt the key to distribute skewed partitions
df.withColumn("salt", (rand() * 10).cast("int"))

# Executor OOM — too much caching
df.unpersist()   # free what you don't need
# Use MEMORY_AND_DISK_SER instead of MEMORY_ONLY

# Container killed (memoryOverhead)
spark.executor.memoryOverhead=4g   # increase for PySpark or native libs

# Broadcast join instead of shuffle join for small tables
spark.sql.autoBroadcastJoinThreshold=100m   # 100MB threshold
⚠️ The #1 OOM cause in production:

Data skew. One partition has 10GB while others have 100MB. No amount of memory increase fixes this — you need to repartition, salt keys, or use AQE skew join optimization (spark.sql.adaptive.skewJoin.enabled=true).

Interview Questions

How is executor memory divided in Spark?

Executor memory (JVM heap) is divided into: Reserved Memory (300MB, hardcoded) for internal Spark objects; User Memory = (1 - spark.memory.fraction) × (heap - 300MB) for UDFs and user data structures; Unified Memory = spark.memory.fraction × (heap - 300MB), which is further split into Storage Memory (for caching) and Execution Memory (for shuffles/joins/sorts). The storage/execution split is soft — they can borrow from each other, with execution having eviction priority.

What causes OOM in Spark executors and how do you fix it?

Common causes: 1) Data skew — one partition is disproportionately large. Fix with salting, repartitioning, or AQE skew join. 2) Over-caching — too many DataFrames cached simultaneously. Fix by unpersisting unused data or using serialized storage levels. 3) Large shuffle buffers — too few partitions forcing large per-partition data. Fix by increasing spark.sql.shuffle.partitions. 4) Container killed (not heap OOM) — native memory or PySpark workers exceed memoryOverhead. Fix by increasing spark.executor.memoryOverhead. Always check Spark UI task metrics and GC logs to identify the root cause.

How do you tune GC for Spark executors?

For Spark 3.x (Java 11+), use G1GC with -XX:MaxGCPauseMillis=200 and -XX:InitiatingHeapOccupancyPercent=35. Key steps: 1) Enable GC logging to identify pause patterns. 2) If young GC is too frequent, increase young gen or reduce allocation rate. 3) If full GC occurs, you have memory pressure — increase heap, reduce caching, or move to off-heap. 4) For large heaps (32g+), G1GC's region-based approach handles fragmentation better than CMS. 5) Consider off-heap memory to remove cached data from GC's scope entirely.

When would you use off-heap memory in Spark?

Use off-heap when: 1) GC pauses exceed acceptable thresholds (>500ms) causing task stragglers. 2) Executor heap is large (32g+) where GC overhead becomes significant. 3) Workload involves large broadcast variables or cached datasets that inflate GC roots. 4) You want predictable latency without GC spikes. Trade-offs: off-heap is harder to debug (not visible in heap dumps), requires explicit size configuration, and can leak if there are Spark bugs. Enable with spark.memory.offHeap.enabled=true and spark.memory.offHeap.size.

What's the difference between MEMORY_ONLY and MEMORY_AND_DISK_SER, and when would you pick each?

MEMORY_ONLY: Stores deserialized Java objects in heap. Fastest access (no deserialization), but highest memory footprint and GC pressure. Partitions that don't fit are recomputed. MEMORY_AND_DISK_SER: Stores serialized bytes in memory, spills to disk if full. Lower memory usage (~2-5× less with Kryo), no recomputation, but pays CPU for serialization/deserialization. Pick MEMORY_ONLY for small datasets accessed repeatedly in tight loops. Pick MEMORY_AND_DISK_SER for large datasets where recomputation is expensive and memory is constrained — this is the production default for most workloads.
