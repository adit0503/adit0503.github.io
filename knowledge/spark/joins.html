The Five Join Strategies

Spark's Catalyst optimizer selects from five physical join implementations based on data sizes, join type, and join condition:

Join strategy selection hierarchy
1. Broadcast Hash Join (BHJ)
   → One side fits in memory (< autoBroadcastJoinThreshold)
   → Equi-join only
   → No shuffle needed

2. Sort Merge Join (SMJ)
   → Default for large-large equi-joins
   → Both sides shuffled and sorted by join key
   → Most common in production

3. Shuffle Hash Join (SHJ)
   → One side is much smaller (fits in hash table per partition)
   → Equi-join only
   → Disabled by default (spark.sql.join.preferSortMergeJoin=true)

4. Broadcast Nested Loop Join (BNLJ)
   → Non-equi joins where one side is small enough to broadcast
   → O(N × M) but avoids shuffle for the small side

5. Cartesian Product Join
   → Cross join / no join condition
   → O(N × M) — generates all combinations
   → Use only when intentional (small datasets)

Broadcast Hash Join (BHJ)

The fastest join strategy — avoids shuffle entirely by broadcasting the smaller table to all executors.

How It Works

  1. The smaller table (build side) is collected to the driver
  2. Driver broadcasts it as a hash table to all executors
  3. Each executor probes the hash table with rows from the larger table (stream side)
  4. No shuffle on either side — fully partition-local after broadcast

Requirements

  • Build side must fit in memory: size ≤ spark.sql.autoBroadcastJoinThreshold (default: 10MB)
  • Must be an equi-join (for hash table lookup)
  • Build side can't be the streaming side in a left/right outer join
Broadcast Hash Join examples
from pyspark.sql.functions import broadcast

# Automatic — Spark broadcasts if estimated size < threshold
spark.conf.set("spark.sql.autoBroadcastJoinThreshold", "100m")  # 100MB
result = orders.join(products, "product_id")  # products < 100MB → BHJ

# Explicit broadcast hint (overrides threshold check)
result = orders.join(broadcast(products), "product_id")

# SQL hint syntax
spark.sql("""
  SELECT /*+ BROADCAST(p) */ o.*, p.name
  FROM orders o JOIN products p ON o.product_id = p.id
""")

# Verify in explain:
result.explain()
# == Physical Plan ==
# BroadcastHashJoin [product_id], [id], Inner, BuildRight
# :- FileScan parquet [orders]
# +- BroadcastExchange HashedRelationBroadcastMode
#    +- FileScan parquet [products]
🔑 Key insight:

The 10MB default threshold is very conservative. In production with executors having 8-16g memory, you can safely increase to 100-500MB. The trade-off: broadcast uses driver memory to collect the table and executor memory to hold the hash table. Watch driver OOM if the table is larger than expected (e.g., after a filter that doesn't reduce size as much as estimated).

Sort Merge Join (SMJ)

The default strategy for large-to-large equi-joins. Both tables are shuffled by join key and then merge-joined.

How It Works

  1. Both tables are shuffled (Exchange) so that rows with the same key land on the same partition
  2. Each partition is sorted by the join key
  3. A merge-join algorithm walks both sorted partitions simultaneously (O(N + M) per partition)
  4. Extremely memory-efficient — doesn't need to build a hash table for either side

Characteristics

  • Requires 2 shuffle stages (one per table) + sort on both sides
  • Works well for very large tables (TB-scale) where hash tables won't fit
  • Supports all equi-join types: inner, left/right/full outer, semi, anti
  • Can be shuffle-free if both tables are pre-bucketed on the join key
Sort Merge Join in explain plan
# Physical plan for SMJ:
# == Physical Plan ==
# SortMergeJoin [user_id], [user_id], Inner
# :- Sort [user_id ASC], false, 0
# :  +- Exchange hashpartitioning(user_id, 200)  ← shuffle
# :     +- FileScan parquet [events]
# +- Sort [user_id ASC], false, 0
#    +- Exchange hashpartitioning(user_id, 200)  ← shuffle
#       +- FileScan parquet [users]

# Eliminating shuffle with bucketing:
events.write.bucketBy(256, "user_id").sortBy("user_id").saveAsTable("events_b")
users.write.bucketBy(256, "user_id").sortBy("user_id").saveAsTable("users_b")

# Now join has NO Exchange nodes:
spark.table("events_b").join(spark.table("users_b"), "user_id").explain()
# SortMergeJoin [user_id], [user_id], Inner
# :- FileScan parquet [events_b]   ← no Exchange!
# +- FileScan parquet [users_b]    ← no Exchange!

Shuffle Hash Join (SHJ)

Both tables are shuffled by join key, then the smaller side is built into a hash table per partition.

How It Works

  1. Both tables are shuffled so same keys land on same partition
  2. For each partition, the smaller side is loaded into a hash table
  3. The larger side probes the hash table for matches
  4. No sorting required (unlike SMJ)

When It's Selected

  • spark.sql.join.preferSortMergeJoin=false (disabled by default)
  • One side is ≤ 3× the broadcast threshold per partition (small enough for per-partition hash table)
  • Can be faster than SMJ when one side is much smaller (avoids sort cost)
  • Risk: per-partition hash table may not fit in memory → OOM
Enabling Shuffle Hash Join
# Disabled by default — SMJ is preferred as it's more memory-safe
spark.sql.join.preferSortMergeJoin=false

# Use hint to force SHJ
spark.sql("""
  SELECT /*+ SHUFFLE_HASH(small_table) */ *
  FROM large_table JOIN small_table ON large_table.key = small_table.key
""")

# Good when:
# - One side is significantly smaller per partition
# - Data is already partially sorted (sort overhead > hash build)
# - Join keys have high cardinality (sort is expensive)
⚠️ SHJ risks:

Unlike SMJ which can spill to disk during sort, the hash table in SHJ must fit in memory for each partition. If a partition is skewed (one key dominates), the hash table can blow up memory. Prefer SMJ for production workloads unless you've verified partition sizes.

Broadcast Nested Loop Join (BNLJ)

Used for non-equi joins (e.g., range conditions, inequality joins) when one side is small enough to broadcast.

How It Works

  1. The smaller side is broadcast to all executors (like BHJ)
  2. For each row on the stream side, iterate through ALL rows of the broadcast side
  3. Apply the join condition (can be any expression, not just equality)
  4. O(N × M) complexity — but no shuffle needed

When It's Used

  • Non-equi join conditions: a.date BETWEEN b.start AND b.end
  • Theta joins: a.value > b.threshold
  • One side must be small enough to broadcast
  • Falls back to Cartesian Product if neither side is broadcastable
Broadcast Nested Loop Join example
# Non-equi join — range condition
# "Find all events that fall within each campaign's date range"
result = events.join(
    broadcast(campaigns),
    (events.event_date >= campaigns.start_date) &
    (events.event_date <= campaigns.end_date)
)

# Physical plan shows BroadcastNestedLoopJoin:
# BroadcastNestedLoopJoin BuildRight, Inner,
#   ((event_date >= start_date) AND (event_date <= end_date))
# :- FileScan parquet [events]
# +- BroadcastExchange
#    +- FileScan parquet [campaigns]

# Optimization: if possible, rewrite as equi-join + filter
# (e.g., join on date key, then filter range)

Cartesian Product Join

The most expensive join — produces the cross product of all rows from both sides. Only used when there's no join condition or both sides are too large for broadcast in a non-equi join.

Characteristics

  • Output size = N × M rows
  • No join condition required (or non-equi with both sides too large for broadcast)
  • Spark requires explicit crossJoin or setting spark.sql.crossJoin.enabled=true
  • Use only with very small tables or when cross product is intentionally needed
Cartesian Product Join
# Explicit cross join
result = df1.crossJoin(df2)

# SQL syntax
spark.sql("SELECT * FROM t1 CROSS JOIN t2")

# Accidental cartesian — Spark blocks this by default:
# spark.sql("SELECT * FROM t1, t2")  # Error without spark.sql.crossJoin.enabled

# Enable if intentional:
spark.conf.set("spark.sql.crossJoin.enabled", "true")

# Legitimate use cases:
# - Generating all combinations of small lookup tables
# - Feature engineering: all pairs for similarity computation (small datasets)
# - Calendar/dimension table generation

How Spark Picks a Join Strategy

The Catalyst optimizer uses this decision tree (simplified):

Join strategy selection logic
IF equi-join:
  IF one side ≤ autoBroadcastJoinThreshold (or has broadcast hint):
    → Broadcast Hash Join (BHJ)
  ELIF preferSortMergeJoin=true (default):
    → Sort Merge Join (SMJ)
  ELIF one side is small enough per partition:
    → Shuffle Hash Join (SHJ)
  ELSE:
    → Sort Merge Join (SMJ)

ELIF non-equi join:
  IF one side ≤ autoBroadcastJoinThreshold (or has broadcast hint):
    → Broadcast Nested Loop Join (BNLJ)
  ELSE:
    → Cartesian Product Join (with join condition as filter)

# Size estimation uses:
# - Table statistics (ANALYZE TABLE ... COMPUTE STATISTICS)
# - File sizes from catalog
# - Estimated output of previous operations
# - AQE runtime statistics (Spark 3.0+)
🔑 Why statistics matter:

Spark's size estimates can be wildly wrong without table statistics. A 10GB table filtered to 1MB might still be estimated as 10GB (no filter selectivity stats). Run ANALYZE TABLE or rely on AQE's runtime statistics to get accurate join strategy selection. Wrong estimates = wrong join strategy = orders of magnitude performance difference.

Join Hints

You can override Spark's join strategy selection using hints:

All join hints (Spark 3.0+)
# DataFrame API
from pyspark.sql.functions import broadcast

# BROADCAST hint — force Broadcast Hash Join
large_df.join(broadcast(small_df), "key")

# SQL hints (Spark 3.0+)
SELECT /*+ BROADCAST(t2) */ * FROM t1 JOIN t2 ON t1.key = t2.key
SELECT /*+ MERGE(t1, t2) */ * FROM t1 JOIN t2 ON t1.key = t2.key
SELECT /*+ SHUFFLE_HASH(t2) */ * FROM t1 JOIN t2 ON t1.key = t2.key
SELECT /*+ SHUFFLE_REPLICATE_NL(t2) */ * FROM t1 JOIN t2 ON t1.key = t2.key

# Hint priority (highest to lowest):
# 1. BROADCAST (broadcastjoin, mapjoin)
# 2. MERGE (shuffle_merge, mergejoin, sort_merge)
# 3. SHUFFLE_HASH
# 4. SHUFFLE_REPLICATE_NL (cartesian product with shuffle)

# Multiple hints — highest priority wins
SELECT /*+ BROADCAST(t2), MERGE(t1) */ *  → BROADCAST wins

# DataFrame hint API (alternative to broadcast function)
df2_hinted = df2.hint("broadcast")
result = df1.join(df2_hinted, "key")

Skewed Joins & AQE

Data skew in joins means one join key has disproportionately more records, creating a single bottleneck task that takes far longer than others.

Identifying Skew

  • Spark UI → Stage with join → one task has 10-100× more input/shuffle read
  • One task runs for 30 minutes while others finish in 30 seconds
  • OOM on specific tasks (the skewed partition exceeds memory)

AQE Skew Join Optimization (Spark 3.0+)

AQE automatically detects and handles skew at runtime:

  1. After shuffle write, AQE checks partition sizes
  2. Identifies partitions that are skewed (size > skewedPartitionFactor × median AND > skewedPartitionThresholdInBytes)
  3. Splits the skewed partition into multiple sub-partitions
  4. Replicates the corresponding partition from the other join side to match
  5. Multiple tasks process the sub-partitions in parallel
AQE skew join configuration
# Enable AQE skew join handling
spark.sql.adaptive.enabled=true
spark.sql.adaptive.skewJoin.enabled=true

# When is a partition "skewed"?
# Partition is skewed if BOTH conditions are true:
spark.sql.adaptive.skewJoin.skewedPartitionFactor=5
  # partition_size > 5 × median_partition_size
spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes=256MB
  # AND partition_size > 256MB

# How to split the skewed partition:
spark.sql.adaptive.advisoryPartitionSizeInBytes=128MB
  # Each sub-partition targets ~128MB

Manual Skew Handling (When AQE Isn't Enough)

Manual skew handling techniques
# Technique 1: Key Salting
# Add random salt to skewed key, replicate other side
NUM_SALTS = 20

# Identify hot keys
hot_keys = skewed_df.groupBy("join_key").count() \
    .filter(col("count") > threshold).select("join_key").collect()

# Salt the skewed side
salted = skewed_df.withColumn("salt", (rand() * NUM_SALTS).cast("int"))

# Replicate the other side
replicated = other_df.crossJoin(
    spark.range(NUM_SALTS).withColumnRenamed("id", "salt"))

# Join on composite key
result = salted.join(replicated,
    (salted.join_key == replicated.join_key) &
    (salted.salt == replicated.salt))

# Technique 2: Isolate Hot Keys
# Process hot keys separately with broadcast, union results
hot_key_list = ["key1", "key2"]  # known skewed keys

hot_left = large_df.filter(col("key").isin(hot_key_list))
normal_left = large_df.filter(~col("key").isin(hot_key_list))

hot_right = small_df.filter(col("key").isin(hot_key_list))
normal_right = small_df.filter(~col("key").isin(hot_key_list))

# Broadcast join for hot keys, SMJ for normal
hot_result = hot_left.join(broadcast(hot_right), "key")
normal_result = normal_left.join(normal_right, "key")
final = hot_result.union(normal_result)
🔑 AQE skew join vs manual salting:

Prefer AQE skew join — it's automatic, requires no code changes, and adapts to changing data patterns. Use manual salting only when: AQE doesn't handle your specific pattern (e.g., multi-column skew), you're on Spark < 3.0, or the skew is extreme (single key has 50%+ of data) and you need finer control over the split factor.

Semi & Anti Joins

Left Semi Join

  • Returns rows from the left table that have a match in the right table
  • Only left columns in output (right table used only for filtering)
  • Similar to WHERE EXISTS (subquery) or IN (subquery)
  • More efficient than inner join when you don't need right-side columns

Left Anti Join

  • Returns rows from the left table that do NOT have a match in the right table
  • Similar to WHERE NOT EXISTS (subquery) or NOT IN (subquery)
  • Useful for finding orphaned records or new arrivals
Semi and Anti join examples
# Left Semi Join — "users who placed at least one order"
active_users = users.join(orders, "user_id", "left_semi")
# Equivalent SQL: SELECT * FROM users WHERE EXISTS
#   (SELECT 1 FROM orders WHERE orders.user_id = users.user_id)

# Left Anti Join — "users who never placed an order"
inactive_users = users.join(orders, "user_id", "left_anti")
# Equivalent SQL: SELECT * FROM users WHERE NOT EXISTS
#   (SELECT 1 FROM orders WHERE orders.user_id = users.user_id)

# Why semi/anti are faster than inner + distinct:
# Inner join: shuffles both sides, produces matches, then deduplicates
# Semi join: stops at first match per left row (no duplicates generated)

# Performance comparison:
# BAD — inner join + select left columns + distinct
result = users.join(orders, "user_id", "inner") \
    .select(users.columns).distinct()

# GOOD — left semi (single pass, no dedup needed)
result = users.join(orders, "user_id", "left_semi")

Join Reordering

When joining multiple tables, the order of joins significantly affects performance. Spark's Cost-Based Optimizer (CBO) can reorder joins to minimize intermediate data size.

Enabling Join Reordering

Join reordering configuration
# Enable CBO and join reordering
spark.sql.cbo.enabled=true
spark.sql.cbo.joinReorder.enabled=true
spark.sql.cbo.joinReorder.dp.star.filter=false

# Maximum number of tables in join reorder (default 12)
spark.sql.cbo.joinReorder.dp.threshold=12

# Requires table and column statistics:
ANALYZE TABLE orders COMPUTE STATISTICS
ANALYZE TABLE orders COMPUTE STATISTICS FOR COLUMNS user_id, product_id
ANALYZE TABLE users COMPUTE STATISTICS
ANALYZE TABLE products COMPUTE STATISTICS

Manual Join Ordering Rules

  1. Filter first — apply predicates before joins to reduce table sizes
  2. Join small with large first — smallest result set feeds into next join
  3. Broadcast smallest tables — eliminate shuffles for dimension tables
  4. Join on partition key — if data is bucketed, join bucket-compatible tables first
Manual join ordering example
# BAD: join two large tables first, then filter
result = orders.join(events, "user_id") \     # huge shuffle
    .join(broadcast(products), "product_id") \
    .filter(col("order_date") > "2024-01-01")

# GOOD: filter first, then join with broadcast, then large join
filtered_orders = orders.filter(col("order_date") > "2024-01-01")
with_products = filtered_orders.join(broadcast(products), "product_id")
result = with_products.join(events, "user_id")
# First join: broadcast (no shuffle), Second join: smaller left side → less shuffle
⚠️ CBO limitations:

Join reordering only works with accurate statistics. If you don't run ANALYZE TABLE, the CBO has no information to optimize. Also, CBO currently only handles inner joins for reordering — outer joins maintain their specified order.

Interview Questions

When does Spark choose Broadcast Hash Join vs Sort Merge Join?

Spark chooses Broadcast Hash Join when one side of an equi-join has an estimated size ≤ spark.sql.autoBroadcastJoinThreshold (default 10MB) or when a broadcast hint is provided. The smaller side is broadcast as a hash table to all executors — no shuffle needed. Sort Merge Join is chosen when both sides exceed the broadcast threshold — both sides are shuffled by join key, sorted, and merged. BHJ is O(N) with no shuffle; SMJ is O(N log N + M log M) with two shuffles. BHJ is dramatically faster but limited by memory. In production, increase the threshold to 100-500MB and ensure table statistics are accurate.

How do you handle data skew in joins?

Three approaches, in order of preference: 1) AQE Skew Join (Spark 3.0+) — enable spark.sql.adaptive.skewJoin.enabled=true. AQE detects skewed partitions at runtime and automatically splits them, replicating the other side. Zero code changes. 2) Key Salting — append random salt (0-N) to the skewed key on the large side, replicate the small side N times with all salt values. Distributes the hot key across N partitions. 3) Isolate Hot Keys — process known skewed keys separately with broadcast join, process remaining keys with normal join, union results. Choose based on: AQE for most cases, salting for extreme skew (single key = 50%+ data), isolation for a few known problematic keys.

What is the broadcast threshold and how to change it?

spark.sql.autoBroadcastJoinThreshold (default: 10MB) is the maximum estimated size of a table that Spark will automatically broadcast for a join. Change it via: spark.conf.set("spark.sql.autoBroadcastJoinThreshold", "100m") or at submit time with --conf. Set to -1 to disable auto-broadcast entirely. The estimate comes from table statistics (catalog), file sizes, or CBO estimates. Pitfall: if statistics are stale, Spark may broadcast a table that's grown beyond memory limits, causing driver OOM. Always ensure stats are up to date or use explicit broadcast() hints when you know the table is small.

What's the difference between left_semi and left_anti joins? When would you use each?

Left Semi: Returns left-side rows that HAVE a match on the right. No right-side columns in output. Equivalent to WHERE EXISTS. Use for: "find users who have orders." Left Anti: Returns left-side rows that have NO match on the right. Equivalent to WHERE NOT EXISTS. Use for: "find users without orders" or "find new records not yet in target table" (incremental loads). Both are more efficient than equivalent inner/left join + filter patterns because: 1) they stop at first match (no duplicate generation), 2) no deduplication step needed, 3) only left columns are shuffled/output.

How can you eliminate shuffle in a join entirely?

Three ways to achieve shuffle-free joins: 1) Broadcast Hash Join — broadcast the small side. No shuffle on either side. Limited by memory. 2) Bucketing — pre-partition both tables on the join key with the same bucket count. At join time, Spark recognizes matching partitioners and skips shuffle. Requires writing tables in bucketed format upfront. 3) Co-located data — if both DataFrames were already shuffled by the same key in a previous stage (same partitioner), the join reuses existing partitioning. Check explain() for Exchange nodes — if none appear under the join, no shuffle occurs.
