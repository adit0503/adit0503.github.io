Spark SQL, Catalyst & Tungsten

The optimizer and execution engine that make Spark SQL fast — from logical plan generation through Catalyst's rule-based and cost-based optimization to Tungsten's whole-stage code generation.

Query Execution Flow

Every Spark SQL query (whether written as DataFrame API or SQL string) passes through the same pipeline:

Query execution phases
SQL / DataFrame API
       ↓
┌─────────────────────────────────────────┐
│ 1. PARSING                              │
│    SQL string → Unresolved Logical Plan  │
│    DataFrame API → Unresolved Logical Plan│
└─────────────────────────────────────────┘
       ↓
┌─────────────────────────────────────────┐
│ 2. ANALYSIS (Catalog resolution)        │
│    Resolve table names, column names,   │
│    data types using the Catalog         │
│    → Analyzed Logical Plan              │
└─────────────────────────────────────────┘
       ↓
┌─────────────────────────────────────────┐
│ 3. LOGICAL OPTIMIZATION (Catalyst)      │
│    Apply rule-based optimizations:      │
│    predicate pushdown, column pruning,  │
│    constant folding, filter combining   │
│    → Optimized Logical Plan             │
└─────────────────────────────────────────┘
       ↓
┌─────────────────────────────────────────┐
│ 4. PHYSICAL PLANNING                    │
│    Convert logical ops to physical:     │
│    Select join strategy, scan method,   │
│    sort implementation. CBO picks best. │
│    → Physical Plan (SparkPlan)          │
└─────────────────────────────────────────┘
       ↓
┌─────────────────────────────────────────┐
│ 5. CODE GENERATION (Tungsten)           │
│    Whole-stage codegen fuses operators  │
│    into optimized Java bytecode         │
│    → Generated code + RDDs              │
└─────────────────────────────────────────┘
       ↓
   EXECUTION on cluster
🔑 Key insight:

The DataFrame API and SQL are semantically identical — both produce the same logical plan. There is zero performance difference between df.filter(col("x") > 5).select("y") and spark.sql("SELECT y FROM t WHERE x > 5"). They go through the same optimizer.

Catalyst Optimizer Internals

Catalyst is a rule-based optimizer with cost-based extensions. It transforms logical plans using pattern-matching rules organized into batches that run iteratively until the plan stabilizes (fixed-point).

Rule-Based Optimization (RBO)

Rules are applied in batches. Each batch runs repeatedly until no rules produce changes or a max iteration limit is reached:

Predicate Pushdown

  • Moves filter conditions as close to the data source as possible
  • Pushes predicates below joins, projections, and aggregations
  • Pushes predicates into data sources (Parquet/ORC skip row groups, JDBC adds WHERE clause)
Predicate pushdown example
# Before optimization:
# Project [name]
#   Filter [age > 25]
#     Join [users.id = orders.user_id]
#       Scan [users]
#       Scan [orders]

# After predicate pushdown:
# Project [name]
#   Join [users.id = orders.user_id]
#     Filter [age > 25]      ← pushed below join
#       Scan [users]         ← further pushed into scan (partition/row-group pruning)
#     Scan [orders]

# Even pushed to data source level:
# FileScan parquet [users] PushedFilters: [IsNotNull(age), GreaterThan(age,25)]

Column Pruning

  • Only reads columns that are actually used downstream
  • Propagates required columns up from the final projection
  • Columnar formats (Parquet, ORC) benefit enormously — skip entire column chunks

Constant Folding

  • Evaluates constant expressions at compile time
  • WHERE date > '2024-01-01' AND 1=1 → WHERE date > '2024-01-01'
  • SELECT 2 + 3 AS x → SELECT 5 AS x

Other Key Rules

  • CombineFilters: merges adjacent filters into one (AND)
  • PushDownPredicatesThrough: pushes through Union, Join, Aggregate
  • SimplifyConditionals: simplifies CASE WHEN true THEN x → x
  • ReplaceNullWithFalse: in filter context, NULL evaluates to false
  • EliminateOuterJoin: converts outer join to inner when null-filtering conditions exist
  • PropagateEmptyRelation: short-circuits when input is provably empty

Cost-Based Optimization (CBO)

CBO uses table and column statistics to make decisions the RBO cannot:

  • Join Reordering: with N tables, there are N! possible orderings. CBO uses dynamic programming to find the ordering that minimizes intermediate result sizes
  • Build Side Selection: in broadcast/hash joins, pick the smaller side as build
  • Join Strategy Selection: choose between BHJ, SMJ, SHJ based on actual estimated sizes
Enabling CBO
# Enable CBO
spark.sql.cbo.enabled=true
spark.sql.cbo.joinReorder.enabled=true

# Collect statistics
ANALYZE TABLE orders COMPUTE STATISTICS
ANALYZE TABLE orders COMPUTE STATISTICS FOR COLUMNS user_id, amount, order_date

# Column stats collected: min, max, num_nulls, distinct_count, avg_col_len, max_col_len
# Optional histograms (better for skewed data):
ANALYZE TABLE orders COMPUTE STATISTICS FOR COLUMNS user_id
-- generates equi-height histogram with 254 buckets by default

# Check statistics
DESC EXTENDED orders
-- shows: Statistics: 5.2 GB, 120000000 rows
⚠️ Stale statistics:

If you load new data but don't re-run ANALYZE, the CBO will use outdated stats. A table that grew from 100MB to 10GB will still be estimated at 100MB — leading to incorrect broadcast join selection (driver OOM). Schedule ANALYZE as part of your ETL pipeline, or rely on AQE runtime stats.

Tungsten Execution Engine

Tungsten (Spark 1.5+) is the execution backend that bypasses JVM object model overhead. It addresses three problems:

1. Memory Management — UnsafeRow

  • Traditional JVM: each Row object has 16-byte header + field pointers + actual data → 5× overhead
  • UnsafeRow: stores data in a flat binary format on off-heap memory (or on-heap byte arrays)
  • Fixed-length fields stored inline, variable-length (strings) stored with offset+length pointers
  • No garbage collection pressure — memory is explicitly managed by Spark's memory manager
  • Comparison/hashing operates directly on bytes (no deserialization to Java objects)
UnsafeRow binary layout
# Row with schema: (int, string, long)
# 
# ┌──────────────────────────────────────────────────────┐
# │ Null Bitmap (8 bytes)  │ Fixed: int(4) │ Fixed: offset+len(8) │ Fixed: long(8) │
# │ [bit flags for nulls]  │ 42            │ points to var region  │ 1625097600     │
# ├──────────────────────────────────────────────────────┤
# │ Variable-length region: "hello world" (UTF-8 bytes)  │
# └──────────────────────────────────────────────────────┘
#
# Total: ~40 bytes vs ~120 bytes for Java Object representation
# 
# Key benefits:
# - No GC (managed memory)
# - Cache-friendly (contiguous memory)
# - Direct binary comparison (no boxing/unboxing)

2. Cache-Aware Computation

  • Algorithms designed to fit within L1/L2 CPU cache lines (64 bytes)
  • Sort algorithms operate on binary key prefixes stored contiguously
  • Hash tables use open addressing with linear probing (cache-friendly vs chaining)
  • Cache miss reduction: 10-100× speedup for sort and hash operations vs Java collections

3. Code Generation

  • Instead of interpreting an operator tree (virtual dispatch per row per operator), generate a specialized Java function for the entire pipeline
  • Eliminates virtual function calls, auto-boxing, and unnecessary data movement
  • Generated code is compiled to bytecode by Janino (embedded Java compiler)

Whole-Stage Code Generation

Whole-stage codegen (WSCG) is the most impactful Tungsten optimization. It fuses an entire pipeline of operators into a single optimized function.

Without Codegen (Volcano Iterator Model)

Traditional execution: virtual calls per row
# For query: SELECT name FROM users WHERE age > 25
# 
# Execution without codegen:
# 
# for each row in scan:
#     row = scan.next()                    ← virtual dispatch
#     if filter.evaluate(row):             ← virtual dispatch
#         result = project.evaluate(row)   ← virtual dispatch
#         output(result)                   ← virtual dispatch
#
# 4 virtual function calls per row × millions of rows = massive overhead
# CPU branch prediction fails, instruction cache thrashed

With Whole-Stage CodeGen

Generated code: tight inner loop
# Spark generates something like:
#
# while (scan.hasNext()) {
#     UnsafeRow row = scan.next();
#     int age = row.getInt(1);          // direct field access
#     if (age > 25) {                   // inlined filter
#         outputRow.setString(0, row.getString(0)); // inlined projection
#         append(outputRow);
#     }
# }
#
# Single tight loop — no virtual dispatch, CPU branch prediction works,
# fits in instruction cache, SIMD-friendly

# In explain() output, codegen stages marked with asterisk (*):
# *(1) Filter (age > 25)
# +- *(1) ColumnarToRow
#    +- FileScan parquet [name, age]
#
# The *(1) means these operators are fused into one codegen stage

When Codegen Breaks

  • Too many columns: generated method exceeds 8000 bytes (JIT won't compile) → spark.sql.codegen.hugeMethodLimit=8000
  • Complex expressions: deeply nested CASE/WHEN, very large IN lists
  • Python UDFs: force a boundary — data must be serialized to Python and back
  • Operations without codegen support: some external data sources, certain aggregate functions
🔑 Performance impact:

Whole-stage codegen delivers 2-10× performance improvement for CPU-bound queries. It's enabled by default (spark.sql.codegen.wholeStage=true). If you see operators WITHOUT asterisks in explain(), investigate why codegen was disabled — it often means a UDF boundary or unsupported operator.

AQE from SQL Perspective

Dynamic Partition Pruning (DPP)

In star-schema queries, the fact table is joined with dimension tables that have filters. DPP propagates the dimension filter to prune fact table partitions at scan time:

Dynamic partition pruning
# Star schema query:
SELECT f.amount, d.category
FROM facts f
JOIN dim_product d ON f.product_id = d.id
WHERE d.category = 'Electronics'

# Without DPP: scan ALL fact partitions, then join and filter
# With DPP: 
#   1. Spark first executes the dimension filter (small, fast)
#   2. Collects matching product_ids
#   3. Pushes them as IN-list filter into the fact table scan
#   4. Fact table skips partitions that don't contain those product_ids

# Enable:
spark.sql.optimizer.dynamicPartitionPruning.enabled=true  # default true in 3.0+

# DPP works when:
# - Fact table is partitioned by the join key
# - Dimension filter is selective
# - Dimension side is small enough to broadcast

Runtime Filter Insertion

  • AQE can insert Bloom filters at runtime based on join-side statistics
  • The filter is pushed to the scan of the larger side, skipping non-matching rows early
  • spark.sql.optimizer.runtime.bloomFilter.enabled=true

Reading Physical Plans

How to read explain() output
df.explain(True)  # shows all plan phases
df.explain("cost")  # shows cost estimates
df.explain("formatted")  # readable format with stats

# Key operators to recognize:
# 
# Exchange         → SHUFFLE (expensive!) — data redistributed across partitions
# Sort             → Full sort of data — check if needed or can be eliminated
# HashAggregate    → Partial + final aggregation (efficient)
# SortMergeJoin    → Both sides shuffled and sorted (large join)
# BroadcastHashJoin → Small side broadcast (fast, no shuffle)
# FileScan         → Reading from storage
#   PushedFilters: → Predicates pushed to data source
#   PartitionFilters: → Partition pruning applied
# 
# *(1) prefix     → Whole-stage codegen active (good!)
# No * prefix     → Codegen disabled (investigate why)
#
# WholeStageCodegen stages are numbered *(1), *(2), etc.
# Each represents a codegen boundary — fewer is better

# Example plan reading:
# == Physical Plan ==
# *(3) HashAggregate(keys=[user_id], functions=[sum(amount)])
# +- Exchange hashpartitioning(user_id, 200)    ← SHUFFLE (stage boundary)
#    +- *(2) HashAggregate(keys=[user_id], functions=[partial_sum(amount)])
#       +- *(2) Project [user_id, amount]
#          +- *(2) Filter (amount > 100)
#             +- *(1) ColumnarToRow
#                +- FileScan parquet [user_id, amount, status]
#                     PushedFilters: [GreaterThan(amount,100)]
#
# Reading bottom-up:
# 1. FileScan reads only needed columns, pushes filter to Parquet
# 2. ColumnarToRow converts columnar Parquet batches to rows (codegen stage 1)
# 3. Filter + Project + partial HashAggregate fused in codegen stage 2
# 4. Exchange = shuffle by user_id (200 partitions)
# 5. Final HashAggregate completes the sum in codegen stage 3
🔑 Red flags in physical plans:

1) Multiple Exchange nodes — can you eliminate with broadcast or bucketing? 2) Sort before SortMergeJoin when data is already sorted — consider bucketing. 3) BroadcastNestedLoopJoin — indicates non-equi join, very slow for large data. 4) Missing PushedFilters — your predicate isn't pushing down to the source. 5) No asterisk (*) — codegen disabled, check for UDF boundaries.

Interview Questions

What are the phases of Spark SQL query execution?

1) Parsing: SQL/DataFrame → Unresolved Logical Plan (AST). 2) Analysis: Resolve table/column references using the Catalog → Analyzed Logical Plan. 3) Logical Optimization: Catalyst applies rules (predicate pushdown, column pruning, constant folding, filter combining) iteratively → Optimized Logical Plan. 4) Physical Planning: Convert logical operators to physical (select join strategy, scan type). CBO picks optimal plan using statistics. 5) Code Generation: Tungsten's whole-stage codegen fuses operators into compiled Java bytecode. 6) Execution: Generated code runs as RDD tasks on the cluster. All DataFrame and SQL queries follow the same pipeline — they're semantically equivalent.

How does predicate pushdown work in Spark SQL?

Predicate pushdown operates at two levels: 1) Logical level: The Catalyst optimizer moves filter conditions as close to the source as possible — below joins, through projections, below aggregations (when safe). This reduces the amount of data flowing through the plan. 2) Physical level: Pushed filters are sent to the data source connector. For Parquet/ORC, this enables row group skipping using min/max statistics and dictionary filtering. For JDBC, it adds WHERE clauses to the SQL pushed to the database. For Delta/Iceberg, it enables data file skipping using manifest-level stats. You can verify pushdown in explain() by checking PushedFilters: in the FileScan node.

What is Whole-Stage Code Generation and why is it important?

WSCG fuses multiple physical operators (filter, project, aggregate, etc.) into a single optimized Java function that processes rows in a tight loop. Without codegen: the Volcano iterator model calls virtual functions for each operator for each row — millions of virtual dispatches, CPU branch prediction failures, and instruction cache thrashing. With codegen: operators are compiled into a single method — no virtual dispatch, the JIT compiler can optimize the loop, CPU pipelines and caches work efficiently. Result: 2-10× speedup for CPU-bound queries. In explain(), codegen stages are marked with *(N). Boundaries occur at shuffles, Python UDFs, or operators that don't support codegen. Enabled by default via spark.sql.codegen.wholeStage=true.

How does CBO differ from rule-based optimization?

Rule-Based (RBO): Applies deterministic transformation rules regardless of data characteristics — predicate pushdown always pushes filters down, column pruning always removes unused columns. These are always beneficial. Cost-Based (CBO): Uses collected statistics (table sizes, column cardinalities, histograms) to make data-dependent decisions — which join order minimizes intermediate data, which table should be the broadcast/build side, whether to use BHJ vs SMJ. CBO requires ANALYZE TABLE to collect stats and spark.sql.cbo.enabled=true. Without stats, CBO falls back to file-size estimates which can be wildly inaccurate (e.g., after heavy filtering). AQE partially addresses this by using runtime statistics from completed shuffle stages.

What is Dynamic Partition Pruning and when does it apply?

DPP optimizes star-schema queries where a filtered dimension table is joined to a large fact table. Instead of scanning the entire fact table and filtering post-join, Spark: 1) Executes the dimension filter first (fast, small table). 2) Collects the matching join keys. 3) Pushes them as a runtime filter into the fact table scan. 4) The fact table skips entire partitions that don't contain matching keys. Requirements: fact table must be partitioned by the join key, dimension filter must be selective, the dimension side must be small enough to broadcast. Enabled by default in Spark 3.0+ (spark.sql.optimizer.dynamicPartitionPruning.enabled=true). This can reduce fact table scan volume by 10-100× for selective dimension filters.
