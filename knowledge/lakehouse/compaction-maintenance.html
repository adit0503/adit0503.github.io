Essential maintenance operations for lakehouse tables — compaction strategies, vacuum/snapshot expiry, metadata maintenance, scheduling, and monitoring to keep tables performant.

Why Table Maintenance Is Critical

Lakehouse tables degrade over time without active maintenance. The three core problems:

Small Files Problem

  • Streaming ingestion creates many small files (one per micro-batch per partition)
  • Each file has fixed overhead: metadata reads, file open/close, Parquet footer parsing
  • 1000 small files (1MB each) is far slower to read than 8 large files (125MB each)
  • Query planning time scales with file count (manifest scanning, listing)

Dead Files

  • UPDATE and DELETE operations mark old files as removed but don't physically delete them
  • These orphaned files consume storage indefinitely
  • Storage costs grow unbounded without cleanup

Metadata Bloat

  • Each commit adds to the transaction log / metadata layer
  • Thousands of small manifests (Iceberg) or JSON commits (Delta) slow down query planning
  • Snapshot count grows: each one references manifest lists that reference manifests
🔑 Bottom line:

Without maintenance, query performance degrades linearly with write activity. A table that was fast when first created becomes progressively slower. Maintenance is not optional — it's part of operating a lakehouse.

Compaction — Merging Small Files

Compaction combines multiple small files into fewer, larger files (target: 128MB–1GB depending on the table and engine).

Bin-Packing

  • Groups small files and rewrites them into files of target size
  • Preserves existing sort order — doesn't re-sort data
  • Fastest compaction strategy (minimal CPU, mostly I/O bound)
  • Use for general-purpose file consolidation

Target File Size

  • 128MB – 256MB: Good for streaming tables with frequent reads, lower latency
  • 512MB – 1GB: Good for batch analytics tables with scan-heavy queries
  • Larger files = fewer files = faster planning, but slower individual file reads for selective queries
Bin-pack compaction across formats
-- Delta Lake: OPTIMIZE (bin-pack)
OPTIMIZE my_table;
OPTIMIZE my_table WHERE date = '2025-01-15';

-- Iceberg: rewrite_data_files with binpack strategy
CALL catalog.system.rewrite_data_files(
    table => 'db.my_table',
    strategy => 'binpack',
    options => map(
        'target-file-size-bytes', '134217728',   -- 128MB
        'min-file-size-bytes', '67108864',       -- 64MB (skip files above this)
        'max-file-size-bytes', '201326592'       -- 192MB
    )
);

-- Hudi: compaction (MOR tables only)
-- Merges log files into base files
spark.sql("CALL run_compaction(table => 'my_table', op => 'schedule')")
spark.sql("CALL run_compaction(table => 'my_table', op => 'run')")

Sorting During Compaction

Beyond just merging files, compaction can also re-sort data to improve data skipping effectiveness.

Z-ORDER (Multi-Dimensional Clustering)

  • Interleaves bits of multiple sort columns using a Z-curve (Morton code)
  • Each file ends up with tight min/max ranges for all Z-ordered columns
  • Enables file-skipping on any combination of the Z-ordered columns
  • Best for 2-4 high-cardinality columns used together in queries

Hilbert Curves

  • Alternative space-filling curve that preserves locality better than Z-curve
  • Better min/max clustering for some data distributions
  • Used in Iceberg's sort-based compaction and some Databricks optimizations

Linear Sort

  • Standard sort on one column (most common: timestamp or primary key)
  • Simple but only helps predicates on the sort column
  • Fastest compaction (standard merge-sort) — good when queries always filter on one column
Sort-based compaction
-- Delta: Z-ORDER during OPTIMIZE
OPTIMIZE my_table ZORDER BY (customer_id, product_category);

-- Iceberg: sort-based compaction
CALL catalog.system.rewrite_data_files(
    table => 'db.my_table',
    strategy => 'sort',
    sort_order => 'customer_id ASC NULLS LAST, order_date DESC'
);

-- Iceberg: Z-ORDER via sort with zorder function
CALL catalog.system.rewrite_data_files(
    table => 'db.my_table',
    strategy => 'sort',
    sort_order => 'zorder(customer_id, product_category)'
);
💡 When to sort vs bin-pack:

Use bin-pack for tables where you just need to reduce file count (streaming ingest cleanup). Use sort-based compaction for analytical tables where query performance on specific filter columns matters. Sort is more expensive (full data shuffle + sort) but gives better read performance.

Vacuum & Expire Snapshots

After compaction rewrites files, old files remain on disk. Vacuum (Delta), expire_snapshots (Iceberg), and clean (Hudi) physically delete them.

Retention Considerations

  • Time travel — files must be retained for the time-travel window (default: 7 days Delta, configurable for Iceberg)
  • Concurrent readers — active queries may be reading old snapshots; vacuuming those files causes failures
  • Compliance — some regulations require data retention; vacuum must respect these
  • Rule of thumb — retention ≥ max(longest_running_query, time_travel_window, compliance_requirement)
Vacuum/expiry across formats
-- Delta: VACUUM
VACUUM my_table RETAIN 168 HOURS;  -- 7 days
VACUUM my_table DRY RUN;           -- preview only

-- Iceberg: expire_snapshots + remove_orphan_files
CALL catalog.system.expire_snapshots(
    table => 'db.my_table',
    older_than => TIMESTAMP '2025-01-08 00:00:00',
    retain_last => 5
);

CALL catalog.system.remove_orphan_files(
    table => 'db.my_table',
    older_than => TIMESTAMP '2025-01-08 00:00:00'
);

-- Hudi: clean (remove old file slices)
spark.sql("CALL run_clean(table => 'my_table')")
-- Config: hoodie.cleaner.commits.retained = 10

Metadata Maintenance

Beyond data files, the metadata layer itself needs maintenance.

Iceberg Manifest Rewriting

  • Over time, manifests become fragmented (many small manifests from many commits)
  • Rewriting manifests consolidates them, improving query planning speed
  • rewrite_manifests creates new, optimally-sized manifests

Delta Checkpoint Optimization

  • Checkpoints are auto-created every 10 commits
  • For very active tables, checkpoint files themselves can get large
  • Multi-part checkpoints split large checkpoints into smaller pieces
Metadata maintenance operations
-- Iceberg: rewrite manifests for faster planning
CALL catalog.system.rewrite_manifests('db.my_table');

-- Iceberg: clean up metadata files
-- (old metadata.json files accumulate)
-- Configure: write.metadata.delete-after-commit.enabled = true
-- Or: write.metadata.previous-versions-max = 100

-- Delta: force checkpoint creation
-- (automatic every 10 commits, but can be triggered)
from delta.tables import DeltaTable
dt = DeltaTable.forPath(spark, "/path/to/table")
dt.generate("symlink_format_manifest")  -- for Presto/Trino compatibility

-- Hudi: metadata table compaction
-- Hudi's internal metadata table also needs compaction
"hoodie.metadata.compact.max.delta.commits": 10

Delta OPTIMIZE + VACUUM Workflow

Complete Delta maintenance workflow
-- Step 1: Compact small files
OPTIMIZE catalog.db.orders
WHERE order_date >= current_date() - INTERVAL 7 DAYS
ZORDER BY (customer_id);

-- Step 2: Remove old files
VACUUM catalog.db.orders RETAIN 168 HOURS;

-- Step 3: Analyze table for statistics (optional, improves CBO)
ANALYZE TABLE catalog.db.orders COMPUTE STATISTICS FOR ALL COLUMNS;

-- Scheduling: run OPTIMIZE daily, VACUUM weekly
-- OPTIMIZE on recent partitions (where small files accumulate)
-- VACUUM on entire table (old files across all partitions)

Iceberg Maintenance Workflow

Complete Iceberg maintenance workflow
-- Step 1: Compact data files (merge small files + apply deletes)
CALL catalog.system.rewrite_data_files(
    table => 'db.orders',
    strategy => 'binpack',
    options => map('target-file-size-bytes', '134217728')
);

-- Step 2: Rewrite manifests for optimal query planning
CALL catalog.system.rewrite_manifests('db.orders');

-- Step 3: Expire old snapshots
CALL catalog.system.expire_snapshots(
    table => 'db.orders',
    older_than => TIMESTAMP '2025-01-08 00:00:00',
    retain_last => 3
);

-- Step 4: Remove orphan files (files not in any snapshot)
CALL catalog.system.remove_orphan_files(
    table => 'db.orders',
    older_than => TIMESTAMP '2025-01-08 00:00:00'
);

-- ORDER MATTERS:
-- 1. rewrite_data_files first (creates new clean files)
-- 2. expire_snapshots (makes old snapshots deletable)
-- 3. remove_orphan_files last (cleans up physical files)
⚠️ Order matters for Iceberg:

Always expire_snapshots before remove_orphan_files. If you remove orphan files while snapshots still reference them, you'll corrupt the table. Expiring snapshots first ensures files are truly unreferenced before deletion.

Hudi Compaction + Clean Workflow

Complete Hudi maintenance workflow
# MOR Table: Compaction (merge logs into base files)
# Option 1: Inline (during writes)
hudi_options = {
    "hoodie.compact.inline": "true",
    "hoodie.compact.inline.max.delta.commits": 5,
}

# Option 2: Async compaction (separate job)
spark.sql("""
    CALL run_compaction(
        table => 'db.orders',
        op => 'run',
        options => map('compaction-strategy',
            'org.apache.hudi.table.action.compact.strategy.BoundedIOCompactionStrategy')
    )
""")

# Clean: remove old file slices
# Config in write job:
hudi_clean_options = {
    "hoodie.cleaner.policy": "KEEP_LATEST_COMMITS",
    "hoodie.cleaner.commits.retained": 10,
    "hoodie.clean.automatic": "true",  # clean during writes
}

# Archive: compress timeline metadata
# Old timeline entries archived to .hoodie/archived/
hudi_archive_options = {
    "hoodie.archive.automatic": "true",
    "hoodie.keep.min.commits": 20,
    "hoodie.keep.max.commits": 30,
}

Scheduling & Automation

When to Run

  • Off-peak hours — maintenance competes with production reads for I/O and compute
  • After heavy write periods — streaming tables accumulate small files during the day
  • Frequency: OPTIMIZE daily (hot partitions), VACUUM weekly, manifest rewrite weekly

Automation with Airflow

Airflow DAG for table maintenance
from airflow import DAG
from airflow.providers.apache.spark.operators.spark_submit import SparkSubmitOperator
from datetime import datetime, timedelta

default_args = {
    "owner": "data-platform",
    "retries": 2,
    "retry_delay": timedelta(minutes=10),
}

with DAG(
    "lakehouse_maintenance",
    default_args=default_args,
    schedule_interval="0 2 * * *",  # 2 AM daily
    start_date=datetime(2025, 1, 1),
    catchup=False,
) as dag:

    optimize_orders = SparkSubmitOperator(
        task_id="optimize_orders",
        application="/jobs/maintenance/optimize.py",
        conf={
            "spark.sql.shuffle.partitions": "200",
            "spark.executor.memory": "8g",
        },
        application_args=["--table", "silver.orders", "--days-back", "7"],
    )

    vacuum_orders = SparkSubmitOperator(
        task_id="vacuum_orders",
        application="/jobs/maintenance/vacuum.py",
        application_args=["--table", "silver.orders", "--retain-hours", "168"],
    )

    optimize_orders >> vacuum_orders

Monitoring

Key metrics to track for table health:

  • File count per partition — alert when > 1000 files in a single partition
  • Average file size — should be close to target (128MB–1GB); alert when avg < 32MB
  • Metadata size — manifest count (Iceberg), transaction log size (Delta)
  • Snapshot count — unbounded growth means expire_snapshots isn't running
  • Compaction lag (Hudi MOR) — number of uncompacted log files per file group
  • Dead file storage — total bytes in removed-but-not-vacuumed files
Monitoring queries
-- Iceberg: file count and size stats
SELECT
    COUNT(*) AS file_count,
    SUM(file_size_in_bytes) / (1024*1024*1024) AS total_gb,
    AVG(file_size_in_bytes) / (1024*1024) AS avg_mb,
    MIN(file_size_in_bytes) / (1024*1024) AS min_mb,
    MAX(file_size_in_bytes) / (1024*1024) AS max_mb
FROM catalog.db.orders.files;

-- Iceberg: snapshot count
SELECT COUNT(*) AS snapshot_count FROM catalog.db.orders.snapshots;

-- Delta: file stats via DESCRIBE DETAIL
DESCRIBE DETAIL my_table;
-- Returns: numFiles, sizeInBytes, ...

-- Delta: check small files
SELECT
    input_file_name() AS file_path,
    COUNT(*) AS row_count
FROM my_table
GROUP BY input_file_name()
HAVING row_count < 1000  -- suspiciously small files

Common Pitfalls

⚠️ Pitfall 1: Vacuuming too aggressively

Setting retention to 0 hours or very short periods breaks time travel and can fail concurrent queries. Always ensure retention > max(longest_query_duration, time_travel_SLA).

⚠️ Pitfall 2: Compaction during peak reads

Compaction rewrites files, which means concurrent readers may see file-not-found if the old files are removed too quickly. Schedule compaction during low-traffic windows. For Iceberg, readers use snapshot isolation so this is less of a concern — but resource contention (CPU, I/O) still applies.

⚠️ Pitfall 3: Manifest explosion (Iceberg)

If you write thousands of tiny commits (streaming micro-batches), each creates a new manifest. Manifest count grows linearly with commits. Run rewrite_manifests regularly or increase commits-per-manifest-group setting.

⚠️ Pitfall 4: Never running maintenance at all

The most common pitfall. Tables that were fast when created become progressively slower over weeks/months. If no one owns maintenance, it doesn't happen. Make it a DAG in your orchestrator and monitor it.

Interview Questions

Why is compaction needed in a lakehouse?

Lakehouse tables accumulate small files over time — especially with streaming ingestion (one file per micro-batch per partition) and update-heavy workloads (each MERGE creates new files). Small files degrade read performance because: (1) each file has fixed overhead (open, read footer, close), (2) query planning scans file metadata proportional to file count, (3) parallelism is limited by file count for very small files. Compaction merges small files into larger ones (target 128MB–1GB), dramatically reducing file count and improving both planning time and read throughput.

What happens if you never run VACUUM?

Storage grows indefinitely. Every UPDATE, DELETE, and MERGE creates new data files and logically removes old ones — but the old files remain physically on disk. Without VACUUM: (1) Storage costs increase linearly with write activity (you're paying for current + all historical versions). (2) File listings become slower (more files to enumerate in object storage). (3) Time travel continues to work (the upside). For a table with 1TB of active data and daily full-table updates, you could accumulate 7TB+ of dead files in a week. VACUUM is essential for cost control.

How should you schedule table maintenance in production?

Use your orchestrator (Airflow, Dagster, Prefect) to schedule maintenance as a DAG: (1) OPTIMIZE/compact daily during off-peak hours — target partitions with recent writes. (2) VACUUM/expire_snapshots weekly with safe retention (7+ days). (3) Manifest rewrite (Iceberg) weekly. (4) ANALYZE TABLE after major data changes for optimizer statistics. Dependencies: optimize before vacuum (compact first, then clean up old files). Monitor execution time and add alerts for failures. For streaming tables, consider more frequent compaction (every few hours).

What is Z-ORDER and how does it improve query performance?

Z-ORDER is a multi-dimensional sorting technique using a space-filling Z-curve (Morton code). It interleaves bits of multiple columns to co-locate data points that are close in any dimension. After Z-ordering by (customer_id, order_date), each Parquet file has tight min/max ranges for both columns. When a query filters on WHERE customer_id = 'X' AND order_date > '2025-01-01', the engine can skip files whose min/max ranges don't match — even though data can't be perfectly sorted on two columns simultaneously. Z-ORDER gives good (not perfect) clustering for any subset of the Z-ordered columns.

What are the compaction strategies for streaming tables?

Streaming tables need more frequent maintenance: (1) Frequent bin-pack compaction — run every 1-4 hours targeting recent partitions where micro-batch files accumulate. (2) Trigger-based compaction — compact when file count in a partition exceeds threshold (e.g., > 100 files). (3) Hudi MOR async compaction — run compaction as a separate streaming job that continuously merges logs into base files. (4) Auto-OPTIMIZE (Databricks) — automatically compacts after each write (delta.autoOptimize.optimizeWrite = true). (5) Sorted compaction less frequently (daily) for data skipping benefits. Key: separate compaction from ingestion to avoid adding latency to the streaming pipeline.
