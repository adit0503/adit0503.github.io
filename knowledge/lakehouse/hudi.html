Hudi Architecture

Apache Hudi (Hadoop Upserts Deletes and Incrementals) provides record-level insert, update, and delete capabilities on data lakes. Its architecture revolves around timelines, file groups, and file slices.

Core Concepts

  • Timeline — an ordered log of all actions (commits, compactions, cleans) performed on the table. Similar in spirit to Delta's transaction log.
  • File Group — the unit of parallelism. Each file group is identified by a fileId and contains one or more file slices. A record always belongs to the same file group (determined by the index).
  • File Slice — a snapshot of a file group at a specific commit time. Contains a base file (Parquet) and optionally log files (Avro) for MOR tables.
  • Metadata Table — a Hudi-managed table storing file listings, column stats, and bloom filter indexes for faster planning.
Hudi table structure
my_hudi_table/
├── .hoodie/
│   ├── hoodie.properties                  # table config
│   ├── 20250115101530.commit              # completed commit
│   ├── 20250115111530.commit              # completed commit
│   ├── 20250115121530.compaction.requested
│   └── metadata/                          # internal metadata table
├── partition=2025-01-15/
│   ├── filegroup-001/
│   │   ├── base-001_20250115101530.parquet   # base file (file slice 1)
│   │   ├── base-001_20250115111530.parquet   # base file (file slice 2, COW)
│   │   └── .log-001_20250115111530.log       # log file (MOR only)
│   └── filegroup-002/
│       └── base-002_20250115101530.parquet
└── partition=2025-01-16/
    └── ...
🔑 Key insight:

Unlike Delta/Iceberg where any file can be affected by an update, Hudi's indexing maps each record to a specific file group. This means updates always know exactly which file to modify — no need to scan the entire table to find affected files.

Copy-on-Write (COW)

In COW tables, every write (insert, update, delete) produces a new version of the entire Parquet file containing the affected records.

How It Works

  1. Writer receives a batch of records (some new, some updates)
  2. Index lookup determines which file group each record belongs to
  3. For updated records: read the existing base file, merge with updates, write a new base file (new file slice)
  4. For new records in a new file group: write a fresh base file
  5. Old file slices are retained for time travel (cleaned up later)

Characteristics

  • Read performance: Excellent — readers always read clean Parquet files, no merge needed at read time
  • Write performance: Expensive — even a single-row update requires rewriting the entire file (typically 128MB)
  • Storage: Higher (each update creates a full copy of the file)
  • Latency: Higher write latency due to full file rewrites
COW write — what happens on update
# Before update:
# file_group_001: base_001_ts1.parquet (100,000 records)

# Update 5 records in file_group_001:
# 1. Read base_001_ts1.parquet (all 100,000 records)
# 2. Apply 5 updates in memory
# 3. Write base_001_ts2.parquet (100,000 records — full rewrite)
# 4. Mark base_001_ts1.parquet as older file slice

# After update:
# file_group_001: base_001_ts2.parquet (100,000 records) ← current
#                 base_001_ts1.parquet (100,000 records) ← historical

Merge-on-Read (MOR)

In MOR tables, updates are written as log files (delta logs) rather than rewriting the entire base file. Reads merge the base file with log files on the fly.

How It Works

  1. Writer receives a batch of records
  2. For new inserts: may create a new base file or append to a log file
  3. For updates: append only the changed records to a log file (Avro format)
  4. Reads: merge the base Parquet file with all log files for that file group
  5. Compaction: periodically merge log files into the base file (creates a new clean file slice)

Characteristics

  • Write performance: Fast — only append-write small log files (no full file rewrite)
  • Read performance: Slower — must merge log files with base file at read time
  • Storage: Lower between compactions (log files are small)
  • Latency: Much lower write latency — suitable for near-real-time ingestion

Two Query Types on MOR

  • Snapshot query — merges base + logs at read time (sees latest data, slower)
  • Read-optimized query — reads only base files (faster, but may miss recent updates not yet compacted)
MOR write — log file appends
# Before update:
# file_group_001: base_001_ts1.parquet (100,000 records)

# Update 5 records:
# 1. Write only the 5 changed records to log_001_ts2.log (Avro, tiny file)
# 2. Done! No full file rewrite.

# After update:
# file_group_001: base_001_ts1.parquet (100,000 records) ← base
#                 log_001_ts2.log (5 records) ← delta log

# Snapshot read: read base + merge with log → 100,000 records (5 updated)
# Read-optimized: read base only → 100,000 records (stale 5 records)

When to Use COW vs MOR

CriteriaCOWMOR
Read/Write ratioRead-heavyWrite-heavy
Write latencyHigher (full rewrite)Lower (log append)
Read latencyLower (clean files)Higher (merge on read)
Update frequencyLow-to-mediumHigh (streaming/CDC)
Ingestion latencyMinutes to hoursSeconds to minutes
Compaction neededNoYes (critical for read perf)
💡 Rule of thumb:

If your table gets updated frequently (CDC, streaming) and read latency tolerance is minutes → MOR. If your table is batch-updated once/twice daily and read performance is critical (BI dashboards) → COW.

Write Operations

  • insert — adds new records. Uses index to check for duplicates (rejects if key exists in strict mode).
  • upsert — insert new records and update existing ones (based on record key). The most common operation.
  • delete — removes records matching a condition. Produces empty records with delete markers.
  • bulk_insert — optimized for first-time loads. Skips index lookup for speed. Use for initial table population.
Hudi write operations with Spark
hudi_options = {
    "hoodie.table.name": "orders",
    "hoodie.datasource.write.table.type": "COPY_ON_WRITE",
    "hoodie.datasource.write.operation": "upsert",
    "hoodie.datasource.write.recordkey.field": "order_id",
    "hoodie.datasource.write.precombine.field": "updated_at",
    "hoodie.datasource.write.partitionpath.field": "order_date",
    "hoodie.upsert.shuffle.parallelism": 200,
}

# Upsert
df.write.format("hudi") \
    .options(**hudi_options) \
    .mode("append") \
    .save("/data/hudi/orders")

# Delete
delete_df.write.format("hudi") \
    .options(**{**hudi_options,
        "hoodie.datasource.write.operation": "delete"}) \
    .mode("append") \
    .save("/data/hudi/orders")

# Bulk insert (initial load — no index lookup)
df.write.format("hudi") \
    .options(**{**hudi_options,
        "hoodie.datasource.write.operation": "bulk_insert",
        "hoodie.bulkinsert.sort.mode": "GLOBAL_SORT"}) \
    .mode("overwrite") \
    .save("/data/hudi/orders")

Indexing

Hudi's index maps a record key to a file group — this is what makes upserts efficient (no full-table scan to find the target file).

Index Types

  • Bloom Filter Index (default) — stores bloom filters in file footers. On upsert, checks bloom filters to identify candidate files, then does exact lookup. Good for most workloads.
  • Simple Index — joins incoming records against all base files. Works for any key type but expensive for large tables.
  • HBase Index — stores record-key → file-group mapping in an external HBase instance. Sub-second lookups for massive tables. Requires HBase infrastructure.
  • Bucket Index — hash-based file group assignment. Consistent hashing on the record key determines the file group. No index lookup needed — O(1) routing. Good for large-scale workloads with known key distribution.
Index configuration
# Bloom filter index (default)
"hoodie.index.type": "BLOOM"
"hoodie.bloom.index.parallelism": 200
"hoodie.bloom.index.prune.by.ranges": "true"

# Bucket index (no lookup overhead)
"hoodie.index.type": "BUCKET"
"hoodie.bucket.index.num.buckets": 256
"hoodie.bucket.index.hash.field": "order_id"

# HBase index (external store)
"hoodie.index.type": "HBASE"
"hoodie.index.hbase.zkquorum": "zk1:2181,zk2:2181"
"hoodie.index.hbase.table": "hudi_index"

Compaction in MOR

Compaction merges log files into base files, creating clean Parquet files. Critical for maintaining read performance in MOR tables.

Compaction Strategies

  • Inline compaction — runs within the same write job. Simpler but increases write latency.
  • Async compaction — separate job runs compaction independently. Better for production (doesn't delay writes).
  • Scheduled compaction — Hudi creates compaction plans on the timeline; a separate process executes them.
Compaction configuration
# Inline compaction (runs during write)
"hoodie.compact.inline": "true"
"hoodie.compact.inline.max.delta.commits": 5  # compact every 5 commits

# Async compaction (separate job)
"hoodie.compact.inline": "false"

# Run compaction as a separate Spark job:
from hudi import HoodieCompactor
spark.sql("CALL run_compaction(table => 'hudi_table', op => 'run')")

# Compaction strategy
"hoodie.compaction.strategy": "org.apache.hudi.table.action.compact.strategy.BoundedIOCompactionStrategy"
"hoodie.compaction.target.io": "512000"  # target IO in KB per compaction
⚠️ Compaction lag:

If compaction falls behind writes, log files accumulate and read performance degrades significantly. Monitor the number of log files per file group and compaction lag. Set alerts when log file count exceeds a threshold (e.g., > 10 logs per file group).

Hudi with Spark

Complete Hudi Spark configuration
from pyspark.sql import SparkSession

spark = SparkSession.builder \
    .appName("HudiApp") \
    .config("spark.serializer", "org.apache.spark.serializer.KryoSerializer") \
    .config("spark.sql.catalog.spark_catalog",
            "org.apache.spark.sql.hudi.catalog.HoodieCatalog") \
    .config("spark.sql.extensions",
            "org.apache.spark.sql.hudi.HoodieSparkSessionExtension") \
    .config("spark.jars.packages",
            "org.apache.hudi:hudi-spark3.4-bundle_2.12:0.14.0") \
    .getOrCreate()

orders_v1 = spark.read.format("hudi") \
    .option("as.of.instant", "20250115101530") \
    .load("/data/hudi/orders")

# Spark SQL
spark.sql("CREATE TABLE orders USING hudi ...")
spark.sql("INSERT INTO orders SELECT ...")
spark.sql("UPDATE orders SET status = 'shipped' WHERE order_id = 'X'")

Incremental Queries

Hudi's killer feature: pull only records that changed since a given commit — perfect for ETL pipelines that process deltas.

Incremental query pattern
# Read only changes since a specific commit
incremental_df = spark.read.format("hudi") \
    .option("hoodie.datasource.query.type", "incremental") \
    .option("hoodie.datasource.read.begin.instanttime", "20250115101530") \
    .option("hoodie.datasource.read.end.instanttime", "20250115121530") \
    .load("/data/hudi/orders")

# In streaming: use Hudi as a streaming source
stream_df = spark.readStream.format("hudi") \
    .option("hoodie.datasource.query.type", "incremental") \
    .option("hoodie.datasource.read.begin.instanttime", "20250115000000") \
    .load("/data/hudi/orders")

# Process incremental changes and write to downstream
incremental_df.filter("_hoodie_is_deleted = false") \
    .write.format("hudi") \
    .options(**downstream_options) \
    .mode("append") \
    .save("/data/hudi/silver_orders")

Interview Questions

What are the trade-offs between COW and MOR in Hudi?

COW (Copy-on-Write): Every update rewrites the entire Parquet file containing the record. Reads are fast (always clean Parquet) but writes are expensive (O(file_size) per update). Best for read-heavy workloads with infrequent updates. MOR (Merge-on-Read): Updates append to small log files (Avro). Writes are fast (O(update_size)) but reads must merge base files with logs (slower). Requires compaction to maintain read performance. Best for write-heavy, streaming/CDC workloads where write latency matters more than read latency.

How does Hudi indexing work?

Hudi's index maps each record key to a specific file group. On upsert, the index tells the writer exactly which file(s) to update — no full-table scan. Bloom Filter (default): stores bloom filters in Parquet footers; during upsert, checks filters to identify candidate files, then does point lookup. Bucket Index: uses consistent hashing on the record key — O(1) routing with no lookup. HBase Index: stores key→file-group mapping in external HBase for sub-second lookups on billion-record tables. The index is what makes Hudi uniquely efficient at record-level upserts compared to Delta/Iceberg.

When would you choose Hudi over Iceberg or Delta?

Choose Hudi when: (1) You have a high-frequency upsert workload (CDC from OLTP databases with thousands of updates/sec) — Hudi's MOR + index makes this efficient. (2) You need near-real-time incremental processing — Hudi's incremental query is first-class. (3) You're on AWS (EMR/Glue have strong Hudi support). Choose Iceberg for multi-engine environments and partition evolution. Choose Delta for Databricks-centric environments and tight Spark integration.

What is compaction in MOR and why is it critical?

Compaction in MOR tables merges accumulated log files (Avro deltas) back into base files (Parquet), producing a clean new file slice. Without compaction, log files grow unbounded and read performance degrades because every read must merge base + all logs. Compaction can be inline (during writes — simpler but adds latency), async (separate job — recommended for production), or scheduled (Hudi plans compaction on the timeline; a separate executor runs it). Monitor compaction lag — if it falls behind, reads slow down dramatically.

How do incremental queries work in Hudi?

Hudi's timeline tracks every commit with a timestamp. An incremental query reads only records that were committed between two timestamps (begin.instanttime and optionally end.instanttime). This returns only changed records (inserts, updates, deletes) — not the full table. It's implemented by scanning the timeline for commits in the range, then reading only the file slices (base + logs) created in those commits. This is the foundation for efficient ETL: each pipeline run pulls only what's new, processes it, and advances the checkpoint. Much cheaper than re-scanning the full table.
