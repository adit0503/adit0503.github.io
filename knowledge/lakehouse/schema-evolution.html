Schema Evolution & Partition Strategies

Why Schema Evolution Matters

In production data pipelines, schemas change constantly:

  • Business changes — new features require new columns (shipping_cost, discount_code)
  • Source changes — upstream APIs add/remove/rename fields without warning
  • Data model improvements — splitting columns, changing types, normalizing structures
  • Compliance — adding audit columns, removing PII columns

Traditional approaches required downtime: drop table, recreate with new schema, backfill all data. Modern lakehouse formats handle schema changes as metadata operations without touching data files.

🔑 Key principle:

Schema evolution should be a metadata-only operation. Old data files continue to be readable under the new schema (new columns return NULL for old files; dropped columns are simply not read). No data rewriting required.

Iceberg Schema Evolution

Iceberg has the most sophisticated schema evolution among lakehouse formats. It uses internal column IDs (not names or positions) to map schema fields to data file columns.

Supported Operations (All Metadata-Only)

  • Add column — new column assigned a new ID; old data files return NULL
  • Drop column — column ID removed from schema; data files unchanged
  • Rename column — column ID stays the same; only the name mapping changes
  • Reorder columns — purely presentational; doesn't affect data
  • Widen type — int→long, float→double, decimal(P,S)→decimal(P',S) where P'≥P
  • Nested fields — add/drop/rename fields within structs, maps, and lists
Iceberg schema evolution SQL
-- Add columns
ALTER TABLE catalog.db.orders ADD COLUMN shipping_cost DECIMAL(8,2);
ALTER TABLE catalog.db.orders ADD COLUMN discount_code STRING AFTER customer_id;

-- Rename column (safe — uses column ID internally)
ALTER TABLE catalog.db.orders RENAME COLUMN amount TO order_amount;

-- Widen type
ALTER TABLE catalog.db.orders ALTER COLUMN order_amount TYPE DECIMAL(12,2);

-- Drop column
ALTER TABLE catalog.db.orders DROP COLUMN legacy_status;

-- Nested evolution (structs)
ALTER TABLE catalog.db.orders ADD COLUMN address.zip_code STRING;
ALTER TABLE catalog.db.orders DROP COLUMN address.line2;

-- Reorder
ALTER TABLE catalog.db.orders ALTER COLUMN shipping_cost AFTER order_amount;
💡 Why column IDs matter:

In Hive/old Spark tables, columns are mapped by position. If you add a column in the middle or rename a column, old data files become misaligned — data corruption. Iceberg assigns each column a unique integer ID at creation time. Parquet files store data keyed by this ID, not by column name or position. Rename, reorder, and add operations only change the ID-to-name mapping in metadata.

Delta Lake Schema Evolution

Delta Lake provides schema evolution through write-time options and DDL commands.

Schema Enforcement (Default)

By default, Delta rejects writes with mismatched schemas. This prevents accidental schema drift.

Schema Evolution Options

Delta schema evolution
# mergeSchema: adds new columns from source to target
df.write.format("delta") \
    .mode("append") \
    .option("mergeSchema", "true") \
    .save("/path/to/table")

# In MERGE statements:
spark.conf.set("spark.databricks.delta.schema.autoMerge.enabled", "true")

# overwriteSchema: replace entire schema (only with overwrite mode)
df.write.format("delta") \
    .mode("overwrite") \
    .option("overwriteSchema", "true") \
    .save("/path/to/table")

# DDL commands
ALTER TABLE my_table ADD COLUMNS (
    shipping_cost DECIMAL(8,2) COMMENT 'Shipping cost in USD',
    discount_code STRING
);

ALTER TABLE my_table CHANGE COLUMN old_name new_name STRING;
ALTER TABLE my_table DROP COLUMN deprecated_field;

# Column mapping (Delta 2.0+) enables rename/drop without rewrite
ALTER TABLE my_table SET TBLPROPERTIES (
    'delta.columnMapping.mode' = 'name',
    'delta.minReaderVersion' = '2',
    'delta.minWriterVersion' = '5'
);
⚠️ Column mapping requirement:

By default, Delta uses column names for mapping (like Hive). To safely rename or drop columns without data rewrite, you must enable delta.columnMapping.mode = 'name'. This is a one-way upgrade — once enabled, older readers may not be able to read the table.

Hudi Schema Evolution

Hudi supports schema evolution with automatic schema reconciliation during writes.

Hudi schema evolution
# Automatic schema evolution during writes
hudi_options = {
    "hoodie.datasource.write.reconcile.schema": "true",
    # New columns in source are automatically added to the table
    # Missing columns in source are filled with NULL
}

# Explicit schema changes via Spark SQL (Hudi 0.13+)
spark.sql("ALTER TABLE hudi_table ADD COLUMNS (new_col STRING)")
spark.sql("ALTER TABLE hudi_table RENAME COLUMN old_col TO new_col")
spark.sql("ALTER TABLE hudi_table ALTER COLUMN amount TYPE DECIMAL(12,2)")

# Schema on write behavior:
# - New column in DataFrame → added to Hudi table schema
# - Column type widening → automatically applied
# - Column removal → use explicit DDL (data files unaffected)

Backward vs Forward Compatibility

Backward Compatibility

New schema can read old data. Always true for:

  • Adding columns (old files → NULL for new columns)
  • Widening types (old int values readable as long)
  • Renaming columns (in Iceberg — tracked by ID)

Forward Compatibility

Old schema can read new data. True for:

  • Adding columns (old readers ignore unknown columns)
  • NOT true for type changes, renames (in non-ID-based systems), or drops

Breaking Changes

  • Narrowing types (long→int) — potential data loss
  • Changing column semantics (amount now in cents instead of dollars)
  • Removing columns that downstream consumers depend on
💡 Strategy for breaking changes:

Version your tables. Instead of modifying silver.orders destructively, create silver.orders_v2 with the new schema, backfill from Bronze, then migrate consumers. Keep v1 running during transition period.

Partition Strategies

Partitioning physically separates data into directories/file groups based on column values. Critical for query performance — the right partition scheme enables partition pruning (skipping entire directories of irrelevant data).

Common Strategies

  • By time — most common: date, year/month/day, hour. Ideal for time-series data, event logs, transactions.
  • By category — region, country, product_type. Ideal when queries always filter on category.
  • Composite — date + region, year + month. For multi-dimensional access patterns.
  • Hash/Bucket — bucket(customer_id, 256). For high-cardinality columns where range partitioning would create too many partitions.
  • Hidden transforms (Iceberg) — day(event_time), hour(event_time). Users don't need to know partition details.
Partition strategies across formats
-- Delta: explicit partitioning
CREATE TABLE orders (
    order_id STRING,
    customer_id STRING,
    amount DECIMAL(10,2),
    order_date DATE,
    region STRING
) USING DELTA
PARTITIONED BY (order_date, region);

-- Iceberg: hidden partitioning with transforms
CREATE TABLE orders (
    order_id STRING,
    customer_id STRING,
    amount DECIMAL(10,2),
    order_time TIMESTAMP,
    region STRING
) USING iceberg
PARTITIONED BY (day(order_time), region);

-- Iceberg: bucket partitioning
CREATE TABLE customers (
    customer_id STRING,
    name STRING,
    email STRING
) USING iceberg
PARTITIONED BY (bucket(64, customer_id));

-- Hudi: partition path
"hoodie.datasource.write.partitionpath.field": "order_date"
"hoodie.datasource.write.hive_style_partitioning": "true"

Partition Evolution

Iceberg uniquely supports changing the partition scheme without rewriting data — partition evolution.

How It Works

  • Each data file records which partition spec was in effect when it was written
  • When the partition spec changes, new files use the new spec
  • Old files retain their original partitioning
  • Query planning handles both specs: it knows how to prune files from any spec
Partition evolution (Iceberg)
-- Original: daily partitions
CREATE TABLE events (...) PARTITIONED BY (day(event_time));

-- Table grows: daily partitions too large (>10GB each)
-- Evolve to hourly without rewriting data:
ALTER TABLE events ADD PARTITION FIELD hour(event_time);
ALTER TABLE events DROP PARTITION FIELD day(event_time);

-- Now: new data → hourly partitions
--      old data → still in daily partitions
--      queries → correctly prune both

-- Another evolution: add region partitioning
ALTER TABLE events ADD PARTITION FIELD region;
-- New data: partitioned by (hour(event_time), region)
-- Old data: partitioned by day(event_time) only
-- All coexist transparently
🔑 Why this matters:

In Delta/Hive, changing partitioning requires: (1) create new table with new partition scheme, (2) backfill all historical data (potentially TBs), (3) swap table names, (4) update all downstream consumers. In Iceberg, it's a single ALTER TABLE — zero data movement, zero downtime.

Over-Partitioning vs Under-Partitioning

Over-Partitioning Symptoms

  • Too many small files (each partition has files < 10MB)
  • Slow query planning (thousands of partitions to list)
  • High storage overhead (many small Parquet files with disproportionate metadata)
  • Example: Partitioning by (date, hour, user_id) → millions of partitions with 1-10 records each

Under-Partitioning Symptoms

  • Full table scans even with selective filters
  • Very large files (>10GB) that are slow to read for selective queries
  • No pruning possible — queries touch all data
  • Example: No partitioning on a 10TB time-series table queried by date range

Solutions

  • Over-partitioned → reduce partition granularity (hour → day, remove low-selectivity partition columns)
  • Under-partitioned → add partitioning on the most common filter column, or use Z-ORDER for multi-column pruning
  • Target: each partition should produce files in the 128MB–1GB range

Partition Best Practices

Column Selection Criteria

  • Query patterns — partition on columns that appear in WHERE clauses of most queries
  • Cardinality — moderate cardinality (100s–10,000s of distinct values). Too low = not useful, too high = over-partitioning
  • File size targets — choose granularity so each partition has ~128MB–1GB of data
  • Growth patterns — time-based partitions naturally support incremental processing

Guidelines by Data Volume

< 128MB/dayMonthly or no partitioningDaily partitions would be too small
128MB – 10GB/dayDailySweet spot for daily partitions

Dynamic vs Static Partition Overwrite

Static Partition Overwrite

Explicitly specify which partition to overwrite. Only that partition is replaced.

Static partition overwrite
# Delta: replaceWhere
df.write.format("delta") \
    .mode("overwrite") \
    .option("replaceWhere", "order_date = '2025-01-15'") \
    .save("/path/to/orders")

# Only the partition date=2025-01-15 is replaced
# Other partitions are untouched

Dynamic Partition Overwrite

Overwrite all partitions that exist in the source DataFrame. Partitions not in the source are untouched.

Dynamic partition overwrite
# Spark config for dynamic partition overwrite
spark.conf.set("spark.sql.sources.partitionOverwriteMode", "dynamic")

# DataFrame has data for dates 2025-01-15 and 2025-01-16
df.write.format("delta") \
    .mode("overwrite") \
    .save("/path/to/orders")

# Result: only partitions 2025-01-15 and 2025-01-16 are overwritten
# All other partitions remain untouched

# Iceberg: overwritePartitions()
df.writeTo("catalog.db.orders").overwritePartitions()
⚠️ Danger with dynamic overwrite:

If your source DataFrame is accidentally empty (e.g., upstream failure), dynamic overwrite will overwrite zero partitions — which is safe. But if it has partial data for a partition, it will replace the entire partition with that partial data. Always validate source completeness before dynamic overwrite.

SCD Patterns in Lakehouse

SCD Type 1 — Overwrite

Simply update the record in place. No history preserved. Use MERGE with UPDATE.

SCD Type 1 with MERGE
MERGE INTO dim_customers AS target
USING staging_customers AS source
ON target.customer_id = source.customer_id
WHEN MATCHED THEN
    UPDATE SET
        name = source.name,
        email = source.email,
        address = source.address,
        updated_at = current_timestamp()
WHEN NOT MATCHED THEN
    INSERT (customer_id, name, email, address, created_at, updated_at)
    VALUES (source.customer_id, source.name, source.email,
            source.address, current_timestamp(), current_timestamp());

SCD Type 2 — Historical Tracking

Preserve full history. Each change creates a new row with effective dates. Old row gets an end date.

SCD Type 2 with MERGE
-- Step 1: Close existing active records that have changes
MERGE INTO dim_customers AS target
USING (
    SELECT s.customer_id, s.name, s.email, s.address
    FROM staging_customers s
    JOIN dim_customers d
        ON s.customer_id = d.customer_id
        AND d.is_current = true
    WHERE s.name != d.name OR s.email != d.email OR s.address != d.address
) AS changes
ON target.customer_id = changes.customer_id AND target.is_current = true
WHEN MATCHED THEN
    UPDATE SET
        is_current = false,
        effective_end = current_timestamp();

-- Step 2: Insert new version for changed records + new records
INSERT INTO dim_customers
SELECT
    customer_id,
    name,
    email,
    address,
    current_timestamp() AS effective_start,
    NULL AS effective_end,
    true AS is_current
FROM staging_customers s
WHERE EXISTS (
    -- Changed records (now closed above)
    SELECT 1 FROM dim_customers d
    WHERE d.customer_id = s.customer_id AND d.is_current = false
    AND d.effective_end = current_timestamp()
)
OR NOT EXISTS (
    -- Brand new records
    SELECT 1 FROM dim_customers d WHERE d.customer_id = s.customer_id
);

SCD Type 3 — Previous Value Column

Keep the previous value in a separate column. Limited history (only one previous value).

SCD Type 3
MERGE INTO dim_customers AS target
USING staging_customers AS source
ON target.customer_id = source.customer_id
WHEN MATCHED AND target.email != source.email THEN
    UPDATE SET
        previous_email = target.email,
        email = source.email,
        email_changed_at = current_timestamp()
WHEN NOT MATCHED THEN
    INSERT (customer_id, name, email, previous_email, email_changed_at)
    VALUES (source.customer_id, source.name, source.email, NULL, NULL);

Interview Questions

How does Iceberg handle schema evolution without rewriting data files?

Iceberg assigns each column a unique integer ID at creation time. Parquet data files reference columns by these IDs (stored in Parquet metadata), not by column name or position. When you rename a column, only the ID→name mapping in the metadata file changes — data files are untouched. When you add a column, it gets a new ID that doesn't exist in old files — reads return NULL. When you drop a column, its ID is removed from the schema — data files still have the data but it's never read. This ID-based approach makes all evolution operations metadata-only, regardless of table size.

What is partition evolution and which format supports it best?

Partition evolution changes a table's partition scheme without rewriting existing data. Only Iceberg fully supports it. Each data file records which partition spec was active when it was written. When you change the spec (e.g., day(ts) → hour(ts)), new files use the new spec while old files keep theirs. Query planning handles both specs transparently. In Delta/Hive, changing partitioning requires a full table rewrite (potentially terabytes). This makes Iceberg uniquely suited for tables whose access patterns evolve over time — you can adapt partitioning to match changing query patterns with zero downtime.

How do you handle schema changes in a streaming pipeline?

Strategy depends on the change type: (1) Additive changes (new columns) — use mergeSchema=true (Delta) or Iceberg's ADD COLUMN. Streaming queries auto-pick-up new columns on restart. (2) Type widening — apply ALTER TABLE, then restart the stream. (3) Breaking changes (rename, remove, type narrowing) — you can't evolve a running stream mid-flight. Create a new table version, deploy new streaming job to write to v2, backfill from Bronze, then migrate consumers. (4) Schema registry — for Kafka/Avro sources, use a schema registry with compatibility checks (BACKWARD, FORWARD) to prevent breaking changes at the source.

What are the symptoms of over-partitioning and how do you fix it?

Symptoms: (1) Thousands of tiny files (< 10MB each) across many partitions. (2) Slow query planning because listing thousands of partition directories in object storage is expensive. (3) OPTIMIZE/compaction runs very slowly (too many partitions to process). (4) Write amplification — each micro-batch creates a file per partition, multiplying small file count. Fixes: Reduce partition granularity (hour→day, remove low-selectivity partition columns). Use Iceberg's partition evolution to change without rewriting. Alternatively, replace fine-grained partitioning with Z-ORDER/liquid clustering on the over-partitioned columns — you get file-skipping without the partition overhead.

How do you implement SCD Type 2 in a lakehouse?

SCD Type 2 maintains full history by creating a new row for each change with effective dates. Implementation: (1) Add columns: effective_start, effective_end (NULL = current), is_current (boolean). (2) On change detection: MERGE to set is_current = false and effective_end = now() on the existing active row. (3) INSERT the new version with is_current = true and effective_start = now(). This typically requires a two-pass approach (close old + insert new) because MERGE can't both update and insert for the same source row. Delta and Iceberg's MERGE support this pattern. Partition by is_current or effective_start to optimize queries for the "current" view while preserving history.
