Medallion Architecture (Bronze/Silver/Gold)

A layered data design pattern that incrementally improves data quality as it flows through Bronze (raw), Silver (cleaned), and Gold (business-level) layers in a lakehouse.

What Is Medallion Architecture

Medallion architecture is a data design pattern used in lakehouse platforms that organizes data into multiple layers (typically three) based on quality and refinement level. Each layer serves a distinct purpose and enables separation of concerns, independent reprocessing, and clear data lineage.

Why It Exists

  • Separation of concerns — ingestion logic is decoupled from business logic and analytics
  • Reprocessing — if transformation logic changes, you can re-derive Silver/Gold from Bronze without re-ingesting from source
  • Data quality — quality improves progressively; raw data is always preserved as the source of truth
  • Debugging — when analytics look wrong, you can trace back through layers to find where data diverged
  • Team boundaries — data engineers own Bronze→Silver, analytics engineers own Silver→Gold
🔑 Core principle:

Bronze is append-only and preserves raw data exactly as received. You never lose data — even if business rules change, you can always go back to Bronze and recompute everything downstream.

Bronze Layer — Raw Ingestion

The Bronze layer is the landing zone for all raw data entering the lakehouse. Data arrives in its original format with minimal or no transformations applied.

Characteristics

  • Schema-on-read — store data as-is; apply schema during consumption
  • Append-only — never update or delete; each batch/stream appends new records
  • No transformations — no business logic, no data type casting, no joins
  • Source metadata preserved — include ingestion timestamp, source system name, batch ID, filename
  • Full fidelity — retain all columns from source, even those you don't currently need
  • Deduplication deferred — duplicates from source are acceptable here; handled in Silver

Common File Formats

  • JSON (semi-structured API responses, event streams)
  • Avro (Kafka consumers)
  • Parquet (batch extracts from databases)
  • CSV (legacy flat-file feeds)
Bronze ingestion with metadata columns
from pyspark.sql import functions as F

raw_df = (
    spark.readStream
    .format("kafka")
    .option("subscribe", "orders")
    .option("startingOffsets", "earliest")
    .load()
)

bronze_df = raw_df.select(
    F.col("key").cast("string").alias("kafka_key"),
    F.col("value").cast("string").alias("raw_payload"),
    F.col("topic"),
    F.col("partition").alias("kafka_partition"),
    F.col("offset").alias("kafka_offset"),
    F.col("timestamp").alias("kafka_timestamp"),
    F.current_timestamp().alias("ingested_at"),
    F.lit("kafka-orders-prod").alias("source_system")
)

bronze_df.writeStream \
    .format("delta") \
    .outputMode("append") \
    .option("checkpointLocation", "/checkpoints/bronze_orders") \
    .toTable("bronze.orders")

Silver Layer — Cleaned & Conformed

The Silver layer contains enterprise-conforming data. This is where you clean, deduplicate, standardize schemas, and apply business keys — but not business aggregations.

Transformations Applied

  • Parsing — extract structured fields from raw JSON/Avro payloads
  • Deduplication — remove duplicates using business keys + event timestamps
  • Data type casting — enforce correct types (string dates → timestamp, string amounts → decimal)
  • Standardization — normalize field names (camelCase → snake_case), apply consistent null handling
  • Business key assignment — generate surrogate keys, map natural keys
  • SCD Type 2 — maintain historical dimension records with effective dates
  • Filtering — remove corrupt, test, or invalid records (quarantine to a separate table)
  • Conforming — align data from multiple sources to a single schema
Silver layer — parse, deduplicate, conform
from pyspark.sql import functions as F
from pyspark.sql.window import Window

# Read from Bronze
bronze_orders = spark.readStream.table("bronze.orders")

# Parse JSON payload
parsed_df = bronze_orders.select(
    F.from_json(
        F.col("raw_payload"),
        "order_id STRING, customer_id STRING, amount DOUBLE, status STRING, order_date STRING"
    ).alias("data"),
    F.col("kafka_offset"),
    F.col("ingested_at")
).select("data.*", "kafka_offset", "ingested_at")

# Cast types
typed_df = parsed_df.withColumn(
    "order_date", F.to_timestamp("order_date", "yyyy-MM-dd'T'HH:mm:ss")
).withColumn(
    "amount", F.col("amount").cast("decimal(10,2)")
)

# Deduplicate within micro-batch using window
dedup_window = Window.partitionBy("order_id").orderBy(F.desc("kafka_offset"))
deduped_df = typed_df.withColumn(
    "row_num", F.row_number().over(dedup_window)
).filter("row_num = 1").drop("row_num")

# Write to Silver with MERGE for cross-batch dedup
deduped_df.writeStream \
    .format("delta") \
    .outputMode("append") \
    .option("checkpointLocation", "/checkpoints/silver_orders") \
    .toTable("silver.orders")
💡 Pro tip:

For cross-batch deduplication, use Delta Lake's MERGE statement with foreachBatch. Within-batch dedup can use window functions, but true exactly-once semantics require MERGE on the business key.

Gold Layer — Business Aggregates

The Gold layer contains business-level aggregates and analytics-ready datasets. These tables are optimized for consumption by BI tools, dashboards, ML feature stores, and business users.

Characteristics

  • Aggregated — pre-computed metrics (daily revenue, customer LTV, product rankings)
  • Denormalized — joins pre-materialized, no need for complex queries at read time
  • Business-logic applied — revenue recognition rules, customer segmentation, SLA calculations
  • KPI tables — directly map to business questions and dashboard widgets
  • Access-controlled — often the only layer exposed to business users and BI tools
  • Performance-optimized — partitioned, Z-ordered, and compacted for fast reads
Gold layer — daily revenue aggregation
-- Gold table: daily revenue summary
CREATE OR REPLACE TABLE gold.daily_revenue AS
SELECT
    DATE(order_date) AS order_day,
    COUNT(DISTINCT order_id) AS total_orders,
    COUNT(DISTINCT customer_id) AS unique_customers,
    SUM(amount) AS gross_revenue,
    SUM(CASE WHEN status = 'refunded' THEN amount ELSE 0 END) AS refunds,
    SUM(amount) - SUM(CASE WHEN status = 'refunded' THEN amount ELSE 0 END) AS net_revenue,
    AVG(amount) AS avg_order_value
FROM silver.orders
WHERE status IN ('completed', 'refunded')
GROUP BY DATE(order_date)
ORDER BY order_day;

Implementation with Delta Lake / Iceberg

Both Delta Lake and Apache Iceberg provide the ACID guarantees needed to implement medallion architecture reliably.

Creating Tables at Each Layer

Delta Lake — table creation
-- Bronze: wide schema, append-only
CREATE TABLE bronze.orders (
    kafka_key STRING,
    raw_payload STRING,
    topic STRING,
    kafka_partition INT,
    kafka_offset BIGINT,
    kafka_timestamp TIMESTAMP,
    ingested_at TIMESTAMP,
    source_system STRING
)
USING DELTA
PARTITIONED BY (DATE(ingested_at))
TBLPROPERTIES ('delta.appendOnly' = 'true');

-- Silver: structured, business-keyed
CREATE TABLE silver.orders (
    order_id STRING,
    customer_id STRING,
    amount DECIMAL(10,2),
    status STRING,
    order_date TIMESTAMP,
    processed_at TIMESTAMP
)
USING DELTA
PARTITIONED BY (DATE(order_date));

-- Gold: aggregated, analytics-ready
CREATE TABLE gold.daily_revenue (
    order_day DATE,
    total_orders BIGINT,
    unique_customers BIGINT,
    gross_revenue DECIMAL(15,2),
    net_revenue DECIMAL(15,2),
    avg_order_value DECIMAL(10,2)
)
USING DELTA
PARTITIONED BY (order_day);
MERGE pattern for Silver upserts
MERGE INTO silver.orders AS target
USING bronze_batch AS source
ON target.order_id = source.order_id
WHEN MATCHED AND source.kafka_offset > target.kafka_offset THEN
    UPDATE SET
        status = source.status,
        amount = source.amount,
        processed_at = current_timestamp()
WHEN NOT MATCHED THEN
    INSERT (order_id, customer_id, amount, status, order_date, processed_at)
    VALUES (source.order_id, source.customer_id, source.amount,
            source.status, source.order_date, current_timestamp());

Data Quality at Each Layer

Each layer should enforce progressively stricter quality gates.

Bronze Quality

  • Basic schema validation (is the payload parseable?)
  • Completeness checks (did we receive expected number of records?)
  • No transformation — quarantine completely malformed records

Silver Quality

  • Not-null constraints on business keys (order_id, customer_id)
  • Referential integrity checks (does customer_id exist in silver.customers?)
  • Range validations (amount > 0, order_date not in the future)
  • Uniqueness constraints (no duplicate order_ids)

Gold Quality

  • Business rule validations (net_revenue = gross_revenue - refunds)
  • Trend anomaly detection (today's revenue within 3σ of rolling average)
  • Completeness (no missing dates in time-series tables)
Delta Lake Expectations (Databricks)
@dlt.expect_or_drop("valid_order_id", "order_id IS NOT NULL")
@dlt.expect_or_drop("positive_amount", "amount > 0")
@dlt.expect_or_fail("valid_date", "order_date <= current_date()")
@dlt.expect("known_status", "status IN ('pending','completed','refunded','cancelled')")

@dlt.table(name="silver_orders")
def silver_orders():
    return spark.readStream.table("bronze.orders").select(...)

OBT vs Star Schema at Gold Layer

Two dominant modeling approaches for the Gold layer:

One Big Table (OBT)

  • Single wide denormalized table with all dimensions flattened alongside facts
  • Pros: No joins needed at query time, simple for BI tools, great read performance
  • Cons: Data duplication, larger storage, slower writes, harder to maintain
  • Best for: specific dashboards, high-read use cases, limited dimension cardinality

Star Schema

  • Central fact table surrounded by dimension tables (customers, products, time)
  • Pros: Normalized storage, easier updates, flexible ad-hoc queries
  • Cons: Requires joins (though lakehouse engines handle this well)
  • Best for: enterprise data warehouse patterns, reusable dimensions, ad-hoc analytics
⚠️ Trade-off decision:

Use OBT when you have a specific, high-frequency dashboard with known access patterns. Use Star Schema when multiple teams query the same dimensions in different ways. In practice, many teams use Star Schema at Gold with materialized OBT views for specific dashboards.

Incremental Processing Patterns

Processing all data from scratch every run is expensive. Incremental patterns process only new/changed data.

Watermark-Based

  • Track a high-watermark column (e.g., modified_at timestamp)
  • Each run processes records where modified_at > last_watermark
  • Simple but can miss late-arriving data or backdated updates

CDC-Based (Change Data Capture)

  • Capture INSERT/UPDATE/DELETE operations from source database transaction log
  • Tools: Debezium, AWS DMS, Fivetran, Airbyte
  • Apply changes using MERGE INTO at Silver layer
  • Most reliable for keeping Silver in sync with OLTP sources

Change Tracking (Delta CDF / Iceberg Incremental)

  • Use the table format's built-in change tracking
  • Delta: Change Data Feed (CDF) — read changes between versions
  • Iceberg: Incremental read with snapshot range
Delta CDF for incremental Silver → Gold
-- Enable CDF on Silver table
ALTER TABLE silver.orders SET TBLPROPERTIES ('delta.enableChangeDataFeed' = 'true');

-- Read only changes since last version
changes_df = spark.read.format("delta") \
    .option("readChangeFeed", "true") \
    .option("startingVersion", last_processed_version) \
    .table("silver.orders")

# Filter to inserts and updates only
new_data = changes_df.filter(
    F.col("_change_type").isin("insert", "update_postimage")
)

# Merge into Gold
new_data.createOrReplaceTempView("silver_changes")
spark.sql("""
    MERGE INTO gold.daily_revenue AS target
    USING (
        SELECT DATE(order_date) AS order_day, ...
        FROM silver_changes
        GROUP BY DATE(order_date)
    ) AS source
    ON target.order_day = source.order_day
    WHEN MATCHED THEN UPDATE SET ...
    WHEN NOT MATCHED THEN INSERT ...
""")

Real Example: E-Commerce Pipeline

Let's trace an order event through all three layers:

Source Event (Kafka)

Raw Kafka message
{
  "order_id": "ORD-2025-78432",
  "customer_id": "CUST-1192",
  "items": [
    {"sku": "SKU-001", "qty": 2, "unit_price": 29.99},
    {"sku": "SKU-044", "qty": 1, "unit_price": 149.99}
  ],
  "total": 209.97,
  "status": "completed",
  "shipping_address": {"city": "Seattle", "state": "WA", "zip": "98101"},
  "order_date": "2025-01-15T14:23:11Z"
}

Bronze

Stored as-is with metadata: raw JSON payload + kafka_offset + ingested_at + source_system. No parsing.

Silver

Parsed into structured columns. Items array exploded into silver.order_items. Order-level data in silver.orders. Customer address normalized. Deduped on order_id.

Gold

Aggregated into gold.daily_revenue, gold.customer_ltv, gold.product_performance. Joined with silver.customers and silver.products for denormalized reporting.

💡 Architecture tip:

Keep Bronze→Silver and Silver→Gold as separate pipelines (separate Spark jobs or DLT pipelines). This allows independent scaling, failure isolation, and different processing frequencies (Bronze: real-time, Silver: micro-batch, Gold: hourly/daily).

Interview Questions

What is medallion architecture and why would you use it?

Medallion architecture is a multi-layered data organization pattern in a lakehouse that progressively improves data quality. Bronze stores raw ingested data as-is (append-only, schema-on-read). Silver contains cleaned, deduplicated, conforming data with proper types and business keys. Gold contains business-level aggregates and analytics-ready tables. You use it because it enables: reprocessing from raw data when logic changes, clear separation of concerns between ingestion and business logic, independent team ownership, and progressive quality enforcement.

What are the responsibilities of each layer — Bronze vs Silver vs Gold?

Bronze: Raw ingestion only — append data with source metadata, no transformations, preserve full fidelity, schema-on-read. Silver: Data engineering — parse payloads, cast types, deduplicate, standardize schemas, apply business keys, enforce referential integrity, implement SCD Type 2. Gold: Business analytics — aggregate metrics, apply business rules (revenue recognition, segmentation), denormalize for performance, create KPI tables directly consumed by dashboards and BI tools.

How do you handle schema changes in a medallion architecture?

At Bronze, schema changes are a non-issue because you store raw data (JSON strings, Avro with schema registry). At Silver, use schema evolution features (Delta's mergeSchema, Iceberg's metadata-only evolution) to add new columns. For breaking changes (renamed/removed fields), version your Silver tables or create new ones and backfill. At Gold, downstream views may need updates. Key pattern: Bronze absorbs all changes without breaking; Silver adapts with schema evolution; Gold is rebuilt from Silver.

OBT vs Star Schema — when would you use each at the Gold layer?

OBT (One Big Table): Use when you have a specific, high-frequency dashboard with well-known query patterns, few dimensions, and read performance is critical. All dimensions are flattened into a single wide table — no joins at query time. Star Schema: Use when multiple teams query the same data in different ways, dimensions are reused across multiple fact tables, or you need flexibility for ad-hoc queries. In practice, many teams maintain a Star Schema at Gold and create materialized OBT views for specific high-traffic dashboards.

How do you implement incremental processing between layers?

Three main patterns: (1) Watermark-based — track a high-watermark column (e.g., modified_at); each run processes records newer than the last watermark. Simple but can miss late-arriving data. (2) CDC-based — use tools like Debezium to capture source DB changes (INSERT/UPDATE/DELETE) and apply them via MERGE INTO at Silver. Most reliable for OLTP sync. (3) Change Data Feed — use Delta CDF or Iceberg incremental reads to pull only changed records between table versions. Best for Silver→Gold because you're reading from a table format that already tracks changes.
