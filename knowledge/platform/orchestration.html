Airflow Architecture

Core Components

  • Scheduler: The brain of Airflow. Parses DAG files, determines which tasks are ready to run (dependencies met, schedule triggered), and places them in the executor queue. In Airflow 2.x, supports multiple schedulers for HA (active-active with database row-level locking).
  • Executor: Determines HOW tasks run. LocalExecutor (single machine, multiprocess), CeleryExecutor (distributed workers via message queue), KubernetesExecutor (each task runs in a dedicated pod), CeleryKubernetesExecutor (hybrid).
  • Metadata Database: PostgreSQL/MySQL storing all state — DAG definitions, task instances, XComs, connections, variables, pools. The single source of truth. Must be highly available for production.
  • Workers: Processes that execute tasks. With CeleryExecutor: long-running worker processes pulling from a queue. With KubernetesExecutor: ephemeral pods created per task.
  • Webserver: Flask-based UI for DAG visualization, task logs, manual triggers, connection management. Reads from metadata DB — stateless and horizontally scalable.
  • Triggerer (Airflow 2.2+): Async event loop that efficiently waits for external conditions (deferrable operators). Replaces polling sensors, reducing worker slot consumption.

DAG Design Principles

Idempotency

  • Every task must produce the same result when executed multiple times with the same input. Running a task twice should not corrupt data or produce duplicates.
  • Pattern: Write to a staging location → validate → atomically swap into the final location. If the task reruns, it overwrites the staging location (same result) and swaps again (no change).
  • Anti-pattern: INSERT INTO target SELECT ... FROM source without deduplication. Rerunning appends duplicates.
  • Correct pattern: INSERT OVERWRITE INTO target PARTITION (dt='{{ ds }}') SELECT ... FROM source. Rerunning overwrites the same partition — idempotent.

Deterministic Outputs

  • Task output should depend only on its inputs and the logical execution date — not on wall-clock time or external mutable state.
  • Use: {{ ds }} (logical date) for partition paths, NOT datetime.now(). This ensures backfills produce correct historical data.
  • Data should be: Written to paths parameterized by execution date. s3://lake/table/dt={{ ds }}/ — each run writes to its date partition.

Atomic Tasks

  • Each task should succeed or fail completely — no partial state left behind on failure.
  • Pattern: Write to a temporary location. On success, move/rename to final location (atomic operation). On failure, temporary files are cleaned up on retry.
  • Anti-pattern: A task that writes 50% of records then fails, leaving partial data in the target. Next retry appends the full set → 150% of expected data.

Common DAG Patterns

Sensor → Transform → Quality Check → Notify

Standard ETL DAG Pattern
from airflow import DAG
from airflow.sensors.s3_key_sensor import S3KeySensor
from airflow.providers.apache.spark.operators.spark_submit import SparkSubmitOperator
from airflow.operators.python import PythonOperator
from airflow.operators.email import EmailOperator
from datetime import datetime, timedelta

default_args = {
    'owner': 'data-platform',
    'retries': 2,
    'retry_delay': timedelta(minutes=5),
    'retry_exponential_backoff': True,
    'execution_timeout': timedelta(hours=2),
    'sla': timedelta(hours=4),
    'on_failure_callback': alert_oncall,
}

with DAG(
    'daily_orders_pipeline',
    default_args=default_args,
    schedule_interval='0 6 * * *',
    start_date=datetime(2026, 1, 1),
    catchup=False,
    max_active_runs=1,
    tags=['production', 'orders', 'daily'],
) as dag:

    # Step 1: Wait for source data to arrive
    wait_for_data = S3KeySensor(
        task_id='wait_for_source_data',
        bucket_name='raw-ingestion',
        bucket_key='orders/dt={{ ds }}/_SUCCESS',
        mode='reschedule',  # Release worker slot while waiting
        timeout=3600 * 6,   # 6 hour timeout
        poke_interval=300,  # Check every 5 minutes
    )

    # Step 2: Transform with Spark
    transform = SparkSubmitOperator(
        task_id='transform_orders',
        application='s3://spark-jobs/orders_transform.py',
        conf={
            'spark.sql.adaptive.enabled': 'true',
            'spark.sql.shuffle.partitions': '200',
        },
        application_args=['--date', '{{ ds }}', '--env', 'production'],
        name='orders_transform_{{ ds_nodash }}',
    )

    # Step 3: Data quality validation
    quality_check = PythonOperator(
        task_id='validate_data_quality',
        python_callable=run_great_expectations_suite,
        op_kwargs={'suite': 'orders_suite', 'date': '{{ ds }}'},
    )

    # Step 4: Notify on success
    notify = EmailOperator(
        task_id='notify_success',
        to='data-consumers@company.com',
        subject='Orders pipeline complete for {{ ds }}',
        html_content='Pipeline completed. Row count: {{ ti.xcom_pull(task_ids="validate_data_quality", key="row_count") }}',
    )

    wait_for_data >> transform >> quality_check >> notify

Backfill Pattern

  • Airflow's catchup=True with a start_date in the past will automatically create DAG runs for every missed interval.
  • CLI backfill: airflow dags backfill --start-date 2026-01-01 --end-date 2026-01-31 daily_orders_pipeline
  • Key requirement: Tasks must be idempotent and parameterized by {{ ds }}. Backfill reruns historical dates — if a task uses datetime.now(), backfill produces wrong results.
  • Concurrency control: Set max_active_runs=3 to limit parallel backfill runs (prevent overwhelming source systems).

Dynamic DAGs

Dynamic DAG Generation
# Generate DAGs dynamically from configuration
import yaml
from airflow import DAG
from airflow.operators.python import PythonOperator

# Load table configuration from YAML
with open('/opt/airflow/config/tables.yaml') as f:
    tables = yaml.safe_load(f)

def create_ingestion_dag(table_config):
    dag_id = f"ingest_{table_config['schema']}_{table_config['name']}"
    
    with DAG(
        dag_id=dag_id,
        schedule_interval=table_config.get('schedule', '@daily'),
        start_date=datetime(2026, 1, 1),
        catchup=False,
        tags=['ingestion', table_config['schema']],
    ) as dag:
        
        extract = PythonOperator(
            task_id='extract',
            python_callable=extract_table,
            op_kwargs={'table': table_config['name'], 'schema': table_config['schema']},
        )
        
        load = PythonOperator(
            task_id='load_to_lake',
            python_callable=load_to_iceberg,
            op_kwargs={'table': table_config['name']},
        )
        
        extract >> load
    
    return dag

# Create a DAG for each table in config
for table in tables:
    globals()[f"ingest_{table['schema']}_{table['name']}"] = create_ingestion_dag(table)

Conditional Branching

  • Use BranchPythonOperator to choose execution path at runtime based on conditions.
  • Use case: If data volume > threshold, use Spark for processing. If small, use Pandas. If no new data, skip processing entirely.
  • Important: Downstream tasks of non-chosen branches are skipped (not failed). Use trigger_rule='none_failed_min_one_success' on join tasks to handle convergence correctly.

Operator Best Practices

When to Use Each Operator

  • PythonOperator: Quick logic, API calls, data validation, XCom manipulation. Keep functions short (<100 lines). Don't process large datasets in-memory — delegate to Spark/SQL.
  • BashOperator: Running CLI tools (dbt, spark-submit, aws cli). Useful for wrapping existing scripts. Avoid complex bash logic — use PythonOperator instead.
  • SparkSubmitOperator: Spark jobs. Configure resources (executor memory, cores) per task based on data volume. Use --conf for runtime parameters.
  • KubernetesPodOperator: Tasks needing custom environments (different Python version, specific libraries, GPU). Full isolation. Useful for ML training, heavy data processing, or tasks with conflicting dependencies.
  • SqlOperator / BigQueryOperator: SQL transformations executed in the warehouse. Preferred for SQL-heavy workflows — push computation to the engine.
  • DbtOperator: Running dbt models. DbtRunOperator for builds, DbtTestOperator for validation. Integrates dbt's DAG with Airflow's DAG.
Anti-pattern: Using PythonOperator to load a 50GB dataset into memory, transform it with Pandas, then write it back. This will OOM the worker and is incredibly slow. Delegate heavy data processing to distributed engines (Spark, BigQuery, Redshift) — Airflow should ORCHESTRATE, not PROCESS.

XCom & Data Passing

XCom Fundamentals

  • XCom (Cross-Communication) allows tasks to share small pieces of metadata. Stored in the metadata database.
  • Size limit: Default backend stores XCom in the DB — practical limit ~48KB per value (serialized JSON). NOT for large data.
  • Push/Pull: Tasks push via return value or ti.xcom_push(key, value). Downstream tasks pull via ti.xcom_pull(task_ids='upstream_task', key='key') or Jinja template {{ ti.xcom_pull(...) }}.

Data Passing Strategies

  • XCom for metadata: Row counts, file paths, partition values, status flags. Small values only.
  • S3/GCS for data: Upstream task writes data to a known path (parameterized by execution date). Downstream task reads from that path. XCom passes the path string if it's dynamic.
  • Custom XCom backend: Airflow 2.x supports custom XCom backends (S3XComBackend) — automatically serializes large XCom values to object storage. Transparent to task code.
  • TaskFlow API (Airflow 2.x): Decorated functions with @task automatically handle XCom — return values from one task are passed as arguments to the next. Cleaner syntax, same underlying XCom mechanism.
TaskFlow API — Clean Data Passing
from airflow.decorators import dag, task
from datetime import datetime

@dag(schedule_interval='@daily', start_date=datetime(2026, 1, 1), catchup=False)
def orders_pipeline():

    @task
    def extract(ds=None):
        """Extract data, return metadata (not the data itself)"""
        path = f's3://raw/orders/dt={ds}/'
        row_count = run_extraction(path)  # Writes to S3
        return {'path': path, 'row_count': row_count}

    @task
    def validate(extract_result):
        """Validate data quality using metadata from extract"""
        if extract_result['row_count'] == 0:
            raise ValueError(f"No rows extracted to {extract_result['path']}")
        run_quality_checks(extract_result['path'])
        return extract_result['path']

    @task
    def transform(validated_path, ds=None):
        """Transform data at the validated path"""
        output_path = f's3://curated/orders/dt={ds}/'
        spark_transform(input_path=validated_path, output_path=output_path)
        return output_path

    # Clean functional pipeline — XCom handled automatically
    extracted = extract()
    validated = validate(extracted)
    transform(validated)

orders_pipeline()

Error Handling

Retry Configuration

  • retries: Number of automatic retry attempts before marking task as failed. Set based on failure mode — transient errors (network, throttling) warrant 2-3 retries. Logic bugs warrant 0 retries (will never self-heal).
  • retry_delay: Wait between retries. Use retry_exponential_backoff=True for exponential backoff (prevents thundering herd on shared resources).
  • retry_delay + exponential: First retry after 5 min, second after 10 min, third after 20 min. Gives transient issues time to resolve.

SLA Monitoring

  • Set sla=timedelta(hours=4) on a task — if the task hasn't completed within 4 hours of the DAG's scheduled time, Airflow sends an SLA miss notification.
  • Use case: "Orders must be available by 10 AM. DAG runs at 6 AM. SLA = 4 hours. If not done by 10 AM, page oncall."
  • sla_miss_callback: Custom function called on SLA miss — send PagerDuty alert, post to Slack, create incident ticket.

Alerting Patterns

  • on_failure_callback: Function called when a task fails all retries. Send alert with task details, log link, and runbook reference.
  • on_retry_callback: Function called on each retry — useful for logging retry context or escalating if specific error types recur.
  • on_success_callback: Useful for tracking successful completion metrics (pipeline runtime, data freshness).

Dead Letter Queue Pattern

  • For pipelines processing multiple items (e.g., 100 files), don't fail the entire DAG if one file fails. Process all files, collect failures, and route them to a dead letter queue for manual review.
  • Implementation: Try/except within the task, log failures to a DLQ table/S3 path. Mark task as success if >95% succeeded. Separate DAG processes DLQ items with human review.

Airflow at Scale

Multiple Schedulers (Airflow 2.x)

  • Airflow 2.x supports multiple active schedulers — they coordinate via database row-level locking (no leader election needed).
  • Benefit: HA (scheduler failure doesn't stop scheduling) and throughput (scheduling capacity scales horizontally).
  • Requirement: Metadata database must support row-level locking (PostgreSQL recommended, MySQL with InnoDB).

Database Tuning

  • The metadata DB is the critical bottleneck at scale (>500 DAGs, >10K daily task instances).
  • Connection pooling: Use PgBouncer between Airflow and PostgreSQL. Prevents connection exhaustion from many workers.
  • Cleanup: Implement airflow db clean to purge old task instances, logs, and XComs. Without cleanup, the DB grows unbounded and queries slow down.
  • Indexes: Ensure proper indexes on dag_run, task_instance tables. Default schema is optimized but verify with EXPLAIN on slow queries.

DAG Serialization

  • Enable dag_serialization (default in Airflow 2.x) — the scheduler serializes DAGs to the database instead of webserver parsing DAG files directly.
  • Benefit: Webserver doesn't need access to DAG files. Faster UI page loads. Reduces DAG parsing overhead across components.
  • Min file process interval: How often the scheduler re-parses DAG files. Default 30s. Increase for large DAG counts to reduce scheduler CPU.

When to choose Dagster over Airflow: If your team values testability, local development experience, and asset-based thinking (focusing on WHAT data exists rather than HOW tasks run), Dagster is increasingly the better choice for new projects. Production Anti-Patterns

  • Fat DAGs: 200+ tasks in a single DAG. Causes slow scheduling, painful debugging, and cascading failures. Break into smaller DAGs connected via sensors or datasets.
  • Using Airflow as a data processor: PythonOperator loading 100GB into memory. Airflow orchestrates — it should trigger Spark/SQL, not replace them.
  • Non-idempotent tasks: INSERT without OVERWRITE. Rerunning creates duplicates. Always design for safe rerunning.
  • Hardcoded dates: Using datetime.now() instead of {{ ds }}. Breaks backfills and makes testing impossible.
  • Shared global state: Tasks communicating via global variables or shared files outside XCom/S3. Breaks with distributed executors (CeleryExecutor, KubernetesExecutor).
  • Long-running sensors in worker slots: A mode='poke' sensor occupies a worker slot while waiting (potentially hours). Use mode='reschedule' or deferrable operators instead.
  • No alerting: Tasks fail silently. Always set on_failure_callback with PagerDuty/Slack integration for production DAGs.
  • Ignoring execution_timeout: A stuck task runs forever, blocking the worker slot. Always set a reasonable timeout.

Interview Questions

How would you design Airflow DAGs for a data platform with 200 tables needing daily ingestion, transformation, and quality checks?

I'd use a layered DAG architecture with dynamic generation. First, a configuration-driven approach: maintain a YAML file per table defining source, schedule, quality rules, and dependencies. A factory function generates one DAG per table from this config — giving 200 individual DAGs with independent scheduling and failure isolation (one table's failure doesn't block others). Each generated DAG follows the pattern: S3Sensor (wait for source) → SparkSubmitOperator (transform) → PythonOperator (Great Expectations validation) → notification. Cross-table dependencies (e.g., dim_customer must complete before fact_orders) are handled via Airflow 2.x Datasets — the upstream DAG produces a Dataset on completion, the downstream DAG's schedule triggers when its input Datasets are updated. This decouples the DAGs while maintaining correct execution order. For the transformation layer (silver → gold), I'd use a separate set of DAGs that depend on multiple upstream Datasets completing. Monitoring: a meta-DAG that runs every hour checking which table DAGs have missed their SLA, aggregating across all 200 into a single dashboard. KubernetesExecutor for heterogeneous resource needs — small tables get minimal pods, large tables get high-memory pods configured per DAG.

Your Airflow scheduler is falling behind — DAGs are being scheduled minutes or hours late. Diagnose and fix.

Scheduler performance issues typically stem from four areas. First, DAG parsing overhead: if the scheduler takes 30+ seconds to parse all DAG files, scheduling frequency drops. Check dagbag_import_timeout and the scheduler's DAG processing time in metrics. Fix: reduce DAG complexity (no expensive imports at parse time), increase min_file_process_interval, use DAG serialization (default in 2.x), and move expensive initialization inside task functions (not at module level). Second, metadata DB bottleneck: check DB query latency, connection pool exhaustion, and table sizes. Fix: deploy PgBouncer, run airflow db clean to purge old records, verify indexes on task_instance and dag_run tables, consider upgrading the DB instance. Third, worker pool exhaustion: all worker slots occupied by running/queued tasks. Sensors in poke mode are the #1 cause — each holds a slot while waiting. Fix: switch sensors to mode='reschedule' or deferrable operators, increase worker count, set appropriate pool limits per DAG category. Fourth, too many concurrent DAGs: if max_active_runs is high across hundreds of DAGs, the scheduler spends all time managing state rather than scheduling new work. Fix: lower max_active_runs, add multiple schedulers (Airflow 2.x HA), or split into multiple Airflow deployments per team/domain.

Compare KubernetesExecutor vs CeleryExecutor. When would you choose each?

CeleryExecutor maintains a pool of long-running workers that pull tasks from a Redis/RabbitMQ queue. Tasks start instantly (no pod startup) but share the worker environment (same Python version, same libraries). Choose Celery when: tasks are homogeneous (similar resource needs), latency matters (sub-second task start), steady workload patterns (predictable capacity), and the team doesn't run Kubernetes. KubernetesExecutor creates a new pod per task — full isolation, custom Docker images per task, and auto-scaling via the K8s cluster autoscaler. Tasks have 15-45 second startup latency (pod scheduling + image pull). Choose Kubernetes when: tasks have vastly different resource needs (one needs 2GB, another needs 64GB), you need dependency isolation (tasks with conflicting library versions), workloads are bursty (scale to zero during off-hours), or multi-tenancy requires strong isolation. For most data platform teams already on Kubernetes, KubernetesExecutor is the better default — the auto-scaling and isolation benefits outweigh the startup latency for ETL workloads (which typically run for minutes to hours, making 30 seconds negligible).

How do you make Airflow DAGs testable? What's your testing strategy for pipeline code?

I test at three levels. Unit tests: extract business logic from operators into pure Python functions — these are trivially testable with pytest. A transform function that takes a DataFrame and returns a DataFrame is tested with sample data, asserting output schema and values. No Airflow context needed. Integration tests: test the DAG structure itself — verify task dependencies are correct, required parameters are set, and no import errors exist. Airflow provides DagBag for loading DAGs and asserting structure: assert dag.task_dict['transform'].upstream_task_ids == {'extract'}. Also test that templated parameters render correctly: ti.render_templates() and assert rendered values match expectations. End-to-end tests: run the DAG against a test environment with synthetic data. Use Airflow's test mode (airflow tasks test dag_id task_id execution_date) for individual tasks. For full DAG runs, maintain a staging Airflow environment that processes test datasets daily. Mock external dependencies (use LocalStack for S3, testcontainers for databases) to avoid flaky tests from network issues. The key principle: keep task callables thin (just wiring) and business logic in testable modules.
