Why Governance Matters at Scale

Data governance becomes non-negotiable once an organization reaches a certain threshold of data assets, teams, and regulatory exposure. Without governance, organizations suffer from:

  • Trust erosion: Analysts can't determine if data is correct, fresh, or complete — leading to "shadow" data pipelines where each team maintains their own version of truth.
  • Compliance risk: GDPR fines reach 4% of global revenue. CCPA, HIPAA, SOX all mandate data handling controls. Without cataloging and lineage, fulfilling a "right to delete" request across 200 tables is impossible.
  • Productivity loss: Engineers spend 30-40% of time finding, understanding, and validating data. A proper catalog with lineage reduces this to minutes instead of days.
  • Incident blast radius: Without lineage, a bad schema change in one upstream table silently corrupts 50 downstream dashboards. With lineage, impact analysis is instant.
  • Cost inefficiency: Duplicate datasets proliferate. Teams store the same data 3-5x because they don't know it already exists elsewhere.
Governance maturity model: Level 1 — Catalog exists but nobody uses it. Level 2 — Catalog is populated with automated metadata. Level 3 — Quality checks run on every pipeline. Level 4 — Data contracts enforce producer-consumer agreements. Level 5 — Full observability with automated incident detection and lineage-based impact analysis. Most organizations are at Level 1-2. Lead engineers should target Level 3-4.

Data Catalog Landscape

Hive Metastore (HMS)

  • The original data lakehouse catalog. Stores table schemas, partition metadata, storage locations in a relational database (MySQL/PostgreSQL).
  • Strengths: Universal compatibility — Spark, Presto, Trino, Hive, Flink all read HMS. Battle-tested at massive scale (10,000+ tables).
  • Weaknesses: No lineage, no data quality, no access control (just metadata storage). Schema-only — no column descriptions, ownership, tags.
  • Architecture: Thrift-based service backed by RDBMS. Can become a bottleneck at scale — partition listing for tables with 100K+ partitions causes slow queries.

AWS Glue Data Catalog

  • AWS-managed Hive Metastore replacement. Serverless, auto-scaling, integrated with all AWS analytics services.
  • Strengths: Zero operations, tight integration with Athena/EMR/Redshift Spectrum/Glue ETL. Crawlers auto-discover schemas. Cross-account sharing via Resource Access Manager.
  • Weaknesses: AWS-locked, limited search/discovery capabilities, no native lineage tracking (need separate tools). 1M partition limit per table (soft limit, raisable).
  • Best practice: Use Glue Catalog as the primary metadata store for lakehouse tables. Complement with DataHub/OpenMetadata for discovery and lineage.

Databricks Unity Catalog

  • Three-level namespace (catalog.schema.table) with built-in RBAC, lineage, and audit logging.
  • Strengths: Fine-grained access control (row/column level), automatic lineage capture for all Spark jobs, data sharing via Delta Sharing (open protocol), integrated data quality with Expectations.
  • Weaknesses: Databricks-only ecosystem (vendor lock). Requires all workloads to go through Unity Catalog-enabled clusters. Migration from HMS can be complex.
  • Key differentiator: Unity Catalog captures lineage automatically — no instrumentation needed. Every SELECT, INSERT, MERGE is tracked at column level.

DataHub (LinkedIn)

  • Open-source metadata platform with rich search, lineage visualization, and governance features.
  • Architecture: Metadata graph store (GMS) backed by Elasticsearch + Neo4j/MySQL. REST and GraphQL APIs. Kafka-based ingestion.
  • Strengths: Rich UI for data discovery, automatic lineage from Spark/Airflow/dbt, ownership tracking, data quality integration, tags and glossary terms, impact analysis.
  • Integration: Ingestion plugins for Hive, Glue, BigQuery, Snowflake, dbt, Airflow, Spark, Kafka, and 50+ sources.

OpenMetadata

  • Open-source catalog built on a centralized metadata schema standard. REST API-first design.
  • Differentiator: Built-in data quality, profiling, and test suites (no separate tool needed). Integrated lineage, glossary, policies, and team ownership.
  • Architecture: Single-server deployment (simpler than DataHub). Elasticsearch for search, MySQL/PostgreSQL for storage.

Data Lineage Approaches

Automatic Lineage via Spark

  • Spark query plans contain complete information about source and target datasets. Tools extract lineage by hooking into Spark's listener interface.
  • SparkListener API: Captures onJobEnd events with logical plan details (input/output datasets, columns used).
  • OpenLineage Spark integration: A Spark plugin that emits OpenLineage events automatically for every job — no code changes required.

OpenLineage Standard

  • An open standard for metadata and lineage collection. Defines a common JSON schema for run/job/dataset events.
  • Producers: Spark, Airflow, dbt, Flink, Great Expectations — all emit OpenLineage events.
  • Consumers: Marquez (reference implementation), DataHub, Atlan, and others ingest OpenLineage events.
  • Event types: START (job begins), COMPLETE (job succeeds with lineage), FAIL (job fails with error info).
OpenLineage Event (JSON)
{
  "eventType": "COMPLETE",
  "eventTime": "2026-01-15T10:30:00Z",
  "run": {
    "runId": "run-abc123"
  },
  "job": {
    "namespace": "spark-production",
    "name": "daily_customer_aggregation"
  },
  "inputs": [
    {
      "namespace": "s3://datalake-raw",
      "name": "customers/dt=2026-01-15",
      "facets": {
        "schema": {
          "fields": [
            {"name": "customer_id", "type": "LONG"},
            {"name": "email", "type": "STRING"},
            {"name": "created_at", "type": "TIMESTAMP"}
          ]
        }
      }
    }
  ],
  "outputs": [
    {
      "namespace": "s3://datalake-curated",
      "name": "customer_daily_summary",
      "facets": {
        "schema": {
          "fields": [
            {"name": "customer_id", "type": "LONG"},
            {"name": "order_count", "type": "INT"},
            {"name": "total_revenue", "type": "DECIMAL"}
          ]
        },
        "columnLineage": {
          "fields": {
            "customer_id": {"inputFields": [{"namespace": "s3://datalake-raw", "name": "customers/dt=2026-01-15", "field": "customer_id"}]},
            "total_revenue": {"inputFields": [{"namespace": "s3://datalake-raw", "name": "orders/dt=2026-01-15", "field": "amount"}]}
          }
        }
      }
    }
  ]
}

Manual Annotation

  • For pipelines that don't support automatic extraction (legacy ETL, stored procedures, third-party tools), lineage must be manually annotated.
  • Approach: Maintain a YAML/JSON manifest per pipeline declaring inputs and outputs. CI/CD publishes these to the catalog.
  • dbt: Automatic lineage from SQL references. Every ref('model_name') and source('schema', 'table') creates a lineage edge.
Column-level lineage is the gold standard. Table-level lineage tells you "Job X reads table A and writes table B." Column-level tells you "Column B.total_revenue comes from SUM(A.amount)." This enables precise impact analysis when a specific column changes.

Data Quality Frameworks

Great Expectations

  • Python-based data quality framework. Define "expectations" (assertions) against datasets. Run validation to check if data meets expectations.
  • Core concepts: Expectation Suite (collection of checks), Validator (runs checks against a batch), Checkpoint (orchestrates validation), Data Docs (HTML reports).
  • Example expectations: expect_column_values_to_not_be_null, expect_column_values_to_be_between, expect_column_value_lengths_to_be_between, expect_table_row_count_to_be_between.
  • Integration: Embed in Airflow DAGs (validate after each transform step), integrate with Spark DataFrames, generate OpenLineage quality facets.

AWS Deequ / PyDeequ

  • Built on Spark — performs data quality checks at scale on distributed datasets. Originally from Amazon.
  • Strengths: Native Spark integration, constraint suggestion (auto-generates checks from data profiling), anomaly detection (statistical thresholds).
  • Use case: Ideal for Spark/EMR pipelines where data lives in S3. Run checks as a Spark job within the same cluster.

Soda

  • SQL-based data quality checks. Define checks in YAML using SodaCL (Soda Checks Language). Connects to any SQL-queryable source.
  • Strengths: Simple YAML syntax, works with warehouses (Snowflake, BigQuery, Redshift), anomaly detection, freshness checks, schema validation.
  • SodaCL example: checks for orders: - row_count > 0 - missing_count(customer_id) = 0 - duplicate_count(order_id) = 0

AWS Glue Data Quality

  • Native Glue feature — define rules in DQDL (Data Quality Definition Language). Runs as part of Glue ETL jobs.
  • Strengths: Zero infrastructure (serverless), integrated with Glue workflows, auto-generated recommendations from data profiling.
  • DQDL rules: Completeness "column" > 0.95, Uniqueness "id" = 1.0, ColumnValues "amount" between 0 and 10000.

from great_expectations.core import ExpectationSuite

Data Contracts

Data contracts formalize the agreement between data producers and consumers — defining schema, quality guarantees, freshness SLAs, and ownership.

Schema Registry

  • Centralized schema store (Confluent Schema Registry, AWS Glue Schema Registry) that enforces schema compatibility on write.
  • Compatibility modes: BACKWARD (new schema can read old data), FORWARD (old schema can read new data), FULL (both), NONE (no checks).
  • Enforcement: Producers must register schemas before publishing. Incompatible changes are rejected — preventing breaking downstream consumers.

Producer-Consumer Agreements

  • Contract contents: Schema definition (required/optional fields, types), quality rules (nullability, ranges, uniqueness), freshness SLA (data available by X time), ownership (team, on-call contact), change management (notification process, deprecation timeline).
  • Enforcement mechanisms: CI/CD schema validation, automated quality checks on producer writes, alerting on SLA violations.
  • Tools: dbt contracts (enforce column types and constraints), Soda contracts, custom YAML definitions in version control.
Data Contract Definition (YAML)
contract:
  name: customer_orders
  version: "2.1"
  owner: data-platform-team
  
schema:
  type: record
  fields:
    - name: order_id
      type: string
      required: true
      unique: true
    - name: customer_id
      type: long
      required: true
    - name: amount
      type: decimal
      required: true
      constraints:
        min: 0
        max: 1000000
    - name: status
      type: string
      enum: [pending, processing, shipped, delivered, cancelled]
    - name: created_at
      type: timestamp
      required: true

quality:
  - row_count: "> 0"
  - null_rate(customer_id): "= 0%"
  - freshness(created_at): "< 2 hours"
  
sla:
  availability: "99.9%"
  freshness: "data landed by 06:00 UTC daily"
  notification_channels: ["#data-alerts", "oncall@company.com"]

change_policy:
  breaking_change_notice: "14 days"
  deprecation_notice: "90 days"

PII Detection & Classification

  • Column-name heuristics: Flag columns named email, ssn, phone, address, dob, credit_card. Simple regex-based rules catch 60-70% of PII.
  • Pattern matching: Regex patterns for known PII formats — email (user@domain), SSN (XXX-XX-XXXX), phone numbers, credit cards (Luhn validation).
  • ML-based classification: AWS Macie, Google Cloud DLP, Microsoft Purview — scan data content and classify columns as PII with confidence scores.
  • Catalog integration: Tag detected PII columns in the data catalog. Auto-apply access restrictions (column masking, encryption) based on classification.
  • Continuous scanning: New tables/columns should be auto-scanned on creation. Weekly full scans catch drift (columns repurposed for PII without updating metadata).
PII is not just about emails and SSNs. Quasi-identifiers (zip code + birth date + gender) can uniquely identify individuals through linkage attacks. Address governance must consider k-anonymity for analytical datasets. A column might not be PII alone but becomes PII when combined with others.

Data Access Patterns

RBAC — Role-Based Access Control

  • Users are assigned roles (data_engineer, analyst, admin). Roles have permissions on datasets (SELECT, INSERT, ALTER).
  • Implementation: Databricks Unity Catalog grants, AWS Lake Formation permissions, Ranger policies for Hive/HDFS.
  • Pattern: Team → Role → Permissions. Example: marketing_analysts → analyst_role → SELECT on curated.marketing.*

ABAC — Attribute-Based Access Control

  • Access decisions based on attributes of the user, resource, and environment. More flexible than RBAC for complex policies.
  • Example: "Users in EU region can access EU customer data. Users with security_clearance >= 3 can access PII columns."
  • Implementation: AWS Lake Formation tag-based access, custom policy engines (OPA — Open Policy Agent).

Column-Level Security

  • Restrict or mask specific columns based on user role. PII columns (SSN, email) visible only to authorized roles.
  • Dynamic masking: Query returns masked values (email → j***@company.com) for unauthorized users. No separate physical copies needed.
  • Tools: Databricks column masks, BigQuery column-level security, Redshift dynamic data masking, Ranger column masking.

Row-Level Security

  • Users see only rows they're authorized to access. Multi-tenant isolation without separate tables.
  • Example: Regional managers see only data for their region. Partners see only their own customer data.
  • Implementation: Databricks row filters, BigQuery row-level access policies, PostgreSQL RLS policies.

Compliance — GDPR & Retention

GDPR Right-to-Delete Implementation

  1. Identify all datasets containing the user: Use lineage graph to find all downstream tables containing user_id. Without lineage, this is a manual audit of 200+ tables — weeks of work.
  2. Delete from source systems: Issue DELETE/anonymization in OLTP databases. CDC propagates deletions downstream (if configured).
  3. Delete from lakehouse: For Iceberg/Delta tables — issue DELETE WHERE user_id = X (ACID delete). For raw Parquet/CSV — requires full partition rewrite (expensive).
  4. Delete from backups/archives: This is the hardest part. Cold storage (Glacier), old snapshots, and replicas all need purging. Some organizations accept "erasure on next access/restoration" as compliant.
  5. Verify deletion: Run a validation query across all identified datasets confirming zero rows for the user_id. Generate an audit log/certificate of deletion.
GDPR Delete — Iceberg Implementation
-- Step 1: Delete from all Iceberg tables containing user
-- (Identified via lineage graph query)
DELETE FROM curated.customers WHERE user_id = 12345;
DELETE FROM curated.orders WHERE customer_id = 12345;
DELETE FROM curated.sessions WHERE user_id = 12345;
DELETE FROM curated.support_tickets WHERE requester_id = 12345;

-- Step 2: Expire old snapshots (physically remove old data files)
-- Without this, deleted data still exists in previous snapshots
CALL catalog.system.expire_snapshots('curated.customers', TIMESTAMP '2026-01-01 00:00:00', 100);

-- Step 3: Remove orphan files (cleanup unreferenced data files)
CALL catalog.system.remove_orphan_files('curated.customers');

-- Step 4: Verify deletion
SELECT COUNT(*) FROM curated.customers WHERE user_id = 12345; -- Must be 0
SELECT COUNT(*) FROM curated.orders WHERE customer_id = 12345; -- Must be 0

-- Automation: Parameterized stored procedure triggered by deletion request queue

Data Retention Policies

  • Policy definition: Each dataset has a retention period (30 days, 1 year, 7 years) based on business need and regulatory requirement.
  • Implementation: S3 lifecycle rules for raw data (transition to Glacier → delete after retention). Iceberg/Delta table maintenance jobs that delete partitions older than retention period.
  • Audit trail: Log all retention policy executions — what was deleted, when, by which policy. Required for compliance audits.

Data Observability

Freshness Monitoring

  • Track when each dataset was last updated. Alert when freshness exceeds SLA (e.g., table not updated in 4 hours when SLA is 2 hours).
  • Implementation: Query table metadata (last_modified_time for Iceberg/Delta, S3 object timestamps for raw files). Compare against expected schedule.
  • Tools: Monte Carlo, Elementary, custom Airflow sensors, CloudWatch metrics.

Volume Anomaly Detection

  • Track row counts per partition/load. Alert on significant deviations from historical patterns.
  • Statistical approach: Rolling 7-day average ± 3 standard deviations. Values outside this range trigger investigation.
  • Examples: Daily orders table normally has 50K-70K rows. Alert if < 10K (source issue) or > 200K (duplicate ingestion).

Schema Change Detection

  • Monitor for unexpected schema changes (new columns, type changes, dropped columns). Alert consumers before changes propagate.
  • Implementation: Compare current schema snapshot against previous version in catalog. Publish schema diff events to consumers.
The five pillars of data observability: Freshness (is data arriving on time?), Volume (is the expected amount of data present?), Schema (has the structure changed?), Distribution (are values within expected ranges?), Lineage (what's the blast radius of an issue?). A mature platform monitors all five continuously.

Interview Questions

How would you implement data lineage across a platform with 500+ tables, Spark jobs, Airflow DAGs, and dbt models?

I'd implement a multi-pronged lineage strategy using OpenLineage as the unifying standard. For Spark jobs, I'd deploy the OpenLineage Spark plugin (spark.extraListeners configuration) which automatically captures input/output datasets from query plans — zero code changes needed. For Airflow, the OpenLineage Airflow provider emits lineage events from each task. For dbt, lineage comes natively from ref() and source() declarations in the manifest.json. All three producers emit to a central Marquez or DataHub instance via the OpenLineage API. For legacy pipelines without OpenLineage support, I'd maintain YAML manifest files in version control declaring inputs/outputs, ingested via CI/CD. The key is making lineage capture automatic and zero-friction — if developers have to manually annotate, adoption will be below 20%. Column-level lineage is achievable for Spark (via plan analysis) and dbt (via SQL parsing) but requires more effort for legacy systems.

A GDPR right-to-delete request comes in for a user whose data exists across 200 tables in your lakehouse. Walk through your implementation.

First, I'd use the lineage graph to identify all datasets containing this user — querying the catalog for tables with user_id/customer_id columns and tracing downstream from the source customer table. This gives me the complete blast radius. Next, I'd execute deletion in topological order — starting from leaf tables (no dependents) and working upstream to avoid foreign key issues. For Iceberg/Delta tables, I'd issue DELETE WHERE user_id = X which creates new data files without the user's records. For raw S3 Parquet, I'd rewrite affected partitions excluding the user's rows. After deletion, I'd run EXPIRE SNAPSHOTS and REMOVE ORPHAN FILES on Iceberg tables to physically purge old data files — without this step, data is logically deleted but physically still exists. I'd then verify deletion with COUNT queries across all affected tables. The entire process is automated via a deletion service triggered by a compliance queue, producing an audit certificate with timestamps and affected datasets. For backups, I'd either rewrite or accept "erasure on restoration" depending on legal counsel's interpretation. The whole system depends on having accurate, complete lineage — which is why governance is prerequisite to compliance.

Compare Great Expectations, Deequ, and Soda for data quality. When would you choose each?

Great Expectations is my default choice for Python-heavy teams and mixed environments — it supports Spark DataFrames, Pandas, and SQL backends with the richest expectation library (200+ built-in checks). It excels at generating human-readable data docs and integrates well with Airflow. Deequ (PyDeequ) is optimal for Spark-native environments where all data lives in S3/HDFS — it runs natively on Spark without additional infrastructure, supports constraint suggestion from data profiling (auto-generates checks), and has anomaly detection built in. Choose Deequ when you're already on EMR/Databricks and want minimal additional tooling. Soda is best for SQL-first teams and warehouse-heavy architectures (Snowflake, BigQuery, Redshift) — its YAML-based SodaCL syntax is the simplest to adopt, and it connects directly via SQL without needing a Spark cluster. For a lakehouse with both Spark pipelines and SQL queries, I'd use Deequ within Spark jobs and Soda for SQL-layer validation, with Great Expectations as the orchestration framework that ties both together and publishes unified quality metrics to the data catalog.

How do you implement data contracts between producer and consumer teams? What happens when a contract is violated?

Data contracts are formalized as versioned YAML files stored in the producer team's repository, defining schema (column names, types, nullability), quality guarantees (freshness SLA, completeness thresholds), and change management policies (notice period for breaking changes). Enforcement happens at multiple levels: CI/CD validates that producer code changes don't violate the declared contract (schema compatibility check against the registry), runtime quality checks validate that actual data meets quality thresholds after every pipeline run, and monitoring validates freshness SLAs continuously. When a contract is violated, the system follows an escalation path: (1) automated alert to the producer team with specific violation details, (2) if not resolved within SLA, escalate to the producer's engineering manager, (3) if chronic, trigger a contract renegotiation process. The key principle is that producers own their output quality — they can't ship bad data and say "not my problem." Tooling-wise, I'd use Schema Registry for schema evolution enforcement, Great Expectations for runtime quality validation, and a custom contract service that tracks SLA compliance and generates violation reports. Consumer teams subscribe to contracts and receive proactive notifications of planned changes.

Design a data observability system that detects anomalies before they reach downstream consumers.

The system operates in three layers: collection, detection, and response. Collection layer captures metrics from every pipeline execution — row counts, null rates, value distributions, schema snapshots, execution timestamps, and data freshness per table. These metrics are stored in a time-series database (InfluxDB or Prometheus) with table/column as dimensions. Detection layer runs statistical anomaly detection on each metric stream — I'd use a combination of Z-score (for normally distributed metrics like row counts), IQR-based detection (for skewed distributions), and seasonal decomposition (for metrics with daily/weekly patterns like weekend drops in order volume). The detection runs immediately after each pipeline completes, comparing current run against historical baselines. Response layer uses lineage to determine blast radius — if an anomaly is detected in table A, immediately identify all downstream tables B, C, D that will be affected. The system can either: (a) halt downstream pipelines (circuit breaker pattern) to prevent bad data propagation, or (b) alert consumers and let them decide. I'd implement circuit breakers for critical paths (revenue reporting) and alerts for non-critical paths. The entire system is bootstrapped from existing pipeline telemetry — no additional instrumentation needed beyond what Airflow/Spark already produce. Tools like Elementary (dbt-native) or Monte Carlo (managed) provide this out-of-the-box, or build custom with Prometheus + Grafana + PagerDuty.
