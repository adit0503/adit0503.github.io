Data Modeling Paradigms

Third Normal Form (3NF)

  • Fully normalized — every non-key column depends on the key, the whole key, and nothing but the key. No redundancy.
  • Use case: OLTP systems (minimize write anomalies, enforce data integrity). Not ideal for analytics (too many JOINs).
  • Example: Orders table references customer_id (FK). Customer details only in customers table. No denormalization.

Kimball Dimensional Model

  • Optimized for analytical queries. Central fact tables (measures/events) surrounded by dimension tables (context/attributes). The star schema is the primary implementation.
  • Principles: Facts are numeric measures at the grain of a business event. Dimensions provide context (who, what, where, when). Conformed dimensions are shared across fact tables for cross-process analysis.
  • Philosophy: Bottom-up design — build individual dimensional models per business process (orders, shipments, returns), then connect via conformed dimensions.

Data Vault

  • Designed for enterprise data warehouses with multiple sources, audit requirements, and historical tracking. Three entity types: Hubs (business keys), Links (relationships), Satellites (attributes over time).
  • Hubs: Contain unique business keys (customer_id, order_number). Never change. Represent business entities.
  • Links: Represent relationships between hubs (customer PLACED order). Many-to-many relationships. Also immutable.
  • Satellites: Contain descriptive attributes with temporal validity (effective_date, load_date). Change over time — new satellite records added as attributes change.
  • Strengths: Full audit trail, handles multiple source integration cleanly, parallel loading (no dependencies between hubs/links/satellites). Weaknesses: complex for analysts to query directly — requires a presentation layer on top.

One Big Table (OBT)

  • Single wide denormalized table containing all dimensions and facts flattened together. No JOINs needed at query time.
  • Use case: Analytics/BI dashboards where query simplicity and performance matter more than storage efficiency. Common in modern cloud warehouses where storage is cheap and JOIN performance is variable.
  • Tradeoffs: Extreme query simplicity (no JOINs, analysts need only one table) vs. data redundancy, complex ETL to maintain, and update anomalies (dimension change requires updating every row).
Choosing a paradigm: 3NF for OLTP sources. Kimball dimensional for most analytical use cases (best balance of query performance and maintainability). Data Vault for enterprise warehouses with 50+ source systems and strict audit requirements. OBT for specific BI use cases where query simplicity is paramount and data freshness requirements allow full rebuilds. In practice, most modern platforms use Kimball in the gold/mart layer with OBT for specific dashboard-focused tables.

Star Schema

Fact Tables

  • Central table containing numeric measures (amount, quantity, duration) and foreign keys to dimension tables.
  • Grain: The most critical design decision — what does one row represent? One transaction? One daily summary? One line item? Define grain first, then identify dimensions and facts.
  • Measures: Additive (sum across all dimensions — revenue, quantity), semi-additive (sum across some dimensions — account balance sums across accounts but not across time), non-additive (ratios, percentages — cannot be summed).

Dimension Tables

  • Wide, descriptive tables providing context for facts. Few rows (thousands to millions), many columns (50-100+).
  • Attributes: Textual descriptions, hierarchies, flags, categories. Enable GROUP BY, FILTER, and human-readable results.
  • Denormalized within dimensions: Dimension tables are intentionally denormalized. A product dimension contains product → subcategory → category → department all in one row (no need for separate category table).

Surrogate Keys

  • Synthetic integer keys (auto-increment or hash-based) used as primary keys in dimension tables and foreign keys in fact tables.
  • Why not natural keys?: Natural keys can change (company merges → new ID), have different formats across sources, or be large (composite keys). Surrogate keys are stable, compact, and uniform.
  • Implementation: dim_customer_key INT in both dim_customer and fact_orders. Join on this key. The natural key (customer_id from source) is stored as an attribute in the dimension for lookup.

Conformed Dimensions

  • Dimensions shared across multiple fact tables with identical structure and content. Enable cross-process analysis.
  • Example: dim_date is conformed — used by fact_orders, fact_shipments, fact_returns. A query joining all three on date_key gives consistent time analysis.
  • Governance: Conformed dimensions are owned centrally. Changes require cross-team coordination since multiple fact tables depend on them.
Star Schema — Orders Domain
-- Fact table: one row per order line item
CREATE TABLE fact_order_lines (
    order_line_key    BIGINT PRIMARY KEY,  -- Surrogate key
    order_key         BIGINT,              -- FK → dim_order
    customer_key      BIGINT,              -- FK → dim_customer
    product_key       BIGINT,              -- FK → dim_product
    date_key          INT,                 -- FK → dim_date (YYYYMMDD)
    store_key         BIGINT,              -- FK → dim_store
    promotion_key     BIGINT,              -- FK → dim_promotion
    -- Measures (additive)
    quantity          INT,
    unit_price        DECIMAL(10,2),
    discount_amount   DECIMAL(10,2),
    net_amount        DECIMAL(10,2),
    tax_amount        DECIMAL(10,2),
    shipping_cost     DECIMAL(10,2)
);

-- Dimension table: customer context
CREATE TABLE dim_customer (
    customer_key      BIGINT PRIMARY KEY,  -- Surrogate key
    customer_id       VARCHAR(50),          -- Natural key (from source)
    first_name        VARCHAR(100),
    last_name         VARCHAR(100),
    email             VARCHAR(200),
    customer_segment  VARCHAR(50),          -- Gold, Silver, Bronze
    acquisition_channel VARCHAR(50),        -- Organic, Paid, Referral
    city              VARCHAR(100),
    state             VARCHAR(50),
    country           VARCHAR(50),
    region            VARCHAR(50),          -- Denormalized hierarchy
    first_order_date  DATE,
    lifetime_value    DECIMAL(12,2),
    is_active         BOOLEAN,
    -- SCD Type 2 metadata
    effective_date    DATE,
    expiry_date       DATE,
    is_current        BOOLEAN
);

Snowflake Schema

  • Extension of star schema where dimension tables are normalized into sub-dimensions. A product dimension splits into product → subcategory → category tables.
  • Advantage: Reduced storage (no redundancy in dimension hierarchies), easier dimension maintenance (update category once, not in every product row).
  • Disadvantage: More JOINs at query time (3-4 joins to traverse a hierarchy vs. 1 join in star). Modern columnar engines make this less painful than historically.
  • When to use: Large dimensions with deep hierarchies (geographic: country → state → city → zip) where storage or maintenance burden of full denormalization is significant. Rarely preferred over star schema in modern analytics — storage is cheap, query performance matters more.

Slowly Changing Dimensions

SCD Type 1 — Overwrite

  • Simply overwrite the old value. No history preserved. Customer moves from NYC to LA → update city = 'LA'.
  • Use when: History doesn't matter (correcting typos, non-business-critical attributes).
  • Implementation: Simple UPDATE statement. Cheapest to maintain.

SCD Type 2 — Add New Row

  • Insert a new dimension row for each change. Previous row gets an expiry_date. Current row has is_current = true.
  • Columns added: surrogate_key, effective_date, expiry_date (or end_date), is_current flag.
  • Use when: Full history is needed for point-in-time analysis ("What was the customer's segment when they placed this order 6 months ago?").
  • Join strategy: Fact table stores the surrogate_key that was current at transaction time — naturally points to the correct historical version.
  • Challenge: Dimension table grows (one customer = many rows). Requires careful key management in the ETL pipeline.

SCD Type 3 — Add New Column

  • Keep previous and current values in separate columns. current_city and previous_city.
  • Use when: Only need to track one prior version (not full history). Rarely used — limited to specific analytical requirements.

SCD Type 4 — History Table

  • Maintain current dimension (always up-to-date) and a separate history table logging all changes with timestamps.
  • Use when: Query performance on current state is critical (no filtering by is_current needed), but history must be available for audit.

SCD Type 6 — Hybrid (1+2+3)

  • Combine Type 2 (full history rows) with Type 3 (current value column on every row). Every historical row also shows the CURRENT value.
  • Example: Customer moved NYC → LA → Chicago. Row 1: effective=NYC, current=Chicago. Row 2: effective=LA, current=Chicago. Row 3: effective=Chicago, current=Chicago.
  • Use when: Need both point-in-time analysis AND current-state reporting from the same table without JOINing the current version.

Fact Table Types

Transaction Fact

  • One row per business event/transaction at the atomic grain. Most common type.
  • Examples: Order placed, payment received, item shipped, click event.
  • Characteristics: Additive measures, grows continuously, sparse (not every combination of dimensions has rows).

Periodic Snapshot Fact

  • One row per entity per time period. Captures the state at regular intervals.
  • Examples: Daily account balance, monthly inventory levels, weekly pipeline metrics.
  • Characteristics: Semi-additive measures (balance can be summed across accounts but not across dates — use latest or average for time). Dense — every period has a row even with no activity.

Accumulating Snapshot Fact

  • One row per entity that gets UPDATED as the entity progresses through a process/lifecycle.
  • Examples: Order lifecycle (date_ordered, date_shipped, date_delivered, date_returned). Insurance claim (date_filed, date_reviewed, date_approved, date_paid).
  • Characteristics: Multiple date keys (one per milestone). Row is updated (not inserted) as milestones occur. Useful for lag/duration analysis.

Factless Fact

  • Records events or conditions with no numeric measures — just the combination of dimension keys.
  • Examples: Student attendance (student_key, class_key, date_key — no measure, just "was present"). Product promotion coverage (product_key, promotion_key, store_key — "this product was on promotion at this store").
  • Use case: Answer "what DIDN'T happen" — students who were absent = all expected combinations MINUS factless fact rows.

One Big Table (OBT) Pattern

The OBT pattern denormalizes everything into a single wide table — all facts and all dimension attributes in every row. No joins needed at query time.

When OBT Works

  • Dashboard-specific tables: A Looker/Tableau dashboard backed by one table with all needed fields. Analysts don't need to understand star schema JOINs.
  • Column-oriented storage: In Parquet/ORC/BigQuery, wide tables don't penalize queries that only read a few columns (column pruning). Storage cost of redundancy is low.
  • Read-heavy workloads: When a table is read 1000x for every 1 write, optimizing for read performance (no JOINs) outweighs write complexity.

When OBT Fails

  • Dimension updates: If customer_segment changes, you must update EVERY row containing that customer. For a 10B row fact table with 1M customers, a segment change requires touching millions of rows.
  • Multiple grains: OBT works at one grain. If you need order-level AND line-item-level analysis, you need two OBTs or a star schema.
  • Data freshness: Full OBT rebuild is expensive. Incremental updates with denormalization logic is complex and error-prone.
OBT Construction (dbt model)
-- models/marts/obt_orders.sql
-- One Big Table: all order data denormalized for dashboard consumption

WITH orders AS (
    SELECT * FROM {{ ref('stg_orders') }}
),
customers AS (
    SELECT * FROM {{ ref('dim_customers') }}
    WHERE is_current = TRUE
),
products AS (
    SELECT * FROM {{ ref('dim_products') }}
),
stores AS (
    SELECT * FROM {{ ref('dim_stores') }}
)

SELECT
    -- Order facts
    o.order_id,
    o.order_date,
    o.quantity,
    o.unit_price,
    o.discount_amount,
    o.net_amount,
    o.tax_amount,
    o.shipping_cost,
    o.total_amount,
    
    -- Customer dimension (denormalized)
    c.customer_id,
    c.customer_name,
    c.customer_segment,
    c.acquisition_channel,
    c.city AS customer_city,
    c.state AS customer_state,
    c.country AS customer_country,
    c.region AS customer_region,
    c.first_order_date,
    c.lifetime_value,
    
    -- Product dimension (denormalized)
    p.product_id,
    p.product_name,
    p.brand,
    p.category,
    p.subcategory,
    p.department,
    p.unit_cost,
    p.margin_pct,
    
    -- Store dimension (denormalized)
    s.store_id,
    s.store_name,
    s.store_type,
    s.store_city,
    s.store_state,
    
    -- Derived metrics
    o.net_amount - (o.quantity * p.unit_cost) AS gross_profit,
    DATEDIFF('day', c.first_order_date, o.order_date) AS customer_tenure_days

FROM orders o
LEFT JOIN customers c ON o.customer_id = c.customer_id
LEFT JOIN products p ON o.product_id = p.product_id
LEFT JOIN stores s ON o.store_id = s.store_id

Activity Schema

  • A modeling approach where ALL user activities are stored in a single table with a flexible schema — activity_type, entity_id, timestamp, and a JSON/MAP column for event-specific attributes.
  • Schema: (activity_id, customer_id, activity_type, activity_ts, feature_1, feature_2, feature_3, revenue_impact, ...)
  • Advantage: Single table for all customer analytics — "show me all activities for customer X" is a simple filter, not a UNION across 20 tables. New activity types don't require schema changes.
  • Disadvantage: Sparse columns (most activities only use a few features), loss of strong typing, harder to enforce data quality per activity type.
  • Best for: Customer 360 analytics, user journey analysis, event-driven architectures where activity variety is high and evolving.

Medallion Architecture as Modeling Paradigm

Bronze Layer (Raw)

  • Raw data as-is from source systems. No transformations, no deduplication, no schema enforcement.
  • Purpose: Immutable audit trail, source of truth for reprocessing, schema-on-read flexibility.
  • Format: Same format as source (JSON, CSV) or minimal conversion (Parquet for efficiency). Partitioned by ingestion date.
  • Retention: Long (1-7 years) — enables full reprocessing from raw data.

Silver Layer (Cleaned/Conformed)

  • Cleaned, deduplicated, schema-enforced, and conformed data. Business rules applied. Standard naming conventions.
  • Transformations: Type casting, null handling, deduplication, PII masking, standardization (country codes, date formats), CDC application (MERGE operations).
  • Format: Iceberg/Delta tables with enforced schemas. This is the "enterprise data model" layer.
  • Consumers: Data engineers building gold tables, advanced analysts doing ad-hoc exploration.

Gold Layer (Business/Consumption)

  • Business-level aggregations, KPIs, dimensional models, and OBTs optimized for specific use cases.
  • Examples: dim_customer, fact_orders (star schema), obt_daily_revenue (dashboard table), ml_feature_store (ML features).
  • Consumers: BI tools (Looker, Tableau), ML pipelines, APIs, business stakeholders.
  • Modeling: This is where Kimball dimensional modeling lives — star schemas with conformed dimensions.
Medallion ≠ just three copies of data. Each layer serves a distinct purpose: bronze for auditability, silver for enterprise conformity, gold for business consumption. The anti-pattern is treating it as "raw → slightly less raw → aggregated." True silver is a governed, tested, schema-enforced enterprise layer that multiple gold consumers can trust.

Modeling for Lakehouse

Late-Arriving Facts

  • Events that arrive after their logical time period has closed (a Monday transaction arriving on Wednesday). Common in mobile apps, IoT, and distributed systems.
  • Handling: Use MERGE (not INSERT OVERWRITE) so late-arriving data can be applied to historical partitions without full rewrite. Iceberg's row-level deletes make this efficient.
  • Impact on reporting: Daily reports may change retroactively. Implement "report_date" vs "event_date" distinction. Downstream consumers should handle evolving historical partitions.

Partition Strategies

  • Date partitioning: Most common. Partition by event_date or ingestion_date. Enables time-based pruning for analytical queries.
  • High-cardinality partitioning: Avoid partitioning by customer_id (millions of values = millions of tiny files). Use bucketing instead.
  • Iceberg hidden partitioning: Partition by month(event_ts) — users query WHERE event_ts BETWEEN ..., engine auto-prunes to relevant months. No exposed partition column needed.
  • Over-partitioning risk: Too many partitions = too many small files = slow metadata operations and poor query performance. Target partition sizes of 128MB-1GB.

dbt Modeling Patterns

Staging → Intermediate → Marts

  • Staging (stg_): 1:1 with source tables. Rename columns, cast types, apply basic filters. No business logic. Materialized as views (no storage cost).
  • Intermediate (int_): Business logic that combines staging models. Deduplication, enrichment, calculation of derived fields. May not be exposed to end users. Materialized as views or ephemeral.
  • Marts (dim_, fact_, obt_): Final consumption-ready models. Dimensional models, OBTs, aggregates. Materialized as tables (for performance). Tested extensively.

Metrics Layer

  • A centralized definition of business metrics (KPIs) that ensures consistent calculation regardless of where the metric is consumed (BI tool, API, report).
  • Problem solved: "Revenue" is calculated differently by 3 teams — one includes tax, one excludes refunds, one uses a different exchange rate. The metrics layer provides ONE canonical definition.
  • Implementation: dbt Metrics (semantic layer), MetricFlow, Cube.js, Looker LookML. Define metric = measure + dimensions + time grain + filters.
  • Example: metric: monthly_active_users = COUNT(DISTINCT user_id) WHERE activity_date >= DATEADD(month, -1, CURRENT_DATE) FROM fact_user_activities
  • Benefits: Single source of truth for definitions, version-controlled metric logic, automatic drill-down and slice-by-dimension support, consistent results across BI tools and APIs.
dbt Metrics Definition
# models/metrics/revenue_metrics.yml
metrics:
  - name: total_revenue
    label: "Total Revenue"
    description: "Sum of net order amounts excluding cancelled orders"
    type: simple
    type_params:
      measure: net_amount
    filter: |
      {{ Dimension('order_status') }} != 'cancelled'

  - name: average_order_value
    label: "Average Order Value"
    description: "Average net amount per order"
    type: derived
    type_params:
      expr: total_revenue / order_count
      metrics:
        - name: total_revenue
        - name: order_count

  - name: customer_lifetime_value
    label: "Customer LTV"
    description: "Total revenue per customer over their lifetime"
    type: simple
    type_params:
      measure: net_amount
    dimensions:
      - customer_id
    time_grains: [day, week, month, quarter, year]

Interview Questions

Design the dimensional model for an e-commerce platform. What fact tables and dimensions would you create?

I'd design around the core business processes: orders, shipments, returns, and page views. The primary fact table is fact_order_lines at the line-item grain — one row per product per order with measures: quantity, unit_price, discount, net_amount, tax, shipping_cost. This atomic grain enables both line-item analysis and order-level aggregation (SUM by order_id). Supporting fact tables: fact_shipments (shipment events with delivery dates — accumulating snapshot), fact_returns (return events with return_reason), and fact_page_views (clickstream — transaction grain, very high volume).

Conformed dimensions shared across all facts: dim_customer (SCD Type 2 for segment changes), dim_product (with full category hierarchy denormalized), dim_date (calendar + fiscal attributes), dim_store/channel (online vs retail). Each fact table uses surrogate keys to join dimensions. The date dimension enables time-intelligence queries (YoY comparison, rolling averages) without complex date math. I'd also create an accumulating snapshot fact_order_lifecycle tracking milestones (ordered → paid → picked → shipped → delivered → returned) with date keys for each milestone — enabling fulfillment funnel analysis. For the gold layer specifically consumed by BI, I'd add an OBT (obt_daily_orders_summary) that pre-joins the most common fact + dimension combinations for Looker dashboards, refreshed daily.

Explain SCD Type 2. How do you implement it efficiently in a lakehouse environment, and how does it interact with fact tables?

SCD Type 2 preserves full history by inserting a new dimension row whenever an attribute changes, with effective/expiry dates and a current flag. Implementation in a lakehouse: I use dbt snapshots which automatically detect changes (via timestamp or check strategy), insert new rows with dbt_valid_from/dbt_valid_to columns, and maintain the current flag. The snapshot runs daily, comparing current source state against the snapshot table and inserting new rows for any changes detected.

The key interaction with fact tables: when a fact event occurs, the ETL must look up the CURRENT surrogate key for the dimension and store it in the fact row. This means the fact table permanently records which version of the dimension was active at transaction time. A query "what was the customer's segment when they placed order #1234?" joins fact_orders.customer_key to dim_customer.customer_key — automatically getting the historical version. For current-state reporting (total revenue by current segment), join on natural key WHERE is_current = TRUE, or use SCD Type 6 (add current_segment column to every row). Performance consideration in lakehouse: SCD2 dimensions with millions of historical rows can be large. Partition the dimension by is_current or use Z-ordering on customer_id to optimize lookups. For Iceberg, MERGE is efficient for applying changes — match on natural key, update expiry on old row, insert new row, in a single atomic operation.

Compare star schema vs OBT vs Data Vault. When would you choose each for a modern data platform?

Star schema (Kimball) is my default for the gold/mart layer — it provides the best balance of query performance, analytical flexibility, and maintainability. Facts at atomic grain enable any aggregation. Conformed dimensions enable cross-process analysis. It's well-understood by analytics engineers and works with all BI tools. Choose star schema for: general-purpose analytical platforms, multiple consumer teams, complex multi-dimensional analysis requirements.

OBT works for specific dashboard-focused use cases where a single team needs a simple, pre-joined table. I'd use OBT for: a specific Looker Explore backing one dashboard (all fields in one table, no LookML joins needed), ML feature stores (wide tables for feature vectors), or small analytical domains where rebuild is cheap (<100M rows). OBT fails at scale — dimension updates become expensive, and it's inflexible for ad-hoc analysis beyond its designed use case.

Data Vault is for enterprise-scale data integration with 50+ source systems, strict audit requirements, and continuous source evolution. Its hub-link-satellite pattern handles merging disparate sources (multiple CRM systems with different customer IDs) and preserves complete audit history. Choose Data Vault for: regulated industries (banking, healthcare), large organizations with many source systems, platforms where schema changes daily. The tradeoff is complexity — Data Vault requires a presentation layer (star schema or OBT) on top for analyst consumption because raw hub-link-satellite queries are impractical for business users.

How do you handle late-arriving facts and retroactive dimension changes in a lakehouse?

Late-arriving facts (events arriving after their logical time period) are common in mobile, IoT, and distributed systems. In a lakehouse with Iceberg/Delta, I handle them via MERGE operations that can update historical partitions efficiently. The key design decision: partition by event_date (logical time) not ingestion_date. When a late fact arrives for 3 days ago, the MERGE targets the correct historical partition. Iceberg's row-level operations make this efficient — only affected data files are rewritten, not the entire partition. Downstream consumers must be aware that historical partitions can change — I implement a "data stability" metadata column (is_final BOOLEAN) and a notification system that alerts when historical data is modified.

For retroactive dimension changes (customer's segment was corrected for the past 3 months): with SCD Type 2, this is handled by inserting a correction row with an effective_date in the past, adjusting the chain of valid_from/valid_to dates. Facts already written with the old surrogate key remain pointing to the old (incorrect) version — which may or may not be desired. If historical facts need to reference the corrected dimension, a backfill job re-assigns surrogate keys based on the corrected dimension timeline. This is expensive but necessary for accurate historical reporting. Alternatively, use SCD Type 6 where the current value is propagated to all historical rows — a single UPDATE fixes all historical rows when a correction is needed, since they always show current alongside effective values.

Describe the dbt modeling pattern of staging → intermediate → marts. How does this apply to a medallion lakehouse architecture?

The dbt layering pattern maps cleanly to medallion architecture with subtle differences. Staging models (stg_) correspond to bronze-to-silver initial transformation — they're 1:1 with source tables, performing only structural changes: column renaming for consistency, type casting, basic null handling, and timestamp standardization. They're materialized as views (zero storage cost) since they're always consumed by downstream models, never queried directly. Each staging model references a dbt source declaration, creating a clean interface between raw data and the transformation layer.

Intermediate models (int_) represent complex business logic within the silver layer — joining related tables, deduplicating, calculating derived fields, and applying business rules. They're the "heavy lifting" layer but aren't exposed to end consumers. Examples: int_orders_with_payments joins orders + payment events to determine payment status. int_customer_order_history aggregates per-customer. Materialized as ephemeral (inlined into downstream queries) or views. The key principle: intermediate models make the final mart models simple and auditable.

Marts (dim_, fact_, obt_) are the gold layer — consumption-ready models materialized as tables for performance. They implement the chosen modeling paradigm (star schema, OBT). These are heavily tested (dbt tests for uniqueness, not-null, referential integrity, accepted values) and documented. Each mart serves a specific business domain: marts/marketing, marts/finance, marts/product. The mapping: bronze = dbt sources, silver = staging + intermediate, gold = marts. dbt provides the transformation logic; Iceberg/Delta provides the storage and transaction guarantees; Airflow/dbt Cloud provides the orchestration.
