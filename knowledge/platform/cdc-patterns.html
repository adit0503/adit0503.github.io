CDC Fundamentals

Change Data Capture (CDC) is the process of identifying and capturing changes made to data in a source system, then delivering those changes to downstream consumers in near real-time. Three fundamental approaches exist:

Log-Based CDC

  • Reads the database's transaction log (binlog, WAL, redo log) to extract committed changes. The transaction log is an append-only record of every modification.
  • Advantages: Minimal impact on source database (reads log files, not query tables), captures all changes including DELETEs, preserves transaction ordering, sub-second latency achievable.
  • Disadvantages: Requires database-specific knowledge, log format can change between versions, log retention management needed, initial snapshot separate from ongoing CDC.
  • Used by: Debezium, DMS, GoldenGate, Maxwell, Canal.

Query-Based CDC

  • Polls the source database periodically using SQL queries to detect changes (usually via a last_modified timestamp or version column).
  • Pattern: SELECT * FROM orders WHERE updated_at > :last_check_timestamp
  • Advantages: Simple to implement, database-agnostic, no special permissions needed.
  • Disadvantages: Cannot capture DELETEs (row is gone), higher source load (repeated full-table scans), latency limited by polling interval, misses changes between polls if timestamp resolution is insufficient.
  • Used by: Kafka Connect JDBC Source (timestamp+incrementing mode), Sqoop incremental imports, custom ETL scripts.

Trigger-Based CDC

  • Database triggers fire on INSERT/UPDATE/DELETE and write changes to a shadow/audit table. CDC consumer reads from the shadow table.
  • Advantages: Captures all operations (including DELETEs), works with any database supporting triggers, captures before/after images.
  • Disadvantages: Significant performance impact on source (trigger fires on every write), doubles write load, complex trigger maintenance, schema changes require trigger updates.
  • Used by: Legacy CDC implementations, audit logging systems. Generally discouraged for high-volume production CDC.
Decision framework: Log-based CDC is the gold standard for production systems. Use query-based only when log access is impossible (managed databases without log export, third-party systems). Never use trigger-based for high-throughput OLTP systems — the performance penalty makes it impractical above ~1000 TPS.

Log-Based CDC Internals

MySQL Binary Log (Binlog)

  • What it is: An ordered sequence of events describing data modifications. Used for replication and point-in-time recovery.
  • Formats: STATEMENT (logs SQL), ROW (logs actual row changes — required for CDC), MIXED (combination). CDC requires ROW format.
  • Row format details: Each binlog event contains table_id, column values BEFORE (for UPDATE/DELETE) and AFTER (for INSERT/UPDATE). Controlled by binlog_row_image: FULL (all columns), MINIMAL (only changed + PK columns), NOBLOB.
  • CDC reads binlog by: Connecting as a replication replica — using the MySQL replication protocol (COM_BINLOG_DUMP command). This is a streaming connection — changes are pushed as they're committed.
  • GTID (Global Transaction ID): MySQL 5.6+ supports GTIDs which provide unique transaction identifiers across the cluster. CDC tools use GTIDs for reliable position tracking (no more binlog file + position fragility).

PostgreSQL Write-Ahead Log (WAL)

  • What it is: PostgreSQL's transaction log — every committed change is written to WAL before being applied to data files. Ensures durability and crash recovery.
  • Logical decoding: PostgreSQL 9.4+ can decode WAL entries into logical change events (INSERT, UPDATE, DELETE with row data). Requires wal_level = logical.
  • Replication slots: A slot reserves WAL segments for a consumer. Ensures no WAL is recycled before the consumer reads it. Critical for reliable CDC — but dangerous if consumer stops (WAL accumulates unbounded).
  • Output plugins: pgoutput (native, used by Debezium), wal2json (JSON output), test_decoding (text output for debugging).
  • Publication/Subscription: PostgreSQL 10+ native logical replication. Define a PUBLICATION (set of tables) and SUBSCRIPTION (consumer). Debezium uses this mechanism internally.

Oracle Redo Log

  • What it is: Oracle's transaction log. Online redo logs are circular (overwritten). Archive logs are sequential copies preserved for recovery.
  • LogMiner: Oracle's SQL-based interface to read redo/archive logs. Returns change records as SQL statements. Used by DMS (default mode) and some Debezium configurations.
  • Supplemental logging: Must be enabled for CDC — ensures redo logs contain enough column data to reconstruct before/after images. Without it, only changed columns are logged (insufficient for MERGE operations downstream).
  • Binary Reader: Direct binary parsing of redo logs. Faster than LogMiner, lower source impact. Used by GoldenGate and DMS Binary Reader mode.
  • ASM (Automatic Storage Management): If redo logs are on ASM, binary reader needs ASM access. LogMiner works regardless of storage.

SHOW BINLOG EVENTS IN 'mysql-bin.000042' LIMIT 10;

AWS DMS Architecture & Patterns

Architecture Components

  • Replication Instance: EC2-based engine that performs the data movement. Sized by vCPU/memory. Multi-AZ for production HA.
  • Source/Target Endpoints: Connection configurations with credentials, SSL, and engine-specific settings.
  • Replication Task: Defines the migration — table mappings, transformations, task type (Full Load, CDC, or both).

DMS CDC Patterns

  • Pattern 1 — Database to S3 Lake: DMS captures CDC → writes Parquet to S3 with date partitions → downstream job MERGEs into Iceberg/Delta. Most common lakehouse ingestion pattern.
  • Pattern 2 — Database to Kafka: DMS publishes CDC events to MSK topics (one topic per table). Downstream consumers process independently. Lower latency than S3 pattern.
  • Pattern 3 — Database to Database: DMS replicates between OLTP databases (Oracle to PostgreSQL migration). Full load + ongoing CDC until cutover.
  • Pattern 4 — Multi-task fan-out: Multiple DMS tasks from same source to different targets (S3 + Kafka + Redshift simultaneously). Each task reads from the same log position independently.

DMS Limitations

  • At-least-once delivery only — duplicates possible during restarts. Downstream must handle idempotency.
  • Limited DDL support — complex schema changes may require task restart.
  • No transformation beyond basic rename/filter — complex logic needs a downstream processing layer.
  • Managed black box — limited debugging visibility when issues occur.

Oracle GoldenGate

Architecture

  • Extract process: Reads source transaction log (redo/archive logs) and writes changes to local trail files. Runs on or near the source database server.
  • Trail files: Proprietary binary format storing captured changes. Sequential, append-only. Stored locally or on shared storage. Configurable retention and sizing.
  • Data Pump: Optional process that moves trail files from source system to target system over the network. Handles network interruptions gracefully.
  • Replicat process: Reads trail files on the target side and applies changes to the target database. Supports parallel apply, conflict detection, and custom mapping.
  • Manager process: Controls all other processes, manages ports, handles trail file cleanup, reports status.

Bidirectional Replication

  • GoldenGate supports active-active (bidirectional) replication between two or more databases. Both sides can receive writes.
  • Conflict Detection: When the same row is modified on both sides, GoldenGate detects the conflict using before-image comparison.
  • Conflict Resolution: Configurable strategies — timestamp-based (latest wins), site priority (primary site wins), custom PL/SQL resolution procedures.
  • Loop prevention: Each transaction is tagged with its origin. Replicat skips changes that originated from its own site — preventing infinite replication loops.

GoldenGate for Big Data

  • GoldenGate for Big Data extends replication to non-Oracle targets: HDFS, Kafka, HBase, Cassandra, Elasticsearch, S3.
  • Handlers: Java-based handlers format and write data to each target type. Kafka handler supports Avro/JSON with schema registry integration.
  • Use case: Oracle OLTP → GoldenGate → Kafka → Spark Streaming → Data Lake. Sub-second latency from Oracle to analytics.
GoldenGate Extract Configuration
-- Extract process configuration (source side)
EXTRACT ext_prod
USERID ogg_user, PASSWORD ogg_pass
EXTTRAIL ./dirdat/aa
TRANLOGOPTIONS EXCLUDETAG 00
REPORTCOUNT EVERY 60 SECONDS, RATE

-- Capture all DML on specified tables
TABLE hr.employees;
TABLE hr.departments;
TABLE sales.orders, COLS (order_id, customer_id, amount, status, updated_at);

-- Filter: only capture rows where region = 'US'
TABLE sales.transactions, FILTER (@STREQ(region, 'US'));

-- Replicat process configuration (target side)
REPLICAT rep_target
USERID target_user, PASSWORD target_pass
ASSUMETARGETDEFS
DISCARDFILE ./dirrpt/rep_target.dsc, PURGE

-- Apply with conflict resolution
MAP hr.employees, TARGET hr.employees,
  RESOLVECONFLICT (UPDATEROWEXISTS, (DEFAULT, USEMAX (updated_at))),
  RESOLVECONFLICT (INSERTROWEXISTS, (DEFAULT, OVERWRITE));

MAP sales.orders, TARGET analytics.orders_replica;

Debezium & Kafka Connect

Architecture

  • Debezium is a set of Kafka Connect source connectors that capture changes from databases and publish them as events to Kafka topics.
  • Kafka Connect framework: Provides distributed, fault-tolerant, scalable execution. Handles offset management, task distribution, and worker coordination.
  • Connectors available: MySQL, PostgreSQL, MongoDB, SQL Server, Oracle, Cassandra, Vitess, DB2, Spanner.
  • Output format: Each change event contains: before (previous row state), after (new row state), source (metadata — database, table, position), op (c=create, u=update, d=delete, r=read/snapshot).

Snapshotting

  • Initial snapshot: On first start, Debezium reads the entire current state of each table (SELECT *) and publishes as "read" events. Then switches to streaming mode for ongoing changes.
  • Snapshot modes: initial (full snapshot then streaming), schema_only (capture schema but skip data — start streaming from current position), never (only streaming, must have valid offsets), when_needed (re-snapshot if offsets are lost).
  • Incremental snapshots (Debezium 1.6+): Snapshot specific tables without stopping streaming. Uses a signaling table — INSERT a signal row to trigger snapshot of a table. Interleaves snapshot chunks with streaming changes.

Outbox Pattern

  • Application writes business events to an outbox table within the same database transaction as the domain change. Debezium captures the outbox table changes and publishes to Kafka.
  • Why: Ensures exactly-once semantics between database state and Kafka — no dual-write problem. If the transaction commits, the event is guaranteed to be published (eventually).
  • Implementation: Debezium's outbox.event.router SMT routes events from the outbox table to the appropriate Kafka topic based on the event's aggregate type.

CDC to Lakehouse Patterns

Pattern 1: CDC → S3 → MERGE into Iceberg

  1. Ingestion: DMS/Debezium writes CDC events as Parquet files to S3, date-partitioned (s3://raw/table/dt=2026-01-15/).
  2. Apply job: Scheduled Spark job reads new CDC files, applies operations to the target Iceberg table using MERGE INTO.
  3. MERGE logic: Match on primary key. WHEN MATCHED AND op='d' THEN DELETE. WHEN MATCHED AND op='u' THEN UPDATE. WHEN NOT MATCHED AND op='c' THEN INSERT.
  4. Frequency: Every 5-15 minutes for near-real-time. Hourly for batch-oriented platforms. Micro-batch with Spark Structured Streaming for sub-minute.

Pattern 2: CDC → Kafka → Spark Streaming → Delta

  1. Ingestion: Debezium publishes CDC events to Kafka topics in real-time.
  2. Processing: Spark Structured Streaming reads from Kafka, applies business logic (deduplication, enrichment), writes to Delta Lake using foreachBatch with MERGE.
  3. Latency: End-to-end 10-60 seconds depending on micro-batch interval.
  4. Advantage: Single pipeline handles both streaming and late-arriving data. Delta's ACID guarantees prevent partial writes.
CDC MERGE into Iceberg (Spark SQL)
-- Read new CDC files from S3 (incremental — only new files since last run)
CREATE TEMPORARY VIEW cdc_changes AS
SELECT *, ROW_NUMBER() OVER (
    PARTITION BY primary_key 
    ORDER BY _dms_ingestion_timestamp DESC
) as rn
FROM parquet.`s3://raw-cdc/orders/dt=2026-01-15/`
WHERE rn = 1;  -- Deduplicate: keep only latest change per key

-- Apply CDC operations to target Iceberg table
MERGE INTO catalog.curated.orders AS target
USING cdc_changes AS source
ON target.order_id = source.order_id
WHEN MATCHED AND source.Op = 'D' THEN DELETE
WHEN MATCHED AND source.Op IN ('U', 'I') THEN UPDATE SET
    target.customer_id = source.customer_id,
    target.amount = source.amount,
    target.status = source.status,
    target.updated_at = source.updated_at,
    target._cdc_timestamp = source._dms_ingestion_timestamp
WHEN NOT MATCHED AND source.Op IN ('I', 'U') THEN INSERT (
    order_id, customer_id, amount, status, updated_at, _cdc_timestamp
) VALUES (
    source.order_id, source.customer_id, source.amount, 
    source.status, source.updated_at, source._dms_ingestion_timestamp
);

Exactly-Once Delivery Challenges

  • The fundamental problem: CDC involves two systems (source database + target). Ensuring each change is applied exactly once requires distributed transaction coordination — which is impractical at scale.
  • At-least-once reality: All CDC tools (DMS, Debezium, GoldenGate) provide at-least-once delivery. Duplicates occur during restarts, rebalances, and network partitions.
  • Idempotent apply: The target must handle duplicates gracefully. MERGE INTO is naturally idempotent (applying the same update twice produces the same result). INSERT-only targets need deduplication.
  • Kafka exactly-once: Debezium with Kafka transactions (EOS) provides exactly-once within Kafka — but not end-to-end to the final target. The consumer-to-target leg must still be idempotent.
  • Deduplication strategies: (1) Primary key-based MERGE (most common), (2) Event ID + dedup window (track processed event IDs in a state store), (3) Optimistic locking (version column comparison before apply).
Common mistake: Teams assume Kafka's exactly-once semantics solve the entire problem. EOS only guarantees exactly-once within the Kafka ecosystem (produce → topic → consume). The final write to a database/lake is still at-least-once unless the consumer implements idempotent writes. Always design your target apply logic to be idempotent — MERGE with primary key matching, or upsert with version/timestamp comparison.

Schema Evolution in CDC

Types of Schema Changes

  • Additive (safe): ADD COLUMN — new records have the column, old records have NULL. All CDC tools handle this gracefully.
  • Type widening (mostly safe): INT → BIGINT, VARCHAR(50) → VARCHAR(200). Log-based CDC captures the new type. Target schema needs updating.
  • Breaking: DROP COLUMN, RENAME COLUMN, ALTER TYPE (narrowing), table RENAME. These can break CDC pipelines.

Handling Strategies

  • Debezium: Publishes schema change events to a dedicated topic (schema-changes.inventory). Consumers can react to schema changes proactively. Avro schema registry enforces compatibility — breaking changes are rejected at the registry level.
  • DMS: Limited DDL handling. ADD COLUMN works. Breaking DDL may require task stop → manual schema sync → restart. Use EventBridge to automate detection and response.
  • GoldenGate: DDL replication supported (can replicate CREATE/ALTER/DROP statements). Most robust DDL handling among the three.
  • Target-side evolution: Iceberg and Delta Lake support schema evolution natively (mergeSchema, addColumns). The apply layer should enable schema evolution to absorb new columns automatically.

Ordering Guarantees

  • Within a single row: All CDC tools guarantee ordering for changes to the same primary key. An INSERT → UPDATE → DELETE sequence will be delivered in order.
  • Across rows in same transaction: GoldenGate preserves transaction boundaries. Debezium preserves ordering within a topic partition. DMS applies in transaction order (with BatchApplyPreserveTransaction).
  • Kafka partitioning: Debezium uses the primary key as the Kafka message key → same key always goes to same partition → ordering within a key is guaranteed. Cross-key ordering requires single-partition topics (which limits throughput).
  • Multi-table transactions: If a transaction spans tables A and B, and they map to different Kafka topics, the consumer sees changes independently. Reconstructing the original transaction boundary requires the transaction ID metadata field.
  • Out-of-order handling: For targets receiving events out of order (possible with multi-partition topics), use a "latest wins" strategy — compare source.ts_ms (source transaction timestamp) and only apply if newer than current target row.

Monitoring CDC Pipelines

Key Metrics

  • Replication lag: Time between source commit and target apply. The primary health indicator. Alarm threshold depends on SLA (sub-second for real-time, minutes for near-real-time).
  • Throughput: Events/second being captured and applied. Monitor for drops (source issue) or spikes (batch jobs, migrations).
  • Consumer lag (Kafka): Difference between latest offset and consumer's current offset. Growing lag = consumer can't keep up.
  • Source log retention: Available log history. If CDC falls behind and logs expire, a re-snapshot is needed (expensive). Monitor WAL size (PostgreSQL), binlog retention (MySQL).
  • Error rate: Failed applies (constraint violations, type mismatches, missing tables). Non-zero error rate = data loss risk.

Alerting Strategy

  • P1 (page): Replication lag > 5 minutes (for real-time SLA), error rate > 0 on critical tables, connector/task in FAILED state.
  • P2 (ticket): Replication lag > 30 minutes, WAL/binlog approaching retention limit, throughput drop > 50% from baseline.
  • P3 (review): Schema change detected, new table added without CDC coverage, minor throughput variance.

Interview Questions

Design a CDC pipeline to replicate 50 source tables from PostgreSQL to a data lakehouse with near-real-time freshness and exactly-once semantics.

I'd implement Debezium with Kafka as the CDC backbone. Deploy a Debezium PostgreSQL connector configured with pgoutput plugin, capturing all 50 tables into individual Kafka topics (cdc.production.{table_name}). Use Avro serialization with Schema Registry for efficient serialization and schema evolution support. For the apply layer, I'd use Spark Structured Streaming reading from all 50 Kafka topics, processing micro-batches every 30 seconds. Each micro-batch applies changes to Iceberg tables using MERGE INTO — this provides idempotent apply (exactly-once semantics at the target) even though Kafka delivery is at-least-once. The MERGE key is the table's primary key, and I'd deduplicate within each micro-batch by keeping only the latest event per key (using source.ts_ms). For tables with high change volume (>10K events/sec), I'd increase Kafka topic partitions and use parallel MERGE operations. Monitoring: track Debezium's MilliSecondsBehindSource metric, Kafka consumer lag, and post-apply freshness checks (compare latest source timestamp in Iceberg metadata vs current time). Schema evolution is handled automatically — Debezium publishes schema changes, Iceberg's mergeSchema absorbs new columns.

Compare DMS, GoldenGate, and Debezium. When would you choose each, and what are their critical limitations?

Choose AWS DMS for simple, managed CDC to AWS targets (S3, Redshift, Kafka). Its strength is zero infrastructure management — provision a replication instance and start a task. Best for: one-time migrations with ongoing replication, database-to-S3 lake ingestion, teams without Kafka expertise. Limitations: at-least-once only, limited transformation, poor DDL handling, AWS-only targets, debugging is difficult in the managed black box.

Choose Oracle GoldenGate for Oracle-centric environments requiring bidirectional replication, sub-second latency, or complex conflict resolution. It's the only production-grade tool for active-active Oracle replication. Best for: Oracle-to-Oracle HA, financial systems requiring zero data loss, bidirectional sync between data centers. Limitations: expensive licensing ($17.5K/processor), complex configuration, Oracle-centric (limited non-Oracle source support), requires DBA expertise.

Choose Debezium for Kafka-native architectures where CDC events are first-class citizens consumed by multiple downstream systems. Best for: event-driven microservices, real-time analytics, multi-consumer CDC (publish once, consume many), outbox pattern implementations. Limitations: requires Kafka infrastructure (Connect cluster, ZooKeeper/KRaft, brokers), operational complexity of managing connectors at scale, snapshot phase can overwhelm source databases if not throttled, replication slot management for PostgreSQL requires careful monitoring.

Your Debezium connector is showing increasing replication lag. The MilliSecondsBehindSource metric has grown from 100ms to 45 minutes over the past hour. Diagnose and resolve.

First, I'd check if the lag growth correlates with a source event (batch job, data migration, high-traffic event). If source TPS spiked from 1K to 50K temporarily, the lag will naturally grow then recover — confirm by checking event throughput metrics. If throughput is normal but lag grows, the issue is on the consumer side.

Check Kafka Connect worker health: CPU, memory, GC pauses. A single-task connector processing 50 tables might be CPU-bound on serialization (especially with Avro and schema lookups). Solution: increase tasks.max to parallelize capture across multiple tasks (each task handles a subset of tables).

Check if a specific table is the bottleneck: large TOAST columns in PostgreSQL, tables with no primary key (requires full row comparison), or tables receiving massive bulk INSERTs. Solution: exclude problematic tables into a separate connector with dedicated tuning, or add missing primary keys.

Check Kafka broker throughput: if the broker cluster is saturated (disk I/O, network), producers back-pressure slows Debezium. Solution: add brokers, increase topic partitions, tune producer batch.size and linger.ms for better throughput.

Immediate mitigation: if lag exceeds WAL retention risk, temporarily increase max_slot_wal_keep_size on PostgreSQL to prevent slot being dropped. Long-term fix: right-size the connector configuration, add tasks, or split into multiple connectors.

How do you handle schema evolution in a CDC pipeline without breaking downstream consumers?

Schema evolution in CDC requires coordination across three layers: source, transport, and target. At the source layer, I'd enforce a change management process — additive changes (ADD COLUMN) are safe and can be deployed without coordination. Breaking changes (DROP, RENAME, TYPE change) require a deprecation workflow: announce 14 days ahead, verify no consumers depend on the affected column/type, then execute.

At the transport layer (Kafka), Schema Registry enforces compatibility. I'd configure BACKWARD compatibility — new schemas can read data written with old schemas. This means consumers with the new schema can process historical events. When a schema change occurs, Debezium automatically registers the new schema version. Incompatible changes are rejected by the registry, preventing accidental breaks.

At the target layer (lakehouse), I'd enable schema evolution on the Iceberg/Delta tables. New columns from CDC are automatically absorbed — Iceberg's spark.sql.catalog.spark_catalog.add-columns-on-schema-mismatch=true or Delta's mergeSchema=true. For type changes, the apply layer maps source types to compatible target types (INT→BIGINT is widening, safe; BIGINT→INT is narrowing, needs explicit handling).

For consumers, I'd implement a schema change notification system: Debezium's schema change topic alerts downstream teams, giving them time to update their processing logic before the change fully propagates through the pipeline.

Explain the Debezium outbox pattern. Why is it needed, and how does it solve the dual-write problem?

The dual-write problem occurs when an application needs to update a database AND publish an event to Kafka atomically. If you write to the database then publish to Kafka, the Kafka publish might fail — leaving the database updated but no event sent. If you publish first then write to the database, the database write might fail — event was sent for a change that didn't happen. There's no distributed transaction that spans both systems reliably.

The outbox pattern solves this by making the event a database write within the same ACID transaction as the domain change. The application writes the domain data AND an event record to an "outbox" table in a single transaction. If the transaction commits, both the domain change and the event record are guaranteed to exist. Debezium captures changes to the outbox table via CDC and publishes them to Kafka. Even if Debezium temporarily fails, the events are safely stored in the outbox table and will be published once Debezium recovers.

Implementation: Create an outbox table with columns (id, aggregate_type, aggregate_id, event_type, payload). Application inserts a row for every domain event. Debezium's outbox.event.router SMT transforms these rows into properly-routed Kafka messages — routing to topic based on aggregate_type, using aggregate_id as the message key (ensuring ordering per entity), and the payload as the message value. The outbox table can be periodically truncated after events are confirmed published (tracked via Debezium offsets). This pattern guarantees eventual consistency between database state and event stream — exactly-once semantics without distributed transactions.
