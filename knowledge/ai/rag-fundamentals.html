RAG Fundamentals & Architecture

Retrieval-Augmented Generation from first principles — why it exists, the ingestion and query pipelines, chunking, embeddings, retrieval, prompt assembly, generation, and the failure modes you must design around. The backbone pattern for grounding foundation models on your own data.

Why RAG Exists

A foundation model (FM) knows only what was in its training data, frozen at a cutoff date. It cannot cite your internal documents, it invents plausible-sounding facts (hallucination), and retraining it on your data is expensive and slow. Retrieval-Augmented Generation (RAG) sidesteps all three problems by fetching relevant context at query time and injecting it into the prompt, so the model answers from evidence rather than memory.

  • Freshness — update the knowledge base, not the model weights.
  • Attribution — return source documents so answers are auditable.
  • Cost — no fine-tuning; you pay for inference plus a vector store.
  • Access control — filter retrieval by user permissions before generation.
🔑 The one-line definition:

RAG = retrieve(query) → augment(prompt, context) → generate(answer). You are turning an open-book exam into a closed-book model by handing it the right pages.

Anatomy of a RAG System

Every RAG system splits into two pipelines that run at different times:

  1. Ingestion (offline / batch) — load documents, clean, chunk, embed, and index them into a vector store. Runs on a schedule or on document change.
  2. Query (online / real-time) — embed the user query, retrieve top-k chunks, assemble a prompt, call the FM, post-process and return with citations.
RAG query flow (pseudocode)
def answer(query, k=5):
    q_vec = embed(query)                      # same model as ingestion
    hits  = vector_store.search(q_vec, k=k,   # ANN search
                                filter=acl(user))
    context = "\n\n".join(h.text for h in hits)
    prompt = f"""Answer using ONLY the context below.
If the answer is not present, say you don't know.

Context:
{context}

Question: {query}"""
    resp = llm.generate(prompt, temperature=0)
    return resp, [h.source for h in hits]     # answer + citations

Ingestion Pipeline

This is where a data engineer adds the most value — it is an ETL pipeline with an embedding step bolted on. Stages:

  1. Extract — pull from S3, Confluence, SharePoint, databases, PDFs, HTML. Parse layout (tables, headings) with tools like Amazon Textract, Unstructured.io, or Apache Tika.
  2. Clean & normalize — strip boilerplate, de-duplicate, fix encoding, redact PII.
  3. Chunk — split into retrievable units (see below).
  4. Enrich — attach metadata: source, section, timestamp, tenant, ACL tags.
  5. Embed — convert each chunk to a vector with an embedding model.
  6. Index — upsert vectors + metadata into the vector store.
💡 Treat embeddings as a derived dataset:

Version your chunking + embedding logic. If you change the chunker or swap the embedding model, you must re-embed everything — mixed embedding spaces silently destroy retrieval quality.

Chunking Strategies

Chunking is the highest-leverage decision in a RAG system. Too large and you dilute relevance and blow the context budget; too small and you fragment meaning.

  • Fixed-size — N tokens with overlap (e.g. 512 tokens, 50 overlap). Simple, ignores structure.
  • Recursive/structural — split on headings → paragraphs → sentences. Respects document layout.
  • Semantic — split where embedding similarity between adjacent sentences drops. Keeps topics intact.
  • Document-aware — one chunk per table row, code block, or slide.
  • Parent-child (small-to-big) — embed small chunks for precise retrieval, but return the larger parent chunk to the LLM for context.
⚠️ Overlap is not free:

Overlap improves recall at chunk boundaries but inflates storage and can return near-duplicate chunks, wasting the context window. De-duplicate retrieved chunks before assembling the prompt.

Retrieval & Prompt Assembly

At query time you embed the question and run an approximate nearest neighbor (ANN) search. Key levers:

  • top-k — how many chunks to fetch. More context ≠ better; the model can get distracted (the "lost in the middle" effect).
  • Metadata filtering — restrict by tenant, date, or ACL before similarity ranking.
  • Hybrid search — combine dense (vector) with sparse (BM25/keyword) for exact terms like IDs and error codes.
  • Reranking — a cross-encoder rescores the top candidates for precision.

The retrieved chunks are assembled into a prompt with clear instructions: answer only from context, cite sources, and admit ignorance when the answer is absent. This last instruction is the single biggest hallucination reducer.

Generation & Grounding

The FM (Claude, an FM on Bedrock, or a Databricks-served model) receives system instructions + context + query. Best practices:

  • Use temperature=0 for factual grounding.
  • Ask for inline citations tied to chunk IDs so answers are verifiable.
  • Add a grounding check: a second pass (or a guardrail) that verifies claims are supported by retrieved context.
  • Stream tokens for UX, but validate citations server-side before display.

Failure Modes

Most "RAG doesn't work" complaints trace to one of these:

  • Retrieval miss — the answer chunk was never fetched (bad chunking, wrong embedding model, no hybrid search).
  • Context stuffing — too many chunks bury the relevant one.
  • Stale index — documents changed but vectors weren't refreshed.
  • Embedding drift — query and documents embedded with different models/versions.
  • Ignoring context — the model answers from its parametric memory anyway; fix with stronger prompting and grounding checks.
🔑 Debugging tip:

Always log the retrieved chunks alongside the generated answer. 80% of RAG bugs are retrieval bugs, not generation bugs — if the right chunk never showed up, no prompt will save you.

The Data Engineer's Role

RAG ingestion is a data pipeline. Your existing skills map directly:

  • Orchestration — Airflow/Dagster DAGs to refresh embeddings incrementally on CDC events.
  • Incremental processing — only re-embed changed documents (hash the source, upsert deltas).
  • Data quality — validate chunk counts, embedding dimensions, null text, and de-duplication.
  • Governance — carry lineage and ACLs from source into vector metadata (Unity Catalog, Lake Formation).
  • Medallion pattern — Bronze (raw docs) → Silver (cleaned chunks) → Gold (embedded, indexed).

Interview Questions

When would you choose RAG over fine-tuning?

Use RAG when knowledge changes frequently, must be attributable, or is access-controlled — it grounds answers in retrievable evidence and updates instantly. Use fine-tuning to teach the model a behavior, format, or style (tone, JSON structure, domain jargon), not facts. They are complementary: fine-tune for how to respond, RAG for what to respond with. RAG is cheaper to maintain and far easier to audit.

Your RAG system returns irrelevant answers. How do you debug it?

Isolate retrieval from generation. First log and inspect the top-k retrieved chunks: if the correct chunk isn't there, it's a retrieval problem — check chunking strategy, embedding model consistency, and add hybrid (BM25 + vector) search plus a reranker. If the correct chunk is retrieved but the answer is still wrong, it's a generation/prompting problem — tighten the instruction to answer only from context, lower temperature, and add a grounding check.

How do you keep a RAG index fresh at scale?

Drive ingestion from change data capture. Hash each source document; on change, re-chunk and re-embed only the affected documents and upsert by a stable chunk key, deleting orphaned chunks. Orchestrate with Airflow/Dagster on a schedule or event trigger. For high-velocity sources, use a streaming ingest (e.g. Auto Loader → embed → upsert). Track index freshness as an SLA metric.

Why does chunk size matter so much?

Chunk size controls the granularity of retrieval. Large chunks carry more context but dilute the embedding (one vector must represent many ideas), reducing similarity precision and consuming the context budget. Small chunks embed precisely but fragment meaning across boundaries. The parent-child pattern resolves this: embed small chunks for accurate matching, then return the larger parent for the LLM to reason over.

How do you enforce access control in RAG?

Attach ACL metadata (user, group, tenant, classification) to every chunk at ingestion, carried from the source system's permissions. At query time, apply a metadata filter before the similarity search so a user can never retrieve — and therefore never see summarized — content they aren't authorized for. Never rely on the LLM to redact; filter at the retrieval layer where it's deterministic and auditable.
