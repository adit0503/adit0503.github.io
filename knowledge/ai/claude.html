The Claude Model Family

Claude ships in tiers that trade capability for speed and cost — a lightweight fast tier (Haiku), a balanced workhorse (Sonnet), and a top-capability tier (Opus). The engineering skill is routing: use the smallest model that meets the quality bar for each task, and reserve the biggest for genuinely hard reasoning.

🔑 Cost lever:

Model tiering is the biggest cost control you have. Classify or draft with a fast/cheap model, escalate only hard cases to a larger one. This alone can cut spend by an order of magnitude.

Messages & System Prompts

Claude uses a messages format: an optional system prompt (role, rules, persona) plus alternating user and assistant turns. The system prompt sets behavior; the conversation carries the task.

Anthropic Messages API
import anthropic
client = anthropic.Anthropic()

msg = client.messages.create(
    model="claude-sonnet-4-20250514",
    max_tokens=1024,
    system="You are a data engineering assistant. Answer only from the provided context.",
    messages=[{"role": "user", "content": "Explain this DAG failure."}],
    temperature=0,
)
print(msg.content[0].text)

Prompting Best Practices

  • Be explicit — state the goal, format, and constraints directly. Claude follows clear instructions well.
  • Use XML tags — Claude is tuned to respect structure like <context>…</context> and <instructions>…</instructions> to separate data from directives.
  • Give examples — a few-shot example of the exact input/output shape beats paragraphs of description.
  • Prefill the response — start the assistant turn (e.g. with {) to force JSON or a format.
  • Ask for reasoning — "think step by step" for complex tasks, or use extended thinking.
  • Ground it — instruct it to answer only from provided context and to say when it doesn't know.
💡 Separate data from instructions:

Wrap retrieved documents or user-supplied content in XML tags and tell Claude the tagged content is data, not commands. This is a simple, effective defense against prompt injection in RAG apps.

Tool Use

Claude supports structured tool use: you provide tool definitions with JSON schemas, Claude emits a tool_use block, your code runs it and returns a tool_result, and Claude continues. This is the foundation for agents (see the Agentic AI article) and for connecting Claude to databases, search, and APIs.

  • Parallel tool use — Claude can request several independent tools at once.
  • Forced tool choice — require a specific tool or any tool when you need structured output.
  • Available on Bedrock — the same tool-use pattern works through the Bedrock Converse API.

Prompt Caching

Prompt caching lets you mark a large, stable prefix (a system prompt, a big reference document, tool definitions) as cacheable. Subsequent calls reuse the cached prefix at a large discount and lower latency — ideal for RAG over a fixed corpus, long system prompts, or repeated document Q&A.

⚠️ Cache the stable part:

Put the unchanging content (instructions, reference docs) at the front and mark it cacheable; keep the variable part (the user's question) after it. Reordering or editing the prefix busts the cache.

Extended Thinking & Vision

  • Extended thinking — the model reasons through a problem before answering, improving multi-step math, coding, and analysis. Budget the thinking tokens for hard tasks only.
  • Vision — Claude can read images: screenshots, charts, diagrams, scanned documents. Useful for multimodal RAG and document understanding.
  • Long context — large context windows let you pass whole documents; combine with caching to keep it affordable.

Interview Questions

How do you control cost when building on Claude?

Route by difficulty: use the cheapest tier (Haiku) for classification, extraction, and drafting, and escalate only hard reasoning to Sonnet/Opus. Add prompt caching for stable prefixes (system prompt, reference docs, tool schemas) to cut repeated input cost and latency. Cap max tokens, use temperature 0 to avoid rambly retries, and trim retrieved context to only what's relevant. Model tiering usually delivers the largest savings.

Why use XML tags in Claude prompts?

Claude is trained to respect structural delimiters, so wrapping sections in tags like <context>, <instructions>, and <example> reliably separates data from directives and improves instruction-following. It also hardens against prompt injection: you can tell Claude that tagged content is untrusted data to be used, not commands to be obeyed — a practical defense in RAG pipelines.

Explain prompt caching and when it pays off.

Prompt caching stores a marked, stable prefix so repeated calls reuse it at a large discount and lower latency instead of reprocessing it every time. It pays off when many requests share a large constant portion — a long system prompt, big tool definitions, or a fixed reference document in RAG. Keep the cacheable content at the front and the variable user input after it; any change to the prefix invalidates the cache.

How does tool use work with Claude?

You pass tool definitions with JSON input schemas. When Claude decides a tool is needed, it returns a structured tool_use block with arguments; your application executes the tool and sends back a tool_result, and Claude continues reasoning with that output. It supports parallel tool calls and forced tool choice for structured output. The same pattern is available through the Bedrock Converse API, so it's portable across direct-API and AWS deployments.

How would you get reliable JSON output from Claude?

Specify the exact schema and give a few-shot example of the desired output, set temperature 0, and prefill the assistant turn with the opening brace to force it into JSON mode. Even more robust: define a tool whose input schema is your target structure and force that tool choice, so Claude returns validated structured arguments. Always validate the parsed output and retry on schema violations.
