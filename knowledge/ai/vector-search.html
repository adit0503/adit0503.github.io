Vector Search — ANN, HNSW & Vector DBs

How approximate nearest neighbor search works under the hood — HNSW and IVF indexes, the recall/latency trade-off, filtering, hybrid search, and how to choose between pgvector, OpenSearch, Pinecone, and Databricks Vector Search for a production platform.

The Nearest Neighbor Problem

Given a query vector, find the k stored vectors closest to it. A brute-force scan compares the query to every vector — O(N × d). That's fine for thousands of vectors, but for tens of millions it's too slow for interactive latency. This is where approximate methods come in.

🔑 The core trade-off:

Vector search trades a little recall (did we find the true top-k?) for a huge gain in speed. Every index parameter is a knob on this recall-vs-latency dial.

Approximate Nearest Neighbor

ANN algorithms build an index that lets you skip most comparisons. The two dominant families:

  • Graph-based — HNSW. Best recall/latency for most workloads; higher memory.
  • Cluster/quantization-based — IVF, PQ. Lower memory, tunable, common at massive scale.

Recall is measured as recall@k against a brute-force ground truth. Production targets are typically 0.95+.

HNSW Explained

Hierarchical Navigable Small World builds a multi-layer proximity graph. Upper layers are sparse (long hops for coarse navigation); lower layers are dense (fine-grained). A search starts at the top, greedily hops toward the query, and descends layer by layer.

  • M — edges per node. Higher M → better recall, more memory.
  • efConstruction — candidate list size while building. Higher → better graph, slower builds.
  • efSearch — candidate list size at query time. Higher → better recall, higher latency. Tune this per query without rebuilding.
pgvector — HNSW index
CREATE INDEX ON docs
  USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);

-- tune recall vs latency at query time
SET hnsw.ef_search = 100;

SELECT id, text
FROM docs
ORDER BY embedding <=> :query_vec   -- cosine distance
LIMIT 5;

IVF & Product Quantization

IVF (Inverted File) clusters vectors into nlist centroids (k-means). At query time you search only the nprobe nearest clusters instead of all of them.

  • nlist — number of clusters. More clusters → finer partitions.
  • nprobe — clusters searched per query. Higher → better recall, slower.

Product Quantization (PQ) compresses each vector into a compact code by splitting it into sub-vectors and quantizing each. IVF-PQ is the workhorse for billion-scale corpora (used by FAISS) — massive memory savings at a modest recall cost, usually recovered with a full-precision rescore of the top candidates.

💡 Rule of thumb:

Under ~10M vectors and you want simplicity → HNSW. Hundreds of millions to billions with tight memory budgets → IVF-PQ. Already on Postgres and modest scale → pgvector with HNSW.

Filtered & Hybrid Search

Real queries aren't pure similarity — they carry constraints (tenant, date, ACL) and exact terms (error codes, IDs).

  • Metadata filtering — restrict candidates by attributes. Pre-filter (filter then search — accurate, can be slow) vs post-filter (search then filter — fast, may under-return). Good engines do filtered ANN natively.
  • Hybrid search — fuse dense (vector) with sparse (BM25/keyword) scores, typically via Reciprocal Rank Fusion. Catches exact matches embeddings miss.
  • Reranking — a cross-encoder rescores the fused top candidates for final precision.
⚠️ Post-filter under-return trap:

If you retrieve top-20 then filter by tenant, you may be left with two results because the other 18 belonged to other tenants. Over-fetch, or use an engine with native pre-filtered ANN.

Choosing a Vector Store

  • pgvector — vectors alongside relational data in Postgres. Great when you already run Postgres and are at moderate scale; transactional consistency for free.
  • OpenSearch / Elasticsearch (k-NN) — strong hybrid search, mature ops, native on AWS. Good when you also need full-text.
  • Amazon OpenSearch Serverless — the default vector store behind Bedrock Knowledge Bases.
  • Pinecone / Weaviate / Milvus / Qdrant — purpose-built vector DBs with managed scaling and rich filtering.
  • Databricks Vector Search — vectors governed by Unity Catalog, auto-synced from Delta tables. Ideal when your data already lives in the lakehouse (see the Databricks Mosaic AI article).

Interview Questions

Explain HNSW and its key parameters.

HNSW is a multi-layer proximity graph. Higher layers are sparse for coarse, long-distance navigation; lower layers are dense for fine search. A query enters at the top and greedily walks toward the nearest neighbors, descending layers. M sets edges per node (recall vs memory), efConstruction controls build-time graph quality, and efSearch controls the query-time candidate list — the main runtime knob for trading latency against recall, adjustable without rebuilding.

HNSW vs IVF-PQ — when do you pick which?

HNSW gives the best recall/latency and is simplest to operate, but memory grows with the graph — great up to tens of millions of vectors. IVF-PQ compresses vectors and searches only a few clusters, so it scales to hundreds of millions or billions with far less memory, at some recall cost you recover with a rescore pass. Choose HNSW for quality and simplicity at moderate scale; IVF-PQ for huge corpora under memory constraints.

What is hybrid search and why does it matter?

Hybrid search fuses dense vector similarity with sparse keyword scoring (BM25), usually via Reciprocal Rank Fusion. Embeddings capture meaning but miss exact tokens like part numbers, error codes, or rare acronyms; BM25 nails those but misses paraphrases. Combining them improves recall across both query types. A reranker on the fused candidates then sharpens precision.

Pre-filtering vs post-filtering in vector search?

Pre-filtering applies metadata constraints before the ANN search, guaranteeing all candidates are eligible but potentially slowing the search. Post-filtering runs ANN first and filters after, which is fast but can under-return when many top hits are ineligible. For correctness with selective filters (e.g. per-tenant), use an engine with native pre-filtered ANN or over-fetch generously before filtering.

When would you use Databricks Vector Search over a standalone vector DB?

When your source data already lives in Delta tables and you want governance and lineage from Unity Catalog carried into retrieval. Databricks Vector Search can auto-sync an index from a Delta table so embeddings stay fresh as data changes, without a separate ETL job to a standalone store. It reduces the operational surface and keeps ACLs consistent between the lakehouse and the retrieval layer.
