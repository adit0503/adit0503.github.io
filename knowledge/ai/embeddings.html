Embeddings — Models, Similarity & Fine-Tuning

What embeddings actually are, how similarity is measured, choosing an embedding model, dimensionality and cost trade-offs, normalization, and when to fine-tune. The numeric foundation that makes vector search and RAG possible.

What Is an Embedding

An embedding is a dense vector of floating-point numbers that positions a piece of text (or an image, audio, code) in a high-dimensional space where semantic similarity becomes geometric proximity. "Cancel my subscription" and "how do I end my plan" land near each other even though they share no keywords.

An embedding model is a neural network (usually a transformer encoder) trained so that related inputs produce nearby vectors and unrelated inputs produce distant ones. The output is a fixed-length vector — 384, 768, 1024, or 1536 dimensions are common.

🔑 Mental model:

Keyword search matches strings. Embedding search matches meaning. That is the entire reason semantic retrieval and RAG work.

Similarity Metrics

  • Cosine similarity — angle between vectors; ignores magnitude. The default for text. Range −1 to 1.
  • Dot product — cosine × magnitudes. Fast, and equal to cosine when vectors are normalized.
  • Euclidean (L2) distance — straight-line distance; sensitive to magnitude.

For normalized embeddings, cosine and dot product rank identically — so most vector databases store normalized vectors and use dot product for speed.

cosine similarity
import numpy as np

def cosine(a, b):
    return np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b))

# If vectors are pre-normalized, this reduces to a dot product:
# cosine(a, b) == np.dot(a, b)

Choosing an Embedding Model

Selection criteria, in priority order:

  • Domain fit — does it perform on your data (legal, financial, code)? Check the MTEB benchmark and, better, evaluate on your own queries.
  • Deployment mode — API (Amazon Titan Embeddings / Cohere on Bedrock, OpenAI) vs self-hosted open models (BGE, E5, GTE, Nomic) for data residency.
  • Multilingual — if content spans languages, pick a multilingual model.
  • Context length — max tokens per input; long-document models reduce chunking pressure.
  • Cost & latency — per-token API price vs GPU hosting cost.
⚠️ Model consistency is non-negotiable:

Documents and queries MUST be embedded with the same model and version. Mixing embedding spaces produces garbage retrieval. When you upgrade the model, re-embed the entire corpus.

Dimensions & Cost

Higher dimensionality can capture more nuance but costs more to store and search. A 1536-dim float32 vector is 6 KB; ten million of them is 60 GB before index overhead.

  • Matryoshka embeddings — models trained so you can truncate to fewer dimensions with graceful quality loss, trading accuracy for storage/speed.
  • Quantization — store as int8 or binary vectors to cut memory 4–32×, with a small recall hit (recover via a rescore pass).
  • Storage math — plan capacity as N_chunks × dims × bytes_per_value plus index structure overhead.

Normalization & Pitfalls

  • Normalize to unit length if you use dot-product indexes.
  • Asymmetric tasks — some models expect a query prefix vs a passage prefix (e.g. E5's query: / passage:). Skipping this quietly halves quality.
  • Truncation — inputs longer than the model's context are silently cut; chunk first.
  • Batch drift — ensure the same preprocessing (casing, whitespace) at ingest and query time.

Fine-Tuning Embeddings

Off-the-shelf models work for most cases. Fine-tune when your domain vocabulary is unusual and retrieval quality plateaus. Approaches:

  • Contrastive fine-tuning — train on (query, positive passage, negative passage) triples so relevant pairs pull together and irrelevant ones push apart.
  • Hard negatives — mine near-miss passages (retrieved but wrong) as negatives; this is where most of the gain comes from.
  • Adapter/LoRA — cheap parameter-efficient tuning instead of full retraining.
💡 Cheaper before fine-tuning:

Before investing in fine-tuning, try a better base model, hybrid search, and a reranker. These usually close most of the quality gap at a fraction of the effort.

Interview Questions

Why cosine similarity instead of Euclidean distance for text?

Cosine measures the angle between vectors, ignoring magnitude, so it captures semantic direction regardless of text length or token count. Two documents about the same topic point in the same direction even if one is far longer. Euclidean distance is magnitude-sensitive and would penalize length differences. When embeddings are normalized to unit length, cosine and dot product are equivalent, which is why vector DBs normalize and use dot product for speed.

You upgraded your embedding model. What must you do?

Re-embed the entire corpus. Old vectors live in a different geometric space, so mixing them with new query embeddings breaks similarity. Do a blue/green migration: build a new index with the new model, backfill all chunks, validate retrieval quality on a golden query set, then cut queries over. Never serve queries against a partially migrated index.

How do you cut vector storage costs without wrecking recall?

Use quantization (int8 or binary) to shrink vectors 4–32×, then add a rescore pass on the top candidates using full-precision vectors to recover accuracy. Alternatively use Matryoshka embeddings and truncate to fewer dimensions. Combine with metadata filtering so you search a smaller candidate set. Measure recall@k on a labeled set before and after to quantify the trade-off.

When is fine-tuning an embedding model worth it?

When your domain has specialized vocabulary (medical codes, financial instruments, internal jargon) and retrieval quality plateaus despite a strong base model, hybrid search, and reranking. Fine-tune contrastively on query/passage pairs with mined hard negatives. If you lack labeled pairs, generate synthetic queries from your documents with an LLM. Otherwise, prefer the cheaper wins first.
