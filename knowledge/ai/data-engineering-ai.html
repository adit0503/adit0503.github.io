AI for Data Engineering & Data for AI

The two-way relationship between data engineering and GenAI — using LLMs to accelerate pipeline work (code, docs, quality, migration), and building the data platform that feeds AI: embedding pipelines, feature stores, vector sync, and governance.

A Two-Way Street

GenAI touches data engineering in two directions. AI for DE: LLMs accelerate how you build and operate pipelines. Data for AI: DE builds the pipelines that make GenAI possible — embeddings, retrieval, features, and governance. A modern data engineer works both sides.

🔑 The durable skill:

GenAI didn't replace data engineering — it created a new consumer of clean, governed, well-modeled data. The teams that ship reliable AI are the ones with strong data foundations underneath.

AI for Data Engineering

  • Code generation — draft PySpark/SQL/dbt from a description; convert between dialects.
  • Pipeline documentation — auto-generate docs and column descriptions from code and schemas.
  • Data quality rules — suggest expectations/tests from profiling a dataset.
  • Debugging — explain a stack trace or a slow query plan and propose fixes.
  • Semantic layer / text-to-SQL — let analysts query in natural language over a governed model (with guardrails and read-only access).
  • Anomaly triage — summarize failing runs and cluster related incidents.
⚠️ Verify generated pipeline code:

LLM-drafted transformations can be subtly wrong (join keys, null handling, timezone). Treat generated code as a first draft — review, test against real data, and reconcile counts before promoting.

AI-Assisted Migration

A high-value, real-world use: migrating on-prem or legacy workloads to the cloud. LLMs translate stored procedures and legacy ETL to Spark/dbt, generate validation queries, and draft reconciliation logic — compressing timelines dramatically. The engineering discipline is in the validation harness: automated row counts, checksums, and business-rule reconciliation between source and target confirm the conversion is correct, not just plausible.

Data for AI

The platform work that makes GenAI possible:

  • Ingestion & chunking — turn source documents into retrievable, metadata-rich chunks (see Grounding FMs on Unstructured Data).
  • Embedding pipelines — compute and refresh vectors incrementally.
  • Vector sync — keep the index consistent with source (Delta Sync, CDC-driven upserts).
  • Feature stores — serve fresh features for models and for prompt enrichment.
  • Governance — carry lineage, PII tags, and ACLs from source into every downstream AI asset.

Embedding Pipelines

An embedding pipeline is an ETL job with an embed step, and it follows the medallion pattern:

Incremental embedding pipeline
# Silver → Gold, incremental by content hash
changed = (spark.read.table("silver.doc_chunks")
                 .where("_change_type IN ('insert','update')"))

embedded = (changed
    .withColumn("embedding", embed_udf("chunk_text"))   # batched model call
    .select("chunk_id", "doc_id", "chunk_text",
            "embedding", "acl_tags", "updated_at"))

(embedded.write
    .format("delta").mode("append")
    .saveAsTable("gold.doc_embeddings"))
# Vector index Delta-syncs from gold.doc_embeddings
  • Batch embedding calls to amortize model latency and cost.
  • Upsert by a stable chunk key; delete orphaned chunks when source rows disappear.
  • Orchestrate with Airflow/Dagster; trigger on CDC or schedule.

Data Quality for AI

  • Chunk integrity — assert non-empty text, expected token ranges, no duplicates.
  • Embedding validity — correct dimensionality, no NaNs, consistent model version.
  • Freshness SLAs — index lag behind source under a threshold.
  • Retrieval regression tests — a golden query set that must keep passing after each refresh.
  • PII controls — redaction verified before embedding; sensitive tags propagated for filtering.
💡 Same rigor, new artifacts:

Apply the data-quality discipline you already use on tables to chunks and vectors. "Is this embedding dataset correct and fresh?" is just a new flavor of a question you've answered for years.

Interview Questions

How does GenAI change the data engineer's role?

It adds a new consumer of data — GenAI applications need clean, chunked, embedded, governed data to retrieve from — and a new set of tools that accelerate the work itself (code generation, documentation, migration, text-to-SQL). The core discipline is unchanged: reliable ingestion, modeling, quality, and governance. Engineers now also own embedding pipelines, vector index freshness, and carrying lineage/ACLs into AI assets.

You used an LLM to convert legacy ETL to Spark. How do you trust the result?

With a validation harness, not by eyeballing. Run the source and converted pipeline on the same input and reconcile: exact row counts, column checksums/hashes, aggregate totals, and business-rule assertions. Test edge cases (nulls, duplicates, timezones, late data). Only promote when reconciliation passes within tolerance. The LLM compresses the writing time; the engineering value is in proving correctness automatically.

Design an incremental embedding pipeline.

Follow medallion: raw docs in Bronze, cleaned chunks with metadata in Silver, embeddings in Gold. Drive it from Change Data Feed/CDC so only inserted or updated chunks are re-embedded. Batch the embedding model calls for throughput, upsert by a stable chunk key, and delete orphaned chunks when source rows vanish. Sync the vector index from the Gold table (e.g. Delta Sync), and assert dimensionality, non-null text, and freshness as quality checks.

What data-quality checks are specific to AI/embedding datasets?

Beyond standard null/uniqueness checks: verify embedding dimensionality matches the model, no NaN/zero vectors, and a single consistent embedding-model version across the corpus. Assert chunk text is non-empty and within expected token ranges, de-duplicate near-identical chunks, verify PII redaction ran before embedding, and monitor index freshness lag. Add retrieval regression tests on a golden query set so refreshes can't silently degrade quality.

How do you safely expose text-to-SQL to analysts?

Constrain it heavily. Generate SQL against a governed semantic layer/curated model rather than raw tables, execute with a read-only role, allow-list SELECT only, and enforce row/scan limits and timeouts. Apply column-level access controls so restricted fields never appear, validate generated SQL before running, log every query for audit, and show the SQL to the user for transparency. Provide schema context and few-shot examples to improve accuracy.
