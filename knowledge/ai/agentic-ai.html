Agentic AI — Tools, Planning & Multi-Agent

What makes an LLM an agent — tool calling, the reasoning-action loop, memory, planning patterns like ReAct and reflection, multi-agent orchestration, MCP, and the guardrails needed to run agents safely in production data workflows.

Agent vs Chatbot vs Workflow

A chatbot generates text. A workflow runs a fixed sequence of LLM calls you wired together. An agent is an LLM that decides its own next action — it chooses which tools to call, in what order, and when it's done, based on the results it observes.

  • Workflow — you control the path; predictable, cheaper, easier to test.
  • Agent — the model controls the path; flexible, handles open-ended tasks, harder to bound.
🔑 Design principle:

Prefer the simplest thing that works. Use a fixed workflow when the steps are known; reach for agency only when the task genuinely requires dynamic decision-making. Agents add latency, cost, and failure surface.

Tool Use / Function Calling

Tools are what let an LLM act on the world — query a database, call an API, run code, search a vector store. You describe each tool with a name, description, and a JSON schema of parameters. The model responds with a structured tool call; your code executes it and returns the result.

Tool definition (Claude / Bedrock style)
tools = [{
  "name": "query_warehouse",
  "description": "Run a read-only SQL query against the analytics warehouse.",
  "input_schema": {
    "type": "object",
    "properties": {
      "sql": {"type": "string", "description": "A SELECT statement"}
    },
    "required": ["sql"]
  }
}]

# The model returns a tool_use block; you execute it and
# send the result back as a tool_result, then it continues.
⚠️ Never trust tool arguments blindly:

An agent generating SQL, shell commands, or API calls is an injection surface. Validate and constrain every argument — allow-list operations, enforce read-only, parameterize queries, and sandbox execution.

The Agent Loop

The core is a loop: the model reasons, picks an action, observes the result, and repeats until it produces a final answer or hits a limit.

  1. Observe — current state, user goal, prior tool results.
  2. Think — reason about the next step.
  3. Act — call a tool (or answer).
  4. Observe result — feed the tool output back in.
  5. Repeat until done or a max-step / budget guard fires.

Memory & Context

  • Short-term — the conversation / scratchpad in the context window. Bounded by token limits.
  • Long-term — a vector store or database the agent reads/writes across sessions (RAG for memory).
  • Context management — summarize or prune old turns; retrieve only what's relevant to avoid overflow and cost.

Planning Patterns

  • ReAct — interleave Reasoning and Acting: think, act, observe, repeat. The default agent pattern.
  • Plan-and-execute — draft a full plan first, then execute steps; cheaper and more controllable for known task shapes.
  • Reflection / self-critique — the agent reviews its own output and revises. Improves quality at the cost of more calls.
  • Tree-of-thought — explore multiple reasoning branches and pick the best.

Multi-Agent Systems

Split a complex task across specialized agents coordinated by an orchestrator.

  • Orchestrator-worker — a lead agent decomposes the task and delegates to sub-agents (e.g. a retrieval agent, a SQL agent, a writer agent).
  • Isolation — each sub-agent gets its own context and toolset, keeping prompts focused and reducing cross-talk.
  • Trade-off — more agents mean more coordination overhead, latency, and cost. Justify each one.
💡 When multi-agent pays off:

Parallelizable subtasks (research many sources at once) or clearly separable skills. For linear tasks, a single agent with good tools usually beats a swarm.

MCP & Tool Standards

The Model Context Protocol (MCP) is an open standard for connecting models to tools and data sources through a uniform interface. Instead of hand-wiring every integration, an MCP server exposes tools/resources that any MCP-aware client can consume — decoupling tool providers from agent runtimes. AWS Bedrock Agents, Claude, and others increasingly interoperate through such standardized tool interfaces.

Production Concerns

  • Step & cost limits — hard caps to prevent runaway loops.
  • Observability — trace every reasoning step, tool call, and token spend (LangSmith, LangFuse, Bedrock traces).
  • Determinism — pin model versions, use low temperature for tool-selection reliability.
  • Human-in-the-loop — require approval before high-impact actions (writes, deletes, spend).
  • Guardrails — input/output filtering, PII redaction, and permission checks around every tool.

Interview Questions

What distinguishes an agent from a normal LLM chain?

In a chain/workflow, the control flow is fixed by the developer — the LLM fills in text at predetermined steps. In an agent, the LLM decides the control flow: which tool to call, with what arguments, in what order, and when the task is complete, based on observed results. Agents are more flexible for open-ended tasks but add latency, cost, and unpredictability, so you use them only when dynamic decision-making is genuinely required.

Explain the ReAct pattern.

ReAct interleaves Reasoning and Acting in a loop. The model produces a thought, chooses an action (tool call), observes the result, then reasons again with that new information — repeating until it can answer. Interleaving reasoning with tool feedback lets the agent correct course based on real observations rather than committing to a plan blindly, which reduces compounding errors.

How do you stop an agent from running forever or racking up cost?

Enforce hard bounds: a max-step count, a token/cost budget, and a wall-clock timeout that terminate the loop. Detect repetition (same tool + args) and break. Use low temperature for reliable tool selection, add a final-answer forcing prompt when near the limit, and require human approval for high-impact actions. Trace every step so you can see where loops form.

An agent generates SQL to answer analytics questions. What are the risks and mitigations?

Risks: destructive or expensive queries, injection via crafted inputs, and data exfiltration. Mitigations: grant a read-only role, allow-list statement types (SELECT only), enforce row/scan limits and query timeouts, validate the generated SQL before execution, apply column-level access controls, and run in an isolated warehouse/schema. Log every query for audit and add human approval for anything outside the guardrails.

When is a multi-agent architecture worth the complexity?

When subtasks are parallelizable (independent research streams) or require distinctly separate skills/tools that benefit from isolated context. An orchestrator decomposes and delegates, keeping each agent's prompt focused. For linear, dependent tasks the coordination overhead, added latency, and cost usually outweigh the benefit — a single well-equipped agent is simpler and often better.
