Grounding FMs on Unstructured Data

How to add the context of PDFs, scanned documents, images, audio, HTML, and email into a foundation model — parsing, layout-aware extraction, multimodal embeddings, metadata enrichment, and the ingestion pipeline that turns messy files into retrievable context.

The Unstructured Data Problem

An estimated majority of enterprise data is unstructured — contracts, reports, emails, tickets, recordings, scanned forms. Foundation models can reason over this content, but only if you extract, clean, and structure it into something retrievable. This extraction is a classic data-engineering job, just with new targets: chunks and vectors instead of rows and columns.

🔑 The reframe:

"Adding unstructured context to an FM" is an ETL problem. Extract from the source, transform into clean chunks with metadata, load into a vector store, and retrieve at query time. Your lakehouse skills transfer directly.

Ways to Add Context to an FM

Four escalating options, cheapest first:

  1. In-context (prompt stuffing) — paste the document into the prompt. Simple, but bounded by the context window and costly per call.
  2. RAG — retrieve only relevant chunks at query time. The default for large, changing corpora.
  3. Long-context / caching — large context windows plus prompt caching let you keep a big reference document resident cheaply across calls.
  4. Fine-tuning — bake in behavior/style. Not for facts — expensive to keep current.
💡 Decision rule:

Small, stable reference that fits the window → in-context or caching. Large, changing knowledge → RAG. Need a consistent behavior/format → fine-tune. Most enterprise systems land on RAG, often combined with prompt caching.

Parsing & Extraction

Getting clean text out of files is where most quality is won or lost.

  • PDFs — digital PDFs extract cleanly; scanned PDFs need OCR. Preserve reading order and headings.
  • Office/HTML — strip navigation, boilerplate, and styling; keep semantic structure.
  • Tools — Amazon Textract (OCR + forms + tables), Unstructured.io, Apache Tika, LlamaParse, Docling.
  • Layout-aware parsing — capture headings, sections, and hierarchy so chunking can respect structure.

Tables, Layout & OCR

Tables are the classic RAG killer — flattening a table to plain text scrambles rows and columns. Handle them explicitly:

  • Extract tables as structured data (Textract table API) and serialize each row into a self-describing sentence, or store as Markdown/HTML tables.
  • OCR scanned documents before chunking; check confidence scores and flag low-confidence pages.
  • For complex layouts (multi-column, forms), use layout models rather than naive text extraction.
⚠️ Garbage in, garbage retrieved:

If parsing mangles the text, no embedding model or reranker can recover it. Invest in extraction quality first — it's the highest-ROI stage of the whole pipeline.

Images, Audio & Multimodal

  • Images — either caption them with a vision model (e.g. Claude's vision capability) and embed the caption, or use a multimodal embedding model to embed the image directly.
  • Charts/diagrams — ask a vision model to describe the data, then index the description.
  • Audio — transcribe with a speech-to-text model (Amazon Transcribe), then treat as text; keep timestamps as metadata.
  • Multimodal RAG — retrieve across text and image vectors in the same space and pass both to a multimodal FM.

Metadata & Enrichment

Metadata is what makes retrieval filterable, governable, and auditable. Attach at ingestion:

  • Provenance — source system, document ID, URL, page/section, ingest timestamp.
  • Access control — owner, tenant, classification, ACL tags carried from the source.
  • Semantic tags — LLM-generated summary, entities, topic — useful for filtering and hybrid search.
  • Freshness — effective/expiry dates so stale content can be excluded or down-weighted.

A Reference Ingestion Pipeline

Unstructured → retrievable context (medallion)
Bronze:  land raw files in S3 (versioned, immutable)
            │  trigger: S3 event / CDC / schedule
            ▼
Silver:  parse + OCR (Textract) → clean text
         extract tables as structured rows
         detect & redact PII
         attach provenance + ACL metadata
            │
            ▼
Gold:    chunk (structure-aware, parent-child)
         embed (Titan / Cohere on Bedrock)
         upsert vectors + metadata into
         vector store (OpenSearch / Databricks
         Vector Search) — incremental by content hash

Orchestrate with Airflow or Dagster; process incrementally by hashing each source file so only changed documents are re-parsed and re-embedded. Track counts and embedding dimensions as data-quality checks.

💡 Managed shortcut:

AWS Bedrock Knowledge Bases and Databricks Vector Search can automate much of this — point them at S3 / a Delta table and they handle chunking, embedding, and indexing. Build custom only when you need control over parsing, chunking, or metadata that the managed path doesn't expose.

Interview Questions

What options exist to give a foundation model access to your private documents, and how do you choose?

In-context prompting (paste it in — for small, stable docs), RAG (retrieve relevant chunks — for large, changing corpora), long-context with prompt caching (keep a big reference resident cheaply), and fine-tuning (for behavior/format, not facts). Choose by data size, volatility, and need for attribution. Most enterprise systems use RAG, often with prompt caching, because knowledge changes and must be auditable and access-controlled.

How do you handle tables and scanned PDFs in a RAG pipeline?

Don't flatten tables to plain text — it scrambles row/column relationships. Extract them as structured data (e.g. Textract's table API) and serialize each row into a self-describing sentence or keep Markdown/HTML tables. For scanned PDFs, run OCR first, check confidence scores, and flag low-confidence pages for review. Use layout-aware parsing to preserve headings and reading order so chunking respects document structure.

How would you add images to a RAG system?

Two approaches. Caption-and-embed: use a vision model to generate a rich text description of each image/chart, then embed and index the caption alongside text. Or use a multimodal embedding model to embed images directly into a shared space so text queries can retrieve images. For charts and diagrams, captioning the underlying data usually retrieves better than raw image embedding. Pass retrieved images to a multimodal FM for the final answer.

Why is parsing the highest-ROI stage of unstructured ingestion?

Because errors there propagate irrecoverably. If extraction mangles reading order, drops table structure, or produces OCR noise, the chunks are wrong, the embeddings encode garbage, and no reranker or prompt can fix it. Clean, layout-aware extraction is the foundation everything downstream depends on, so it deserves the most engineering attention and quality checks.

How do you keep unstructured ingestion incremental and governed?

Land raw files immutably in Bronze, then process only changed files by hashing content and comparing to the last run — re-parse and re-embed just the deltas, upserting by a stable chunk key. Carry provenance and ACL metadata from source into every chunk so retrieval can be filtered and audited. Redact PII in Silver. Orchestrate with Airflow/Dagster and treat chunk counts and embedding dimensions as data-quality assertions.
