Why Naive RAG Isn't Enough

Naive RAG — embed query, fetch top-k, stuff into prompt — breaks on real workloads: ambiguous queries, questions that need multiple documents, exact-term lookups, and answers scattered across sources. Advanced RAG adds stages before and after retrieval to fix each failure.

🔑 Frame RAG as a pipeline:

query → transform → retrieve (hybrid) → rerank → assemble → generate. Each stage is independently measurable and tunable.

Query Transformation

  • Query rewriting — clean a messy conversational query into a standalone search query.
  • Multi-query — generate several paraphrases, retrieve for each, and merge results to boost recall.
  • HyDE (Hypothetical Document Embeddings) — ask the LLM to draft a hypothetical answer, embed that, and search with it; the fake answer often sits closer to real passages than the raw question.
  • Decomposition — break a complex question into sub-questions, retrieve for each, then synthesize.

Hybrid Retrieval & Fusion

Run dense (vector) and sparse (BM25) retrieval in parallel and fuse the rankings, typically with Reciprocal Rank Fusion (RRF), which combines ranks rather than raw scores so the two systems' incomparable scores don't need calibration.

Reciprocal Rank Fusion
def rrf(rankings, k=60):
    scores = {}
    for ranking in rankings:            # e.g. [dense_hits, bm25_hits]
        for rank, doc_id in enumerate(ranking):
            scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank)
    return sorted(scores, key=scores.get, reverse=True)

Reranking

Retrieval uses a bi-encoder (query and doc embedded separately) for speed. A cross-encoder reranker scores each (query, passage) pair jointly, which is far more accurate but too slow to run over the whole corpus. So you retrieve a large candidate set (say 50) cheaply, then rerank down to the best 5.

  • Managed rerankers: Cohere Rerank (available on Bedrock), voyage-rerank.
  • Reranking is often the single biggest quality win after hybrid search.
💡 Retrieve wide, rerank narrow:

Over-fetch candidates to maximize recall, then let the cross-encoder maximize precision on the shortlist. This two-stage design gets you the best of both.

Contextual & Parent-Child Retrieval

  • Parent-child (small-to-big) — embed small chunks for precise matching, return the enclosing parent for full context.
  • Contextual retrieval — prepend an LLM-generated summary of the document to each chunk before embedding, so isolated chunks retain their context ("this snippet is from the Q3 revenue section of the 2025 annual report").
  • Sentence-window — embed single sentences, expand to a window of neighbors at return time.

GraphRAG

Some questions ("how are these two entities connected?", "summarize themes across the whole corpus") can't be answered by independent chunks. GraphRAG extracts entities and relationships into a knowledge graph, then retrieves subgraphs or community summaries. It excels at multi-hop reasoning and global questions, at the cost of a heavier, LLM-driven ingestion step.

Agentic RAG

Instead of a fixed retrieve-then-generate flow, an agent decides whether to retrieve, which source to query, and whether the retrieved evidence is sufficient — looping to refine the query if not. This handles multi-step research and routing across multiple knowledge bases, trading determinism for adaptability. (See the Agentic AI article.)

Evaluating RAG

You cannot improve what you don't measure. Split metrics by stage:

  • Retrieval — recall@k, precision@k, MRR, nDCG against a labeled query→relevant-doc set.
  • Generation — faithfulness (is every claim supported by context?), answer relevance, context precision/recall. Tools: RAGAS, LLM-as-judge, Bedrock/MLflow evaluation.
  • End-to-end — correctness on a golden Q&A set, plus latency and cost per query.
⚠️ Build the eval set first:

Without a golden set of questions and expected sources/answers, every "improvement" is a guess. Curate 50–200 representative queries before you start tuning.

Interview Questions

What is a reranker and why add one?

A reranker is a cross-encoder that scores a (query, passage) pair jointly, reading both together rather than comparing pre-computed embeddings. It's far more accurate than the bi-encoder used for initial retrieval but too slow to run over the whole corpus. So you retrieve a wide candidate set cheaply, then rerank the shortlist for precision. It's typically the biggest quality gain after adding hybrid search.

Explain HyDE and when it helps.

HyDE (Hypothetical Document Embeddings) asks the LLM to generate a plausible answer to the query, then embeds that hypothetical answer and uses it for retrieval. The generated text resembles the target passages more than a terse question does, improving matches for underspecified or short queries. The trade-off is an extra LLM call and the risk the hypothetical drifts off-topic; it helps most when queries are vague.

When would you reach for GraphRAG?

For multi-hop questions about relationships between entities and for global/thematic questions that require synthesizing across the whole corpus rather than a few chunks. GraphRAG builds a knowledge graph of entities and relations and retrieves subgraphs or community summaries. The cost is a heavier, LLM-driven ingestion pipeline, so use it only when standard chunk retrieval provably fails those query types.

How do you evaluate a RAG system?

Separate retrieval from generation. Measure retrieval with recall@k, precision@k, MRR, and nDCG against a labeled query-to-document set. Measure generation with faithfulness (claims grounded in context), answer relevance, and context precision/recall — often via LLM-as-judge frameworks like RAGAS. Track end-to-end correctness on a golden Q&A set plus latency and cost. Build that golden set before tuning anything.

Why Reciprocal Rank Fusion instead of adding scores?

Dense and sparse retrievers produce scores on incomparable scales (cosine similarity vs BM25), so summing them requires fragile normalization. RRF fuses by rank position — each document gets 1/(k + rank) from each list — which is robust, parameter-light, and needs no score calibration. It reliably blends heterogeneous rankers, which is exactly what hybrid search requires.
