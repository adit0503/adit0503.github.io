AI Engineering Interview Prep

Core Concepts

RAG vs fine-tuning vs long-context — how do you choose?

RAG for large, changing, attributable, access-controlled knowledge. Fine-tuning to instill behavior, format, or domain style — not facts. Long-context (with prompt caching) for a bounded, stable reference that fits the window. They combine: fine-tune for how to respond, RAG for what to respond with, caching to keep it cheap. Default to RAG for enterprise knowledge because it's fresh, auditable, and cheap to maintain.

Walk me through what happens on a single RAG query.

Embed the query with the same model used at ingestion; apply metadata/ACL filters; run ANN search for top candidates; optionally fuse with keyword (BM25) results and rerank with a cross-encoder; assemble the best chunks into a prompt that instructs the model to answer only from context and cite sources; call the FM at low temperature; run a grounding check; return the answer with citations. Log the retrieved chunks for debugging.

Cosine vs dot product vs Euclidean — which and why?

Cosine for text — it's magnitude-invariant, capturing semantic direction regardless of length. Dot product equals cosine when vectors are normalized and is faster, so vector DBs normalize and use it. Euclidean is magnitude-sensitive and rarely preferred for text embeddings. The practical answer: normalize embeddings and use dot-product/cosine.

What are the biggest sources of RAG failure?

Mostly retrieval, not generation: bad chunking, embedding-model/version mismatch between query and docs, missing hybrid search for exact terms, stale indexes, and context stuffing that buries the answer. Generation-side failures — ignoring context, hallucinating — are usually fixed with stronger grounding prompts, low temperature, and grounding checks. Always inspect retrieved chunks first.

What is an agent and when do you avoid one?

An agent is an LLM that chooses its own actions (tools) in a reasoning loop until it's done. Avoid agency when the steps are known — a fixed workflow is cheaper, faster, and testable. Use agents only for genuinely open-ended or dynamic tasks, and bound them with step/cost/time limits, validated tools, and human approval for high-impact actions.

Platform & Tooling

When Bedrock, when Databricks Mosaic AI, when roll-your-own?

Bedrock when you're AWS-native and want managed models, Knowledge Bases, Agents, and Guardrails governed by IAM with data staying in your account. Databricks Mosaic AI when your data lives in Delta/Unity Catalog and you want Vector Search with Delta Sync, serving, and one governance model end to end. Roll your own only when you need control the managed platforms don't offer, accepting the operational burden of running vector DBs, pipelines, and evaluation yourself.

How do you pick an embedding model?

Evaluate on your own queries, not just leaderboards. Weigh domain fit, deployment mode (API like Titan/Cohere on Bedrock vs self-hosted for residency), multilingual needs, context length, and cost/latency. Ensure the same model+version embeds documents and queries. Try a strong base model plus hybrid search and reranking before considering fine-tuning.

HNSW vs IVF-PQ at scale?

HNSW gives the best recall/latency and is simplest — great to tens of millions of vectors, but memory-hungry. IVF-PQ compresses vectors and probes a few clusters, scaling to hundreds of millions/billions with far less memory at some recall cost recovered by a rescore pass. Pick HNSW for quality and simplicity, IVF-PQ for huge corpora under memory constraints.

System Design — Enterprise RAG Assistant

"Design a company-wide assistant that answers from internal docs across SharePoint, Confluence, and S3, respecting per-user permissions."

How would you architect it?

Ingestion: connectors pull from each source on a schedule/CDC; parse with layout-aware extraction and OCR; chunk (parent-child); attach provenance + ACL metadata inherited from source permissions; redact PII; embed and upsert into a vector store, incremental by content hash. Query: authenticate the user, resolve their groups, apply ACL pre-filter, hybrid retrieve + rerank, assemble a grounded prompt, generate with a low-temp FM (Claude on Bedrock), run a grounding guardrail, return with citations. Governance: filter at retrieval — never rely on the model to withhold. Ops: trace every request, golden-set eval on each index refresh, monitor freshness/cost/feedback. Managed path: Bedrock Knowledge Base + Guardrails, or Databricks Vector Search + Unity Catalog.

How do you guarantee a user never sees unauthorized content?

Enforce access at the retrieval layer with deterministic metadata filters derived from the user's identity and groups, applied before similarity search, so unauthorized chunks are never candidates and can't be summarized into an answer. Carry ACLs from source at ingestion and keep them fresh. Use pre-filtered ANN (or over-fetch then filter) to avoid under-returning. Audit every query. The LLM is never the security boundary.

System Design — Agentic Analytics

"Let business users ask questions answered by querying the warehouse."

How do you build it safely?

An agent with a constrained SQL tool over a governed semantic layer, not raw tables. Provide schema + metric definitions and few-shot examples as context. Execute with a read-only role, allow-list SELECT, enforce row/scan limits and timeouts, apply column-level access, and validate generated SQL before running. Show the SQL for transparency, cite the tables used, cap agent steps/cost, and log every query. Escalate ambiguous questions back to the user rather than guessing. Add caching for repeated questions.

How do you evaluate and monitor it?

Build a golden set of question→expected-SQL/answer pairs; measure execution accuracy (does the SQL run and return the right result) and answer correctness, not just string match. Online: track query success rate, user feedback, escalation rate, and cost per query via traces. Alert on failure/refusal spikes and cost regressions. Version prompts, schema context, and model together, and canary changes against the golden set before rollout.

System Design — Multimodal Document Search

"Search across scanned contracts, images, and tables, returning grounded answers with citations."

How do you handle the mixed content?

Per modality: OCR + layout parsing for scanned contracts (flag low-confidence pages); extract tables as structured rows serialized into self-describing text; caption images/charts with a vision model (or use multimodal embeddings) and index the description. Chunk with structure awareness, attach page/section provenance, and embed into a shared retrieval layer. At query time, hybrid retrieve + rerank, pass text and any relevant images to a multimodal FM (e.g. Claude vision), and return answers citing the exact document, page, and region. Invest most in extraction quality — it caps everything downstream.

How do you keep it fresh and correct as documents change?

Land raw files immutably in Bronze; process incrementally by hashing content so only changed documents are re-parsed and re-embedded, upserting by stable chunk key and deleting orphans. Orchestrate with Airflow/Dagster on events or schedule. Assert extraction quality (OCR confidence), embedding dimensionality, and de-duplication as data-quality checks, track index freshness as an SLA, and run a golden retrieval regression set after each refresh so quality can't silently drift.
