Model Context Protocol (MCP)

The open standard for connecting AI applications to tools and data — what MCP is, its client/server architecture, the tools/resources/prompts primitives, transports, why it matters for agent ecosystems, and the security considerations that come with it.

The M×N Integration Problem

Before a standard existed, every AI application had to write custom integration code for every tool and data source it wanted to use. With M applications and N tools, you're facing M×N bespoke integrations. The Model Context Protocol (MCP), an open standard introduced by Anthropic, turns that into M+N: each tool exposes an MCP server once, and each application implements an MCP client once.

🔑 The analogy:

MCP is often called "USB-C for AI." A single standardized interface lets any compliant client plug into any compliant server, decoupling tool providers from the models and apps that consume them.

Architecture

MCP is a client-server protocol built on JSON-RPC:

  • Host — the AI application the user interacts with (an IDE assistant, a chat app, an agent runtime).
  • Client — lives inside the host and maintains a 1:1 connection to a server.
  • Server — a program that exposes capabilities (tools, data, prompts) over MCP. It wraps a database, an API, a filesystem, etc.

A host can connect to many servers at once, composing capabilities from multiple sources without knowing their internals.

Primitives — Tools, Resources, Prompts

MCP servers offer three kinds of capability:

  • Tools — executable functions the model can call (query a DB, send a request, run an action). Model-controlled, like function calling.
  • Resources — read-only data the host can load into context (files, records, documents). Application-controlled.
  • Prompts — reusable, parameterized prompt templates the server exposes for common workflows. User-controlled.
💡 Tools vs Resources:

Tools do things (side effects, actions); Resources provide things (context, data). Keeping this split clean helps the host decide what the model may invoke versus what merely enriches context.

Transports & Lifecycle

  • stdio — the server runs as a local subprocess communicating over standard input/output. Ideal for local tools (filesystem, local DB).
  • Streamable HTTP — for remote servers over the network, supporting streaming responses.
  • Discovery — on connect, the client asks the server what tools/resources/prompts it offers; the host then advertises those tools to the model.
  • Capability negotiation — client and server agree on supported features during initialization.
Conceptual MCP flow
1. Host starts, launches/connects to MCP server(s)
2. Client ↔ Server: initialize + capability negotiation
3. Client: "list tools" → Server returns tool schemas
4. Host advertises those tools to the model
5. Model emits a tool call → Client forwards to Server
6. Server executes, returns result → Client → model context
7. Model continues with the result

Why It Matters

  • Reusability — write an MCP server for your data platform once; any MCP-aware assistant can use it.
  • Ecosystem — a growing library of prebuilt servers (databases, cloud APIs, search, filesystems) you can plug in.
  • Portability — swap the host/model without rewriting integrations; swap a server without touching the app.
  • Data-platform angle — expose governed warehouse queries, catalog lookups, or pipeline controls as MCP tools so assistants operate through a controlled, audited interface.

Security Considerations

Standardizing tool access also standardizes the attack surface — treat MCP servers as privileged components.

  • Trust the server — a malicious or compromised server can return poisoned tool descriptions or data (a prompt-injection vector). Only connect to servers you trust.
  • Least privilege — scope each server's credentials and permissions tightly; prefer read-only where possible.
  • Human approval — gate high-impact tool calls behind confirmation.
  • Auth & audit — authenticate remote servers, and log every tool invocation for accountability.
  • Validate inputs/outputs — don't let tool arguments or results flow unchecked into privileged actions.
⚠️ Tool descriptions are untrusted input:

The model reads a server's tool descriptions, so a hostile server can attempt to steer behavior through them. Vet servers, isolate them, and apply the same defense-in-depth you'd use for any external integration.

Interview Questions

What problem does MCP solve?

The combinatorial integration problem: without a standard, every AI app needs custom code for every tool and data source (M×N integrations). MCP defines an open client-server protocol so each tool exposes one MCP server and each app implements one MCP client, collapsing it to M+N. It decouples tool providers from models and applications — the "USB-C for AI" idea — enabling reuse and portability across the ecosystem.

Explain MCP's three primitives.

Tools are executable functions the model can invoke to take actions (with side effects) — model-controlled, like function calling. Resources are read-only data the host loads into context, such as files or records — application-controlled. Prompts are reusable, parameterized templates the server exposes for common workflows — typically user-invoked. The clean split is that tools do things while resources provide context.

How does MCP relate to function calling?

Function calling is a model capability — the model emits a structured request to invoke a described function. MCP is the standardized transport and discovery layer around that: it defines how a host discovers available tools from servers, negotiates capabilities, and routes calls and results over JSON-RPC. So the model still "function calls," but MCP standardizes where those tools come from and how they're connected, so integrations are reusable across hosts.

What are the main security risks with MCP?

An untrusted or compromised server can return malicious tool descriptions or data that steer the model (prompt injection), or abuse over-broad credentials. Mitigate by only connecting to trusted servers, scoping each server's permissions to least privilege (read-only where possible), authenticating remote servers, gating high-impact actions behind human approval, validating tool inputs/outputs, and auditing every invocation. Treat tool descriptions as untrusted input.

How would you use MCP on a data platform?

Expose governed platform capabilities as MCP servers — for example a read-only warehouse query tool over a semantic layer, a data-catalog lookup resource, or controlled pipeline operations — so any MCP-aware assistant interacts through a single audited, permissioned interface instead of bespoke integrations. This centralizes access control and logging, keeps credentials server-side, and lets you swap the assistant/model without rewriting the integration.
