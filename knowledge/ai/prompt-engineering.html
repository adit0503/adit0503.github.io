Prompt Engineering — Patterns & Structured Output

The reliable techniques — clear instructions, few-shot examples, chain-of-thought, decomposition, structured/JSON output, and prompt-injection defense — plus how to treat prompts as versioned, testable production artifacts rather than one-off strings.

Anatomy of a Good Prompt

A robust prompt is explicit about role, task, constraints, and output format. Vague prompts produce vague, inconsistent results. The components:

  • Role / system — who the model is and its overarching rules.
  • Task — the specific instruction, stated directly.
  • Context — the data to work from (retrieved chunks, documents), clearly delimited.
  • Constraints — length, tone, what to do when unsure, what not to do.
  • Format — the exact output shape, ideally with an example.
🔑 Positive instructions beat negative ones:

"Respond in 2–3 sentences of plain text" works better than "don't be verbose." Tell the model what to do, not just what to avoid — it steers toward the target instead of guessing the boundary.

Zero-, Few-Shot & CoT

  • Zero-shot — instruction only. Fine for simple, well-understood tasks.
  • Few-shot — include a handful of input→output examples. The single most reliable way to lock in format and edge-case handling. Make examples diverse and representative.
  • Chain-of-thought (CoT) — ask the model to reason step by step before answering. Improves multi-step math, logic, and analysis. Pair with a final, clearly delimited answer so you can parse it.
💡 Hide the reasoning, keep the answer:

For user-facing apps, let the model reason in a scratchpad section (or use extended thinking) but return only the final answer in a parseable block. You get CoT quality without dumping raw reasoning on the user.

Decomposition & Chaining

Complex tasks fail as one giant prompt. Break them into steps, each with a focused prompt, and pass outputs forward (prompt chaining). Example RAG-adjacent chain: extract entities → generate a search query → retrieve → summarize with citations. Smaller, single-purpose steps are more accurate, cheaper to debug, and let you use a cheap model for easy steps.

Structured Output

For anything programmatic you need machine-parseable output, not prose.

  • Specify the schema explicitly and give one example instance.
  • Tool/function calling — define the target structure as a tool input schema and let the model return validated arguments. The most robust approach.
  • Prefill — start the assistant turn with { to force JSON.
  • Validate + retry — parse against your schema; on failure, send the error back and ask for a fix.
Structured extraction prompt
System: You extract data. Return ONLY valid JSON matching:
{"vendor": string, "amount": number, "currency": string, "date": "YYYY-MM-DD"}
If a field is missing, use null. No prose, no markdown.

User: <invoice>{{raw_invoice_text}}</invoice>

# Then validate the parsed JSON against a schema and retry on failure.

Prompt Injection Defense

Prompt injection is the SQL injection of the LLM era: untrusted content (a retrieved document, a user message, a web page) contains instructions that hijack the model. In RAG and agent systems this is a real attack surface.

  • Separate data from instructions — wrap untrusted content in delimiters (XML tags) and tell the model the tagged content is data to analyze, never commands to follow.
  • Least privilege on tools — an injected instruction can only do damage if the agent has a dangerous tool. Read-only, allow-listed, validated tools limit blast radius.
  • Output filtering — scan responses for leaked system prompts, unexpected tool calls, or policy violations.
  • Don't trust retrieved text as authority — treat corpus content as potentially adversarial, especially if any of it is user-generated.
⚠️ There is no perfect fix:

Prompt injection can't be fully eliminated with prompting alone. Defense in depth — delimiting, least-privilege tools, human approval for high-impact actions, and output guardrails — is the realistic posture.

Prompts as Production Artifacts

  • Version control — store prompts in source control with review, not hardcoded strings scattered in code.
  • Template + variables — separate the stable template from injected variables; sanitize the variables.
  • Evaluate changes — run every prompt edit against a golden test set before shipping (see LLMOps).
  • Pin the model — a prompt tuned for one model version may regress on another.
  • Cache the stable prefix — put instructions/examples first so prompt caching applies.

Interview Questions

Few-shot vs zero-shot — when do you add examples?

Use zero-shot for simple, unambiguous tasks the model already handles well. Add few-shot examples when you need a specific output format, consistent edge-case handling, or the task is nuanced — examples anchor behavior far more reliably than verbose instructions. Keep examples diverse and representative of real inputs, and watch token cost since they're sent on every call (prompt caching helps).

How do you get reliable JSON out of an LLM?

Best: define the structure as a tool/function input schema and force that tool, so the model returns validated arguments. Otherwise specify the exact schema with one example, set temperature 0, and prefill the response with the opening brace. Always parse and validate against a schema in code and retry on failure by feeding the validation error back. Never assume the first output is well-formed.

What is prompt injection and how do you defend against it?

It's when untrusted content — a retrieved document, user input, or web page — smuggles instructions that override your intended behavior. Defense is layered: delimit untrusted content in tags and tell the model it's data not commands; give agents only least-privilege, validated, read-only tools so an injected command can't do harm; filter outputs for leaks and rogue tool calls; and require human approval for high-impact actions. It can't be fully eliminated by prompting alone, so defense in depth is the goal.

When would you decompose a task into multiple prompts instead of one?

When a single prompt has to do several distinct things and accuracy drops or debugging becomes impossible. Chaining focused single-purpose prompts (extract → query → retrieve → summarize) is more accurate, isolates failures to a specific step, and lets you route easy steps to a cheaper model. The trade-off is more calls and orchestration, so balance step count against latency and cost.

Why treat prompts like code?

Because they directly determine production behavior. Store them in version control with review, separate the stable template from sanitized variables, and run every change against a golden evaluation set before shipping so you catch regressions. Pin the model version since a prompt tuned for one model can degrade on another, and structure prompts so the stable prefix is cacheable. Untracked prompt edits are silent production changes.
