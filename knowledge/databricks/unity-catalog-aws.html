UC Architecture on AWS

  • Metastore: The top-level container in Unity Catalog. One metastore per region per Databricks account. Backed by Databricks-managed infrastructure (not in customer AWS account).
  • Workspace binding: Multiple workspaces in the same region attach to the same metastore. Data governed centrally, accessible from any bound workspace.
  • Account-level administration: UC is managed at the Databricks account level (not workspace level). Account admins create metastores, storage credentials, and external locations.
  • Single source of truth: UC replaces per-workspace Hive Metastore — all table metadata, permissions, and lineage are centralized.

IAM Integration

Storage Credentials — IAM Roles with Trust Policy

  • A storage credential is an IAM role in your AWS account that UC uses to access S3 data.
  • Trust policy: The role trusts Databricks' UC service principal (specific IAM role in Databricks' account) to assume it.
  • External ID: Prevents confused-deputy attacks — UC includes your Databricks account ID as external ID when assuming the role.
  • Self-assume pattern: The role also trusts itself, allowing UC to re-assume with a scoped-down session policy (restricting to specific S3 prefixes per query).
Storage Credential IAM Role (Terraform)
resource "aws_iam_role" "unity_catalog_storage" {
  name = "databricks-uc-storage-credential"
  
  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Effect = "Allow"
        Principal = {
          AWS = "arn:aws:iam::414351767826:role/unity-catalog-prod-UCMasterRole-${var.uc_role_id}"
        }
        Action = "sts:AssumeRole"
        Condition = {
          StringEquals = {
            "sts:ExternalId" = var.databricks_account_id
          }
        }
      },
      {
        # Self-assume for session policy scoping
        Effect = "Allow"
        Principal = {
          AWS = "arn:aws:iam::${data.aws_caller_identity.current.account_id}:role/databricks-uc-storage-credential"
        }
        Action = "sts:AssumeRole"
      }
    ]
  })
}

resource "aws_iam_role_policy" "uc_s3_access" {
  role = aws_iam_role.unity_catalog_storage.id
  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Effect = "Allow"
        Action = [
          "s3:GetObject",
          "s3:PutObject",
          "s3:DeleteObject",
          "s3:ListBucket",
          "s3:GetBucketLocation"
        ]
        Resource = [
          "arn:aws:s3:::${var.data_bucket}",
          "arn:aws:s3:::${var.data_bucket}/*"
        ]
      },
      {
        Effect = "Allow"
        Action = [
          "sts:AssumeRole"
        ]
        Resource = "arn:aws:iam::${data.aws_caller_identity.current.account_id}:role/databricks-uc-storage-credential"
      }
    ]
  })
}

# Register in Unity Catalog
resource "databricks_storage_credential" "main" {
  name = "production-s3-credential"
  aws_iam_role {
    role_arn = aws_iam_role.unity_catalog_storage.arn
  }

Three-Level Namespace

catalog.schema.table

  • Catalog: Top-level grouping. Patterns: per-environment (dev, staging, prod), per-domain (finance, marketing, platform), per-team.
  • Schema: Logical grouping within a catalog. Maps to a database concept. Contains tables, views, functions, volumes.
  • Table/View: Actual data objects with column-level metadata, statistics, and governance.

Managed vs External Locations

Managed Storage

  • Databricks controls the physical storage location (S3 bucket configured for the metastore).
  • When you CREATE TABLE without specifying LOCATION, data goes to managed storage.
  • Lifecycle tied to table: DROP TABLE deletes the underlying files.
  • Simplest option: No external location setup needed. Good for derived tables (silver/gold), temporary data, development.

External Locations

  • Customer's S3 bucket registered with Unity Catalog via a storage credential.
  • CREATE EXTERNAL TABLE ... LOCATION 's3://my-bucket/path/' — data lives in your bucket, governed by UC.
  • Lifecycle independent: DROP TABLE removes UC metadata but NOT the physical files.
  • Use cases: Data shared with non-Databricks tools, data produced by external systems, compliance requirements for data location control.
External Location Setup
-- Create external location (requires storage credential)
CREATE EXTERNAL LOCATION finance_data
URL 's3://company-data-lake/finance/'
WITH (STORAGE CREDENTIAL production_s3_cred)
COMMENT 'Finance team data lake partition';

-- Grant access to create tables at this location
GRANT CREATE EXTERNAL TABLE ON EXTERNAL LOCATION finance_data TO `finance-engineers`;
GRANT READ FILES ON EXTERNAL LOCATION finance_data TO `finance-analysts`;

-- Create external table at the location
CREATE EXTERNAL TABLE prod.finance.transactions (
  txn_id BIGINT,
  account_id BIGINT,
  amount DOUBLE,
  txn_type STRING,
  txn_ts TIMESTAMP
)
USING DELTA
LOCATION 's3://company-data-lake/finance/transactions/';

-- External volumes (for file-level access)
CREATE EXTERNAL VOLUME prod.finance.raw_files
LOCATION 's3://company-data-lake/finance/raw/';

-- List files in volume
LIST '/Volumes/prod/finance/raw_files/';

Credential Vending

UC doesn't give clusters permanent S3 access. Instead, it vends short-lived, scoped credentials per query:

Flow

  1. User runs SELECT * FROM prod.finance.transactions
  2. UC checks: Does this user have SELECT on this table? (Check ACLs, row filters, column masks.)
  3. UC identifies the physical S3 paths for this table's data files.
  4. UC assumes the storage credential's IAM role with a session policy scoped to ONLY those S3 paths.
  5. UC returns temporary STS credentials (AccessKeyId, SecretAccessKey, SessionToken) to the cluster.
  6. Cluster uses these temporary credentials to read from S3 — can ONLY access the authorized paths.
  7. Credentials expire after ~1 hour; UC refreshes automatically for long-running queries.
Security implication: Even if a user has arbitrary code execution on the cluster (Python notebook), they can only access S3 paths that UC has authorized for their query. The temporary credentials are scoped to specific S3 prefixes — attempting to access other paths returns AccessDenied. This is how UC enforces fine-grained access on shared clusters.

Data Access Control

UC Permission Model
-- GRANT/REVOKE SQL syntax
-- Hierarchy: Account → Metastore → Catalog → Schema → Table

-- Catalog-level
GRANT USE CATALOG ON CATALOG prod TO `data-engineers`;
GRANT CREATE SCHEMA ON CATALOG prod TO `data-engineers`;

-- Schema-level
GRANT USE SCHEMA ON SCHEMA prod.gold_finance TO `analysts`;
GRANT SELECT ON SCHEMA prod.gold_finance TO `analysts`;  -- all tables in schema

-- Table-level
GRANT SELECT ON TABLE prod.gold_finance.revenue TO `finance-team`;
GRANT MODIFY ON TABLE prod.silver_finance.transactions TO `etl-service-principal`;

-- USAGE is required at every level of the hierarchy
-- User needs: USE CATALOG on prod + USE SCHEMA on gold_finance + SELECT on revenue
-- Missing any level → AccessDenied

-- View permissions (good for controlled access)
CREATE VIEW prod.gold_finance.revenue_summary AS
SELECT region, SUM(amount) as total_revenue
FROM prod.gold_finance.revenue
GROUP BY region;

GRANT SELECT ON VIEW prod.gold_finance.revenue_summary TO `executives`;

-- Ownership model
ALTER TABLE prod.finance.transactions OWNER TO `finance-engineering-group`;
-- Owner has ALL PRIVILEGES on the object + can GRANT to others

-- Service principal for automated jobs
GRANT SELECT ON SCHEMA prod.bronze_finance TO `etl-pipeline-sp`;
GRANT MODIFY ON SCHEMA prod.silver_finance TO `etl-pipeline-sp`;

Row-Level & Column-Level Security

Row Filters & Column Masks
-- Row-level security: filter rows based on user identity
CREATE FUNCTION prod.finance.region_filter(region_col STRING)
RETURNS BOOLEAN
RETURN (
  is_account_group_member('global-finance')  -- global team sees all
  OR region_col = CASE
    WHEN is_account_group_member('finance-us') THEN 'US'
    WHEN is_account_group_member('finance-eu') THEN 'EU'
    WHEN is_account_group_member('finance-apac') THEN 'APAC'
    ELSE 'NONE'
  END
);

-- Apply row filter to table
ALTER TABLE prod.finance.transactions
SET ROW FILTER prod.finance.region_filter ON (region);

-- Column masking: mask sensitive values based on user identity
CREATE FUNCTION prod.finance.mask_account(account_id BIGINT)
RETURNS BIGINT
RETURN (
  CASE
    WHEN is_account_group_member('finance-engineering') THEN account_id  -- full access
    ELSE CAST(CONCAT('***', RIGHT(CAST(account_id AS STRING), 4)) AS BIGINT)  -- mask
  END
);

-- Apply column mask
ALTER TABLE prod.finance.transactions
ALTER COLUMN account_id SET MASK prod.finance.mask_account;

-- Now when an analyst queries:
-- SELECT * FROM prod.finance.transactions
-- They see:
-- 1. Only rows matching their region (row filter)
-- 2. account_id is masked (column mask)
-- Completely transparent — no query changes needed!
Performance consideration: Row filters are applied at read time (pushdown to scan). For complex filter functions, this adds overhead to every query. Keep filter functions simple (group membership checks) and ensure the filtered column is part of the table's partition or clustering key for efficient pruning.

Delta Sharing on AWS

  • What it is: Open protocol for secure cross-organization data sharing. Recipients don't need Databricks — any client supporting the Delta Sharing protocol can read shared data.
  • How it works on AWS: Data stays in the provider's S3 bucket. UC generates pre-signed S3 URLs with limited TTL for recipients. No data copying, no duplication.
  • Open recipients: Share with any organization — they download a credential file and use the open-source Delta Sharing client (Python, Spark, pandas, Power BI).
  • Databricks-to-Databricks: Recipients with their own Databricks workspace can access shared data directly as external catalogs.
Delta Sharing Configuration
-- Create a share
CREATE SHARE customer_analytics_share
COMMENT 'Customer analytics data shared with partner org';

-- Add tables/views to the share
ALTER SHARE customer_analytics_share
ADD TABLE prod.gold_analytics.customer_segments;

ALTER SHARE customer_analytics_share
ADD TABLE prod.gold_analytics.monthly_metrics
PARTITION (region = 'US');  -- Share only US partition

-- Create a recipient
CREATE RECIPIENT partner_org
COMMENT 'External analytics partner'
USING ID 'partner-databricks-account-id';  -- Databricks-to-Databricks

-- Or open sharing (non-Databricks recipient)
CREATE RECIPIENT partner_org_open;
-- Download activation link for the recipient

-- Grant share to recipient
GRANT SELECT ON SHARE customer_analytics_share TO RECIPIENT partner_org;

-- Recipient's perspective (in their workspace):
-- CREATE CATALOG partner_data USING SHARE provider_org.customer_analytics_share;
-- SELECT * FROM partner_data.default.customer_segments;

Lineage

  • Automatic: UC captures column-level lineage from all Spark SQL/DataFrame operations without any manual instrumentation.
  • Scope: Tracks lineage for: reads, writes, CREATE TABLE AS, INSERT INTO, MERGE, notebooks, jobs, DLT pipelines.
  • Column-level: Not just "table A → table B" but "table_A.column_x → table_B.column_y" (which source columns feed which target columns).
  • System tables: Query system.access.table_lineage and system.access.column_lineage for programmatic access.
Querying Lineage
-- Upstream dependencies (what feeds into this table)
SELECT
  source_table_full_name,
  source_column_name,
  target_column_name,
  event_time
FROM system.access.column_lineage
WHERE target_table_full_name = 'prod.gold_finance.daily_revenue'
ORDER BY event_time DESC;

-- Downstream dependencies (what reads from this table)
SELECT
  target_table_full_name,
  target_column_name,
  event_time
FROM system.access.column_lineage
WHERE source_table_full_name = 'prod.silver_finance.transactions'
ORDER BY event_time DESC;

-- Impact analysis: if I change this column, what's affected?
SELECT DISTINCT target_table_full_name, target_column_name
FROM system.access.column_lineage
WHERE source_table_full_name = 'prod.bronze_finance.raw_transactions'
  AND source_column_name = 'amount';

Audit Logging

  • system.access.audit: Contains all access events — who accessed what data, when, from which workspace/cluster.
  • Events captured: table reads, writes, permission changes, credential usage, workspace logins, cluster operations.
  • Retention: 365 days by default.
  • Integration with CloudTrail: Databricks also sends audit events to AWS CloudTrail for unified security monitoring.
Audit Log Queries
-- Who accessed sensitive table in last 24 hours?
SELECT
  event_time,
  user_identity.email AS user_email,
  action_name,
  request_params.full_name_arg AS table_name,
  source_ip_address,
  workspace_id
FROM system.access.audit
WHERE action_name IN ('getTable', 'commandSubmit')
  AND request_params.full_name_arg LIKE '%finance%'
  AND event_time >= current_timestamp() - INTERVAL 24 HOURS
ORDER BY event_time DESC;

-- Permission changes audit trail
SELECT
  event_time,
  user_identity.email AS changed_by,
  action_name,
  request_params
FROM system.access.audit
WHERE action_name IN ('updatePermissions', 'grantPermission', 'revokePermission')
  AND event_time >= current_timestamp() - INTERVAL 7 DAYS
ORDER BY event_time DESC;

-- Failed access attempts (security monitoring)
SELECT
  event_time,
  user_identity.email,
  action_name,
  response.status_code,
  response.error_message
FROM system.access.audit
WHERE response.status_code >= 400
  AND event_time >= current_timestamp() - INTERVAL 24 HOURS
ORDER BY event_time DESC;

Migration from HMS to UC

Migration Strategies

  • SYNC command: Copies metadata from HMS to UC without moving data. Table continues to work in both systems during migration window.
  • Table upgrade: ALTER TABLE hive_metastore.schema.table SET OWNER TO ... then register in UC.
  • Handling mounts → external locations: Map each DBFS mount to an equivalent external location with proper credentials and permissions.
HMS to UC Migration
-- Step 1: Create UC equivalent structure
CREATE CATALOG prod;
CREATE SCHEMA prod.finance;

-- Step 2: Upgrade tables (metadata only — no data movement)
-- For managed HMS tables:
CREATE TABLE prod.finance.transactions
AS SELECT * FROM hive_metastore.finance.transactions;
-- Note: This copies data to UC managed storage

-- For external HMS tables (data stays in place):
CREATE EXTERNAL TABLE prod.finance.transactions
LOCATION 's3://existing-bucket/finance/transactions/'
AS SELECT * FROM hive_metastore.finance.transactions WHERE 1=0;
-- Then: SYNC (or use upgrade wizard in UI)

-- Step 3: Bulk upgrade using UC upgrade wizard (UI-based)
-- Or programmatic:
SYNC TABLE prod.finance.transactions 
FROM hive_metastore.finance.transactions;

-- Step 4: Replace mount-based access
-- OLD: spark.read.parquet("/mnt/finance/transactions")
-- NEW: spark.table("prod.finance.transactions")

-- Step 5: Migrate permissions
GRANT SELECT ON TABLE prod.finance.transactions TO `finance-analysts`;

-- Step 6: Validate and switch references
-- Run parallel queries against both to verify data consistency
-- Update notebooks/jobs to reference UC paths
-- Deprecate HMS tables after validation period
Migration order: (1) Start with Gold tables (most visibility, cleanest data, most consumers to migrate). (2) Then Silver (transformation layer). (3) Finally Bronze (ingestion — may require pipeline changes). Migrate consumers before producers — once a Gold table is in UC, analytics users get immediate governance benefits regardless of how Bronze/Silver are still running.

Interview Questions

How does Unity Catalog's credential vending differ from instance profiles for S3 access? What security advantages does it provide?

Instance profiles (legacy): An IAM role attached to the EC2 instance. ALL code running on that cluster — regardless of which user submitted it — gets the same S3 permissions. If the role allows s3:* on the data lake bucket, every user on that cluster can read/write everything. No per-user differentiation, no audit trail per identity.

UC credential vending: UC checks permissions per user, per table, then generates STS temporary credentials scoped to ONLY the specific S3 prefixes that user is authorized to access. Different users on the SAME cluster get different credentials with different S3 access scopes.

Security advantages:

(1) Least privilege: Credentials only allow access to the exact files needed for the authorized query — not the entire bucket.

(2) Per-user audit: Every data access is tied to a user identity in the audit log — not just "someone on cluster X."

(3) Short-lived: Credentials expire in ~1 hour. Leaked credentials have limited blast radius (time-bound + path-scoped).

(4) Row/column security: UC can enforce row filters and column masks BEFORE vending credentials — impossible with instance profiles.

(5) Shared clusters: Multiple users with different access levels can share one cluster safely. With instance profiles, shared clusters mean everyone gets the union of all permissions.

Design a Unity Catalog namespace structure for a company with 5 business domains, 3 environments, and a data mesh approach.

Recommended structure: catalog per domain per environment.

prod_finance.bronze.raw_transactions

prod_finance.silver.transactions

prod_finance.gold.daily_revenue

dev_finance.bronze.raw_transactions (dev mirror)

Catalogs: prod_finance, staging_finance, dev_finance, prod_marketing, staging_marketing, dev_marketing, ..., prod_platform (shared/cross-domain data products).

Why this structure:

(1) Isolation: Each domain team owns their catalogs end-to-end. Can manage schemas, tables, permissions within their domain.

(2) Environment separation: Dev catalog can be granted widely (all engineers). Prod catalog restricted to service principals + read-only for analysts.

(3) Data mesh alignment: Each domain is a "data product" team. They publish tables in their gold schema as data products. Cross-domain access via GRANT or Delta Sharing.

(4) Cross-domain shared data: prod_platform.shared.customer_master — owned by platform team, granted to all domain teams for joins.

Permission model:

- Domain engineers: full access to their domain's dev + staging catalogs, MODIFY on prod bronze/silver, read-only on prod gold.

- Analysts: USE CATALOG + SELECT on prod gold schemas only.

- ETL service principals: MODIFY on prod bronze/silver/gold (for automated pipelines).

You need to migrate 500 tables from Hive Metastore to Unity Catalog with zero downtime. What's your migration strategy?

Phase 1 — Preparation (2 weeks):

(1) Inventory all HMS tables: classify by type (managed vs external), access patterns (who reads/writes), dependencies (downstream jobs). (2) Create UC namespace structure (catalogs, schemas). (3) Set up storage credentials and external locations for all S3 paths. (4) Map HMS permissions → UC permissions (document which groups need access to which tables).

Phase 2 — Shadow migration (2 weeks):

(1) Register external tables in UC pointing to same S3 locations (zero-copy — no data movement). (2) For managed tables: use DEEP CLONE to UC managed storage. (3) Set up dual-write: modify ETL pipelines to write to BOTH HMS and UC tables during transition. (4) Validate: run queries against both, compare results.

Phase 3 — Consumer migration (4 weeks, rolling):

(1) Update notebooks/jobs to read from UC paths instead of HMS paths. (2) Migrate team by team: analytics team first (Gold readers), then engineering (Silver/Bronze). (3) Each team validates, confirms parity, signs off.

Phase 4 — Cutover (1 day):

(1) Stop dual-writes — ETL only writes to UC tables. (2) Remove HMS table references. (3) Disable access to legacy HMS (make read-only as safety net). (4) Monitor for 48 hours.

Zero downtime achieved by: Dual-write period ensures both systems have identical data. Consumer migration is gradual (no big-bang switchover). Rollback plan: revert to HMS paths if issues found.

How do you implement row-level security in Unity Catalog for a multi-tenant SaaS application where each customer should only see their own data?

Implementation:

CREATE FUNCTION tenant_filter(tenant_id_col STRING) RETURNS BOOLEAN RETURN (tenant_id_col = current_user_attribute('tenant_id') OR is_account_group_member('platform-admins'));

ALTER TABLE prod.app.user_activity SET ROW FILTER tenant_filter ON (tenant_id);

How it works: (1) Each user's identity in Databricks is mapped to a tenant_id (via SCIM sync from identity provider, or user attributes). (2) The row filter function evaluates for every row at read time — only rows matching the user's tenant_id are returned. (3) Platform admins (via group membership check) see all rows.

Performance considerations:

(1) Partition on tenant_id: This allows the row filter to be pushed down as partition pruning — UC reads only the relevant partition, not the entire table. Without partitioning, every query scans all tenants' data and filters client-side.

(2) Liquid Clustering on tenant_id: Alternative to partitioning if cardinality is high (1000+ tenants). Co-locates tenant data in few files for efficient filtering.

(3) Caching: Since each user sees different rows, Delta cache effectiveness is reduced. Consider separate tables for very large tenants if performance is critical.

Audit: All access is logged with user identity — full compliance trail of who accessed which tenant's data.

Explain the self-assume IAM role pattern used by Unity Catalog. Why is it necessary?

The pattern: The storage credential IAM role trusts TWO principals: (1) Databricks UC service role (for initial assumption). (2) Itself (for re-assumption with scoped session policy).

Why it's necessary:

Without self-assume: UC assumes the role → gets full permissions of that role (e.g., s3:* on the entire bucket). These credentials are passed to the cluster. A malicious user could use the credentials to access any path within the bucket — even tables they're not authorized to read in UC.

With self-assume: UC assumes the role → then immediately re-assumes the SAME role with an inline session policy that restricts S3 access to ONLY the specific prefixes needed for the current query. The resulting temporary credentials are limited-scope — even if leaked, they can only access the authorized paths.

Example: User queries prod.finance.revenue (stored at s3://lake/finance/revenue/). UC assumes the role → re-assumes with session policy: {"Effect":"Allow","Action":"s3:GetObject","Resource":"arn:aws:s3:::lake/finance/revenue/*"}. The vended credentials CANNOT access s3://lake/finance/payroll/ even though the base role has broad bucket access.

Security benefit: You don't need to create one IAM role per table (unmanageable at scale). One broad role + session policy scoping = fine-grained access without IAM proliferation.
