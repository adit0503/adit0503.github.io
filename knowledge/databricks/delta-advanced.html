Transaction Log Internals

The Delta transaction log (_delta_log/) is the source of truth for table state. Every operation on a Delta table produces a new JSON commit file:

Commit Protocol

  • Commit files: _delta_log/00000000000000000001.json, ...0002.json, etc. Sequential, monotonically increasing.
  • Atomicity: Each commit file is written atomically to S3 using PUT-if-absent semantics (S3's strong consistency guarantees since Dec 2020). On HDFS/ADLS, uses rename-based atomic commit.
  • Content: Each JSON file contains actions — add (new files), remove (deleted files), metaData (schema/config changes), txn (app transaction IDs for idempotency), protocol (reader/writer version requirements).

Conflict Resolution

  • Optimistic concurrency: multiple writers compute their changes independently, then attempt to commit.
  • If two writers target the same commit version, one wins (first to write the file) and the other gets a conflict.
  • Retry semantics: The losing writer checks if the winning commit conflicts logically (overlapping file sets). If not (disjoint partitions), it automatically retries with the next version number. If yes (same files touched), it fails with ConcurrentModificationException.
  • Conflict detection: Based on file-level analysis — if writer A's read set overlaps with writer B's write set, it's a conflict. If they touch different partitions/files, both succeed.

Log Compaction (Checkpoints)

  • Every 10 commits (default), a checkpoint file is written: _delta_log/00000000000000000010.checkpoint.parquet
  • Checkpoint = Parquet file containing the complete table state (all active add actions) at that version — no need to replay previous JSON commits.
  • _last_checkpoint file points to the latest checkpoint version — readers start here instead of scanning all JSON files.
  • Multi-part checkpoints: for large tables (millions of files), checkpoint is split into parts: 00000010.checkpoint.0000000001.0000000005.parquet (part 1 of 5).

Log Retention

  • delta.logRetentionDuration (default: 30 days) — how long commit JSON files are kept. Needed for time travel.
  • delta.checkpointRetentionDuration — how long checkpoints are retained.
  • Setting logRetentionDuration shorter than 7 days can break streaming readers that checkpoint at daily intervals.

MERGE INTO Internals

MERGE is the most complex and performance-critical Delta operation. Understanding its internal mechanics is essential for optimization:

Execution Steps

  1. Target file identification: Delta uses file-level statistics (min/max per column stored in the transaction log) to identify which target files MIGHT contain matching rows. This is "file pruning" — eliminates files where min/max stats prove no match exists.
  2. Partition pruning: If the merge condition includes the partition column (e.g., ON target.date = source.date AND target.id = source.id), entire partitions are skipped without reading files.
  3. Join execution: The pruned target files are read and joined with the source DataFrame. This is typically a sort-merge join or broadcast join depending on source size.
  4. Action resolution: For each matched/unmatched row, the WHEN MATCHED/WHEN NOT MATCHED clauses determine the action (UPDATE, DELETE, INSERT).
  5. File rewrite: Target files containing any touched rows are COMPLETELY REWRITTEN — even if only 1 row in a 1GB file changed, the entire file is rewritten. Untouched files remain as-is.
  6. Commit: Transaction log records remove for old files + add for new files atomically.

Performance Tuning

Optimized MERGE Pattern
-- BAD: No partition pruning — scans ALL target files
MERGE INTO target t
USING source s
ON t.id = s.id
WHEN MATCHED THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *;

-- GOOD: Partition pruning narrows target scan
MERGE INTO target t
USING source s
ON t.date = s.date AND t.id = s.id  -- date is partition column
WHEN MATCHED THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *;

-- EVEN BETTER: Pre-filter source to minimize join size
MERGE INTO target t
USING (
  SELECT * FROM source 
  WHERE date >= current_date() - INTERVAL 3 DAYS  -- limit source window
) s
ON t.date = s.date AND t.id = s.id
WHEN MATCHED AND s.updated_at > t.updated_at THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *;

Key Optimizations

  • spark.databricks.delta.merge.optimizeWrite.enabled = true: Coalesces output files to target size (reduces small file proliferation from MERGE).
  • spark.databricks.delta.merge.repartitionBeforeWrite.enabled = true: Repartitions output by partition columns for optimal file layout.
  • File sizing: Target tables with 1GB files + MERGE touching 1% of rows = 99% file rewrite waste. Use smaller files (128MB) for MERGE-heavy tables to reduce amplification.
  • Z-ORDER on merge key: Co-locates rows with the same merge key in fewer files → fewer files to rewrite per MERGE operation.
Write amplification: MERGE rewrites entire files, not individual rows. If your MERGE updates 100 rows scattered across 100 files (each 1GB), you rewrite 100GB of data to modify 100 rows. Mitigation: (1) Use Liquid Clustering or Z-ORDER on merge keys to co-locate target rows. (2) Use smaller target files for MERGE-heavy tables. (3) Use Deletion Vectors (see below) to avoid full file rewrites.

Deletion Vectors

Deletion Vectors (DVs) are a Databricks innovation that eliminates the need to rewrite entire files for row-level deletions/updates:

How They Work

  • Instead of rewriting a 1GB Parquet file to remove 10 rows, a small DV file is created that marks those 10 rows as "deleted."
  • Format: RoaringBitmap — a compressed bitmap where each set bit represents a deleted row position within the file.
  • Storage: .dv files stored alongside data files. Each DV file corresponds to exactly one data file.
  • Read path: When reading a file with an associated DV, the reader loads the bitmap and skips rows at marked positions. This is applied during Parquet column scan — minimal overhead.

DV Lifecycle

  • Accumulation: Each DELETE/UPDATE/MERGE that touches a file adds entries to its DV (or creates a new DV if none exists).
  • Read amplification: Over time, files with many deleted rows still store the full data — readers scan it all, then filter. A file with 50% deletions reads 2x the necessary data.
  • Compaction resolves DVs: OPTIMIZE rewrites files, physically removing the DV-marked rows. Post-compaction, DV files are cleaned up.
  • Threshold: Databricks recommends compaction when DV density exceeds 10-25% of a file's rows.

DV vs Copy-on-Write (COW) Tradeoff

AspectDeletion Vectors (MOR)Copy-on-Write (COW)
Write speedFast (write small bitmap only)Slow (rewrite entire file)
Read speedSlightly slower (apply bitmap filter)Fastest (no extra filter)

Liquid Clustering

Liquid Clustering replaces partitioning + Z-ORDER with a single, flexible mechanism that adapts over time:

How It Works

  • Uses Hilbert space-filling curves (superior to Z-curves for high-dimensional data) to map multi-dimensional clustering keys into a linear order.
  • Data is physically organized on disk so rows with similar clustering key values are stored in the same files.
  • Incremental: Unlike Z-ORDER which reprocesses ALL data, Liquid Clustering only reorganizes newly added files during OPTIMIZE. Already-clustered files are left alone.
  • No fixed partition boundaries — avoids the small-file problem of over-partitioned tables and the large-file problem of under-partitioned tables.

Hilbert vs Z-Curves

  • Z-curve: Interleaves bits of multiple dimensions. Good for 2-3 columns. Data skipping effectiveness degrades with more columns.
  • Hilbert curve: Better locality preservation — points close in multi-dimensional space remain close on the curve. More effective data skipping for 3+ clustering columns.

When to Use vs Not Use

  • Use: Tables with multiple filter columns in queries, tables with frequent MERGE/UPDATE, tables where partition key cardinality is too high or too low, tables with evolving query patterns.
  • Don't use: Tables with a single dominant filter column AND very clear partition boundaries (e.g., date-partitioned logs where all queries filter by date). Classic partitioning is simpler and equally effective here.
Liquid Clustering Configuration
-- Create table with Liquid Clustering
CREATE TABLE my_catalog.my_schema.events (
  event_id BIGINT,
  user_id BIGINT,
  event_type STRING,
  region STRING,
  event_ts TIMESTAMP,
  payload STRING
) CLUSTER BY (user_id, event_type, region);

-- Change clustering keys without rewriting data
ALTER TABLE my_catalog.my_schema.events
CLUSTER BY (user_id, region);  -- drop event_type, queries evolved

-- Trigger incremental clustering (only new/unclustered files)
OPTIMIZE my_catalog.my_schema.events;

-- Liquid Clustering replaces all of these legacy approaches:
-- ❌ PARTITIONED BY (region)          -- fixed boundaries, skew issues
-- ❌ OPTIMIZE ... ZORDER BY (user_id) -- full rewrite every run
-- ✅ CLUSTER BY (user_id, region)     -- incremental, adaptive
Key advantage: You can change clustering keys with ALTER TABLE without rewriting any existing data. The new keys apply to future OPTIMIZE runs incrementally. This is impossible with partitioning (requires full table rewrite to repartition).

Change Data Feed (CDF)

CDF captures row-level changes (inserts, updates, deletes) and makes them available for downstream consumption:

Internals

  • When enabled, Delta writes additional Parquet files in a _change_data/ directory for operations that modify existing rows (UPDATE, DELETE, MERGE).
  • Pure appends (INSERT) don't create change data files — the commit log's dataChange=true flag + add actions are sufficient.
  • Change types: insert, update_preimage (before value), update_postimage (after value), delete.
  • Each change row includes: _change_type, _commit_version, _commit_timestamp metadata columns.

Reading CDF

CDF Read Patterns
# Enable CDF on a table
spark.sql("""
  ALTER TABLE my_catalog.schema.customers
  SET TBLPROPERTIES ('delta.enableChangeDataFeed' = true)
""")

# Batch read: all changes between versions
changes_df = (spark.read
  .format("delta")
  .option("readChangeFeed", "true")
  .option("startingVersion", 5)
  .option("endingVersion", 10)
  .table("my_catalog.schema.customers")
)

# Batch read: changes since a timestamp
changes_df = (spark.read
  .format("delta")
  .option("readChangeFeed", "true")
  .option("startingTimestamp", "2024-01-15T00:00:00")
  .table("my_catalog.schema.customers")
)

# Streaming read: continuous CDC propagation
cdf_stream = (spark.readStream
  .format("delta")
  .option("readChangeFeed", "true")
  .option("startingVersion", 0)
  .table("my_catalog.schema.customers")
)

# Process changes — propagate to downstream silver table
def process_changes(batch_df, batch_id):
    updates = batch_df.filter("_change_type IN ('update_postimage', 'insert')")
    deletes = batch_df.filter("_change_type = 'delete'")
    
    # MERGE into downstream
    target = DeltaTable.forName(spark, "my_catalog.schema.customers_silver")
    target.alias("t").merge(
        updates.alias("s"), "t.customer_id = s.customer_id"
    ).whenMatchedUpdateAll().whenNotMatchedInsertAll().execute()
    
    # Handle deletes
    if deletes.count() > 0:
        delete_ids = [r.customer_id for r in deletes.select("customer_id").collect()]
        target.delete(col("customer_id").isin(delete_ids))

cdf_stream.writeStream.foreachBatch(process_changes).start()
Production CDC pattern: Enable CDF on all Silver-layer tables. Use streaming CDF reads to propagate changes downstream (Silver → Gold aggregations). This eliminates the need to recompute entire Gold tables — only the changed rows are processed. For a 10TB Silver table with 1% daily change rate, this reduces Gold refresh compute by 99%.

OPTIMIZE Internals

Bin-Packing

  • OPTIMIZE reads small files (below target size) and rewrites them into larger, optimally-sized files.
  • Target file size: Default 1GB for managed tables (configurable via delta.targetFileSize). For Z-ORDERed or Liquid Clustered tables, target is typically 256MB–512MB (smaller files = better data skipping granularity).
  • Algorithm: Groups small files by partition, creates bins that approach target size, writes new consolidated files.
  • Idempotent: running OPTIMIZE on an already-optimized table is a no-op (no files below threshold to compact).

Z-ORDER Internals

  • Morton code: Z-ORDER interleaves the bits of specified column values to create a multi-dimensional sort key. Rows that are close in multiple dimensions end up in the same file.
  • Data skipping: After Z-ORDERing, each file's min/max stats cover a tight range of the Z-ORDER columns. Queries filtering on these columns skip most files.
  • Full rewrite: Z-ORDER OPTIMIZE reads ALL data in the table (or partition) and rewrites it — it cannot be incremental.
  • Diminishing returns: Effective for 2-4 columns. Beyond that, the space-filling curve becomes too dispersed and data skipping degrades.
OPTIMIZE Patterns
-- Basic compaction (bin-packing only)
OPTIMIZE my_catalog.schema.events;

-- Z-ORDER on query filter columns
OPTIMIZE my_catalog.schema.events
ZORDER BY (user_id, event_type);

-- Targeted compaction (only specific partition)
OPTIMIZE my_catalog.schema.events
WHERE date >= '2024-01-01' AND date < '2024-02-01';

-- Check optimization potential
DESCRIBE DETAIL my_catalog.schema.events;
-- numFiles: 50000 (too many?)
-- sizeInBytes / numFiles = avg file size (target: ~1GB)

-- Check file size distribution
SELECT
  count(*) as num_files,
  avg(size) / (1024*1024) as avg_size_mb,
  min(size) / (1024*1024) as min_size_mb,
  percentile(size, 0.5) / (1024*1024) as median_size_mb,
  max(size) / (1024*1024) as max_size_mb
FROM (DESCRIBE DETAIL my_catalog.schema.events).files;

VACUUM

What VACUUM Deletes

  • Files no longer referenced by any version of the table within the retention period.
  • When a MERGE/UPDATE/DELETE rewrites files, the old files are marked as remove in the log but physically remain on S3 for time travel.
  • VACUUM physically deletes these unreferenced files after the retention period expires.

Retention Mechanics

  • Default retention: 7 days (delta.deletedFileRetentionDuration = interval 7 days).
  • VACUUM will not delete any file newer than the retention period — protects concurrent readers.
  • Setting spark.databricks.delta.retentionDurationCheck.enabled = false allows VACUUM with 0-hour retention — extremely dangerous.
Danger: Running VACUUM table RETAIN 0 HOURS with the safety check disabled will delete files that concurrent readers or streaming queries are actively using. This causes FileNotFoundException errors. Never set retention below 7 days unless you're 100% certain no concurrent operations exist (maintenance windows only).
VACUUM Operations
-- Preview what will be deleted (safe — no actual deletion)
VACUUM my_catalog.schema.events DRY RUN;
-- Output: "Found 1,234 files (456.7 GB) eligible for deletion"

-- Execute VACUUM with default 7-day retention
VACUUM my_catalog.schema.events;

-- Custom retention (14 days for tables with long-running queries)
VACUUM my_catalog.schema.events RETAIN 336 HOURS;  -- 14 days

-- Check table history to understand file lifecycle
DESCRIBE HISTORY my_catalog.schema.events LIMIT 20;

Interaction with Time Travel

  • Time travel requires the physical data files to exist. After VACUUM, you cannot time-travel to versions that reference deleted files.
  • delta.logRetentionDuration controls how long the LOG entries are kept (30 days default). Even with log entries, time travel fails if VACUUM removed the data files.
  • Effective time travel window = min(logRetentionDuration, deletedFileRetentionDuration). Usually VACUUM is the limiting factor.

Predictive Optimization

  • What it is: Databricks automatically schedules OPTIMIZE and VACUUM operations based on table usage patterns.
  • How it decides: Monitors table statistics — file count, file sizes, DV density, update frequency, query patterns. Triggers OPTIMIZE when small files accumulate or DV density exceeds threshold.
  • Scheduling: Runs during low-activity periods. Non-blocking — doesn't interfere with production reads/writes.
  • Enabled per table/schema/catalog: ALTER TABLE ... SET TBLPROPERTIES ('delta.enablePredictiveOptimization' = 'true')
  • Cost: Uses serverless compute for maintenance — billed at serverless DBU rates. But eliminates the need for custom maintenance jobs.

Delta UniForm

  • What it does: Generates Iceberg-compatible metadata alongside Delta metadata, allowing the same table to be read by Iceberg-compatible engines (Snowflake, Trino, Dremio, BigQuery) without copying data.
  • How it works: On each Delta commit, UniForm also writes Iceberg manifest files and metadata. The underlying Parquet files are shared — no data duplication.
  • Limitations: Iceberg readers see the table as read-only. Write operations must go through Delta/Databricks. Slight commit overhead (~100ms extra per commit for Iceberg metadata generation).
  • Use case: Multi-engine analytics — data engineering in Databricks, BI queries in Snowflake/Trino, all reading the same physical data.
UniForm Configuration
-- Enable UniForm (Iceberg compatibility)
CREATE TABLE my_catalog.schema.events (
  event_id BIGINT,
  user_id BIGINT,
  event_ts TIMESTAMP,
  payload STRING
) TBLPROPERTIES (
  'delta.universalFormat.enabledFormats' = 'iceberg',
  'delta.enableDeletionVectors' = true
);

-- Enable on existing table
ALTER TABLE my_catalog.schema.events
SET TBLPROPERTIES ('delta.universalFormat.enabledFormats' = 'iceberg');

-- The table is now readable via Iceberg metadata:
-- Iceberg catalog location: s3://bucket/table/metadata/

Low Shuffle MERGE

  • Problem: Standard MERGE rewrites entire files even if only a few rows changed — massive write amplification.
  • Solution: Low Shuffle MERGE (Databricks optimization) uses Deletion Vectors for the unchanged rows and only writes new/modified rows to new files.
  • How: Instead of rewriting the whole file, marks deleted/updated rows via DV, writes only the new/changed rows to small new files.
  • Result: MERGE that previously rewrote 100GB now writes only the delta (e.g., 500MB of actual changes).
  • Requirement: Deletion Vectors must be enabled on the table.
  • Tradeoff: Faster writes but accumulates DVs and small files faster — needs more frequent OPTIMIZE.
Low Shuffle MERGE (Automatic with DVs)
-- Enable prerequisites
ALTER TABLE my_catalog.schema.customers
SET TBLPROPERTIES (
  'delta.enableDeletionVectors' = true
);

-- Low Shuffle MERGE is automatically used when DVs are enabled
-- No additional configuration needed — Databricks optimizer selects it

-- MERGE now:
-- 1. Identifies matching rows in target files
-- 2. Marks old rows as deleted via DV (no file rewrite!)
-- 3. Writes only new/updated rows to new small files
-- 4. Commits: add(new files) + update DV references

-- Monitor: check DV accumulation after frequent MERGEs
SELECT * FROM (DESCRIBE DETAIL my_catalog.schema.customers)
-- numDeletionVectors, numDeletionVectorRows → if high, run OPTIMIZE

Clone Operations

SHALLOW CLONE

  • Creates a new table that references the same data files as the source — no data copied.
  • Metadata only: Only the transaction log is duplicated. Reads still go to the original files.
  • Use cases: Testing (clone prod → run experiments without affecting prod), zero-copy dev environments, point-in-time snapshots for auditing.
  • Limitation: If source is VACUUM'd, shallow clone loses access to deleted files. Clone becomes "broken" for those versions.

DEEP CLONE

  • Physically copies all data files and transaction log — creates an independent table.
  • Use cases: Migration to new storage location, creating independent backups, cross-region replication, archival.
  • Incremental: if run again, only copies files added since last clone (delta sync).
Clone Operations
-- Shallow clone (instant, zero-copy)
CREATE TABLE my_catalog.dev.customers_test
SHALLOW CLONE my_catalog.prod.customers;

-- Shallow clone at specific version (time travel backup)
CREATE TABLE my_catalog.audit.customers_20240115
SHALLOW CLONE my_catalog.prod.customers VERSION AS OF 42;

-- Deep clone (full data copy — may take time for large tables)
CREATE TABLE my_catalog.backup.customers_backup
DEEP CLONE my_catalog.prod.customers;

-- Incremental deep clone (only sync new data)
CREATE OR REPLACE TABLE my_catalog.backup.customers_backup
DEEP CLONE my_catalog.prod.customers;

Interview Questions

Your daily MERGE job on a 5TB Delta table takes 4 hours. The source batch is only 50MB (10K rows). Diagnose and fix this.

Root cause: Write amplification. The 10K source rows are scattered across hundreds of target files (no clustering on merge key). MERGE rewrites every touched file entirely — even though only a few rows per file are modified. 10K rows across 500 files × 1GB average = 500GB rewritten for 50MB of changes.

Fixes (in order of impact):

(1) Enable Deletion Vectors + Low Shuffle MERGE: DV-aware MERGE marks old rows as deleted (bitmap write) and writes only new rows to small files. Eliminates file rewriting entirely. MERGE drops from 4 hours to minutes.

(2) Add Liquid Clustering on merge key: ALTER TABLE ... CLUSTER BY (merge_key_column). After OPTIMIZE, rows with the same merge key are co-located in fewer files. Next MERGE touches fewer files → less rewriting.

(3) Partition pruning in merge condition: If the table is partitioned by date, include date in the ON clause so only today's partition is scanned (not all 5TB).

(4) Reduce target file size: Set delta.targetFileSize = 128mb for MERGE-heavy tables. Smaller files = less waste per file rewrite.

(5) Pre-filter source: Ensure the source DataFrame only contains actually-changed rows (compare hash/timestamp before MERGE to eliminate no-op updates).

Explain how Delta's transaction log provides ACID guarantees without a lock server.

Mechanism: Optimistic concurrency with atomic file writes.

Atomicity: Each operation creates a single commit file (e.g., 000042.json). The commit either fully succeeds (file written) or fully fails (no file). No partial state.

Consistency: Readers always reconstruct table state from the log. They read _last_checkpoint → load checkpoint Parquet → replay subsequent JSON commits → build consistent snapshot.

Isolation (Serializable): Writers attempt to write to the next version number. If another writer wins that version, the conflict detection mechanism checks for logical conflicts (overlapping reads/writes). Non-conflicting operations are auto-retried at the next version. Conflicting operations fail with an exception.

Durability: Once the commit JSON file is successfully written to S3 (which guarantees durability via 11 9's), the transaction is permanent.

Why no lock server: S3's strong read-after-write consistency (since Dec 2020) ensures that once a PUT succeeds, all subsequent reads see the new file. The version numbering scheme provides total ordering. Two writers trying to write version N — S3 will only persist one (first PUT wins under concurrent writes to the same key). The other writer detects the collision on read-back and retries.

When should you use Liquid Clustering vs traditional partitioning + Z-ORDER?

Use Liquid Clustering when:

(1) Your table has multiple filter columns with varying query patterns (users filter by user_id sometimes, region other times). (2) Partition key cardinality is problematic — too high (user_id → millions of tiny partitions) or too low (region → 5 giant partitions). (3) You need to change clustering keys over time as query patterns evolve. (4) Table is MERGE/UPDATE heavy — smaller file targets improve write performance. (5) You want incremental maintenance (OPTIMIZE only touches new files, not entire table).

Stick with partitioning + Z-ORDER when:

(1) You have one dominant filter column with perfect cardinality for partitioning (e.g., daily date partitions for an event log where 100% of queries filter by date). (2) You need Hive-compatible metadata (legacy tools reading partition directories directly). (3) Table has clear data lifecycle requirements (DROP PARTITION for age-off policies).

Key difference: Z-ORDER does a FULL table rewrite on every OPTIMIZE — a 10TB table with Z-ORDER reruns through 10TB of I/O every maintenance window. Liquid Clustering only processes newly-added files incrementally — if you ingested 100GB today, OPTIMIZE processes only those 100GB, not the historical 10TB.

You accidentally ran VACUUM with 0-hour retention on a production table. Downstream streaming jobs are failing with FileNotFoundException. What happened and how do you recover?

What happened: VACUUM deleted all unreferenced files — including files that streaming readers' checkpoints still point to. The streaming query's checkpoint says "next, read file X from offset Y" but file X no longer exists on S3.

Immediate mitigation: (1) The data files are permanently gone from S3 (no S3 versioning? Then truly gone). (2) If S3 versioning is enabled on the bucket, you can recover deleted objects by restoring previous versions. (3) Restart streaming with a new checkpoint — set startingVersion or startingTimestamp to the latest available version (post-VACUUM). You'll miss the changes in the gap.

Full recovery: (1) If you have a DEEP CLONE or backup from before the VACUUM, restore the table from backup. (2) If source data still exists upstream, replay the ingestion pipeline to reconstruct the missing data. (3) If S3 versioning is enabled, restore all deleted objects, then the Delta log will resolve correctly again.

Prevention: (1) Never disable retentionDurationCheck in production. (2) Set VACUUM retention to at least 7 days (minimum safe for concurrent readers). (3) Enable S3 versioning on all Delta table buckets as a safety net. (4) Use Predictive Optimization instead of manual VACUUM to avoid human error.

How does Change Data Feed work internally, and what's the performance impact of enabling it?

Internal mechanism: When CDF is enabled and a mutation occurs (UPDATE, DELETE, MERGE), Delta writes additional Parquet files to a _change_data/ subdirectory containing the change rows with metadata columns (_change_type, _commit_version, _commit_timestamp). For UPDATEs, both pre-image and post-image rows are written.

Important detail: Pure INSERTs do NOT write to _change_data/. Instead, the reader infers inserts from the transaction log's add actions with dataChange=true. This means CDF has zero overhead for append-only workloads.

Performance impact:

(1) Write overhead: For mutations (UPDATE/DELETE/MERGE), ~10-30% additional write I/O (writing change data files). For pure appends: zero overhead.

(2) Storage overhead: Change data files add storage. For a table with 5% daily mutation rate, CDF adds ~10% storage (pre-image + post-image). VACUUMable after retention period.

(3) Read benefit: Downstream consumers read only the changes (potentially 1% of table) instead of re-scanning entire table. The read savings dwarf the write overhead in most production scenarios.

When NOT to use: Tables with massive mutation rates (>50% of rows changed per operation) where change data files would approach the size of the table itself.

Explain Deletion Vectors and how they change the MERGE performance profile. What's the maintenance burden?

Without DVs (Copy-on-Write): MERGE identifies target files containing matched rows → reads entire files → applies changes → writes entirely new files → commits (remove old, add new). A 1GB file with 1 updated row → 1GB read + 1GB write.

With DVs (Merge-on-Read): MERGE identifies target files → creates/updates a small DV file (RoaringBitmap, typically KB in size) marking deleted row positions → writes only new/changed rows to new small files → commits. A 1GB file with 1 updated row → bitmap update (bytes) + new row write (bytes). The old file is NOT rewritten.

Performance profile change: Write time drops dramatically (10-100x faster for selective MERGEs). Read time increases slightly (reader must check bitmap per file). Net effect: massive improvement for write-heavy workloads.

Maintenance burden: (1) DVs accumulate — files with 40% of rows marked as deleted waste 40% of read I/O scanning dead rows. (2) Small files accumulate from writing only changed rows. (3) Solution: Regular OPTIMIZE (compaction resolves DVs by physically removing deleted rows and consolidating small files). (4) Predictive Optimization handles this automatically. (5) Rule of thumb: schedule OPTIMIZE when numDeletionVectorRows / totalRows > 0.25 for any given file.
