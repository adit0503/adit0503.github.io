Control Plane vs Data Plane

Databricks on AWS uses a split-architecture model separating the management infrastructure from customer compute and data:

Control Plane (Databricks-Managed AWS Account)

  • Location: Runs in Databricks' own AWS account (multi-tenant, shared infrastructure).
  • Components: Webapp (UI), REST API endpoints, Notebook server, Job scheduler, Cluster manager, Unity Catalog metastore, MLflow tracking server, Repos (Git integration).
  • Data stored: Notebook commands (encrypted at rest), job configurations, cluster specs, user/group definitions, access control lists, audit logs.
  • Network: Communicates with data plane over secure channels (TLS 1.2+). In SCC deployments, only outbound connections from data plane — no inbound access from control plane.
  • Regional: Deployed per AWS region (us-east-1, eu-west-1, etc.). Your workspace region must match your data plane region.

Data Plane (Customer AWS Account)

  • Location: Runs entirely in the customer's AWS account and VPC.
  • Components: EC2 instances (Spark driver + executors), EBS volumes, cluster network traffic, S3 data access, local shuffle data.
  • Data processed: All customer data stays within the customer's AWS account — never crosses to the control plane.
  • Isolation: Each workspace gets its own VPC (or customer-managed VPC), its own security groups, its own IAM roles.
Key insight: The control plane never sees your data. It sends instructions (launch cluster, run notebook command) to the data plane. The Spark driver processes data in your VPC and sends only results (cell outputs, metrics) back to the control plane UI. This is critical for compliance (HIPAA, PCI-DSS) — data residency stays within your AWS account.

Network Architecture

Classic Deployment (Legacy)

  • Databricks creates a VPC in the customer's account using a cross-account IAM role.
  • The control plane communicates with the data plane via a public IP on the cluster's driver node.
  • Security groups restrict inbound traffic to the Databricks control plane IP range.
  • Risk: Cluster nodes have public IPs — wider attack surface, may violate corporate network policies.

Secure Cluster Connectivity (SCC / No Public IP)

  • Cluster nodes have no public IP addresses — all communication is outbound-only from the data plane.
  • The Spark driver initiates a secure tunnel to the control plane relay endpoint (via NAT gateway).
  • Control plane cannot SSH or connect inbound to any cluster node.
  • Network flow: EC2 (private subnet) → NAT Gateway → Internet → Databricks control plane relay.
  • Requires NAT gateway in each AZ used by Databricks subnets (cost consideration: ~$0.045/hr/NAT + data processing).

AWS PrivateLink

  • Eliminates traversal of the public internet entirely — traffic stays on the AWS backbone.
  • Front-end PrivateLink: Users access the Databricks UI/API via a VPC endpoint in their VPC (no internet needed for workspace access).
  • Back-end PrivateLink: Data plane to control plane communication via VPC endpoint (replaces the NAT gateway path).
  • Requires VPC endpoint services configured in the customer account pointing to Databricks' endpoint service.
  • Enables fully air-gapped deployments (no internet egress from data plane at all).
Terraform — Customer-Managed VPC with SCC + PrivateLink
# Customer VPC for Databricks data plane
resource "aws_vpc" "databricks" {
  cidr_block           = "10.0.0.0/16"
  enable_dns_support   = true
  enable_dns_hostnames = true
  tags = { Name = "databricks-data-plane" }
}

# Private subnets (no public IP assignment)
resource "aws_subnet" "private" {
  count                   = 2
  vpc_id                  = aws_vpc.databricks.id
  cidr_block              = cidrsubnet("10.0.0.0/16", 8, count.index)
  availability_zone       = data.aws_availability_zones.available.names[count.index]
  map_public_ip_on_launch = false  # SCC: no public IPs
}

# NAT Gateway for outbound (if not using back-end PrivateLink)
resource "aws_nat_gateway" "main" {
  allocation_id = aws_eip.nat.id
  subnet_id     = aws_subnet.public[0].id
}

# VPC Endpoint for S3 (Gateway type — free, avoids NAT charges for S3 traffic)
resource "aws_vpc_endpoint" "s3" {
  vpc_id       = aws_vpc.databricks.id
  service_name = "com.amazonaws.${var.region}.s3"
  vpc_endpoint_type = "Gateway"
  route_table_ids   = [aws_route_table.private.id]
}

# VPC Endpoint for STS (required for IAM authentication)
resource "aws_vpc_endpoint" "sts" {
  vpc_id              = aws_vpc.databricks.id
  service_name        = "com.amazonaws.${var.region}.sts"
  vpc_endpoint_type   = "Interface"
  subnet_ids          = aws_subnet.private[*].id
  security_group_ids  = [aws_security_group.vpc_endpoints.id]
  private_dns_enabled = true
}

# Back-end PrivateLink endpoint (data plane → control plane)
resource "aws_vpc_endpoint" "databricks_backend" {
  vpc_id              = aws_vpc.databricks.id
  service_name        = var.databricks_backend_privatelink_service  # provided by Databricks
  vpc_endpoint_type   = "Interface"
  subnet_ids          = aws_subnet.private[*].id
  security_group_ids  = [aws_security_group.databricks_backend_pl.id]
  private_dns_enabled = true
}

VPC Endpoints for S3 (Critical for Performance)

  • S3 Gateway endpoint is free and routes S3 traffic directly from VPC to S3 without traversing NAT gateway.
  • Without it: all S3 reads/writes go through NAT → internet → S3, incurring NAT data processing charges ($0.045/GB).
  • A cluster reading 1TB/day without S3 endpoint = $45/day in NAT charges alone.
Pitfall: Forgetting the S3 VPC Gateway endpoint is the #1 unexpected cost in Databricks on AWS. A single job reading 500GB from S3 costs $22.50 in NAT data processing if routed through NAT. Always create the S3 gateway endpoint — it's free and eliminates this charge entirely.

Workspace Deployment Internals

When you create a Databricks workspace on AWS, the following resources are provisioned:

In the Customer AWS Account (via Cross-Account Role)

  • VPC (if Databricks-managed): /16 CIDR, 2+ private subnets across AZs, NAT gateway, route tables.
  • Security Groups: (1) Internal SG allowing all traffic between cluster nodes (Spark shuffle, block manager). (2) Egress SG allowing outbound HTTPS to control plane. (3) No inbound from public internet (SCC mode).
  • S3 Root Bucket: databricks-workspace-stack-{id}-bucket — stores DBFS root, cluster logs, notebook revision history (encrypted). Default lifecycle: versioning enabled.
  • IAM Cross-Account Role: Trust policy allows Databricks' AWS account to assume this role. Permissions: EC2 (launch/terminate), S3 (root bucket access), VPC (describe, manage ENIs), IAM (passRole for instance profiles).
  • IAM Instance Profile: Attached to EC2 instances at launch — provides S3 access to the running Spark cluster.

Cross-Account IAM Trust

Cross-Account IAM Role Trust Policy
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::414351767826:root"  
      },
      "Action": "sts:AssumeRole",
      "Condition": {
        "StringEquals": {
          "sts:ExternalId": "your-databricks-account-id"
        }
      }
    }
  ]
}
  • 414351767826 is Databricks' production AWS account (us-east-1). Different account IDs for other regions.
  • ExternalId prevents confused-deputy attacks — only your specific Databricks account can assume the role.
  • The cross-account role needs permissions for: ec2:RunInstances, ec2:TerminateInstances, ec2:DescribeInstances, ec2:CreateSecurityGroup, iam:PassRole, s3:* on root bucket, etc.

Instance Profiles & IAM

Legacy: Instance Profiles for S3 Access

  • An EC2 instance profile is attached to cluster nodes at launch time.
  • The IAM role behind the instance profile grants S3 access to specific buckets.
  • Flow: Spark executor → EC2 instance metadata → STS temporary credentials → S3 API call.
  • Configured per-cluster: different clusters can use different instance profiles (different data access).
  • Problem: Coarse-grained (all code on the cluster gets the same S3 access), no table-level governance, no audit trail per user.
Instance Profile IAM Policy for S3 Access
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:PutObject",
        "s3:DeleteObject",
        "s3:ListBucket"
      ],
      "Resource": [
        "arn:aws:s3:::my-data-lake-bucket",
        "arn:aws:s3:::my-data-lake-bucket/*"
      ]
    },
    {
      "Effect": "Allow",
      "Action": [
        "s3:GetBucketLocation",
        "s3:ListAllMyBuckets"
      ],
      "Resource": "arn:aws:s3:::*"
    }
  ]
}

Unity Catalog: Storage Credentials (Modern Approach)

  • UC uses its own IAM role (storage credential) that it assumes via STS to vend temporary, scoped tokens to clusters.
  • Flow: User query → UC checks permissions → UC assumes storage credential role → generates scoped STS token (limited to specific S3 prefixes) → returns token to cluster → cluster accesses S3.
  • Fine-grained: permissions are per-table, per-column, per-user — not per-cluster.
  • Token lifetime: short-lived (typically 1 hour), automatically refreshed.
  • The instance profile on the cluster doesn't need S3 data access — UC handles all data authorization.
Unity Catalog Storage Credential IAM Role (Self-Assume Pattern)
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::414351767826:role/unity-catalog-prod-UCMasterRole-1234"
      },
      "Action": "sts:AssumeRole",
      "Condition": {
        "StringEquals": {
          "sts:ExternalId": "your-databricks-account-id"
        }
      }
    },
    {
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::YOUR_ACCOUNT:role/this-role-itself"
      },
      "Action": "sts:AssumeRole"
    }
  ]
}
Self-assume pattern: The UC storage credential role trusts itself (self-assume). This allows UC to scope down permissions at runtime by assuming the same role with a more restrictive session policy (limiting S3 access to only the paths the user is authorized to read). This is how UC implements fine-grained access without creating hundreds of IAM roles.

DBFS Architecture

Root DBFS (S3-Backed)

  • DBFS (Databricks File System) is an abstraction layer over S3 that provides a POSIX-like path interface (dbfs:/, /dbfs/).
  • The root DBFS is backed by the workspace's S3 root bucket: s3://databricks-workspace-stack-{id}-bucket/
  • Accessible by all users and clusters in the workspace — no per-user isolation by default.
  • Stores: uploaded files, library JARs, temporary data, MLflow artifacts (legacy), init scripts.

DBFS Mounts (Legacy — Avoid)

  • Mount an external S3 bucket to a DBFS path: dbutils.fs.mount("s3a://my-bucket", "/mnt/data")
  • All users with cluster access can read /mnt/data — bypasses Unity Catalog governance entirely.
  • Credentials embedded in the mount configuration (stored in control plane).
  • Problems: No table-level access control, no audit per user, shared credentials, no column masking.

External Locations (UC — Recommended)

  • Register S3 paths as external locations in Unity Catalog with explicit GRANT permissions.
  • Access controlled per-user, audited, supports row/column security.
  • No credentials stored on the cluster — UC vends temporary tokens per request.
Migration: Mount → External Location
-- Legacy mount (AVOID for new development)
-- dbutils.fs.mount("s3a://analytics-prod", "/mnt/analytics")
-- spark.read.parquet("/mnt/analytics/events/")  -- no governance

-- Modern: Unity Catalog External Location
CREATE EXTERNAL LOCATION analytics_prod
URL 's3://analytics-prod/'
WITH (STORAGE CREDENTIAL analytics_cred);

GRANT READ FILES ON EXTERNAL LOCATION analytics_prod TO `data-engineers`;

-- Access via UC-governed path
CREATE EXTERNAL TABLE catalog.schema.events
LOCATION 's3://analytics-prod/events/'
AS SELECT * FROM parquet.`s3://analytics-prod/events/`;

-- Or use volumes for file-level access
CREATE EXTERNAL VOLUME catalog.schema.raw_files
LOCATION 's3://analytics-prod/raw/';
Migration imperative: If you're still using DBFS mounts in production, you have a governance gap. Mounts completely bypass Unity Catalog — anyone on the cluster can read/write mounted data regardless of UC permissions. Migrate to external locations/volumes for any data that requires access control.

Cluster Lifecycle on AWS

Launch Sequence (What Happens When You Start a Cluster)

  1. API call: Control plane receives cluster creation request (instance type, count, Spark config).
  2. Cross-account assume: Control plane assumes the workspace's cross-account IAM role.
  3. EC2 provisioning: RunInstances API calls for driver + worker nodes. Instance profile attached. EBS volumes created (GP3 for root, optional additional volumes for shuffle).
  4. Security group assignment: Internal SG (all-traffic between cluster nodes on all ports) + workspace SG (outbound HTTPS).
  5. Bootstrap: Databricks agent starts on each node → downloads Spark/Delta/Photon binaries from S3 → runs init scripts → starts Spark processes.
  6. Registration: Driver registers with control plane (secure tunnel in SCC mode) → cluster marked "Running" → REPL/notebook attached.

Typical startup time: 3-7 minutes (EC2 provisioning + bootstrap). With instance pools: 30-90 seconds.

EBS Volumes

  • Root volume: GP3, stores OS + Databricks runtime + Spark binaries. Typically 100GB.
  • Additional volumes: Configured per cluster for local shuffle/spill storage. GP3 or IO2 for high-throughput shuffle.
  • Auto-scaling storage: Databricks can auto-attach additional EBS volumes when local disk fills up (prevents out-of-disk failures during large shuffles).
  • Encryption: EBS encryption enabled by default using workspace KMS key or AWS-managed key.

Spot Instance Integration

  • Configuration: first_on_demand specifies how many initial nodes are On-Demand (typically 1 for driver protection).
  • Availability: SPOT (fail if no Spot), SPOT_WITH_FALLBACK (try Spot, fall back to On-Demand), ON_DEMAND.
  • Spot price: spot_bid_max_price = -1 (default) means bid up to On-Demand price — recommended for maximum availability.
  • Eviction handling: Databricks decommissions the node gracefully, moves shuffle data if possible, Spark retries lost tasks.

Instance Pools

  • Pre-warmed EC2 instances in a STOPPED or RUNNING state, ready for immediate attachment to clusters.
  • Configuration: min_idle_instances (minimum warm capacity), max_capacity (total pool size), idle_instance_autotermination_minutes.
  • Reduces cluster startup from 5-7 minutes to 30-90 seconds.
  • Pools can be shared across multiple clusters — first-come-first-served allocation.
  • Cost: you pay for idle instances in the pool (EC2 charges), but save on startup time and reduce Spot interruption risk (instances already allocated).

AWS Glue Catalog Integration

Glue as External Hive Metastore

  • Databricks can use AWS Glue Data Catalog as an external Hive-compatible metastore.
  • Tables created in Spark are visible in Athena, Redshift Spectrum, EMR — shared schema.
  • Configured via: spark.hadoop.hive.metastore.client.factory.class = com.amazonaws.glue.catalog.metastore.AWSGlueDataCatalogHiveClientFactory
  • Limitations: No column-level ACLs, no row security, no lineage — Glue is purely a schema registry.

Unity Catalog vs Glue

FeatureAWS Glue CatalogUnity Catalog
Schema registry✅✅
Column-level security❌ (via Lake Formation)✅ Native
Row-level security❌✅ SQL functions

Production pattern: Use Unity Catalog as the primary metastore for all Databricks workloads (governance, lineage, access control). Register critical tables in Glue additionally (using Delta UniForm or external table sync) only if you need cross-engine access from Athena/EMR/Redshift. Don't use Glue as the sole metastore — you lose all UC governance features.

Multi-Workspace Architecture

Hub-Spoke Model

  • Hub workspace: Central governance workspace hosting the Unity Catalog metastore, shared Delta Sharing server, centralized audit logging.
  • Spoke workspaces: Per-team or per-environment workspaces (dev, staging, prod) attached to the hub's UC metastore.
  • Cross-account: Spoke workspaces can be in different AWS accounts — UC supports cross-account metastore binding.
  • Network: Transit Gateway or VPC peering between spoke VPCs for direct data access (avoids internet traversal between workspaces).

Common Organizational Patterns

  • Per-environment: workspace-dev, workspace-staging, workspace-prod (simplest, clear promotion path).
  • Per-team: workspace-data-engineering, workspace-data-science, workspace-analytics (isolation, separate billing).
  • Per-domain: workspace-finance, workspace-marketing, workspace-platform (data mesh alignment).
Multi-Workspace Account-Level Setup (Databricks CLI)
# Create a metastore (once per region)
databricks unity-catalog metastores create \
  --name "production-metastore" \
  --storage-root "s3://uc-metastore-prod-us-east-1/managed/" \
  --region us-east-1

# Assign metastore to multiple workspaces
databricks unity-catalog metastores assign \
  --workspace-id 1234567890 \  # dev workspace
  --metastore-id "metastore-uuid" \
  --default-catalog-name "dev"

databricks unity-catalog metastores assign \
  --workspace-id 9876543210 \  # prod workspace
  --metastore-id "metastore-uuid" \
  --default-catalog-name "prod"

Security & Encryption

Encryption at Rest

  • S3: SSE-S3 (default) or SSE-KMS with customer-managed CMK. Configure at bucket level — all Databricks writes inherit.
  • EBS: Encrypted by default using workspace-level KMS key. Protects local shuffle/spill data on cluster nodes.
  • Managed services: Control plane data (notebooks, configs) encrypted with Databricks-managed keys, or customer-managed keys (CMK for control plane) for regulated workloads.

Encryption in Transit

  • Control↔Data plane: TLS 1.2+ for all communication (API calls, notebook results, cluster registration).
  • Intra-cluster: Spark encryption enabled via spark.network.crypto.enabled=true + spark.authenticate=true (AES-encrypted shuffle).
  • S3 access: HTTPS enforced for all S3 API calls (TLS 1.2). Bucket policy can deny HTTP.

Network Isolation

  • Customer-managed VPC: Full control over CIDR, subnets, NACLs, route tables. Restrict egress to only Databricks control plane + S3.
  • No public IPs (SCC): Eliminates direct internet exposure of cluster nodes.
  • PrivateLink: Zero internet traversal — all Databricks traffic stays on AWS backbone.
  • DNS: Custom DNS resolution for workspace URLs via Route53 private hosted zones (PrivateLink).

Credential Passthrough (Legacy)

  • Maps the IAM role of the user (via SSO) to the cluster's S3 access.
  • Only supported on single-user clusters (not shared clusters) — one user per cluster.
  • Deprecated in favor of Unity Catalog — UC provides the same per-user credential scoping without the single-user cluster restriction.
Workspace-Level CMK Configuration (Terraform)
resource "databricks_mws_customer_managed_keys" "storage" {
  account_id = var.databricks_account_id
  aws_key_info {
    key_arn   = aws_kms_key.databricks_storage.arn
    key_alias = aws_kms_alias.databricks_storage.name
    key_region = var.region
  }
  use_cases = ["STORAGE"]  # Encrypts S3 root bucket + managed Delta tables
}

resource "databricks_mws_customer_managed_keys" "managed_services" {
  account_id = var.databricks_account_id
  aws_key_info {
    key_arn   = aws_kms_key.databricks_control_plane.arn
    key_alias = aws_kms_alias.databricks_control_plane.name
    key_region = var.region
  }
  use_cases = ["MANAGED_SERVICES"]  # Encrypts notebooks, secrets in control plane
}

Interview Questions

Explain the split between control plane and data plane in Databricks on AWS. What are the security implications?

The control plane runs in Databricks' AWS account and handles orchestration — UI, job scheduling, cluster management, notebook storage, REST APIs. The data plane runs entirely in the customer's AWS account — all EC2 instances, EBS volumes, and S3 data access happen here.

Security implications: (1) Customer data never leaves their AWS account — the control plane only receives cell outputs and metrics, not raw data. (2) For HIPAA/PCI compliance, this separation ensures data residency requirements are met. (3) However, notebook code and cell outputs ARE stored in the control plane — for maximum sensitivity, enable CMK for managed services to encrypt this with your own KMS key. (4) The cross-account IAM role is the trust boundary — audit its permissions carefully, use external ID condition, and limit to minimum required permissions.

Your security team requires zero internet egress from compute nodes. How do you architect this?

Solution: SCC + Back-end PrivateLink + VPC endpoints.

(1) Deploy with Secure Cluster Connectivity (no public IPs). (2) Configure back-end PrivateLink so data plane → control plane communication uses AWS backbone (no NAT, no internet). (3) Add VPC Gateway endpoint for S3 (free, keeps S3 traffic private). (4) Add VPC Interface endpoints for STS, Kinesis (if used), and any other AWS services the workload needs. (5) Remove all routes to internet gateway and NAT gateway from the Databricks subnets' route tables. (6) Configure front-end PrivateLink so users access the workspace UI without internet.

Result: Complete air-gap — zero bytes traverse the public internet. All traffic stays on AWS internal network. Cost: VPC endpoint charges (~$0.01/hr each + $0.01/GB processed) replace NAT gateway costs.

Why is the S3 VPC Gateway endpoint critical for Databricks performance and cost?

Without the S3 Gateway endpoint, all S3 traffic from Databricks clusters routes through the NAT gateway. This creates two problems:

Cost: NAT data processing charges are $0.045/GB. A typical ETL job reading/writing 100GB = $4.50. At 50 jobs/day = $225/day = $6,750/month in pure NAT charges. The S3 Gateway endpoint is completely free and eliminates this entirely.

Performance: NAT gateways have a throughput cap of 45 Gbps per gateway. Multiple large clusters competing for NAT bandwidth creates a network bottleneck. With the Gateway endpoint, S3 traffic takes a direct path with no bandwidth ceiling (limited only by instance network bandwidth).

Always do: Create the S3 Gateway endpoint in every Databricks VPC. Also consider STS, KMS, and Glue Interface endpoints for additional performance gains and security.

How do instance pools reduce cluster startup time, and what's the cost tradeoff?

Mechanism: Instance pools maintain pre-allocated EC2 instances that are already provisioned and have the Databricks base image loaded. When a cluster requests nodes from a pool, it skips the EC2 RunInstances API call (1-3 min), skips AMI boot (1-2 min), and only needs to download the specific Databricks Runtime version and run init scripts (30-60 sec).

Reduction: Startup goes from 5-7 minutes → 30-90 seconds. This is transformative for job clusters that start/stop per job — a pipeline with 10 sequential jobs saves 50-60 minutes of wait time per run.

Cost tradeoff: Idle instances in the pool incur EC2 charges even when no cluster is using them. Mitigation: set idle_instance_autotermination_minutes to 10-15 min so unused instances release quickly. Set min_idle_instances conservatively (2-4) to cover immediate demand without over-provisioning. The cost of 2-3 idle instances is typically far less than the engineering time and pipeline delay savings.

Compare legacy instance profiles with Unity Catalog storage credentials for S3 access. When would you still use instance profiles?

Instance profiles (legacy): IAM role attached to EC2 instances. All code on the cluster gets identical S3 permissions. No per-user differentiation, no table-level controls, no audit trail by user identity.

UC storage credentials (modern): UC vends short-lived STS tokens scoped to the exact S3 paths a user is authorized to access. Per-user access control, full audit logging (who accessed what table when), column masking, row filters — all enforced regardless of what code runs on the cluster.

When instance profiles are still used: (1) Legacy workloads not yet migrated to UC. (2) Infrastructure operations (init scripts, library installation from private S3 repos) that happen before UC is available during cluster bootstrap. (3) Third-party integrations that don't support UC token vending. (4) The cluster still needs a minimal instance profile for accessing the DBFS root bucket and Databricks system resources — but data access should be UC-governed.
