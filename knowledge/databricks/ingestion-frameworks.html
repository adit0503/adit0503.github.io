Auto Loader (cloudFiles)

Auto Loader is Databricks' recommended mechanism for incrementally ingesting files from cloud storage (S3, ADLS, GCS). It automatically discovers new files and processes them exactly once.

Key Capabilities

  • Incremental discovery: Only processes files that haven't been seen before (tracks via internal checkpoint).
  • Schema inference: Automatically infers schema from file contents (JSON, CSV, Avro, Parquet).
  • Schema evolution: Handles new columns, type changes, and unexpected fields gracefully.
  • Exactly-once: Checkpoint-based — each file is processed exactly once, even after restarts.
  • Scalable: Handles millions of files in a directory without performance degradation (with file notification mode).
Auto Loader — Basic Usage
# Streaming read with Auto Loader
df = (spark.readStream
    .format("cloudFiles")
    .option("cloudFiles.format", "json")
    .option("cloudFiles.schemaLocation", "/checkpoints/orders/schema")
    .option("cloudFiles.inferColumnTypes", "true")
    .load("s3://landing-zone/orders/")
)

# Write to Delta Bronze table
(df.writeStream
    .option("checkpointLocation", "/checkpoints/orders/stream")
    .option("mergeSchema", "true")
    .trigger(availableNow=True)  # Process all available, then stop
    .toTable("catalog.bronze.orders")
)

File Notification Mode

Architecture (AWS)

  1. New file lands in S3 bucket.
  2. S3 event notification → SNS topic.
  3. SNS → SQS queue (dedicated queue per Auto Loader stream).
  4. Auto Loader polls SQS queue for new file paths.
  5. Processes only the files listed in SQS messages.

Setup

  • Auto Loader automatically creates the SNS topic and SQS queue if the IAM role has permissions.
  • Or you can pre-create resources and pass them via options: cloudFiles.queueUrl, cloudFiles.subscriptionId.
  • Required IAM permissions: s3:GetBucketNotificationConfiguration, s3:PutBucketNotificationConfiguration, sns:CreateTopic, sns:Subscribe, sqs:CreateQueue, sqs:ReceiveMessage, sqs:DeleteMessage.

Advantages

  • No S3 LIST calls: Avoids expensive recursive directory listing (which is O(n) on total files). Critical for directories with millions of historical files.
  • Near-real-time: File notification arrives within seconds of file landing (vs directory listing which runs on poll interval).
  • Cost-efficient: SQS costs are negligible (~$0.40 per million messages). S3 LIST calls at scale can hit rate limits and cost more.
File Notification Mode — Configuration
df = (spark.readStream

Directory Listing Mode

How It Works

  • Auto Loader recursively lists the source directory on each trigger.
  • Compares listed files against its internal checkpoint (files already processed).
  • New files (not in checkpoint) are processed in the current micro-batch.
  • Default mode when cloudFiles.useNotifications is not set to true.

When to Use

  • Simpler setup — no SNS/SQS configuration needed.
  • Works immediately with any S3 bucket (no notification configuration required).
  • Acceptable for directories with <10K total files or when processing is infrequent (daily batches).

Performance Considerations

  • S3 LIST is O(n) — listing 10 million files takes significant time (~5 min for 10M files).
  • Each trigger repeats the listing — wasteful if only 100 new files arrived since last run.
  • S3 rate limit: 5,500 LIST requests per second per prefix. Deep directories can hit this.
  • Mitigation: Use file notification mode for directories growing beyond 100K files.
Directory Listing Mode Options
df = (spark.readStream
    .format("cloudFiles")
    .option("cloudFiles.format", "parquet")
    .option("cloudFiles.useNotifications", "false")  # Explicit directory listing
    .option("cloudFiles.schemaLocation", "/checkpoints/data/schema")
    # Performance tuning for large directories
    .option("cloudFiles.maxFilesPerTrigger", "1000")  # Limit files per batch
    .option("cloudFiles.maxBytesPerTrigger", "10g")   # Limit bytes per batch
    # Recursive listing
    .option("recursiveFileLookup", "true")
    # Path glob filter
    .option("pathGlobFilter", "*.parquet")
    .load("s3://data-lake/raw/transactions/")
)

Schema Inference & Evolution

Schema Inference

  • On first run, Auto Loader samples files to infer schema and stores it in cloudFiles.schemaLocation.
  • cloudFiles.inferColumnTypes = true: Infers specific types (BIGINT, DOUBLE, TIMESTAMP) instead of defaulting everything to STRING.
  • cloudFiles.schemaHints: Override inferred types for specific columns: "amount DOUBLE, event_ts TIMESTAMP"

Schema Evolution Modes

ModeBehaviorUse Case
addNewColumnsNew fields automatically added as columnsEvolving JSON APIs
rescueUnknown fields captured in _rescued_data columnStrict schema + auditability
failOnNewColumnsPipeline fails on new fields (forces explicit handling)Production contracts
noneNew fields silently droppedFixed-schema targets
Schema Evolution with Rescue Column
df = (spark.readStream
    .format("cloudFiles")
    .option("cloudFiles.format", "json")
    .option("cloudFiles.schemaLocation", "/checkpoints/events/schema")
    .option("cloudFiles.inferColumnTypes", "true")
    .option("cloudFiles.schemaEvolutionMode", "rescue")  # Unknown fields → _rescued_data
    .option("cloudFiles.schemaHints", """
        event_id BIGINT,
        user_id BIGINT,
        event_ts TIMESTAMP,
        amount DOUBLE
    """)
    .load("s3://landing-zone/events/")
)

# _rescued_data contains JSON string of any fields not in the inferred schema
# Useful for debugging and auditing schema drift
df.select("event_id", "user_id", "_rescued_data").filter("_rescued_data IS NOT NULL")
Production recommendation: Use rescue mode for Bronze layer (never lose data, capture unknowns for investigation). Use failOnNewColumns for Silver layer (enforce data contracts — new fields must be explicitly added to the schema by a developer).

Structured Streaming on Databricks

Trigger Modes

once=TrueProcess one batch, then stop (deprecated)Legacy — use availableNow instead

Checkpointing

  • Checkpoints stored in S3 (or DBFS): .option("checkpointLocation", "s3://checkpoints/my-stream/")
  • Contains: offsets (what data has been read), committed offsets (what has been written), metadata.
  • Enables exactly-once: if the stream restarts, it resumes from the last committed offset.
  • Never delete checkpoints unless you want to reprocess from scratch.
  • Never share checkpoints between different streams — each stream needs its own checkpoint directory.
Structured Streaming — Production Configuration
# Streaming pipeline with proper production settings
stream = (spark.readStream
    .format("cloudFiles")
    .option("cloudFiles.format", "json")
    .option("cloudFiles.schemaLocation", "/checkpoints/pipeline/schema")
    .option("cloudFiles.useNotifications", "true")
    .option("maxFilesPerTrigger", "1000")
    .load("s3://landing/events/")
    .transform(apply_transformations)
    .writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", "s3://checkpoints/pipeline/events/")
    .option("mergeSchema", "true")
    # Optimize output file sizes
    .option("spark.databricks.delta.optimizeWrite.enabled", "true")
    .option("spark.databricks.delta.autoCompact.enabled", "true")
    .trigger(availableNow=True)
    .toTable("catalog.bronze.events")
)

# Wait for completion (triggered mode)
stream.awaitTermination()

Streaming from Kafka (MSK)

Kafka/MSK Source Configuration
# Read from Amazon MSK (Kafka) with IAM authentication
kafka_df = (spark.readStream
    .format("kafka")
    .option("kafka.bootstrap.servers", "b-1.msk-cluster.abc.kafka.us-east-1.amazonaws.com:9098")
    .option("subscribe", "user-events,order-events")  # Multiple topics
    .option("startingOffsets", "latest")  # or "earliest" for backfill
    .option("failOnDataLoss", "false")  # Don't fail if offsets expired
    .option("maxOffsetsPerTrigger", "1000000")  # Rate limit
    # MSK IAM Authentication
    .option("kafka.security.protocol", "SASL_SSL")
    .option("kafka.sasl.mechanism", "AWS_MSK_IAM")
    .option("kafka.sasl.jaas.config", """
        software.amazon.msk.auth.iam.IAMLoginModule required;
    """)
    .option("kafka.sasl.client.callback.handler.class",
            "software.amazon.msk.auth.iam.IAMClientCallbackHandler")
    .load()
)

# Parse Kafka value (binary → JSON → struct)
from pyspark.sql.functions import from_json, col
from pyspark.sql.types import *

event_schema = StructType([
    StructField("event_id", StringType()),
    StructField("user_id", LongType()),
    StructField("event_type", StringType()),
    StructField("timestamp", TimestampType()),
    StructField("payload", StringType())
])

parsed_df = (kafka_df
    .select(
        col("topic"),
        col("partition"),
        col("offset"),
        col("timestamp").alias("kafka_timestamp"),
        from_json(col("value").cast("string"), event_schema).alias("data")
    )
    .select("topic", "partition", "offset", "kafka_timestamp", "data.*")
)

# Write to Delta with deduplication
(parsed_df.writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", "s3://checkpoints/kafka-events/")
    .trigger(processingTime="30 seconds")
    .toTable("catalog.bronze.kafka_events")
)

Key Kafka Options

  • startingOffsets: "earliest" (backfill all), "latest" (new data only), or JSON per-partition: '{"topic":{"0":100,"1":200}}'
  • failOnDataLoss: Set false in production — Kafka log compaction or retention can cause offset gaps. true fails the stream on gaps (safer for audit requirements).
  • maxOffsetsPerTrigger: Controls batch size — prevents one trigger from reading too much data and causing OOM.
  • minOffsetsPerTrigger: Minimum records to wait for before processing — reduces small-batch overhead.

Delta as Source & Sink

Delta-to-Delta Streaming (Silver → Gold)
# Read from Delta table as streaming source
silver_stream = (spark.readStream
    .format("delta")
    .option("maxFilesPerTrigger", "100")      # Rate limit: files per batch
    .option("maxBytesPerTrigger", "1g")       # Rate limit: bytes per batch
    .option("ignoreChanges", "true")          # Ignore non-append changes (UPDATEs)
    # .option("ignoreDeletes", "true")        # Ignore DELETE operations
    .table("catalog.silver.events")
)

# foreachBatch pattern for MERGE (upsert) into Gold
from delta.tables import DeltaTable

def upsert_to_gold(batch_df, batch_id):
    gold_table = DeltaTable.forName(spark, "catalog.gold.user_metrics")
    
    # Aggregate the micro-batch
    metrics = (batch_df
        .groupBy("user_id", "event_date")
        .agg(
            count("*").alias("event_count"),
            sum("amount").alias("total_amount")
        )
    )
    
    # MERGE into gold (upsert)
    gold_table.alias("t").merge(
        metrics.alias("s"),
        "t.user_id = s.user_id AND t.event_date = s.event_date"
    ).whenMatchedUpdate(set={
        "event_count": "t.event_count + s.event_count",
        "total_amount": "t.total_amount + s.total_amount"
    }).whenNotMatchedInsertAll().execute()

# Execute with foreachBatch
(silver_stream.writeStream
    .foreachBatch(upsert_to_gold)
    .option("checkpointLocation", "s3://checkpoints/gold-metrics/")
    .trigger(availableNow=True)
    .start()
    .awaitTermination()
)
Important: When reading Delta as a streaming source, the stream fails if the source table has UPDATE or DELETE operations (because these are not append operations). Set ignoreChanges=true to skip non-append commits, or use Change Data Feed (CDF) for proper change propagation: .option("readChangeFeed", "true").

COPY INTO

What It Does

  • Batch ingestion command that loads files into a Delta table.
  • Idempotent: Tracks which files have been loaded — running again won't duplicate data.
  • Does NOT maintain a streaming checkpoint — simply tracks loaded file paths in table metadata.

COPY INTO vs Auto Loader

FeatureCOPY INTOAuto Loader
Processing modelBatch (one-shot)Streaming (incremental)
File trackingTable metadataStreaming checkpoint
Schema evolutionLimitedFull (rescue, addNewColumns)
File discoveryLIST on each executionNotification or incremental LIST
ScalabilityGood for <10K filesMillions of files
Recommended forOne-time loads, small volumesContinuous ingestion, production
COPY INTO Examples
-- Basic COPY INTO
COPY INTO catalog.bronze.transactions
FROM 's3://landing-zone/transactions/'
FILEFORMAT = PARQUET
FORMAT_OPTIONS ('mergeSchema' = 'true')
COPY_OPTIONS ('mergeSchema' = 'true');

-- COPY INTO with transformations
COPY INTO catalog.bronze.events
FROM (
  SELECT 
    _metadata.file_name AS source_file,
    _metadata.file_modification_time AS file_mod_time,
    *
  FROM 's3://landing-zone/events/'
)
FILEFORMAT = JSON
FORMAT_OPTIONS ('inferSchema' = 'true', 'multiLine' = 'true')
COPY_OPTIONS ('force' = 'false');  -- false = skip already-loaded files

Production Ingestion Patterns

Complete Ingestion Pipeline Pattern
# Pattern: Landing Zone → Bronze (Auto Loader) → Silver (Streaming MERGE)

# ============ BRONZE: Raw Ingestion ============
bronze_stream = (spark.readStream
    .format("cloudFiles")
    .option("cloudFiles.format", "json")
    .option("cloudFiles.useNotifications", "true")
    .option("cloudFiles.schemaLocation", "s3://checkpoints/orders/schema")
    .option("cloudFiles.schemaEvolutionMode", "rescue")
    .option("cloudFiles.inferColumnTypes", "true")
    .load("s3://landing-zone/orders/")
    .withColumn("_ingested_at", current_timestamp())
    .withColumn("_source_file", input_file_name())
)

(bronze_stream.writeStream
    .format("delta")
    .option("checkpointLocation", "s3://checkpoints/bronze-orders/")
    .option("spark.databricks.delta.optimizeWrite.enabled", "true")
    .trigger(availableNow=True)
    .toTable("catalog.bronze.orders")
)

# ============ SILVER: Clean + Dedupe ============
silver_stream = (spark.readStream
    .format("delta")
    .option("readChangeFeed", "true")
    .option("startingVersion", 0)
    .table("catalog.bronze.orders")
    .filter("_change_type IN ('insert', 'update_postimage')")
)

def merge_to_silver(batch_df, batch_id):
    from delta.tables import DeltaTable
    
    # Deduplicate within batch (keep latest by updated_at)
    deduped = (batch_df
        .withColumn("rn", row_number().over(
            Window.partitionBy("order_id").orderBy(desc("updated_at"))
        ))
        .filter("rn = 1").drop("rn")
    )
    
    silver = DeltaTable.forName(spark, "catalog.silver.orders")
    silver.alias("t").merge(
        deduped.alias("s"), "t.order_id = s.order_id"
    ).whenMatchedUpdate(
        condition="s.updated_at > t.updated_at",
        set={"*": "s.*"}
    ).whenNotMatchedInsertAll().execute()

(silver_stream.writeStream
    .foreachBatch(merge_to_silver)
    .option("checkpointLocation", "s3://checkpoints/silver-orders/")
    .trigger(availableNow=True)
    .start()
)

Production Considerations

Checkpoint Management

  • Store checkpoints on S3 (durable, survives cluster termination).
  • Use a consistent naming convention: s3://checkpoints/{pipeline}/{table}/
  • Never delete checkpoints in production — causes full reprocessing.
  • If you must reset: rename/archive old checkpoint, start stream with new checkpoint + startingVersion/startingTimestamp.

Handling Late Data

  • Auto Loader processes files in arrival order — late-arriving files are processed when discovered.
  • For windowed aggregations: set withWatermark("event_time", "2 hours") to handle late events.
  • Bronze layer: always accept all data (no watermark filtering). Silver/Gold: apply watermarks for correctness.

Backfill Strategies

  • New pipeline: Point Auto Loader at historical directory, use trigger(availableNow=True) to process all files.
  • Existing pipeline: If checkpoint exists, Auto Loader skips already-processed files. New files in old directories are picked up on next trigger.
  • Force reprocess: Delete checkpoint and restart (reprocesses everything — ensure idempotent writes with MERGE).

Schema Drift Handling

  • Bronze: Use rescue mode — never lose data. New fields go to _rescued_data for investigation.
  • Silver: Use mergeSchema=true on writes to auto-add new columns to Delta table.
  • Gold: Schema changes should be explicit (DDL). Use failOnNewColumns upstream to catch drift before it reaches Gold.

Interview Questions

Compare Auto Loader's file notification mode vs directory listing mode. When does each break down?

File notification mode: S3 → SNS → SQS → Auto Loader polls SQS. O(1) discovery cost per new file regardless of total directory size. Near-real-time (seconds latency).

Breaks down when: (1) SQS message retention expires (14 days max) — if the stream is paused longer than retention, messages are lost and files are missed. Recovery: fall back to directory listing for the gap period. (2) S3 event notifications have eventual consistency — very rarely, a notification is lost. Mitigation: periodic directory listing reconciliation. (3) IAM permissions are complex to set up in locked-down environments.

Directory listing mode: Lists all files in directory, diffs against checkpoint. Simple setup, no infrastructure dependencies.

Breaks down when: (1) Directory has millions of files — listing takes minutes, wastes S3 API calls, and may hit rate limits (5,500 LIST/sec/prefix). (2) High-frequency triggers (every 10 sec) with large directories create excessive S3 costs. (3) Latency scales with directory size — unacceptable for real-time.

Rule of thumb: Use directory listing for <100K files or infrequent (hourly+) triggers. Use file notification for >100K files or sub-minute latency requirements.

Your Auto Loader stream processes JSON files but source teams keep adding new fields, breaking downstream consumers. Design a robust schema evolution strategy.

Multi-layer schema strategy:

Bronze (permissive): Use cloudFiles.schemaEvolutionMode = "rescue". All known fields map to typed columns. Unknown fields land in _rescued_data (JSON string column). Zero data loss, never breaks on schema changes.

Schema monitoring: Create an alerting job that checks _rescued_data IS NOT NULL count. If >0 rows have rescued data, alert the team that new fields have appeared. This gives time to review and promote fields to the schema.

Silver (controlled): Set mergeSchema = true on the Delta write. When you explicitly add new columns to the Silver transformation logic, the Delta table schema expands automatically. But DON'T auto-promote rescued fields — require a code review.

Gold (strict): Schema is fixed by the Gold table DDL. Any new columns must be added via migration (ALTER TABLE). This protects downstream BI tools and dashboards that expect a fixed schema.

Contract enforcement: Publish a schema registry (Confluent Schema Registry or custom) that source teams must update before adding fields. Auto Loader's schemaHints enforces expected types. Combine with DLT expectations for runtime validation.

You need to ingest from Kafka (MSK) with exactly-once semantics into a Delta table. Walk through the architecture and failure modes.

Architecture: Spark Structured Streaming Kafka source → transformations → Delta sink with checkpointing.

Exactly-once guarantee components:

(1) Source (Kafka): Spark tracks committed offsets in the checkpoint. On restart, it resumes from the last committed offset. Kafka messages may be replayed (at-least-once from Kafka side), but Spark deduplicates via offset tracking.

(2) Processing: Deterministic transformations ensure same input → same output. Avoid non-deterministic functions (random(), current_timestamp() for business logic) or accept slight variations on replay.

(3) Sink (Delta): Delta's transaction log ensures atomic writes. The checkpoint records which offsets have been committed to Delta. If the write succeeds but checkpoint update fails → on restart, the batch is replayed, but Delta's idempotent write (via txn ID) prevents duplicates.

Failure modes:

(1) Kafka offset expiration: If retention is 7 days and stream is down for 8 days, offsets are gone. Set failOnDataLoss=false to skip the gap (data loss) or fail and alert for manual recovery from backup.

(2) Checkpoint corruption: Rare but possible (S3 partial write). Recovery: delete checkpoint, restart with specific startingOffsets JSON, accept potential duplicates and run deduplication downstream.

(3) OOM on large batches: A surge of Kafka data causes executor OOM. Set maxOffsetsPerTrigger to cap batch size. Use processingTime trigger to ensure steady processing rate.

What's the difference between trigger(once=True) and trigger(availableNow=True)? When does it matter?

trigger(once=True) [deprecated]: Processes all available data in ONE micro-batch. If 100GB of data is available, it creates one massive batch. This can cause OOM, excessive shuffle, and very long task execution times.

trigger(availableNow=True): Processes all available data in MULTIPLE micro-batches (respecting maxFilesPerTrigger/maxBytesPerTrigger limits), then stops. It's rate-limited and memory-safe.

When it matters: (1) Large backlog: If the stream has been paused and 1TB of data accumulated, once=True tries to process 1TB in one batch (likely OOM). availableNow=True processes it in manageable chunks (e.g., 100 batches of 10GB each). (2) Auto Loader: With maxFilesPerTrigger=1000, availableNow=True processes 1000 files per batch until all files are done. once=True ignores the limit and takes everything. (3) Always use availableNow=True for new development. once=True is deprecated and will be removed.

Design an ingestion architecture for 50TB/day of raw JSON events from 200 different source systems, each with different schemas.

Architecture:

Landing zone: S3 bucket with prefix per source: s3://landing/{source_system}/YYYY/MM/DD/. Each system dumps raw JSON files independently.

Auto Loader (one per source): 200 Auto Loader streams, each with file notification mode (critical at this scale — directory listing would be prohibitive). Use DLT with a parameterized pipeline template: single DLT notebook parameterized by source_system, replicated as 200 pipeline instances.

Schema strategy: Each source has independent schema inference + rescue column. Store schemas in s3://checkpoints/{source}/schema/. No shared schema across sources.

Bronze layout: One Bronze Delta table per source: catalog.bronze.{source_system}. 200 tables, each with source-specific schema. Include metadata columns: _source_file, _ingested_at, _rescued_data.

Compute: DLT pipelines grouped by criticality (high-priority sources on dedicated clusters, low-priority batch together). Use triggered mode every 15 minutes for most sources; continuous mode for real-time sources.

Monitoring: Centralized event log dashboard showing all 200 pipelines: lag, error rate, quality metrics. Alert on: (1) pipeline failure, (2) no new files for 2× expected interval, (3) expectation pass rate drop >5%.

Cost at scale: 50TB/day × $0.02/GB S3 storage/month = $1,000/month storage. Compute: depends on complexity, but Auto Loader with Photon on DLT can process ~2TB/hour per 10-node cluster. ~25 cluster-hours/day for raw ingestion.
