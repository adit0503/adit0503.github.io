What Is Photon

Photon is a C++ native vectorized execution engine developed by Databricks that replaces the JVM-based Spark SQL execution layer (WholeStageCodegen) for supported operations. It's designed to maximize CPU utilization for data-intensive queries on modern hardware.

  • Not a separate system: Photon plugs into the existing Spark SQL infrastructure. The Catalyst optimizer generates the query plan, and Photon executes supported physical operators natively.
  • Transparent: Same SQL/DataFrame API, same semantics, same results — just faster execution for supported operations.
  • Operator-level: Individual operators in the query plan may execute in Photon or fall back to JVM — the plan is a mix of both.

Architecture & Integration

How Photon Integrates with Spark

  1. Query planning: Catalyst optimizer produces a physical plan (same as standard Spark).
  2. Photon eligibility check: Each physical operator is checked for Photon support. Supported operators are marked for native execution.
  3. Code generation: Instead of Spark's WholeStageCodegen (which generates JVM bytecode), Photon uses pre-compiled C++ operator implementations linked at runtime.
  4. Execution: Photon operators execute natively (C++), process column batches, and return results to the Spark framework.
  5. Fallback: Unsupported operators in the same query execute via traditional Spark JVM code. Data is transferred between Photon and JVM layers at operator boundaries.

Key Design Decisions

  • Column-batched: Photon processes data in columnar batches (vectors of ~4096 values per column) rather than one row at a time.
  • No JVM for hot path: The actual data processing (filter, aggregate, join) happens in native C++ — no GC pauses, no JIT warmup, no object overhead.
  • Direct memory access: Operates on off-heap memory managed by Photon's own allocator — not subject to JVM heap limits or garbage collection.

Vectorized Execution Model

Column Batches (Vectors)

  • Data is organized as arrays of values per column (not as rows). A batch of 4096 rows with 10 columns = 10 arrays of 4096 values each.
  • Benefits: (1) CPU cache efficiency — processing one column at a time keeps data in L1/L2 cache. (2) SIMD utilization — process 4-8 values simultaneously with AVX2/AVX-512 instructions. (3) Branch prediction — filter operations on one column are highly predictable.

SIMD Instruction Utilization

  • AVX2 (256-bit): Process 4 BIGINT values or 8 INT values in a single CPU instruction.
  • Vectorized comparisons: Filter WHERE amount > 100 on a column of 4096 doubles → ~512 SIMD compare instructions (vs 4096 scalar comparisons).
  • Vectorized aggregation: SUM, COUNT, MIN, MAX on columnar data achieve near-memory-bandwidth throughput.
  • String operations: Photon's native string handling (LIKE, CONTAINS, SUBSTR) is 5-10x faster than JVM — no object allocation per string, fixed-width comparison buffers.

CPU Cache Line Optimization

  • Modern CPUs have 64-byte cache lines. Processing a column of BIGINT (8 bytes each) fits 8 values per cache line.
  • Sequential column access → minimal cache misses → throughput limited only by memory bandwidth, not cache misses.
  • Row-oriented access (traditional Spark) accesses scattered memory locations → frequent cache misses → 3-10x slower for analytics queries.

Memory Management

  • Native C++ allocator: Photon manages its own memory pool outside the JVM heap. No garbage collector involvement.
  • No GC pauses: JVM-based Spark can experience 10+ second GC pauses on large heaps. Photon's native memory management eliminates this entirely.
  • Memory-mapped I/O: Parquet files are memory-mapped for zero-copy reads where possible — data goes directly from OS page cache to Photon processing buffers without copying through JVM.
  • Buffer pooling: Intermediate results reuse pre-allocated buffers — reduces memory allocation/deallocation overhead for repetitive operations (loop bodies in aggregations).
  • Spill to disk: When Photon's memory budget is exhausted (large hash joins, sorts), it spills to local SSD efficiently — spill format is optimized for re-reading (not Spark's row-based spill format).
Why this matters: A typical Spark executor with 32GB heap spends 5-15% of wall-clock time in GC for aggregation-heavy workloads. Photon eliminates this entirely. For a 4-hour Spark job, that's 12-36 minutes saved just from GC elimination — before counting the vectorization speedup.

When Photon Does NOT Help

  • UDF-heavy workloads: If 60%+ of execution time is in Python/Scala UDFs, Photon can't help (falls back to JVM for UDFs). The non-UDF portions may be faster, but the UDFs dominate runtime.
  • Small datasets (<1GB): Overhead of Photon initialization and the mixed JVM/native runtime exceeds savings. Standard Spark is fine for small data.
  • ML training (MLlib): Machine learning algorithms are compute-bound in specialized ways (linear algebra, gradient descent) that Photon doesn't optimize.
  • RDD API workloads: Pure RDD code (.map, .filter, .flatMap) bypasses the SQL engine entirely — Photon only accelerates SQL/DataFrame operations.
  • ETL with heavy Python logic: If transformations are implemented as Python functions rather than Spark SQL operations, Photon provides no benefit.
  • I/O-bound workloads: If the bottleneck is S3 read throughput (not CPU processing), faster CPU execution doesn't help. Photon helps CPU-bound, not I/O-bound jobs.

Cost-Benefit Analysis

Pricing Model

  • Photon DBU rate: Approximately 2x standard compute DBU rate (varies by tier: Jobs, DLT, SQL).
  • Break-even point: Photon must provide >2x speedup to be cost-neutral. At 3x speedup, you save 33% net cost.
  • Formula: Cost = Runtime_hours × Workers × DBU_per_hour × Price_per_DBU

How to Measure

Cost Comparison Methodology
# Step 1: Run job WITHOUT Photon (standard compute)
# Record: runtime_standard = 4 hours, cluster = 10 workers × i3.xlarge
# Cost_standard = 4h × 10 × 2 DBU/h × $0.15/DBU = $12.00

# Step 2: Run SAME job WITH Photon (Photon-enabled compute)
# Record: runtime_photon = 1.5 hours, cluster = 10 workers × i3.xlarge
# Cost_photon = 1.5h × 10 × 2 DBU/h × $0.30/DBU = $9.00

# Speedup = 4.0 / 1.5 = 2.67x
# Cost savings = ($12.00 - $9.00) / $12.00 = 25% cheaper with Photon

# Decision: Photon provides 2.67x speedup at 2x DBU rate → net 25% savings ✅

# Counter-example where Photon doesn't pay off:
# runtime_photon = 3 hours (only 1.33x speedup)
# Cost_photon = 3h × 10 × 2 × $0.30 = $18.00 (50% MORE expensive!) ❌
Rule of thumb: Enable Photon for SQL/DataFrame-heavy workloads (ETL with SQL transformations, BI queries, Delta MERGE). Disable Photon for Python/UDF-heavy workloads, ML training, or jobs where most time is spent in I/O. Always benchmark both modes for your specific workload before committing.

Photon-Aware Query Tuning

Maximize Photon Utilization

Photon Optimization Patterns
# ❌ BAD: Python UDF breaks Photon execution
from pyspark.sql.functions import udf
@udf("string")
def normalize_email(email):
    return email.strip().lower() if email else None

df.withColumn("email", normalize_email("email"))  # Falls back to JVM

# ✅ GOOD: Native SQL equivalent stays in Photon
df.withColumn("email", lower(trim(col("email"))))  # Photon-accelerated

# ❌ BAD: pandas_udf for simple logic
@pandas_udf("double")
def calc_discount(amount: pd.Series, tier: pd.Series) -> pd.Series:
    return amount * tier.map({"gold": 0.2, "silver": 0.1}).fillna(0.05)

# ✅ GOOD: SQL CASE WHEN stays in Photon
df.withColumn("discount", 
    when(col("tier") == "gold", col("amount") * 0.2)
    .when(col("tier") == "silver", col("amount") * 0.1)
    .otherwise(col("amount") * 0.05)
)

# ❌ BAD: collect() pulls data to driver (bypasses Photon)
results = df.collect()  # Serializes everything to Python driver

# ✅ GOOD: Keep computation in Spark SQL (Photon-accelerated)
result = df.agg(sum("amount"), count("*")).first()

# ❌ BAD: RDD operations (completely outside Photon)
df.rdd.map(lambda row: transform(row)).toDF()

# ✅ GOOD: DataFrame/SQL API (Photon-eligible)
df.select(transform_columns_with_sql_functions)

Additional Tuning Tips

  • Use Delta format: Photon has deep integration with Delta reads/writes (Parquet + column stats + DV application).
  • Avoid Python UDFs: Replace with built-in SQL functions or SQL expression UDFs where possible.
  • Prefer SQL/DataFrame API: Keep transformations in the Spark SQL optimizer's scope.
  • Minimize driver-side operations: collect(), toPandas(), show() pull data out of Photon's native execution.
  • Use broadcast hints for small tables: Photon's hash join with broadcast is extremely efficient — df.join(broadcast(dim_table), ...)

Spark UI with Photon

  • In the SQL/DataFrame query plan view, Photon-executed operators are labeled with "Photon" prefix: PhotonGroupingAgg, PhotonHashJoin, PhotonFilter, PhotonProject.
  • Non-Photon operators appear with standard names: HashAggregate, SortMergeJoin, Filter.
  • Mixed plans: Look for transition points between Photon and non-Photon operators — these are serialization boundaries (potential bottlenecks).
  • Photon metrics: Additional metrics in the SQL tab: "Photon execution time", "rows processed by Photon", "time in native code vs JVM".
  • Goal: Maximize the percentage of execution time in Photon operators. If >80% of time is in Photon operators, you're getting good ROI.

AQE + Photon

Complementary Optimizations

  • AQE (Adaptive Query Execution) optimizes the query PLAN at runtime: coalesce partitions, switch join strategies, handle skew.
  • Photon optimizes the query EXECUTION: faster per-row processing via vectorization.
  • They work together: AQE picks the optimal plan (e.g., converts sort-merge join to broadcast hash join when one side is small) → Photon executes that plan with native C++ performance.

Interaction Points

  • AQE coalesce + Photon: AQE reduces partition count for small stages → fewer tasks with larger batches → better Photon vectorization (larger vectors = better SIMD utilization).
  • AQE skew handling + Photon: AQE splits skewed partitions into smaller chunks → Photon processes each chunk with consistent performance (no single-task bottleneck).
  • AQE join strategy switch + Photon: AQE detects a table is small enough for broadcast → switches to broadcast hash join → Photon's native hash join with broadcast is 5-10x faster than sort-merge.
Enable AQE + Photon (Default on Databricks)
-- Both enabled by default on Databricks Runtime 12.0+
-- Verify settings:
SET spark.sql.adaptive.enabled;                      -- true
SET spark.sql.adaptive.coalescePartitions.enabled;   -- true
SET spark.sql.adaptive.skewJoin.enabled;             -- true
SET spark.databricks.photon.enabled;                 -- true (on Photon clusters)

-- Tuning for maximum combined benefit:
SET spark.sql.adaptive.advisoryPartitionSizeInBytes = 128m;  -- Larger partitions → better Photon batching
SET spark.sql.adaptive.coalescePartitions.minPartitionSize = 64m;  -- Don't create tiny partitions
SET spark.sql.shuffle.partitions = 200;  -- AQE will auto-coalesce from here

Interview Questions

Your team enabled Photon on all clusters but some jobs are now MORE expensive (not faster). How do you diagnose and fix this?

Diagnosis:

(1) Check Photon utilization in Spark UI: Open the SQL tab → look at the query plan. If most operators are non-Photon (standard HashAggregate, SortMergeJoin without "Photon" prefix), the workload isn't Photon-eligible. You're paying 2x DBU for standard JVM execution.

(2) Identify the workload type: Python UDF-heavy jobs, RDD-based ETL, MLlib training, and custom Scala UDFs all bypass Photon. If >50% of execution time is in non-Photon operators, Photon won't pay off.

(3) Check for I/O-bound behavior: If the job spends most time waiting for S3 reads (check task metrics: "Input Read Time" vs "Processing Time"), faster CPU execution doesn't help — you need more parallelism or better data layout.

Fix:

(1) Disable Photon for jobs that are UDF/RDD/ML-heavy — use standard compute at 1x DBU rate. (2) For mixed workloads, rewrite critical UDFs as SQL expressions to make them Photon-eligible. (3) Create a policy: Photon enabled for SQL/ETL clusters, disabled for ML/Python-heavy clusters. (4) Use cluster policies to enforce the right compute type per team/use-case.

Explain how Photon's vectorized execution differs from Spark's WholeStageCodegen. Why is it faster?

Spark WholeStageCodegen:

Generates Java bytecode at runtime that fuses multiple operators into a single function (loop). Processes one row at a time through the fused pipeline. Runs on JVM → subject to: (1) GC pauses. (2) JIT warmup (first ~10K iterations interpreted before JIT compiles). (3) Object allocation overhead (Java Strings, boxed numerics). (4) No explicit SIMD — relies on JVM auto-vectorization (unreliable).

Photon vectorized execution:

Pre-compiled C++ operators process column batches (vectors of ~4096 values). Each operator takes a batch in, produces a batch out. Benefits: (1) No GC (native memory). (2) No JIT warmup (pre-compiled). (3) No object overhead (raw memory arrays). (4) Explicit SIMD via intrinsics (AVX2/AVX-512). (5) Cache-friendly access patterns (sequential column reads).

Net effect: For a simple SELECT SUM(amount) FROM table WHERE status = 'active': WholeStageCodegen processes ~200M rows/sec per core. Photon processes ~800M-1.5B rows/sec per core. The gap widens for string operations and hash joins.

A critical ETL job uses 5 Python UDFs and takes 6 hours. With Photon, it takes 5 hours (only 1.2x speedup) but costs 2x per DBU. How do you make this cost-effective?

Current state: 1.2x speedup at 2x DBU rate = net 67% more expensive with Photon. This is a losing proposition.

Strategy: Eliminate UDFs to unlock Photon's full potential.

(1) Audit each UDF: Classify as: (a) replaceable with built-in functions, (b) replaceable with SQL expression UDF, (c) truly requires Python. Most "custom" UDFs are actually doing things that built-in functions handle: date parsing, string manipulation, conditional logic.

(2) Replace with built-ins: Example: a UDF that parses "2024-01-15T10:30:00Z" → replace with to_timestamp(col, "yyyy-MM-dd'T'HH:mm:ss'Z'"). A UDF that normalizes strings → lower(trim(regexp_replace(col, '[^a-zA-Z0-9]', ''))).

(3) Use SQL expression UDFs: For complex but deterministic logic: CREATE FUNCTION classify_amount(amt DOUBLE) RETURNS STRING RETURN CASE WHEN amt > 1000 THEN 'high' WHEN amt > 100 THEN 'medium' ELSE 'low' END; — these are inlined by Catalyst and Photon-eligible.

(4) Isolate remaining UDFs: If 2 UDFs truly need Python, restructure the pipeline: Photon-eligible stages first (scans, joins, aggregations, SQL transforms), then a narrow UDF stage at the end on minimum data. Minimize data flowing through the Python UDF boundary.

(5) Expected result: Eliminating 4/5 UDFs → 80%+ of the plan becomes Photon-eligible → speedup jumps to 3-5x → cost drops 40-60% with Photon.

How do you determine the break-even point for Photon on a specific workload?

Formula: Break-even when Cost_standard = Cost_photon.

Time_standard × DBU_rate_standard = Time_photon × DBU_rate_photon

If Photon DBU rate = 2x standard: Time_standard × R = Time_photon × 2R → Time_photon = Time_standard / 2

Break-even = 2x speedup. Below 2x → Photon is more expensive. Above 2x → Photon saves money.

Measurement approach:

(1) Run the job on a standard cluster (same instance type). Record: wall-clock time, total DBU consumed (from billing), total cost.

(2) Run the same job on a Photon-enabled cluster (same instance type and count). Record same metrics.

(3) Compare: Speedup = Time_standard / Time_photon. Cost_ratio = Cost_photon / Cost_standard.

(4) If Speedup > DBU_rate_multiplier (typically 2x), Photon is cost-positive.

Gotcha: Run benchmarks multiple times (3+) to account for variance. First run may be slower (cold S3 cache). Use the same data, same cluster size, same Spark config for fair comparison.
