Workflows Architecture

  • Multi-task jobs: A job consists of one or more tasks arranged in a DAG (Directed Acyclic Graph). Tasks execute in dependency order — parallel where possible, sequential where dependencies exist.
  • Managed execution: Databricks handles cluster provisioning, task scheduling, retry logic, and cleanup.
  • Job runs: Each execution of a job is a "run" with a unique run_id. Runs are tracked, logged, and queryable via API.
  • Idempotent design: Jobs should be designed for safe re-execution (retries, manual reruns). Use MERGE/upsert patterns, not raw INSERT.

Job Clusters

Cluster Configuration Options

  • Dedicated job cluster per task: Each task gets a fresh cluster. Maximum isolation, but startup overhead per task.
  • Shared job cluster: Multiple tasks share one cluster. Define a named cluster in job config, reference it from tasks. No startup between tasks (sequential only).
  • Existing cluster: Run on an already-running interactive cluster. Not recommended for production (no isolation, higher DBU rate).
  • Pool-backed: Job cluster backed by an instance pool. Fast startup (30-60 sec) with full isolation.

Multi-Task Job Configuration

Task Dependencies

  • depends_on: Array of upstream task keys. Task runs only after ALL dependencies succeed.
  • Parallel execution: tasks with no dependencies (or satisfied dependencies) run simultaneously.
  • DAG visualization: Databricks UI shows the job as a visual graph with status per task.

Task Values (Cross-Task Communication)

Task Values — Passing Data Between Tasks
# In upstream task notebook (check_data_volume):
row_count = spark.table("prod.bronze.orders").count()
partitions = ["2024-01-01", "2024-01-02", "2024-01-03"]

# Set task values (accessible by downstream tasks)
dbutils.jobs.taskValues.set(key="row_count", value=row_count)
dbutils.jobs.taskValues.set(key="partitions", value=partitions)
dbutils.jobs.taskValues.set(key="status", value="success")

# In downstream task notebook (transform_orders):
# Retrieve values from upstream task
row_count = dbutils.jobs.taskValues.get(
    taskKey="check_data_volume", 
    key="row_count", 
    default=0
)
print(f"Processing {row_count} rows from upstream")

Scheduling & Triggers

Cron-Based Scheduling

Schedule Configuration
{
  "schedule": {
    "quartz_cron_expression": "0 0 6 * * ?",
    "timezone_id": "America/New_York",
    "pause_status": "UNPAUSED"
  }
}

# Common cron patterns:
# Every day at 6 AM ET:       "0 0 6 * * ?"
# Every hour:                  "0 0 * * * ?"
# Every 15 minutes:            "0 0/15 * * * ?"
# Monday-Friday at 8 AM:       "0 0 8 ? * MON-FRI"
# First day of month at 1 AM:  "0 0 1 1 * ?"

File Arrival Triggers

  • Trigger a job when new files arrive in an S3 location.
  • Uses S3 event notifications (SNS/SQS) internally.
  • Configurable: minimum file count, minimum time between triggers, file path patterns.

Continuous Scheduling

  • For always-on streaming jobs: "continuous": {"pause_status": "UNPAUSED"}
  • When the job run completes (or fails), a new run starts automatically.
  • Combined with retry: failed run retries, then a new run starts.

Parameters & Dynamic References

Job and Task Parameters
# Job-level parameters (set at job definition, override at run time)
{
  "parameters": [
    {"name": "env", "default": "prod"},
    {"name": "date", "default": "{{job.start_time.iso_date}}"},
    {"name": "batch_size", "default": "10000"}
  ]
}

# Dynamic references available in parameters:
# {{job.run_id}}              — unique run identifier
# {{job.start_time.iso_date}} — run start date (YYYY-MM-DD)
# {{job.start_time.epoch_ms}} — run start time in epoch ms
# {{task.task_key}}            — current task name
# {{tasks.upstream_task.values.key}} — task value from upstream

# In notebook, access parameters via widgets:
env = dbutils.widgets.get("env")
date = dbutils.widgets.get("date")

# Or via job context:
context = dbutils.notebook.entry_point.getDbutils().notebook().getContext()
run_id = context.currentRunId().get()

Databricks Asset Bundles (DABs)

DABs provide Infrastructure-as-Code for Databricks resources — declarative YAML definitions for jobs, pipelines, clusters, and more:

databricks.yml — Full DABs Example
bundle:
  name: data-engineering-pipeline

variables:
  catalog:
    description: Target Unity Catalog
    default: dev_catalog
  warehouse_id:
    description: SQL Warehouse for quality checks
  notification_email:
    default: data-eng@company.com

workspace:
  root_path: /Users/${workspace.current_user.userName}/.bundle/${bundle.name}/${bundle.environment}

resources:
  jobs:
    daily_etl:
      name: "[${bundle.environment}] Daily ETL Pipeline"
      schedule:
        quartz_cron_expression: "0 0 6 * * ?"
        timezone_id: America/New_York
      
      parameters:
        - name: catalog
          default: ${var.catalog}
        - name: run_date
          default: "{{job.start_time.iso_date}}"
      
      job_clusters:
        - job_cluster_key: etl-cluster
          new_cluster:
            spark_version: 14.3.x-photon-scala2.12
            node_type_id: i3.xlarge
            num_workers: 8
            aws_attributes:
              availability: SPOT_WITH_FALLBACK
              first_on_demand: 1
            instance_pool_id: ${var.pool_id}
      
      tasks:
        - task_key: ingest
          notebook_task:
            notebook_path: ./src/notebooks/ingest.py
            base_parameters:
              catalog: "{{job.parameters.catalog}}"
          job_cluster_key: etl-cluster

        - task_key: transform
          notebook_task:
            notebook_path: ./src/notebooks/transform.py
          job_cluster_key: etl-cluster
          depends_on:
            - task_key: ingest

        - task_key: quality_gate
          sql_task:
            file:
              path: ./src/sql/quality_checks.sql
            warehouse_id: ${var.warehouse_id}
          depends_on:
            - task_key: transform

        - task_key: notify_failure
          notebook_task:
            notebook_path: ./src/notebooks/notify.py
            base_parameters:
              status: "FAILED"
          depends_on:
            - task_key: quality_gate
              outcome: failed
      
      email_notifications:
        on_failure:
          - ${var.notification_email}
      
      max_concurrent_runs: 1

environments:
  dev:
    default: true
    variables:
      catalog: dev_catalog
      warehouse_id: abc123
    workspace:
      host: https://dev.cloud.databricks.com

  prod:
    variables:
      catalog: prod_catalog
      warehouse_id: xyz789
      notification_email: data-eng-oncall@company.com
    workspace:
      host: https://prod.cloud.databricks.com
    permissions:
      - level: CAN_MANAGE
        group_name: data-engineering
DABs CLI Commands
# Validate bundle configuration
databricks bundle validate -e prod

# Deploy to target environment
databricks bundle deploy -e prod

# Run a specific job
databricks bundle run daily_etl -e prod

# Run with parameter override
databricks bundle run daily_etl -e prod --params run_date=2024-01-15

# Destroy resources (tear down)
databricks bundle destroy -e dev

# Summary of what will be deployed
databricks bundle summary -e prod

Orchestration Patterns

ETL Pipeline Pattern

  • Ingest → Transform → Quality Gate → Publish → Notify
  • Quality gate uses a SQL task that queries data quality metrics. If quality check returns failures, downstream tasks are skipped, and notification task triggers.

ML Pipeline Pattern

  • Feature Engineering → Training → Validation → Model Registry → Deployment
  • Conditional task: if validation accuracy > threshold → deploy. Otherwise → alert and stop.

Fan-Out Pattern (for_each)

  • Process each tenant/partition/date independently in parallel.
  • Upstream task produces a list of items (e.g., list of tenant IDs).
  • for_each_task iterates over the list, creating a task instance per item.
  • All instances run in parallel (subject to cluster resources).

Cross-Job Dependencies (run_job task)

  • A task in Job A triggers Job B as a nested run.
  • Use case: shared utility jobs (e.g., "refresh-materialized-views" job called by multiple pipelines).
  • The parent job waits for the child job to complete before continuing.

Error Handling

Error Handling Configuration
{
  "tasks": [
    {
      "task_key": "risky_transform",
      "notebook_task": {"notebook_path": "/transforms/heavy_join"},
      "max_retries": 3,
      "min_retry_interval_millis": 60000,
      "retry_on_timeout": true,
      "timeout_seconds": 3600
    }
  ],
  "email_notifications": {
    "on_failure": ["oncall@company.com"],
    "on_start": [],
    "on_success": []
  },
  "webhook_notifications": {
    "on_failure": [{"id": "slack-webhook-id"}]
  },
  "max_concurrent_runs": 1,
  "run_as": {
    "service_principal_name": "etl-pipeline-sp"
  }
}

Error Handling Features

  • max_retries: Number of retry attempts for a failed task (default: 0). Retries use the same cluster (if still running) or a new one.
  • timeout_seconds: Kill task if it exceeds this duration. Prevents runaway jobs from consuming resources indefinitely.
  • retry_on_timeout: Whether timeout counts as a retriable failure (true) or permanent failure (false).
  • on_failure callback: Downstream task that runs only when upstream FAILS — use for alerting, cleanup, or rollback.
  • Conditional tasks: depends_on.outcome = "failed" — run a task only if the upstream task failed.
  • max_concurrent_runs: 1: Prevent overlapping runs (critical for non-idempotent jobs). New trigger while previous is running → queued or skipped.

When Workflows Suffice

  • All orchestrated tasks run within Databricks (notebooks, DLT, SQL).
  • Dependencies are simple (linear or DAG within one job).
  • No need to coordinate with external systems (APIs, non-Databricks databases, file watchers).
  • Team wants simplicity — no separate orchestration infrastructure to manage.

When You Need External Orchestration (Airflow)

  • Multi-system pipelines: S3 file sensor → trigger Databricks job → call external API → update RDS → send notification.
  • Complex scheduling: data-aware scheduling, pools of connections, SLA monitoring.
  • Cross-platform: orchestrate Databricks + Snowflake + dbt + custom services in one DAG.
  • Organization already has Airflow expertise and infrastructure.
Recommendation: Start with Databricks Workflows for Databricks-native pipelines (simplest, no extra cost, tightest integration). Introduce Airflow only when you need cross-system orchestration or advanced scheduling features. Many organizations run both: Airflow as the top-level orchestrator that triggers Databricks Workflows for the heavy compute.

Interview Questions

Design a multi-task job for a daily ETL pipeline that ingests from 3 sources, transforms data, runs quality checks, and handles failures gracefully.

Job structure (7 tasks, 3 parallel branches):

Parallel ingestion (3 tasks): ingest_orders, ingest_customers, ingest_products — run in parallel (no dependencies between them). Each uses Auto Loader → Bronze Delta table. Shared job cluster for all three (saves startup time).

Transform (1 task): transform_silver — depends on ALL three ingestion tasks. Joins orders with customers and products, deduplicates, applies business logic. Writes to Silver Delta tables using MERGE (idempotent).

Quality gate (1 task): quality_check — SQL task running against a SQL Warehouse. Checks: row count within expected range, null rate below threshold, referential integrity between tables. Uses task values to report pass/fail.

Conditional publish (1 task): publish_gold — depends on quality_check with outcome: true. Only runs if quality passes. Aggregates Silver → Gold tables.

Failure notification (1 task): notify_failure — depends on quality_check with outcome: false. Sends Slack/email alert with failure details. Optionally rolls back partial writes.

Error handling: Each ingestion task has max_retries: 2 (transient S3 errors). Transform has timeout_seconds: 3600. Job-level max_concurrent_runs: 1 prevents overlapping daily runs.

How do Databricks Asset Bundles (DABs) enable CI/CD for Databricks jobs? Walk through the dev-to-prod promotion flow.

DABs CI/CD flow:

1. Development: Engineer works in a feature branch. databricks.yml defines the job with environment-specific variables. They run databricks bundle deploy -e dev to deploy to dev workspace. Test with databricks bundle run -e dev.

2. Pull Request: PR triggers CI pipeline (GitHub Actions/Azure DevOps). CI runs: (a) databricks bundle validate -e staging — catches config errors. (b) Linting (ruff/black for Python). (c) Unit tests (pytest on transformation functions). (d) Optional: deploy to staging and run integration test.

3. Merge to main: Auto-deploys to staging: databricks bundle deploy -e staging. Runs a full pipeline execution in staging with sample data. Validates output (row counts, schema, quality metrics).

4. Production promotion: Manual approval gate (GitHub environment protection rule). On approval: databricks bundle deploy -e prod. DABs handles: different catalog (prod vs dev), different cluster sizes (larger in prod), different schedules (enabled in prod, disabled in dev), different notification recipients.

5. Rollback: Revert Git commit → re-run deploy → previous job definition is restored. Or: databricks bundle destroy -e prod to remove entirely.

Key benefit: The YAML is the source of truth. No manual UI changes in production. All changes are reviewed, versioned, and auditable via Git history.

When would you choose Databricks Workflows over Airflow for job orchestration? What are the limitations of Workflows?

Choose Workflows when:

(1) All tasks execute within Databricks (notebooks, DLT, SQL). (2) You want zero additional infrastructure — Workflows is built into Databricks, no Airflow server/MWAA to manage. (3) You want native integration with Databricks features: job clusters, task values, Unity Catalog lineage tracking, system.billing attribution. (4) Your pipeline is a single job with clear task dependencies (DAG within one job). (5) You value simplicity — DABs YAML is much simpler than Airflow DAG Python code for Databricks-only workloads.

Limitations of Workflows:

(1) No external sensors: Can't wait for a file in S3 or an API to return 200 before triggering (Airflow has S3KeySensor, HttpSensor). Workaround: file arrival trigger (limited) or poll in a notebook (hacky).

(2) No cross-system tasks: Can't natively run a SQL query against RDS, trigger a Lambda, or call an external REST API. Must wrap in a notebook.

(3) Limited backfill: No native concept of data-interval-aware backfill (Airflow's execution_date and catchup). Must parameterize dates manually and run multiple times.

(4) No SLA monitoring: Airflow has built-in SLA miss detection. Workflows has timeout per task but no pipeline-level SLA alerting.

(5) Cross-job dependencies are weak: run_job task exists but lacks the flexibility of Airflow's ExternalTaskSensor or dataset-aware scheduling.

How do you handle dynamic fan-out (processing N partitions in parallel) in Databricks Workflows?

Using for_each_task:

(1) Upstream task determines the list of items to process. Example: query distinct dates that need reprocessing, or list of tenant IDs. Sets the list as a task value: dbutils.jobs.taskValues.set("partitions", ["2024-01-01", "2024-01-02", ...])

(2) for_each_task iterates over the list. Each iteration creates an independent task instance with the item as a parameter. All instances run in parallel (subject to cluster resources).

(3) Nested task receives {{input}} as the current item. Processes that single partition/tenant/date.

Considerations:

(1) Parallelism limit: By default, all items run in parallel. For 1000 items, this means 1000 concurrent task instances — may overwhelm the cluster. Set concurrency limits or use a shared cluster with autoscaling.

(2) Error handling: Individual iterations can fail independently. The for_each completes when all iterations finish. Failed iterations can be retried individually.

(3) Cluster sharing: All for_each iterations share the same job cluster. If processing is CPU-heavy, ensure the cluster has enough workers for the parallelism level.

(4) Alternative: For simple cases, process all partitions in a single Spark job using df.filter(date.isin(dates)) — Spark's built-in parallelism may be more efficient than per-partition job tasks. Use for_each when each partition needs significantly different logic or isolation.
