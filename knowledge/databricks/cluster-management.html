Selection Guidelines

  • Default choice: i3.xlarge or m5d.xlarge for most ETL (local SSDs help shuffle performance).
  • Join-heavy / cache-heavy: r6g.2xlarge (more RAM per vCPU for hash tables and Delta cache).
  • Photon SQL analytics: c6g.xlarge (Photon is CPU-bound, doesn't need excess RAM).
  • Shuffle-heavy (large sorts, wide joins): i3.xlarge (NVMe local disk for spill — orders of magnitude faster than EBS).
  • Cost optimization: Always consider Graviton (r6g/m6g/c6g) — same performance at 20-30% lower cost per hour. Verify your dependencies are ARM-compatible first.

Spot Instance Configuration

Cluster Spot Configuration (JSON)
{
  "num_workers": 10,
  "node_type_id": "i3.xlarge",
  "driver_node_type_id": "i3.xlarge",
  "aws_attributes": {
    "first_on_demand": 1,
    "availability": "SPOT_WITH_FALLBACK",
    "zone_id": "auto",
    "spot_bid_max_price": -1,
    "ebs_volume_type": "GENERAL_PURPOSE_SSD",
    "ebs_volume_count": 1,
    "ebs_volume_size": 100
  },
  "spark_conf": {
    "spark.speculation": "true",
    "spark.speculation.multiplier": "2"
  }
}

Configuration Options

  • first_on_demand: 1: The first node (driver) is always On-Demand — driver failure kills the cluster. Never use Spot for the driver.
  • availability: SPOT_WITH_FALLBACK: Try Spot first; if unavailable after timeout, fall back to On-Demand. Best for production jobs that must complete.
  • availability: SPOT: Spot only — cluster fails if no Spot capacity. Use only for non-critical/retry-tolerant workloads.
  • spot_bid_max_price: -1: Bid up to On-Demand price (default, recommended). Maximizes availability without overpaying.
  • Speculation: Enable spark.speculation=true — if a Spot node is evicted mid-task, speculation re-runs the task on another node immediately.

Spot Savings Estimate

  • Typical Spot discount: 60-80% off On-Demand pricing.
  • 10-worker cluster at $0.312/hr (i3.xlarge On-Demand) = $3.12/hr. With Spot: ~$0.94/hr (70% savings).
  • Risk: 5-15% chance of interruption per hour (varies by instance type and AZ). Mitigate with SPOT_WITH_FALLBACK + speculation.

Instance Pools

Instance Pool Configuration
{
  "instance_pool_name": "etl-workers-pool",
  "node_type_id": "i3.xlarge",
  "min_idle_instances": 2,
  "max_capacity": 50,
  "idle_instance_autotermination_minutes": 15,
  "aws_attributes": {
    "availability": "SPOT_WITH_FALLBACK",
    "zone_id": "auto",
    "spot_bid_max_price": -1
  },
  "preloaded_spark_versions": [
    "14.3.x-scala2.12",
    "14.3.x-photon-scala2.12"
  ],
  "custom_tags": {
    "team": "data-engineering",
    "env": "production"
  }
}

How Pools Work

  • Pre-warmed: min_idle_instances instances are always running (or allocated from Spot). When a cluster starts, it grabs instances from the pool immediately.
  • Startup time reduction: Normal cluster: 5-7 min (EC2 provision + boot + Spark install). Pool-backed: 30-90 sec (instances pre-provisioned, just need to start Spark).
  • Sharing: Multiple clusters can use the same pool. First-come-first-served allocation. Pool refills after cluster terminates (instances return to idle state).
  • Preloaded runtimes: Pre-install specific Databricks Runtime versions — further reduces startup (no runtime download).
  • Cost control: idle_instance_autotermination_minutes: 15 — idle pool instances terminate after 15 min to avoid waste. max_capacity: 50 caps total pool size.
When to use pools: (1) Multi-task jobs where each task uses a new job cluster — pool eliminates startup delay between tasks. (2) Interactive notebooks where developers start/stop clusters frequently. (3) Pipelines with many short-running jobs (startup time > processing time without a pool).

Autoscaling

Standard Autoscaling

  • Scales workers between min_workers and max_workers based on cluster load.
  • Scale-up trigger: Pending tasks in Spark scheduler (tasks waiting for executors).
  • Scale-down: Graceful decommission — waits for running tasks to finish before removing nodes. Default timeout: 50 seconds.
  • Lag: Scale-up can take 3-7 minutes (EC2 provisioning). With pools: 30-90 seconds.

Optimized Autoscaling (Databricks Enhanced)

  • More aggressive scale-up: proactively adds nodes based on workload prediction (not just pending tasks).
  • Faster scale-down: detects idle nodes more quickly.
  • Shuffle-aware: delays node removal if the node holds shuffle data needed by active tasks.
  • Enabled by default on newer Databricks Runtimes.

Autoscaling for Streaming

  • Recommendation: Keep autoscaling conservative for streaming (min ≈ max or narrow range).
  • Frequent scale up/down causes Spark executor churn → lost cached data, recomputation.
  • For steady-state streaming: set min_workers = max_workers (fixed size). Scale manually during known peak hours.
Autoscaling Configuration
{
  "autoscale": {
    "min_workers": 2,
    "max_workers": 20
  },
  "spark_conf": {
    "spark.databricks.cluster.profile": "serverless",
    "spark.databricks.delta.preview.enabled": "true"
  }
}

# For streaming workloads (stable):
{
  "num_workers": 8,  # Fixed, no autoscaling
  "spark_conf": {
    "spark.streaming.backpressure.enabled": "true"
  }
}

Cluster Policies

Cluster policies restrict what cluster configurations users can create — enforce guardrails on cost, security, and compliance:

Cluster Policy — Production Example
{
  "node_type_id": {
    "type": "allowlist",
    "values": ["i3.xlarge", "i3.2xlarge", "r6g.xlarge", "r6g.2xlarge", "m6g.xlarge"],
    "defaultValue": "i3.xlarge"
  },
  "driver_node_type_id": {
    "type": "fixed",
    "value": "i3.xlarge"
  },
  "autoscale.min_workers": {
    "type": "range",
    "minValue": 1,
    "maxValue": 5,
    "defaultValue": 2
  },
  "autoscale.max_workers": {
    "type": "range",
    "minValue": 2,
    "maxValue": 30,
    "defaultValue": 10
  },
  "autotermination_minutes": {
    "type": "range",
    "minValue": 10,
    "maxValue": 120,
    "defaultValue": 30
  },
  "aws_attributes.availability": {
    "type": "fixed",
    "value": "SPOT_WITH_FALLBACK"
  },
  "aws_attributes.first_on_demand": {
    "type": "fixed",
    "value": 1
  },
  "spark_version": {
    "type": "regex",
    "pattern": "14\\.[0-9]+\\.x-.*"
  },
  "custom_tags.team": {
    "type": "fixed",
    "value": "data-engineering"
  },
  "custom_tags.cost_center": {
    "type": "required"
  }
}

Policy Types

  • fixed: Value cannot be changed by users (enforced).
  • allowlist: Users select from approved values only.
  • range: Numeric value within min/max bounds.
  • regex: Value must match pattern (e.g., specific runtime versions).
  • required: User must provide a value (e.g., cost_center tag).
  • forbidden: Attribute cannot be set (e.g., forbid custom Docker images).

Auto-Termination

  • Default: 120 minutes of inactivity before auto-termination.
  • Recommendation: Set to 15-30 minutes for dev clusters. 10 minutes for automated job clusters (they complete and terminate anyway).
  • "Idle" definition: No active Spark jobs, no running commands, no attached notebooks with pending execution.
  • Notebook keepalive: An open notebook with a connected cluster prevents auto-termination even if no code is running. Users leaving notebooks open = wasted compute.
  • Mitigation: Enforce via cluster policy (autotermination_minutes.maxValue: 60) + educate users on detaching from clusters.

Multi-Task Job Cluster Sharing

  • In a multi-task Databricks Job, tasks can share a job cluster or use separate clusters.
  • Shared cluster: All tasks run on the same cluster sequentially. No startup cost between tasks. Use when tasks are sequential and require similar resources.
  • Separate clusters: Each task gets its own cluster. Parallel tasks can run simultaneously. Use when tasks have different resource needs or run in parallel.
  • Pool-backed job clusters: Job cluster uses an instance pool → 30-sec startup per task cluster → best of both worlds (isolation + fast startup).

Serverless Compute

SQL Warehouses (Serverless)

  • Instant startup: Queries start executing in <2 seconds (no cluster provisioning).
  • Auto-scaling: Scales to zero when idle (no charges). Scales up for concurrent queries.
  • Managed by Databricks: No instance type selection, no cluster configuration. Databricks handles all infrastructure.
  • Cost model: Pay per DBU consumed during query execution. Higher per-DBU rate but zero idle cost.
  • Best for: BI dashboards, ad-hoc SQL, low-frequency queries where idle cluster cost outweighs the premium DBU rate.

Serverless for Notebooks/Jobs (Preview)

  • Run notebooks and jobs without configuring clusters.
  • Databricks selects optimal resources based on workload characteristics.
  • Eliminates cluster management entirely — focus on code, not infrastructure.
  • Currently in preview — availability varies by region.

DBU Optimization

DBU Consumption Analysis
-- Query billing usage (system tables)
SELECT
  workspace_id,
  sku_name,
  usage_date,
  SUM(usage_quantity) AS total_dbus,
  SUM(usage_quantity * list_price) AS estimated_cost
FROM system.billing.usage
WHERE usage_date >= current_date() - INTERVAL 30 DAYS
GROUP BY workspace_id, sku_name, usage_date
ORDER BY estimated_cost DESC;

-- Identify top-consuming clusters
SELECT
  cluster_id,
  custom_tags:team AS team,
  SUM(usage_quantity) AS total_dbus,
  SUM(usage_quantity * list_price) AS cost
FROM system.billing.usage
WHERE usage_date >= current_date() - INTERVAL 7 DAYS
  AND sku_name LIKE '%ALL_PURPOSE%'
GROUP BY cluster_id, custom_tags:team
ORDER BY cost DESC
LIMIT 20;

-- Identify expensive jobs
SELECT
  usage_metadata.job_id,
  usage_metadata.job_name,
  SUM(usage_quantity) AS total_dbus,
  COUNT(DISTINCT usage_date) AS days_active
FROM system.billing.usage
WHERE sku_name LIKE '%JOBS%'
  AND usage_date >= current_date() - INTERVAL 30 DAYS
GROUP BY usage_metadata.job_id, usage_metadata.job_name
ORDER BY total_dbus DESC
LIMIT 20;

Optimization Strategies

  • Move to Jobs compute: Convert interactive development to scheduled jobs → 2-3x DBU savings.
  • Right-size clusters: Check Spark UI — if executor utilization <50%, reduce worker count. If GC time >10%, increase memory or add workers.
  • Enable Spot: 60-80% savings on EC2, no DBU rate change. Always use for workers.
  • Auto-terminate aggressive: Set 15-min timeout for interactive, 5-min for job clusters.
  • Photon selectively: Only enable for SQL-heavy workloads where speedup >2x. Disable for UDF/ML workloads.
  • Instance pools: Reduce startup waste (paying for cluster boot time = wasted DBUs).

Cost Allocation & Chargeback

Custom Tags for Chargeback

Tag-Based Cost Allocation
# Enforce tags via cluster policy
# Then query billing by tag:

SELECT
  custom_tags:team AS team,
  custom_tags:cost_center AS cost_center,
  custom_tags:project AS project,
  sku_name,
  SUM(usage_quantity) AS total_dbus,
  SUM(usage_quantity * list_price) AS total_cost
FROM system.billing.usage
WHERE usage_date >= date_trunc('month', current_date())
GROUP BY 
  custom_tags:team,
  custom_tags:cost_center,
  custom_tags:project,
  sku_name
ORDER BY total_cost DESC;

-- Monthly chargeback report per team
SELECT
  custom_tags:team AS team,
  date_trunc('month', usage_date) AS month,
  SUM(CASE WHEN sku_name LIKE '%JOBS%' THEN usage_quantity * list_price ELSE 0 END) AS jobs_cost,
  SUM(CASE WHEN sku_name LIKE '%ALL_PURPOSE%' THEN usage_quantity * list_price ELSE 0 END) AS interactive_cost,
  SUM(CASE WHEN sku_name LIKE '%SQL%' THEN usage_quantity * list_price ELSE 0 END) AS sql_cost,
  SUM(usage_quantity * list_price) AS total_cost
FROM system.billing.usage
WHERE usage_date >= '2024-01-01'
GROUP BY custom_tags:team, date_trunc('month', usage_date)
ORDER BY month, total_cost DESC;

Budget Alerts

  • Set workspace-level budget alerts in Databricks account console.
  • Configure alerts at 50%, 75%, 90%, 100% of monthly budget.
  • Combine with cluster policies to hard-cap per-team resource usage.
  • Use max_dbu_per_hour in cluster policies to prevent runaway costs from over-provisioned clusters.

Interview Questions

Your company's Databricks bill went from $50K/month to $120K/month in 3 months. How do you diagnose and reduce costs?

Diagnosis (prioritized):

(1) Query system.billing.usage: Break down by SKU (All-Purpose vs Jobs vs SQL), by cluster_id, by team tag, by job_name. Identify the top 10 cost drivers.

(2) Common culprits: (a) Developers running production-scale data on interactive clusters (2-3x premium). (b) Clusters left running 24/7 with 120-min auto-termination (paying for idle time). (c) New jobs added without cost review — especially if using large clusters with Photon. (d) Streaming jobs scaled up but never scaled back.

Reduction actions (ordered by impact):

(1) Interactive → Jobs migration: Any notebook running on schedule should use a Jobs cluster. Savings: 50-66% on those workloads.

(2) Auto-termination enforcement: Policy: max 30 min for interactive. This alone can save 20-40% if users leave clusters idle.

(3) Spot instances: If not already using Spot, enable SPOT_WITH_FALLBACK for all workers. Savings: 60-80% on EC2 compute.

(4) Right-sizing: Check top 10 most expensive clusters — are they over-provisioned? Spark UI shows executor utilization. If <50% utilized, cut workers by half.

(5) Photon audit: Identify jobs with Photon enabled that aren't achieving 2x speedup. Disable Photon for those — instant 50% savings per job.

(6) Consolidation: If 10 developers each run their own 8-worker cluster for a few hours daily, consider a shared cluster with proper isolation or a serverless approach.

Design a cluster policy for a team of 15 data engineers that balances autonomy with cost control.

Policy design principles: Allow enough flexibility for legitimate use (different job types need different resources) while preventing accidental waste.

Policy:

(1) Instance types (allowlist): Allow i3.xlarge, i3.2xlarge, r6g.xlarge, r6g.2xlarge, m6g.xlarge, m6g.2xlarge. Block expensive instances (p3, x1, metal). Default: i3.xlarge.

(2) Autoscale bounds: min_workers: 1-4 (range). max_workers: 2-20 (range). Default: 2-8. Prevents accidental 100-node clusters.

(3) Auto-termination: min: 10 min, max: 60 min, default: 20 min. Cannot disable auto-termination.

(4) Spot: Fixed at SPOT_WITH_FALLBACK, first_on_demand=1. No option for full On-Demand (except driver).

(5) Tags (required): cost_center, project. Fixed: team=data-engineering. Enables billing attribution.

(6) Runtime (regex): Only allow LTS versions (14.x or 15.x). Prevent outdated runtimes with security vulnerabilities.

(7) Instance pools: Encourage pool usage by setting pool_id as default. Reduces startup time and Spot availability issues.

Escape hatch: Create a separate "large-cluster" policy requiring manager approval for max_workers > 20. This handles legitimate large-scale jobs without blocking them entirely.

When should you choose Serverless SQL Warehouses over Classic SQL Warehouses?

Choose Serverless when:

(1) Bursty query patterns: BI dashboards with peak hours (9am-5pm) and zero activity at night. Serverless scales to zero — no idle cost. Classic warehouse at minimum 1 cluster running 24/7 = wasted spend at night.

(2) Low total query volume: <100 queries/day. The higher per-DBU rate is offset by zero idle cost. Break-even: if your Classic warehouse runs <4 hours/day of actual query time, Serverless is cheaper.

(3) Instant startup needed: Serverless starts in <2 seconds. Classic cold-starts in 2-5 minutes. If users can't tolerate cold-start latency, Serverless is the only option.

(4) No infrastructure management: Team doesn't want to manage warehouse sizing, scaling policies, or startup/shutdown schedules.

Choose Classic when:

(1) Sustained high load: Hundreds of concurrent queries for hours — Classic at lower DBU rate is cheaper when the warehouse is consistently utilized >60% of the time.

(2) Predictable workload: You know exact peak times and can schedule startup/shutdown — no idle waste.

(3) Network isolation: Classic runs in your VPC. Serverless runs in Databricks' infrastructure — may not meet strict security/compliance requirements (data residency, PrivateLink).

(4) Custom configuration: Need specific Spark settings, custom libraries, or specialized instance types not available in Serverless.

A multi-task job with 8 sequential tasks takes 45 minutes, but 35 minutes is cluster startup (5 min × 7 new clusters). How do you fix this?

Problem: Each task creates a new job cluster, incurring 5-min startup penalty. Total processing time is only 10 minutes but total wall-clock is 45 minutes.

Solutions (from most to least impactful):

(1) Shared job cluster: Configure all 8 tasks to use the same job cluster. One startup (5 min) + sequential tasks (10 min) = 15 min total. Limitation: all tasks must have compatible resource needs and can't run in parallel.

(2) Instance pool: Each task still gets its own cluster, but backed by a pool. Startup drops from 5 min to 30-60 sec per task. Total: 10 min processing + 4 min startup = 14 min. Advantage over shared: tasks can run in parallel if DAG allows, and each can be right-sized independently.

(3) Reduce task granularity: Combine the 8 tasks into 2-3 larger tasks that each do more work. Fewer cluster startups. Tradeoff: less granular retries (if task 3 fails, you re-run a bigger unit of work).

(4) Reuse cluster for sequential tasks: In the multi-task job configuration, group sequential tasks onto the same cluster, but give parallel branches their own clusters. Hybrid approach.

Best practice: Use instance pools (option 2) — it preserves task isolation and retry granularity while eliminating 90% of startup overhead.

How do you implement cost allocation (chargeback) across 5 teams sharing a Databricks workspace?

Implementation:

(1) Enforce tags via cluster policies: Each team gets a cluster policy with "custom_tags.team": {"type": "fixed", "value": "team-name"} and "custom_tags.cost_center": {"type": "required"}. No cluster can start without team identification.

(2) Query system.billing.usage: Billing data includes custom_tags. Build a monthly report: GROUP BY team tag, aggregate DBU cost. Break down by compute type (Interactive, Jobs, SQL, DLT).

(3) Automated reporting: Schedule a Databricks job that generates cost reports, writes to a Gold table, and sends email/Slack summaries per team monthly.

(4) Budget alerts: Set per-team budget alerts at the account level. When team X exceeds 80% of monthly allocation, alert the team lead.

(5) Visibility: Create a shared dashboard showing real-time cost per team, trend vs budget, top-cost clusters/jobs. Transparency drives self-regulation.

For job-level attribution: Add job_name and cluster_id to billing queries. Tag jobs with team + project identifiers. This enables per-project chargeback (more granular than per-team).
